# RTOS 模拟器：9 场景预测、回放与对照实验

前置：任务状态、阻塞、基本 C++ 控制流。返回 [内容总索引](../content-map.md)。本页对应 `src/rtos-sim/scenarios.ts` 的 9 个网页预置场景；`examples/rtos/` 有 8 个独立文件，信号量场景仅在预置表内。

## 实验方法与证据

每次先写预测，再选择场景并记录配置，逐步回放任务状态、对象操作和 stdout，最后修改一个参数比较。导出原始和修改后的 JSON，记录 commit、场景 ID、配置和结束原因。不要只比较动画颜色或截图。

在仓库根目录执行 `node tools/check-rtos-examples.ts` 可核对全部文件和预置。2026-10-20 按预置自带配置运行，事件数基线依次为 36、50、41、36、36、72、35、34、51；第 7 项以 deadlock 结束，其余 completed，均无 error 诊断。事件数是当前实现的回归观察，不是 RTOS 标准要求。

## 1. 时间片与抢占 · round-robin

- **预测**：两个同优先级 worker 各 busy 6ms，时间片为 2 tick，为什么一个 worker 不会独占到结束？
- **观察**：Ready／Running 切换以及两个 worker 的输出；区分工作量、调度点和代码行事件。
- **对照**：时间片改为 1、2、4，其他输入不变，比较 context_switch 的顺序与数量。
- **答案**：相同优先级的可运行任务按模型时间片轮转；增大时间片通常减少轮转机会，但任务创建、阻塞和退出仍会引起切换，不能只用除法预测总事件数。

## 2. 互斥与优先级继承 · mutex

- **预测**：高优先级任务等待 low 持有的 bus 时，谁能解除等待？
- **观察**：`prio_inherit`、`prio_restore` 和 unlock 后的唤醒。
- **对照**：将锁改为 `rtos::mutex bus{rtos::no_priority_inheritance};`。基线只有 low／high，要研究典型三任务反转，应另加入延后唤醒的中优先级 CPU 忙任务，并保存修改源码。
- **答案**：继承临时提升持锁者以缩短被中优先级任务干扰的机会；它不解决死锁，也不消除长临界区。两任务对照不能直接证明中优先级任务造成的饥饿。

## 3. 消息队列 · queue

- **预测**：消费者先等待空队列，生产者发送 42 后哪个任务运行？第二条 84 最终在哪里？
- **观察**：receive 阻塞、send 唤醒和消费者输出 `sample=42`，注意程序只有一次 receive。
- **对照**：容量改为 1，并让生产者先执行或增加发送次数，比较满队列时的 timeout 返回值；必须在代码中保存并检查返回值。
- **答案**：高优先级消费者就绪后可抢占；FIFO 不代表所有消息都会被消费。若原程序第二条留在队列，不能将 completed 解释为业务消息全部交付。

## 4. 信号量同步 · semaphore

- **预测**：初值 0，controller 延后 4ms release，worker 是否能在 release 前输出？
- **观察**：acquire 的阻塞和 release 后的唤醒。
- **对照**：初值改为 1，比较 worker 的启动顺序；保留其他配置。
- **答案**：令牌表示许可／事件，不携带消息 payload，也不是互斥锁的通用替代。模型中的标准库风格名称不证明目标平台的 `std::binary_semaphore` 可用。

## 5. 生命周期 · thread-lifecycle

- **预测**：worker sleep 期间被 suspend，sleep 到期是否立即可运行？
- **观察**：任务的睡眠与挂起状态、resume 后推进和 join 返回。
- **对照**：调整 resume 前的等待时长，记录状态序列，不仅比较 stdout。
- **答案**：唤醒条件与挂起条件是不同约束；join 等待任务结束，不等于发起取消。该模型的任务状态不代表真实内核的控制块和栈回收细节。

## 6. 条件变量与虚假唤醒 · condvar-spurious

- **预测**：每 2 tick 注入虚假唤醒，producer 6ms 后才设置 dataReady，consumer 会否提前继续？
- **观察**：`spurious_wakeup`、谓词重新检查和最终 `dataReady=1`。
- **对照**：先关闭注入，再恢复；若研究非谓词写法，单独保存变更并检查等待后是否重新验证共享条件。
- **答案**：通知或唤醒不等于条件成立；谓词循环在锁保护下复检状态。虚假唤醒频率是教学模型配置，不是对真实系统频率的预测。

## 7. 哲学家与死锁 · dining-philosophers

- **预测**：两个任务按相反顺序取两把锁，中间 sleep，会形成什么等待环？
- **观察**：`deadlock_detected` 及任务—资源环；deadlock 是本例预期教学结果，不是解析错误。
- **对照**：统一两个任务获取锁的顺序，运行同一场景配置；保存无环轨迹。
- **答案**：破坏循环等待能修复这组锁顺序问题；一次无死锁轨迹不能证明任意输入都无死锁，仍需静态锁顺序规则。

## 8. ISR 延迟处理 · isr-deferred

- **预测**：4ms 时触发 ISR，哪部分工作应留给任务？
- **观察**：`isr_enter`／`isr_exit`、`release_from_isr` 与 worker 处理次数。
- **对照**：故意在 ISR 中加入阻塞锁调用，检查行级 error；恢复原例后再确认无 error。
- **答案**：ISR 只发出受支持的通知，把业务处理留给任务；真实平台的 FromISR API、优先级限制和中断返回调度需另查目标内核。

## 9. 定时器与事件组 · timer-eventgroup

- **预测**：sensor 设置 01，单次 timer 设置 10，wait_all 等待 11，先到的位是否足够？
- **观察**：`timer_fire`、事件位组合和 `all ready bits=3`；回调运行在模型 timer_svc，而不是任意 ISR。
- **对照**：将 wait 的 timeout 缩短至条件尚未全部满足的时间，检查失败返回；恢复后再改为 periodic 并解释为何可能达到模拟 tick 上限。
- **答案**：wait_all 需要全部目标位；clear_on_exit 清除匹配的位，不意味着所有未来通知被禁用。periodic 任务仍活跃时，达到上限不自动等于死锁。
