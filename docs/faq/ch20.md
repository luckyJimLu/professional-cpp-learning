### Q97｜算法与容器的职责铁律：`std::remove` / `std::unique` 为何不缩容

`主线 · 阶梯 1/5 迭代器边界契约`

> **Question**
> 调用 `std::remove(vec.begin(), vec.end(), target)` 或 `std::unique(...)` 之后，为什么打印 `vec.size()` 发现容器长度纹丝不动，末尾甚至还多出一些残留的“幽灵元素”？

**Answer**
- **核心结论**：标准库传统算法只接收迭代器区间而**不知道底层容器的存在**，因此绝无权限调用容器的 `erase()` 改变容器大小；`std::remove` 与 `std::unique` 仅仅通过向前覆盖移动（Move-assign）把保留元素紧凑排列到区间前半段，并返回新的逻辑尾后迭代器。
- **底层机制**：以 `std::remove` 为例，它用快慢指针扫描区间，把不等于 `target` 的有效元素前移覆盖被删位置，但逻辑尾后位置之后的旧槽位处于“被移动后的有效但未指定状态（Valid but Unspecified）”，必须紧接着调用容器成员函数 `vec.erase(newEnd, vec.end())` 才能真正截断物理内存（即经典的 Erase-Remove 惯用法）。同样，`std::unique` 只会消除**连续相邻**的重复元素，使用前通常必须先 `std::sort` 排序。
- **设计取舍与边界**：C++20 起，针对按值或按谓词删除元素的场景，应直接使用统一的非成员函数 `std::erase(c, val)` 和 `std::erase_if(c, pred)`，一步到位完成覆盖与缩容；仅当需要原地去重（`unique`）或对 `std::ranges::unique` 返回的子范围操作时，仍需显式配合 `erase()`。
- **代码 / 场景对照**：
```cpp
// [反例] 只调用 std::remove 而不调用 erase，容器尾部残留未指定值
std::remove(vec.begin(), vec.end(), 0); // vec.size() 根本没变！

// [正例] C++20 直接用 std::erase；去重则先排序再配合 ranges::unique + erase
std::erase(vec, 0);
std::ranges::sort(vec);
auto [first, last] = std::ranges::unique(vec);
vec.erase(first, last);
```
- **回归主线**：解决了“增删与去重”的迭代器边界后，在实际工程中对海量数据做排序、局部筛选与查找时，如何避免用全量 $O(n \log n)$ 排序浪费算力？

### Q98｜排序家族（`partial_sort`/`nth_element`）与二分查找前提

`主线 · 阶梯 2/5 排序与查找复杂度`

> **Question**
> 只需要从一百万条日志里找出耗时最长的 Top-10，或者仅求中位数时，为什么直接调用 `std::sort` 是极大的算力浪费？使用 `lower_bound` 做二分查找前又必须满足什么前置契约？

**Answer**
- **核心结论**：全排序 `std::sort` 需要 $O(n \log n)$ 比较，而 Top-K 用 `std::partial_sort` 只需 $O(n \log k)$，求中位数或第 $k$ 大元素用 `std::nth_element` 更是只需均摊 $O(n)$ 线性时间；所有二分查找算法（`lower_bound`、`upper_bound`、`equal_range`、`binary_search`）均要求序列**预先按相同比较器有序（或至少已按目标分区）**，否则触发未定义结果。
- **底层机制**：`std::partial_sort(first, middle, last)` 基于堆选择仅把前 $k$ 个最小元素有序排到 `[first, middle)`，其余元素顺序不作保证；`std::nth_element` 基于快速选择（Introselect）仅把第 $n$ 个元素放到最终排序位置，保证其左侧均不大于它、右侧均不小于它。二分查找方面，`lower_bound` 返回首个 `>= val` 的迭代器，`upper_bound` 返回首个 `> val` 的迭代器，`equal_range` 一次二分同时返回等价区间的上下界（比分别调用两次二分更高效），而 `binary_search` 仅返回 `bool`。
- **设计取舍与边界**：需要保持相等元素原始相对顺序时用 `std::stable_sort` / `std::stable_partition`（允许额外临时内存分配）；仅需二分类分组（如把及格与不及格分开）时用 $O(n)$ 的 `std::partition` 而非排序。
- **代码 / 场景对照**：
```cpp
// [反例] 为取前 5 名或中位数对全量百万级数组做 std::sort
std::ranges::sort(scores);
auto median = scores[scores.size() / 2];

// [正例] Top-K 用 partial_sort，单点中位数用线性复杂度 nth_element
std::ranges::nth_element(scores, scores.begin() + scores.size() / 2);
auto median = scores[scores.size() / 2];
```
- **回归主线**：除了排序与单元素二分，在“大文本子串搜索”和“多序列集合合并”场景中，标准库还提供了专门的加速搜索器与线性集合算法。

### Q99｜子串搜索器（Boyer-Moore）与有序集合运算

`支线 L17 · 高效检索与集合运算`

> **Question**
> 在几兆字节的长文本中反复检索固定模式串时，为什么 `std::search` 默认朴素匹配效率不如 C++17 的 `std::boyer_moore_searcher`？使用 `std::set_intersection` 等集合算法又为何要求输入必须有序且目标容器支持扩容？

**Answer**
- **核心结论**：`std::boyer_moore_searcher` 与 `std::boyer_moore_horspool_searcher`（C++17）预先对模式串构建坏字符/好后缀跳转表，失配时可大步跨越多个字符实现亚线性平均检索；标准库集合算法（`set_union`、`set_intersection`、`set_difference`、`includes`）利用双指针在 $O(N + M)$ 线性时间完成计算，严格要求两段输入序列已按同一规则排序。
- **底层机制**：传统 `std::search(textBegin, textEnd, patBegin, patEnd)` 在最坏情况下可能退化为 $O(N \times M)$；C++17 允许将预构建好的搜索器对象传入 `std::search(textBegin, textEnd, searcher)`（注意构建跳转表本身有预处理开销，只有当模式串较长且在长文本中高频检索时才划算）。集合运算方面，`std::set_intersection` 等写结果到输出迭代器，若传入空 `vector.begin()` 会越界 UB，必须搭配 `std::back_inserter`。
- **设计取舍与边界**：短模式串单次查找用 `std::string_view::find` 或普通 `std::search` 即可；长模式串反复匹配超大文本时选用 `boyer_moore_horspool_searcher`（预处理更轻量、实测常优于完整 Boyer-Moore）。
- **代码 / 场景对照**：
```cpp
// [反例] 长模式串在超大文本中用朴素双层匹配，且集合运算未用插入迭代器
std::set_intersection(a.begin(), a.end(), b.begin(), b.end(), out.begin()); // 空 out 直接越界 UB

// [正例] C++17 Boyer-Moore-Horspool 搜索器 + back_inserter 安全接收交集
std::boyer_moore_horspool_searcher searcher{ pat.begin(), pat.end() };
auto it = std::search(text.begin(), text.end(), searcher);
std::set_intersection(a.begin(), a.end(), b.begin(), b.end(), std::back_inserter(out));
```
- **回归主线**：单线程下的算法复杂度已经压榨到极限，面对现代多核 CPU，C++17 引入的执行策略让标准算法只需多传一个参数就能瞬间多核并行——但前提是你的回调必须经得起并发考验。

### Q100｜C++17/20 并行执行策略与向量化下的竞态陷阱

`主线 · 阶梯 3/5 并行算法与安全`

> **Question**
> 只需给 `std::for_each` 或 `std::sort` 第一个参数传入 `std::execution::par` 或 `par_unseq`，算法就能自动利用多核并行甚至 SIMD 向量化；为什么此时传入一个普通的累加变量 `[&sum](int x) { sum += x; }` 会立刻引发严重的数据竞态甚至死锁？

**Answer**
- **核心结论**：使用并行执行策略（`par`、`par_unseq`、`unseq`）时，标准把**线程安全与防死锁的全部责任**完全交给调用方：多线程并发读写共享非原子变量直接触发数据竞态 UB，而在支持向量化交错执行的 `par_unseq` / `unseq`（C++20）下，甚至连在回调里加普通 `std::mutex` 都会引发同一线程重入自锁死锁！
- **底层机制**：`std::execution::seq` 保证单线程顺序执行；`par` 允许在多条线程上并行执行（若回调需同步，只能使用标准互斥锁或原子操作，但锁争用会抵消并行收益）；`par_unseq` 与 C++20 新增的 `unseq` 允许单线程内以 SIMD 向量指令或乱序交错执行多个元素迭代——如果在向量化的一条指令周期内尝试获取非可重入锁，前一个通道持有锁而同一线程的下一个通道立即请求同一把锁，瞬间死锁。此外，并行算法中一旦抛出未捕获异常，运行时直接调用 `std::terminate()`。
- **设计取舍与边界**：仅在数据量足够大（足以摊薄线程池调度开销）且各元素计算高度独立无共享写状态时才开启 `std::execution::par`；需要并行累加或映射规约时，绝不要在 `for_each` 里加锁或写外部共享变量，而应直接使用原生支持并行的 `std::reduce` 与 `std::transform_reduce`。
- **代码 / 场景对照**：
```cpp
// [反例] 并行策略回调中直接累加外部非原子变量，触发数据竞态 UB
double total = 0.0;
std::for_each(std::execution::par, v.begin(), v.end(), [&](double x) { total += x; });

// [正例] 使用并行友好的 transform_reduce 无锁完成映射与规约
double total = std::transform_reduce(std::execution::par, v.begin(), v.end(), 0.0,
    std::plus<>{}, [](double x) { return x * x; });
```
- **回归主线**：`transform_reduce` 揭示了数值算法在并行化上的巨大威力，实际上 `<numeric>` 家族还有一组专门用于前缀和与元素迁移的利器。

### Q101｜`<numeric>` 规约/扫描家族与 C++20 `shift_left`/`shift_right`

`主线 · 阶梯 4/5 数值规约与移位`

> **Question**
> 为什么计算前缀和或累加时，C++17 的 `std::reduce` 和 `std::inclusive_scan` / `exclusive_scan` 要求二元运算必须满足结合律与交换律（对比 `accumulate`）？C++20 的 `shift_left` 和 `shift_right` 又比 `std::rotate` 适合什么场景？

**Answer**
- **核心结论**：`std::accumulate` 严格按从左到右顺序依次折叠（允许非结合、非交换运算），因此无法并行；`std::reduce` 与 `inclusive_scan`/`exclusive_scan`（C++17）允许编译器任意重排分组与并行树形归并，故要求二元操作满足结合律（`reduce` 还要求交换律）。C++20 `std::shift_left`/`shift_right` 在不要求保留被移出旧元素的情况下直接移动区间内元素，免去 `rotate` 的多余交换。
- **底层机制**：`inclusive_scan` 输出包含当前元素的前缀累计结果（第 $i$ 项含 $a_i$），`exclusive_scan` 则不包含当前元素（第 $0$ 项为初始单位元 `init`）。对于区间内元素整体平移（例如把 `[3, 4, 5]` 左移两格丢弃前两项），`std::rotate` 会把被挤出的前两项搬到尾部做循环交换，而 `std::shift_left` 直接单向移动赋值并把尾部留作已移出状态，少了一半移动操作。
- **设计取舍与边界**：遇到需要严格左结合语义（如字符串拼接或顺序依赖的浮点数高精度求和）继续用 `std::accumulate`（或 C++23 `std::ranges::fold_left`）；可交换结合的数值聚合首选 `std::reduce`。
- **代码 / 场景对照**：
```cpp
// [反例] 只需丢弃头部元素左移数据，却用 std::rotate 多做尾部搬运交换
std::rotate(v.begin(), v.begin() + 2, v.end());

// [正例] C++20 shift_left 单向高效移动，前缀和直接用 inclusive_scan
auto newEnd = std::shift_left(v.begin(), v.end(), 2);
std::inclusive_scan(nums.begin(), nums.end(), prefixSums.begin());
```
- **回归主线**：传统 `<algorithm>` 与 `<numeric>` 算法在 C++20 迁入 `std::ranges` 时仍有不少空白，直到 C++23 才把最关键的几块拼图彻底补齐。

### Q102｜C++23 专属 Ranges 新算法：`fold_left`、`contains` 与前缀匹配

`主线 · 阶梯 5/5 C++23 约束新算法`

> **Question**
> 过去用 `std::ranges` 管道处理完视图后，想做左折叠规约、判断范围是否包含某子序列或检查前缀，为什么往往不得不退回旧的 `std::accumulate` 或手写 `std::search`？C++23 新增了哪些仅限 `std::ranges` 的独占算法？

**Answer**
- **核心结论**：C++23 为 `std::ranges` 独占补充了一批高呼声实用算法——包括补齐数值折叠空白的 `std::ranges::fold_left` / `fold_right`（以及 `fold_left_first` 等变体）、语义直观的子范围探测 `std::ranges::contains` / `contains_subrange`、前后缀匹配 `starts_with` / `ends_with`，以及支持拉链式遍历的 `views::zip` 配套算法。
- **底层机制**：C++20 首批移植 Ranges 算法时遗漏了 `<numeric>` 中的折叠算法，导致 `std::ranges` 下找不到 `accumulate` 替代品；C++23 的 `std::ranges::fold_left` 支持直接传入任意视图（包括哨兵类型与迭代器不同的视图）、投影与初始值。`std::ranges::contains(haystack, needle)` 则终结了每次都要写 `std::ranges::find(r, v) != r.end()` 的繁琐样板。
- **设计取舍与边界**：在 C++23 代码库中，彻底用 `std::ranges::contains` 替代 `find(...) != end()` 判存，用 `std::ranges::fold_left` 替代基于旧式迭代器的 `std::accumulate`，保持全链路 Ranges 风格统一。
- **代码 / 场景对照**：
```cpp
// [反例] C++20 中混用 Ranges 视图与旧式 std::accumulate / find != end
bool hasTarget = std::ranges::find(nums, 42) != nums.end();

// [正例] C++23 ranges::contains 与 ranges::fold_left 原生直连范围与视图
bool hasTarget = std::ranges::contains(nums, 42);
int sum = std::ranges::fold_left(nums | std::views::filter(isOdd), 0, std::plus<>{});
```
- **回归主线**：算法掌握了如何高效处理数据序列，但当数据是面向全球用户的多语言文本或需要复杂模式匹配时，第 21 章将深入本地化区域设置与正则表达式引擎。

## 本轮技术复盘（第 20 章）

### 主线推演回顾
从“算法不增删容器”的迭代器契约出发，对比全排序与 `partial_sort`/`nth_element` 的复杂度级差，剖析 Boyer-Moore 搜索器与有序集合运算，揭示并行执行策略下的数据竞态与死锁红线，最后梳理 `<numeric>` 扫描规约与 C++23 专属 Ranges 算法。

### 高频误区速查
- **误区 1**：调用 `std::remove` 或 `std::unique` 后直接认为容器已缩小 -> 必须配合 `erase()`，或按值/谓词删除直接使用 C++20 `std::erase` / `std::erase_if`。
- **误区 2**：在 `par_unseq` 并行向量化策略回调中使用 `std::mutex` -> 同一线程内 SIMD 通道交错重入锁直接引发死锁。
- **误区 3**：对无序序列调用 `std::lower_bound` 或 `std::set_intersection` -> 违背有序前置契约，结果完全错误。

### 工程落地清单
- Top-K 与中位数场景坚决弃用全排序 `std::sort`，改用 `std::partial_sort` 与 `std::nth_element`。
- 并行规约计算首选 `std::reduce` / `std::transform_reduce`，绝不在并行 `for_each` 中加锁累加共享变量。
- C++23 项目中判存与折叠统一升级为 `std::ranges::contains` 与 `std::ranges::fold_left`。
