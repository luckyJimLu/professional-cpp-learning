### Q1｜跳过前期设计的并发与耦合代价

`主线 · 阶梯 1/5 问题暴露`

> **Question**
> 既然敏捷开发强调“可工作的软件高于详尽的文档”，直接先写核心类再边写边重构，为什么会导致“墙外布管”式补丁与并发竞态失控？

**Answer**
- **核心结论**：敏捷迭代允许设计随需求演进，但不等于跳过前期子系统划分与职责边界设计；核心不变式（如线程安全与跨模块协议）若不在初期内聚于类内部，后期只能被迫散落在所有调用端。
- **底层机制**：以多线程共享队列为例，若初期未把同步原语或无锁机制封装在队列类内部，所有调用方只能在外部手动加锁。随着新成员加入，只要有一处遗漏加锁，就会触发数据竞态（Data Race）与未定义行为（UB）。同理，分别硬编码 `Pawn` 与 `Bishop` 后才发现共享坐标、颜色与移动校验，必然引发棋盘、规则与 UI 子系统的强耦合返工。
- **设计取舍与边界**：前期设计文档应聚焦两层——粗粒度子系统划分（接口、数据流、线程模型）与子系统内部关键类/数据结构；UML 图只求表意清晰而非拘泥语法，避免陷入过度设计的瀑布僵化。
- **代码 / 场景对照**：
```cpp
// [反例] 线程安全漏到调用端，任何新调用点遗漏加锁即发生数据竞态
std::mutex g_queueMutex;
{ std::lock_guard lock{ g_queueMutex }; sharedQueue.push(task); }

// [正例] 将同步原语内聚到队列抽象内部，调用方无需感知锁细节
class ThreadSafeQueue {
public:
    void push(Task t) { std::lock_guard lock{ m_mtx }; m_q.push(std::move(t)); }
private:
    std::mutex m_mtx;
    std::queue<Task> m_q;
};
```
- **回归主线**：前期设计的第一道防线，是划清“谁负责维护不变式”的边界；这直接引出 C++ 程序设计的首条铁律——抽象。

### Q2｜抽象与全私有数据成员原则

`主线 · 阶梯 2/5 抽象边界`

> **Question**
> 既然已经通过设计文档划分了 `ChessBoard` 与 `ChessPiece` 等子系统，如果为了省事把底层数组或数据成员设为 `public` 直接读写，底层会发生什么连锁破坏？

**Answer**
- **核心结论**：暴露底层数据结构（如 `ChessPiece* board[8][8]`）会把实现细节固化为调用方契约，导致无法替换存储布局、无法做边界校验，且迫使每个调用者承担内存管理职责。
- **底层机制**：将所有数据成员设为 `private` 并通过受控成员函数暴露，使类成为唯一的状态守门人。后续即便将二维数组重构为连续的 64 元素一维 `std::vector` 以提升缓存局部性，外部调用代码也无需修改；同时 getter/setter 可统一注入合法性校验、事件通知与调试断点。
- **设计取舍与边界**：简单聚合型数据载体（如仅打包字段的 `struct`）可例外，但凡存在状态不变式或跨模块暴露的类，必须严格执行数据隐藏；性能担忧通常可由编译器内联（Inlining）消除。
- **代码 / 场景对照**：
```cpp
// [反例] 暴露二维裸指针数组，外部越界与内存泄漏无法拦截
ChessPiece* chessBoard[8][8];
chessBoard[9][0] = new Pawn{}; // 越界 UB

// [正例] 隐藏一维连续存储，统一执行越界检查与所有权封装
class ChessBoard {
public:
    void setPieceAt(size_t x, size_t y, std::unique_ptr<ChessPiece> p);
private:
    std::vector<std::unique_ptr<ChessPiece>> m_cells; // 64 个连续槽位
};
```
- **回归主线**：抽象把变化隔离在接口之后，这不仅保护了当前代码，更是实现跨项目、跨类型代码复用的前提。

### Q3｜复用范式与 API、库、框架的边界

`主线 · 阶梯 3/5 复用范式`

> **Question**
> 抽象封装好了棋盘类后，如果新项目需要西洋跳棋盘，直接复制代码改名为什么不算真正的复用？在引入外部组件时，API、库与框架的控制权边界如何取舍？

**Answer**
- **核心结论**：复制粘贴会制造多份分叉代码，修补缺陷时必须多处同步；真正的复用包含编写泛型/可复用代码、复用设计模式，以及复用现有库或框架，而非文本拷贝。
- **底层机制**：C++ 支持多范式与模板泛型编程，将棋盘抽象为 `template <typename PieceType> class GameBoard` 即可零运行期开销地同时服务国际象棋与跳棋。在架构边界上，API 是对外发布的接口契约，库（Library）是具体实现；你的程序主动调用库，而框架（Framework，如 Qt、MFC）掌握主控流并回调你的代码（控制反转）。
- **设计取舍与边界**：需要局部功能（如日志、加密）时优先选库以保留架构自主权；若整个应用的骨架、事件循环与 UI 体系都契合既有生态，则采用框架以换取开发效率，但需接受被框架绑定的迁移成本。
- **代码 / 场景对照**：
```cpp
// [反例] 复制一份 CheckersBoard 并手工替换类型，缺陷修复需双倍维护
class ChessBoard { /* ... */ };
class CheckersBoard { /* 几乎完全重复的二维网格逻辑 */ };

// [正例] 通过类模板参数化棋子类型，一份实现服务多种棋类
template <typename PieceType>
class GameBoard {
public:
    void setPieceAt(size_t x, size_t y, PieceType piece);
};
```
- **回归主线**：决定复用外部库之前，必须先建立客观的性能与工程评估标尺，避免被表面指标误导。

### Q4｜选型评估中的 Big-O 渐近复杂度陷阱

`支线 L1 · 复杂度陷阱`

> **Question**
> 评估第三方库或自研算法时，很多人直接按 Big-O 复杂度选择 $O(\log n)$ 方案而淘汰 $O(n^2)$ 方案，这种做法在底层硬件与实际工程中为什么可能适得其反？

**Answer**
- **核心结论**：Big-O 只刻画数据规模 $n \to \infty$ 时的渐近增长率，忽略了常数因子、缓存命中率、内存分配与 I/O 开销；在小规模数据上，常数项极小的 $O(n^2)$ 往往快于高常数项的 $O(\log n)$。
- **底层机制**：渐近记号抹平了单次操作的真实指令周期与 CPU 缓存未命中代价。同时依据 90/10 法则，程序 90% 的运行时间集中在 10% 的热点代码中；在非热点路径上为追求更低阶 Big-O 引入复杂数据结构，只会增加维护成本与内存碎片。
- **设计取舍与边界**：Big-O 应用于排除明显会随规模爆炸的算法（如指数级 $O(2^n)$），最终选型必须结合实际数据规模、内存布局与真实性能剖析（Profiling）数据，而不是仅凭理论复杂度拍板。
- **代码 / 场景对照**：
```cpp
// [反例] 仅 16 个元素却为追求 O(log n) 引入节点分散的 std::set，缓存命中率低
std::set<int> smallIds;

// [正例] 小规模集合使用连续内存的 std::vector，充分利用 CPU 缓存预取
std::vector<int> smallIds; // 线性扫描在小 n 下常数因子远低于红黑树跳转
```
- **回归主线**：除了性能评估，引入第三方库还潜藏着许可证、二进制兼容性与错误边界等更隐蔽的工程风险。

### Q5｜第三方库的隐蔽工程风险清单

`主线 · 阶梯 4/5 外部依赖评估`

> **Question**
> 假设某个开源或商业库的性能与功能都通过了原型测试，为什么直接合入生产代码仍可能导致法律风险、编译器升级锁定或隐蔽崩溃？

**Answer**
- **核心结论**：库选型必须系统核查许可证传染性、源码可得性、线程安全、内存所有权与错误处理机制，且绝不能把临时验证用的粗糙原型直接演进为生产代码。
- **底层机制**：许可证方面，GPL 等强著佐权（Copyleft）协议可能要求衍生闭源商业软件公开源码，而 MIT、BSD、Boost、Apache 等宽松协议限制更少。若仅提供预编译二进制而无源码，升级编译器或切换 ABI 设置时会被彻底锁定。跨库边界时，若未明确谁分配/谁释放内存（以及能否用智能指针自定义删除器接管），极易引发堆损坏或泄漏；此外，库内部直接弹窗或调用终止函数会破坏宿主程序的控制流。
- **设计取舍与边界**：优先使用 C++ 标准库（正交、跨平台、零额外学习迁移成本，避免 C 风格字符串与 I/O）；安全加密等高门槛领域应信任经实战检验的专业库而非重复造轮子；原型代码验证完毕后应坚决丢弃并按正式设计重写。
- **代码 / 场景对照**：
```cpp
// [反例] 跨 C 库边界拿到裸句柄后手动释放，异常路径直接泄漏
Resource* r = thirdPartyAcquire();
process(r); // 若此处抛异常，下方释放永不执行
thirdPartyRelease(r);

// [正例] 用智能指针绑定库配套的释放函数，明确跨边界所有权
std::unique_ptr<Resource, decltype(&thirdPartyRelease)> r{
    thirdPartyAcquire(), &thirdPartyRelease
};
```
- **回归主线**：明确了抽象、复用与外部依赖边界后，最后一步是在具体系统架构中将各子系统与错误处理机制严密整合。

### Q6｜MVC 职责隔离与系统/用户错误分级

`主线 · 阶梯 5/5 系统整合`

> **Question**
> 在国际象棋这类完整交互程序中，如果把棋盘数据、界面渲染和玩家输入混写在一起，或者把“非法走子”和“内存耗尽”用同一套异常处理，系统架构会出现什么问题？

**Answer**
- **核心结论**：采用 MVC（Model-View-Controller）配合观察者与中介者模式可将核心规则与界面解耦；错误处理必须严格区分系统错误与用户错误，避免正常业务纠错引发程序崩溃。
- **底层机制**：Model（`ChessBoard`、`ChessPiece`）只维护棋局状态与规则；View（`ChessBoardView`、`ChessPieceView`）通过观察者模式订阅状态变化并负责渲染；Controller（`Player` 等）充当中介协调输入；`ErrorLogger` 则结合策略模式与依赖注入（DI）灵活切换日志输出目标。对于系统错误（如底层资源耗尽、文件损坏），应记录日志并抛出异常或优雅退出；对于用户错误（如输入非法坐标），应在输入边界校验并提示重输，不走异常崩溃路径。
- **设计取舍与边界**：单线程交互程序无需过度引入并发复杂性；只有当 View 或日志后端存在多端替换需求（如控制台切换为 GUI）时，解耦收益才会最大化，但即便当前只有单一界面，保持 Model 无 UI 依赖仍是专业底线。
- **代码 / 场景对照**：
```cpp
// [反例] 模型层直接打印错误并终止程序，无法复用到 GUI 或服务端
bool ChessBoard::move(Pos from, Pos to) {
    if (!isLegal(from, to)) { std::println("非法走子"); std::terminate(); }
}

// [正例] 模型层仅返回校验结果，由控制层/视图层决定提示与重输
MoveResult ChessBoard::tryMove(Pos from, Pos to) {
    if (!isLegal(from, to)) { return MoveResult::IllegalMove; }
    // 执行合法走子并通知观察者
}
```
- **回归主线**：至此，我们完成了从宏观子系统划分到抽象、复用、库选型与 MVC 落地的完整程序设计闭环。

## 本轮技术复盘（第 4 章）

### 主线推演回顾
从跳过设计导致的跨模块耦合与并发失控出发，确立了“抽象（数据隐藏）”与“复用（泛型/模式/库）”两大基石，继而厘清了 Big-O 选型误区与第三方库隐藏风险，最终通过 MVC 与错误分级完成子系统整合。

### 高频误区速查
- **误区 1**：把敏捷开发等同于“不写设计直接编码” -> 核心不变式与线程模型必须在初期落入类边界。
- **误区 2**：认为 $O(\log n)$ 永远快于 $O(n^2)$ -> 忽略常数项与缓存局部性在小规模数据上的决定性影响。
- **误区 3**：直接把验证可行性的原型代码改吧改吧上线 -> 原型缺乏错误处理与清晰抽象，会成为长期技术债。

### 工程落地清单
- 新建核心类时，先检查所有数据成员是否为 `private`，并确认不变式是否在类内部闭环。
- 引入第三方库前，逐项核对许可证类型、源码可得性、线程安全、内存释放责任方与错误通知方式。
- 业务核心层（Model）严禁出现任何控制台或 GUI 输出调用，区分系统异常与用户可恢复输入错误。
