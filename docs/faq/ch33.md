### Q175｜Strategy（策略模式）的现代 C++ 演进：虚接口 vs `std::function` vs 模板

`主线 · 阶梯 1/5 行为策略解耦`

> **Question**
> 传统教材实现策略模式（Strategy，如可替换的日志后端或排序策略）必须先定义一个抽象基类再写好几个派生类；在现代 C++ 中，什么时候该用传统虚基类，什么时候用 `std::function`/Lambda 或模板参数替代？

**Answer**
- **核心结论**：策略模式的核心是**把易变的算法/行为细节从宿主类中抽离为可替换组件**；在现代 C++ 中，若策略仅是单一可调用动作且需运行期动态切换，直接持有 `std::function`（或 C++23 `std::move_only_function`）配合 Lambda 最简洁；若策略在编译期已知且追求极致零开销内联，直接作为类模板参数传入（如 `std::set` 的比较器）；只有当策略包含多个关联虚方法与复杂状态时，才保留经典多态接口类。
- **底层机制**：传统虚基类策略每次调用都要经历虚表间接跳转，且为了传几行逻辑不得不新建一套子类样板；用模板策略（Policy-based Design）能让编译器把策略逻辑完全内联到宿主循环中，零虚表开销，代价是策略类型写死在宿主模板签名中不能在运行期换装。
- **设计取舍与边界**：不要为了套用模式而强行制造一整个策略类层次——单函数策略首选 Lambda / `std::function`（运行期可换）或模板形参（编译期零开销）。
- **代码 / 场景对照**：
```cpp
// [反例] 仅为了传入一种格式化策略，硬造抽象基类与一堆只有 3 行代码的子类
class IFormatStrategy { public: virtual std::string fmt(int) = 0; };

// [正例] 轻量单函数策略直接用 std::move_only_function 或模板参数注入
class Logger {
public:
    explicit Logger(std::move_only_function<void(std::string_view)> sink)
        : m_sink{ std::move(sink) } {}
private:
    std::move_only_function<void(std::string_view)> m_sink;
};
```
- **回归主线**：除了替换算法行为，大型系统还经常需要把“如何构造一族相互配套的对象”从业务代码中隔离出来——这就引出了两大创建型工厂模式。

### Q176｜Abstract Factory（抽象工厂）与 Factory Method（工厂方法）的精确分野

`主线 · 阶梯 2/5 创建型工厂模式`

> **Question**
> 抽象工厂（Abstract Factory）和工厂方法（Factory Method）听起来都在“封装 `new` 创建对象”，它们在结构与适用场景上究竟有什么本质区别？现代 C++ 工厂函数应该返回裸指针还是智能指针？

**Answer**
- **核心结论**：**工厂方法**通过派生类重写单个虚方法来决定实例化哪一种具体产品（一对一的单一产品线定制，如 `LeastBusyFactory::createCar()`）；**抽象工厂**则提供一个包含多个创建方法的接口，专门用于生产**相互匹配的一整族关联产品**（如 Windows 风格按钮+滚动条 vs macOS 风格按钮+滚动条，防止混搭出错）。现代 C++ 工厂一律返回 **`std::unique_ptr<Base>`**（需共享时调用方可无缝隐式转为 `shared_ptr`）。
- **底层机制**：在工厂方法中，基类往往已经写好了围绕产品工作的核心流程模板，只把“造哪个具体产品”留给子类重写；而抽象工厂本身通常作为一个整体对象通过依赖注入（DI）传给客户端，确保客户端拿到的所有组件都属于同一主题/平台家族。返回 `std::unique_ptr` 既明确宣示了“工厂把新对象所有权完整移交给调用方”，又允许调用方随时用 `std::shared_ptr<Base> sp = factory.create();` 零成本升级为共享所有权。
- **设计取舍与边界**：绝不要在现代 C++ 工厂返回裸指针 `Product*`（极易引发跨模块所有权不明和泄漏）；简单固定映射关系用静态工厂函数（或 `std::unordered_map<Key, std::function<std::unique_ptr<Base>()>>` 注册表）即可，无需过度套用多层抽象工厂。
- **代码 / 场景对照**：
```cpp
// [反例] 工厂返回裸指针，调用方不知该不该 delete，异常路径必泄漏
virtual Car* createCar() = 0;

// [正例] 现代工厂一律返回 std::unique_ptr 明确移交所有权
class ICarFactory {
public:
    virtual ~ICarFactory() = default;
    [[nodiscard]] virtual std::unique_ptr<Car> createCar() = 0;
};
```
- **回归主线**：对象创建出来后，面对既有的遗留类接口不兼容，或者需要给现有对象加上权限/网络/延迟加载控制时，结构型模式中最容易混淆的“双胞胎”就出场了。

### Q177｜Adapter（适配器）与 Proxy（代理）的本质区别

`主线 · 阶梯 3/5 适配器与代理`

> **Question**
> 适配器模式（Adapter）和代理模式（Proxy）在代码结构上看起来都是“在外部包一层包装类并把调用转发给内部持有的目标对象”，它们在设计意图与接口契约上到底有什么根本不同？

**Answer**
- **核心结论**：**适配器改变接口**——它把一个接口完全不兼容的既有类（如第三方旧日志库）包装成客户端期望的新接口；**代理保持完全相同的接口**——它实现与真实对象完全一致的抽象接口，在调用前后透明地植入额外控制逻辑（如远程网络代理、延迟加载、权限校验、缓存）。
- **底层机制**：当客户端代码面向 `INewLogger` 编程，而手头只有现成的 `LegacyLogger` 时，通过组合（has-a）让 `LoggerAdapter` 继承 `INewLogger` 并在内部持有 `LegacyLogger` 完成参数翻译适配（优先对象适配器而非私有继承类适配器）。而 `NetworkPlayerProxy` 与真实 `RemotePlayer` 继承自同一个 `IPlayer` 接口，客户端根本无从察觉自己面对的是本地替身还是真实对象，代理可在网络连接断开时提供降级缓存或透明重连。
- **设计取舍与边界**：对接接口不匹配的第三方库/遗留模块用 Adapter；在不改变原有接口契约的前提下控制访问权限、隐藏网络延迟或做惰性初始化用 Proxy。
- **代码 / 场景对照**：
```cpp
// [反例] 混淆意图：用继承修改接口同时又在内部做网络重连，职责混乱
// [正例] Adapter 转换不兼容接口；Proxy 保持同名接口注入网络/权限控制
class LoggerAdapter : public INewLogger {
    OldLogger m_legacy; // 转换接口签名
public:
    void log(std::string_view msg) override { m_legacy.writeOld(std::string{ msg }); }
};
```
- **回归主线**：除了“改接口”和“控访问”，还有两对容易混用的模式分别解决“动态叠加功能/链式传递”与“一对多事件广播”。

### Q178｜Decorator（装饰器）与 Chain of Responsibility（责任链）

`主线 · 阶梯 4/5 装饰增强与链式处理`

> **Question**
> 装饰器模式（Decorator）和责任链模式（Chain of Responsibility）都支持把多个对象像套娃或链条一样串联起来，它们在“请求是否会继续向后传递”与“如何动态组合功能”上有何根本差异？

**Answer**
- **核心结论**：**装饰器**（同代理一样保持接口一致）旨在把多层正交功能（如给网页文本依次包上加粗、斜体、边框装饰）**全部叠加执行**，每层都会增强后继续转发给内层；**责任链**则把多个候选处理器串成链表（如 GUI 事件冒泡、多级审批），每个节点判断“自己能否处理该请求”——**一旦能处理就截断消费（或按需传递），否则转交给链上的下一个处理器**。
- **底层机制**：以网页样式装饰为例，`ItalicParagraph` 包裹 `BoldParagraph` 再包裹纯 `Paragraph`，调用 `getHTML()` 时每层都在内层结果外侧套上对应标签，层层叠加取代了第 6 章提到的“继承组合爆炸”；而责任链中，点击事件先交给按钮，按钮不处理才沿着 `m_nextHandler` 传给父面板、主窗口，直至被某个节点消化或到达链尾兜底。
- **设计取舍与边界**：需要运行期自由按任意顺序叠加多重行为修饰时用 Decorator；需要把“请求发送者”与“具体哪一个处理器负责处理”彻底解耦时用 Chain of Responsibility。
- **代码 / 场景对照**：
```cpp
// [反例] 为加粗、斜体、下划线分别定义 BoldItalicParagraph 等组合子类引发类爆炸
// [正例] Decorator 动态嵌套叠加；Chain of Responsibility 按条件截断或透传
class BoldDecorator : public IParagraph {
    std::unique_ptr<IParagraph> m_inner;
public:
    std::string getHTML() const override { return "<b>" + m_inner->getHTML() + "</b>"; }
};
```
- **回归主线**：在事件驱动与 MVC 架构中，还有一种模式几乎无处不在——观察者模式（Observer），但在 C++ 中实现它时最容易埋下悬空指针雷。

### Q179｜Observer（观察者模式）的悬空订阅陷阱与生命周期安全

`支线 L30 · 观察者悬空防护`

> **Question**
> 在 C++ 里实现观察者模式（Subject 持有一组 `Observer*` 指针列表并在状态变化时遍历通知）时，为什么只要有一个观察者窗口被用户提前关闭销毁却忘了主动注销，下一次广播通知就会立刻触发悬空指针段错误？

**Answer**
- **核心结论**：Subject 保存裸指针 `Observer*` 时无法感知观察者是否已经销毁，极易在通知循环中解引用悬空指针引发崩溃；现代 C++ 应采用 **`std::weak_ptr<IObserver>` 列表**（通知前尝试 `.lock()`，若已失效则顺便从列表清理）或由观察者在析构函数中自动执行 RAII 注销（类似 `scoped_connection` 句柄）。
- **底层机制**：`Subject` 绝不应该用 `std::shared_ptr` 强引用观察者，否则会导致“即使窗口已经关闭，观察者对象依然被 Subject 吊着无法析构”的隐性内存泄漏（甚至形成双向循环引用）。改存 `std::weak_ptr` 后，Subject 既不干涉观察者生命周期，又能在 `notify()` 瞬间安全探测观察者是否健在，配合 `std::erase_if` 顺手剔除已过期槽位；此外，若允许观察者在 `onNotify()` 回调内部反过来新增或删除订阅，广播前应先拷贝一份弱指针快照以防迭代器失效。
- **设计取舍与边界**：如果团队已使用信号槽库（如 Boost.Signals2）或具备统一 `shared_ptr` 生命周期体系，首选基于 `weak_ptr` 跟踪或 RAII `Connection` 断连；单向简单回调则可用第 33 章的 `std::function` 包装。
- **代码 / 场景对照**：
```cpp
// [反例] Subject 存裸指针 Observer*，观察者析构忘退订后 notify() 直接段错误
std::vector<IObserver*> m_observers; // 某个窗口关闭后此处变成悬空指针！

// [正例] 存 std::weak_ptr，广播时 lock() 探测存活并顺便惰性清理失效订阅
std::erase_if(m_observers, [](const std::weak_ptr<IObserver>& wp) {
    if (auto sp = wp.lock()) { sp->onNotify(); return false; }
    return true; // 观察者已销毁，自动清理
});
```
- **回归主线**：最后来看整个设计模式家族中最受争议、也最容易被新手滥用的成员——单例模式（Singleton）。

### Q180｜Singleton（单例模式）的线程安全实现与反模式批判

`主线 · 阶梯 5/5 单例实现与替代`

> **Question**
> 为什么“Meyers 单例”（函数内局部 `static` 变量）在 C++11 之后已经天然线程安全且无需加锁，可资深 C++ 架构师却依然把全局单例视为“应当尽量避免的反模式”？工程中更优雅的替代方案是什么？

**Answer**
- **核心结论**：C++11 起标准强制保证函数内局部 `static` 变量初始化天然线程安全，因此 Meyers 单例写法极简且正确；但单例实质上是**伪装成类的全局变量**——它隐匿了类之间的真实依赖关系、跨单元耦合极高、**在单元测试中极难替换为 Mock 对象**，且多个单例在程序退出逆序析构时仍可能互相访问已销毁单例引发崩溃。
- **底层机制**：编写 `Logger::instance().log(...)` 看似随处可调极其方便，实则让十几个业务类的构造函数接口彻底撒谎（签名里完全看不出它依赖了日志或数据库连接），且单测无法并发运行或隔离状态。现代 C++ 架构应坚决以**依赖注入（Dependency Injection）**替代全局单例：在 `main()` 或顶层组合根（Composition Root）只创建一个唯一实例，然后通过构造函数引用或抽象接口逐层向下注入。
- **设计取舍与边界**：仅当某个设施确实全进程物理唯一、无状态依赖且无需在单测中 Mock 替换时才谨慎使用 Meyers 单例（并删除其拷贝与移动操作）；绝大多数所谓“管理器/配置/数据库服务”都应改为普通类 + 依赖注入。
- **代码 / 场景对照**：
```cpp
// [反例] 在业务类深处直接硬编码 Logger::instance() 全局单例，彻底丧失可测试性
void OrderService::submit() { Logger::instance().write("submit"); }

// [正例] 仅在顶层实例化一次，通过依赖注入传给业务类抽象接口，天然可 Mock
class OrderService {
    ILogger& m_logger; // 显式声明依赖，单测可轻松注入 MockLogger
public:
    explicit OrderService(ILogger& logger) : m_logger{ logger } {}
};
```
- **回归主线**：设计模式打通了单进程内的代码组织艺术；全书最后一章（第 34 章）将跨越编译器、操作系统甚至编程语言的边界，探讨跨平台与跨语言互操作实战。

## 本轮技术复盘（第 33 章）

### 主线推演回顾
从现代 C++ 用 Lambda/`std::function`/模板简化 Strategy 策略模式出发，清晰划定 Abstract Factory（产品族）与 Factory Method（单产品子类定制）及智能指针所有权规范，对比了 Adapter（改接口）与 Proxy（同接口控访问）、Decorator（叠加增强）与 Chain of Responsibility（条件截断透传），用 `weak_ptr` 修复了 Observer 悬空订阅漏洞，最后批判性地审视了 Meyers 单例的测试与耦合弊端，确立依赖注入首选地位。

### 高频误区速查
- **误区 1**：为了套用设计模式给单函数策略强行建抽象基类与一堆空壳子类 -> 现代 C++ 首选 Lambda 配合 `std::move_only_function` 或模板参数。
- **误区 2**：工厂接口返回裸指针 `Base*`，或 Subject 保存裸指针 `Observer*` -> 分别造成所有权模糊泄漏与退订遗漏段错误。
- **误区 3**：到处滥用 `Singleton::instance()` 全局访问 -> 破坏依赖显式性、阻断单元测试 Mock 并埋下退出期析构顺序隐患。

### 工程落地清单
- 工厂函数一律返回 `std::unique_ptr<Base>`（明确移交所有权）。
- 观察者模式采用 `std::weak_ptr` 订阅或 RAII 断连句柄，杜绝裸指针悬空。
- 用“顶层单次实例化 + 构造函数依赖注入”全面替代业务层全局单例。
