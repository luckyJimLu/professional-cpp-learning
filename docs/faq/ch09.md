### Q31｜动态资源类中的浅拷贝灾难与 Copy-and-Swap 惯用法

`主线 · 阶梯 1/5 深拷贝与异常安全`

> **Question**
> 当 `Spreadsheet` 类内部持有动态分配的二维单元格数组时，沿用编译器默认生成的拷贝构造与赋值运算符为何会导致双重释放？Copy-and-Swap 惯用法如何优雅地同时解决自赋值与强异常安全？

**Answer**
- **核心结论**：编译器默认生成的浅拷贝只复制指针地址，导致两个 `Spreadsheet` 对象指向同一块堆内存，析构时必然触发双重释放；Copy-and-Swap 通过“先拷贝构造临时副本、再 `noexcept` 交换内部指针”实现强异常安全且天然 immune 于自赋值。
- **底层机制**：传统手写赋值运算符若先 `delete[]` 旧内存再 `new[]` 新内存，一旦 `new[]` 抛出 `std::bad_alloc`，当前对象已被破坏成半残废状态，且若忘记检测 `this == &rhs` 自赋值，会直接把自己刚释放的内存拷给自己。Copy-and-Swap 先用拷贝构造函数构建完整临时副本（若分配失败抛出异常，原对象丝毫未动），再用 `noexcept` 的 `swap()` 交换成员，最后临时对象离开作用域自动释放旧内存。
- **设计取舍与边界**：若对象明确不需要拷贝（如独占硬件会话），直接用 `= delete` 删除拷贝构造与拷贝赋值比强行深拷贝更安全；需要深拷贝且直接手管资源的底层类，优先采用 Copy-and-Swap。
- **代码 / 场景对照**：
```cpp
// [反例] 先删旧内存再分配，既不防自赋值，new 抛异常还会破坏当前对象
Spreadsheet& Spreadsheet::operator=(const Spreadsheet& rhs) {
    delete[] m_cells;
    m_cells = new Cell[rhs.m_size]; // 若此处抛异常，m_cells 变悬空指针
    return *this;
}

// [正例] Copy-and-Swap：强异常安全，且天然安全处理自赋值
Spreadsheet& Spreadsheet::operator=(const Spreadsheet& rhs) {
    Spreadsheet temp{ rhs }; // 失败不影响 *this
    swap(temp);              // noexcept 交换
    return *this;            // temp 析构自动清理旧内存
}
```
- **回归主线**：深拷贝虽保证了安全，但面对即将销毁的临时对象（右值）时，反复分配再释放堆内存极其浪费——这正是移动语义登场的契机。

### Q32｜移动语义、`noexcept` 与“零法则（Rule of Zero）”

`主线 · 阶梯 2/5 移动语义与零法则`

> **Question**
> 右值引用（`&&`）和移动构造如何免除临时对象的深拷贝？为什么必须给移动操作标上 `noexcept`，在 `return` 局部变量时反而不要画蛇添足写 `std::move()`，以及为什么现代 C++ 推崇“零法则”？

**Answer**
- **核心结论**：移动构造直接窃取右值（即将销毁对象）的底层指针并用 `std::exchange` 将源对象置空；标注 `noexcept` 是让 `std::vector` 扩容时敢于使用移动而非退化回拷贝的前提。不要对局部返回值写 `return std::move(local)`，因为这会阻止编译器的 NRVO 拷贝消除；而“零法则”指出：业务类应通过组合 `std::vector`/智能指针来管理资源，从而一个析构/拷贝/移动函数都不用手写。
- **底层机制**：`std::move(x)` 本身不移动任何字节，它只是把左值无条件强转为右值引用以便触发移动重载（若需要显式生成纯右值副本，C++23 提供 `auto(x)` decay copy）。当 `std::vector` 扩容迁移元素时，为维持强异常安全，只有当元素的移动构造函数标为 `noexcept` 时才执行移动，否则被迫退回深拷贝。此外，一旦手写了自定义析构或拷贝操作（Rule of Five），编译器将不再自动生成移动操作。
- **设计取舍与边界**：遵循“零法则”——绝大多数业务类绝不直接管理裸内存，把资源所有权下沉到专用 RAII 句柄类；只有编写底层容器或资源封装类时才遵循“五法则（Rule of Five）”并确保移动操作 `noexcept`。
- **代码 / 场景对照**：
```cpp
// [反例] 对局部返回值滥用 std::move，反而破坏 NRVO 零拷贝优化
Spreadsheet makeSheet() {
    Spreadsheet s{ 10, 10 };
    return std::move(s); // 阻止 NRVO，被迫额外执行一次移动构造
}

// [正例] 标注 noexcept 移动构造，返回局部变量直接 return 触发 NRVO
Spreadsheet(Spreadsheet&& src) noexcept
    : m_cells{ std::exchange(src.m_cells, nullptr) } {}
Spreadsheet makeSheet() { Spreadsheet s{ 10, 10 }; return s; }
```
- **回归主线**：资源拷贝与移动的效率瓶颈打通后，成员函数自身的契约限定（`const`、`mutable`、引用限定与编译期求值）则决定了类的严谨度与执行时机。

### Q33｜`const`、`mutable`、引用限定符与 `constexpr`/`consteval`

`主线 · 阶梯 3/5 成员函数修饰`

> **Question**
> 如果一个 `const` 成员函数需要更新内部缓存或访问计数，为什么要借助 `mutable` 而非去掉 `const`？引用限定符（`&` / `&&`）与 C++20 `consteval` 又各自在保护什么边界？

**Answer**
- **核心结论**：`const` 成员函数承诺不改变对象的外部逻辑状态，`mutable` 允许修改不影响逻辑常量的内部辅助字段（如缓存、互斥锁、计数器）；引用限定符防止对临时右值执行无意义的赋值修改；`constexpr` 允许编译期或运行期求值，而 `consteval`（C++20）强制函数**必须**在编译期求值。
- **底层机制**：成员函数末尾加 `&`（如 `Cell& operator=(const Cell&) &`）可禁止 `getCell() = other;` 这类对临时右值赋值的低级错误；同时可针对右值对象提供 `&&` 重载以直接移出内部成员数据。`constexpr` 函数（及 `constexpr` 类）在入参为编译期常量时可在编译期完成计算并将结果直接烘焙进二进制；`consteval`（立即函数，Immediate Function）则彻底禁止运行期调用，确保零运行期开销。
- **设计取舍与边界**：凡是不修改逻辑状态的读取方法一律标 `const`；切勿滥用 `mutable` 绕过真正的逻辑状态修改；需要强制编译期校验（如格式串或常量查找表）时首选 `consteval`（C++20）。
- **代码 / 场景对照**：
```cpp
// [反例] 缺少 & 引用限定，允许给函数返回的临时右值赋值
getTempCell() = Cell{ 1.0 }; // 编译通过但修改立刻丢弃，毫无意义

// [正例] 用 & 禁止右值赋值，用 mutable 记录逻辑只读的访问计数
class Cell {
public:
    Cell& operator=(const Cell& rhs) &;
    double value() const { ++m_accessCount; return m_value; }
private:
    double m_value{ 0.0 };
    mutable size_t m_accessCount{ 0 };
};
```
- **回归主线**：成员函数修饰之外，类级别共享的数据成员在 C++17 前后也经历了显著的简化演进。

### Q34｜`static` 数据成员与 C++17 `inline` 静态变量

`支线 L6 · 静态成员与内联变量`

> **Question**
> 为什么传统 C++ 在类内声明了一个 `static` 数据成员后，还必须在某个 `.cpp` 文件里再写一次类外定义，否则链接器会报未定义符号错误？C++17 的 `inline static` 如何彻底根除这一繁琐写法？

**Answer**
- **核心结论**：传统类内 `static` 成员声明只是“声明”而非“定义”，不分配存储空间；C++17 引入 `inline` 变量后，直接在类内写 `inline static` 即可完成定义与初始化，且跨多个翻译单元包含头文件也不会违反 ODR。
- **底层机制**：`static` 数据成员属于整个类而非单个对象实例，且 `static` 成员函数没有 `this` 指针，只能访问静态成员。在 C++17 之前，除整型/枚举 `const static` 常量外，所有 `static` 数据成员都必须且只能在单一 `.cpp` 中类外定义一次以分配全局静态存储区。加上 `inline static`（或 C++17 起隐式内联的 `constexpr static`）后，链接器会自动合并各翻译单元的同名定义。
- **设计取舍与边界**：现代 C++17 及以上代码应全面使用 `inline static` 或 `constexpr static` 定义类内静态数据成员，避免头文件与 `.cpp` 割裂维护；注意引用数据成员（`T& m_ref`）虽合法，但会隐式禁用默认拷贝赋值且必须确保被引用对象活得比当前对象更久。
- **代码 / 场景对照**：
```cpp
// [反例] C++17 前必须在头文件声明、再在 .cpp 中重复定义一次
class Sheet { static size_t s_counter; };
// Sheet.cpp 中必须补写：size_t Sheet::s_counter{ 0 };

// [正例] C++17 inline static 直接在类内一步完成定义与初始化
class Sheet {
public:
    inline static size_t s_counter{ 0 };
    static constexpr size_t MaxWidth{ 100 };
};
```
- **回归主线**：类的内部成员打磨完毕后，要让自定义类型像内置 `int`/`double` 一样自然参与运算与比较，就需要遵循规范的运算符重载设计。

### Q35｜非成员 `operator+` 与 C++20 三路比较运算符（`<=>`）

`主线 · 阶梯 4/5 运算符重载演进`

> **Question**
> 为什么二元加法 `operator+` 作为成员函数写完后，`cell + 4` 能编译通过，可 `4 + cell` 却直接报错？而在 C++20 中，三路比较运算符 `<=>` 如何把原本要手写的六个比较运算符压缩到一两行？

**Answer**
- **核心结论**：成员函数形式的 `operator+` 要求左操作数必须是当前类类型，无法触发隐式转换，因此对称二元运算符应优先定义为非成员函数（并复用成员 `operator+=`）；C++20 中只需 `= default` 声明 `<=>`，编译器就能自动生成并重写 `==`、`!=`、`<`、`<=`、`>`、`>=` 全部六种比较。
- **底层机制**：当 `operator+(const Cell& lhs, const Cell& rhs)` 是非成员函数时，编译器会对左右两个操作数对称地尝试隐式转换（若构造函数非 `explicit`），使 `4 + cell` 与 `cell + 4` 均可工作。C++20 引入宇宙飞船运算符 `<=>`（返回 `std::strong_ordering`、`weak_ordering` 或 `partial_ordering`）及表达式重写规则：若定义了 `operator<=>() = default;`，编译器同时自动合成 `operator==`；若自定义了 `<=>`，则通常还需单独提供 `operator==` 以保证等值比较最优性能，其余 `!=` 与四类大小比较全由编译器自动重写推导。
- **设计取舍与边界**：修改左操作数状态的复合赋值（`+=`、`-=`）写成成员函数，对称二元算术运算（`+`、`-`）写成非成员函数并委托给复合赋值；C++20 起优先使用 `auto operator<=>(const T&) const = default;` 彻底告别手写六套比较样板。
- **代码 / 场景对照**：
```cpp
// [反例] C++20 前需手写 ==, !=, <, <=, >, >= 六个运算符，易漏易错
bool operator==(const Cell&, const Cell&);
bool operator!=(const Cell&, const Cell&); // 其余 4 个略

// [正例] C++20 一行默认三路比较，自动覆盖全部六种比较运算
class Cell {
public:
    [[nodiscard]] auto operator<=>(const Cell&) const = default;
private:
    double m_value{ 0.0 };
};
```
- **回归主线**：当类已经兼具安全、高效与优雅的接口时，最后一步是如何把它的对外契约与私有实现彻底隔离，确保未来升级不破坏任何下游客户端。

### Q36｜用 Pimpl（接口与实现分离）构建 ABI 稳定类

`主线 · 阶梯 5/5 稳定接口 Pimpl`

> **Question**
> 第 6 章提到头文件暴露私有成员会破坏 ABI，具体到 C++ 类实现时，使用 `std::unique_ptr<Impl>` 实现 Pimpl 惯用法为什么必须在 `.cpp` 文件中显式定义析构函数（即使它是 `= default`）？

**Answer**
- **核心结论**：Pimpl 将所有私有数据与实现细节移入仅在 `.cpp` 中完整定义的前向声明类 `Impl`，接口类只持有一个 `std::unique_ptr<Impl>`；由于 `std::unique_ptr` 的默认删除器需要 `Impl` 是完整类型才能执行 `delete`，因此接口类的析构函数（及移动操作）必须在 `Impl` 完整可见的 `.cpp` 中定义。
- **底层机制**：若在头文件中依赖编译器隐式内联生成 `~Spreadsheet()`，调用方在包含头文件处实例化 `unique_ptr<Impl>` 的析构时，看到的只是不完整类型 `class Impl;`，从而触发 `sizeof(Impl)` 编译错误。在头文件中仅声明 `~Spreadsheet();`，在 `.cpp` 完整定义 `class Spreadsheet::Impl { ... };` 之后再写 `Spreadsheet::~Spreadsheet() = default;`，即可完美通过编译并隐藏全部私有细节。
- **设计取舍与边界**：Pimpl 会带来一次额外堆分配与间接访问，且所有接口函数需转发给 `m_impl`；适合用于大型模块的公有稳定 API 类，不适合高频创建的小型基础数值类。
- **代码 / 场景对照**：
```cpp
// [反例] 头文件中未声明析构函数，编译器在调用端面对不完整 Impl 报错
class Spreadsheet {
    class Impl;
    std::unique_ptr<Impl> m_impl; // 隐式析构触发 incomplete type 编译错误
};

// [正例] 头文件仅声明析构与移动，.cpp 在 Impl 完整定义后再 = default
// Spreadsheet.cppm: ~Spreadsheet();
// Spreadsheet.cpp:  class Spreadsheet::Impl { /* ... */ };
//                   Spreadsheet::~Spreadsheet() = default;
```
- **回归主线**：至此，单个类的资源管理、移动优化、编译期求值与稳定接口全部收官；接下来进入第 10 章，深入多类协作的继承与多态机制。

## 本轮技术复盘（第 9 章）

### 主线推演回顾
从动态内存类的深拷贝与 Copy-and-Swap 出发，过渡到 `noexcept` 移动语义与现代 C++ 零法则，继而系统梳理 `const`/`mutable`/引用限定、`consteval`、`inline static`、非成员运算符与 C++20 `<=>`，最终落脚到 Pimpl 的完整工程实现。

### 高频误区速查
- **误区 1**：在函数返回局部对象时写 `return std::move(local);` -> 反而阻断 NRVO 拷贝消除，降低性能。
- **误区 2**：自定义移动构造函数却忘了加 `noexcept` -> `std::vector` 扩容时为保异常安全被迫退化回深拷贝。
- **误区 3**：使用 `unique_ptr<Impl>` 实现 Pimpl 却在头文件保留隐式析构 -> 导致不完整类型删除编译失败。

### 工程落地清单
- 业务类严格践行“零法则”，用 `std::vector`、`std::string` 与智能指针替代裸指针成员。
- 凡是手写移动构造/移动赋值，必须标注 `noexcept` 并配合 `std::exchange` 清空源对象。
- C++20 及以上项目中，值语义类的比较运算统一使用 `auto operator<=>(const T&) const = default;`。
