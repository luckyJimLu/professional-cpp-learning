### Q61｜异常的“按值抛、按常引用捕”与 `throw;` 重抛铁律

`主线 · 阶梯 1/5 异常捕获与切片`

> **Question**
> 为什么 C++ 异常处理必须严格遵守“按值抛出（throw by value）、按 `const` 引用捕获（catch by const reference）”？当需要在 `catch` 块里记录日志并把异常继续向上传递时，写 `throw e;` 和写 `throw;` 底层会发生什么截然不同的后果？

**Answer**
- **核心结论**：按值抛出可确保异常对象活在专用异常存储区而非即将销毁的局部栈帧；按 `const` 引用捕获既避免多余拷贝，又防止派生异常被对象切片；重抛时必须写空 `throw;` 才能原样保留原始派生异常类型，写 `throw e;` 会按静态类型拷贝并彻底切掉派生信息。
- **底层机制**：若抛出指向局部变量的指针（`throw &localErr;`），栈展开瞬间该指针立即悬空；若按值捕获（`catch (std::exception e)`），抛出的 `std::runtime_error` 会被切片为基类 `std::exception`，丢失子类信息与虚函数行为。同样，在 `catch (const std::exception& e)` 内部写 `throw e;` 会以静态类型 `std::exception` 构造一个全新的基类异常并抛出去，破坏多态重抛。
- **设计取舍与边界**：严禁抛出裸指针或内置整数，所有自定义异常均应继承自 `std::exception`（或其标准派生类如 `std::runtime_error`），且在 `catch` 块中一律使用 `const ExceptionType&`。
- **代码 / 场景对照**：
```cpp
// [反例] 按值捕获引发切片，且 throw e 再次切片破坏原始异常类型
catch (std::exception e) {
    log(e.what());
    throw e; // 丢失原始派生异常类型！
}

// [正例] 按 const 引用捕获，原样重抛使用裸 throw;
catch (const std::exception& e) {
    log(e.what());
    throw; // 完整保留原始派生异常对象与动态类型
}
```
- **回归主线**：异常抛出后一路向上寻找匹配的 `catch` 块，沿途经过的所有活跃函数栈帧都会被逐层拆除——这就是栈展开机制。

### Q62｜栈展开（Stack Unwinding）、RAII 与 `noexcept` 违约后果

`主线 · 阶梯 2/5 栈展开与 RAII 铁律`

> **Question**
> 异常触发栈展开时，沿途函数里的局部对象和手动 `new` 出来的堆内存分别会遭遇什么？给函数加上 `noexcept` 说明符后，如果内部意外抛出了未捕获异常，为什么连外层的 `catch (...)` 也救不了程序？

**Answer**
- **核心结论**：栈展开会自动逆序调用所有已构造栈对象的析构函数，但绝不会自动释放裸指针指向的堆内存，因此必须靠智能指针/RAII 托管资源；一旦标为 `noexcept` 的函数试图向外抛出异常，运行时会直接调用 `std::terminate()` 强行终止进程，不会继续栈展开。
- **底层机制**：在 `catch` 块里手动 `delete` 再重抛不仅代码臃肿，还容易在多个资源同时存在时遗漏分支；RAII 把清理逻辑绑定在栈对象析构上，无论正常返回还是异常展开都百分之百执行。`noexcept` 允许编译器省略为该函数生成栈展开表并解锁 `std::vector` 移动优化，但它是一项刚性契约——违约直接终止（旧式 C++98 动态异常规范 `throw(int)` 已被 C++17 移除，仅保留 `noexcept` 与条件 `noexcept(expr)`）。
- **设计取舍与边界**：只在确信绝不抛异常（或发生异常程序理应直接中止）的函数上标注 `noexcept`，尤其是移动构造、移动赋值、`swap` 与析构函数；不要盲目给可能触发内存分配的普通函数加 `noexcept`。
- **代码 / 场景对照**：
```cpp
// [反例] 裸指针靠 catch 手动清理，易漏且违背 RAII
auto* p = new Buffer{};
try { work(p); } catch (...) { delete p; throw; }
delete p;

// [正例] 依托 RAII 与栈展开自动清理，仅对真不抛异常的移动/交换标 noexcept
auto p = std::make_unique<Buffer>();
work(p.get()); // 无论是否抛异常，p 均自动释放
```
- **回归主线**：栈展开依赖析构函数兜底，那么最棘手的两个特殊时刻就来了——当异常发生在**构造函数中途**或**析构函数内部**时，语言规则是如何运作的？

### Q63｜构造函数中途异常、析构函数禁抛与函数级 `try` 块

`主线 · 阶梯 3/5 构造与析构异常`

> **Question**
> 如果一个类的构造函数在执行到一半时抛出异常，该类自身的析构函数会被调用吗？为什么绝不能让异常逃逸出析构函数，而构造函数特有的函数级 `try` 块（Function-Try-Block）又能解决什么问题？

**Answer**
- **核心结论**：构造函数中途抛异常意味着对象“从未完全诞生”，因此该类**自身的析构函数不会被调用**，但所有**已经构造完成的基类和成员子对象**会被自动逆序析构；析构函数默认隐式 `noexcept`，绝不允许异常逃逸（否则在栈展开期间二次抛异常直接 `std::terminate()`）；函数级 `try` 块用于捕获**成员初始化列表**中抛出的异常，但它无法吞掉异常，退出时必然重抛。
- **底层机制**：若类内部用裸指针成员在构造函数体内先后 `new` 两块内存，第二块 `new` 抛 `bad_alloc` 时，由于自身析构不执行，第一块内存会永久泄漏；若改用 `std::unique_ptr` 成员，已构造完成的第一个 `unique_ptr` 子对象会自动析构释放内存，完美无漏。函数级 `try` 块（`C::C() try : m_a(...) { ... } catch (...) { ... }`）主要用于记录初始化失败日志或将底层异常翻译为更合适的上层异常再抛出。
- **设计取舍与边界**：绝不在构造函数里直接持有多个裸资源指针——每个资源用独立 RAII 成员封装；析构函数内部若调用可能抛异常的清理接口（如刷新日志或关闭网络），必须在析构函数体内用 `try/catch` 彻底吞掉并记录，绝不向外泄露。
- **代码 / 场景对照**：
```cpp
// [反例] 构造函数持有两个裸指针，第二次 new 失败导致 m_a 永久泄漏
class Dual {
    int* m_a; int* m_b;
public:
    Dual() : m_a{ new int{1} }, m_b{ new int{2} } {} // 若 m_b 抛异常，~Dual 不执行
};

// [正例] 用独立 RAII 成员，已构造的子对象在构造失败时自动逆序清理
class Dual {
    std::unique_ptr<int> m_a{ std::make_unique<int>(1) };
    std::unique_ptr<int> m_b{ std::make_unique<int>(2) };
};
```
- **回归主线**：保障了异常不会造成泄漏与崩溃后，在大型分层系统中，如何让最终捕获到的异常携带完整的“事发现场”与跨层根因链？

### Q64｜嵌套异常与 C++20/23 源位置、调用栈自动诊断

`支线 L11 · 嵌套异常与现代诊断`

> **Question**
> 底层解析模块抛出的异常被上层业务捕获后，往往需要翻译成业务异常再抛出，如何避免丢失原始底层错误？C++20 的 `std::source_location` 与 C++23 的 `std::stacktrace` 又如何免去手写 `__FILE__`/`__LINE__` 宏？

**Answer**
- **核心结论**：使用 `std::throw_with_nested(UpperException{...})` 可把当前活跃的底层异常原封不动地打包进上层异常中，捕获端用 `std::rethrow_if_nested` 递归展开整条根因链；在自定义异常构造函数中提供默认参数 `std::source_location loc = std::source_location::current()`（C++20）与 `std::stacktrace trace = std::stacktrace::current()`（C++23），即可在抛出点自动捕获精准文件名、行号、函数名与完整调用栈。
- **底层机制**：旧式宏 `__FILE__` 和 `__LINE__` 在日志包装函数里会展开成包装函数自身的位置而非调用方位置；而 `std::source_location::current()` 作为默认实参时，C++20 规定它在**调用点**求值，类型安全且零宏污染。C++23 `<stacktrace>` 进一步提供跨平台标准调用栈捕获，直接嵌入自定义异常类即可在故障时输出完整回溯。
- **设计取舍与边界**：`std::stacktrace::current()` 存在一定的运行期采集与符号解析开销，适合用在真正罕见的异常路径或严重错误诊断中，不应放在高频正常控制流里。
- **代码 / 场景对照**：
```cpp
// [反例] 捕获底层异常后直接抛新异常，原始根因与现场位置彻底丢失
catch (const std::runtime_error&) { throw AppError{ "加载失败" }; }

// [正例] 嵌套保留根因，并用 C++20/23 默认实参自动记录抛出点与调用栈
class AppError : public std::exception {
public:
    explicit AppError(std::string msg,
        std::source_location loc = std::source_location::current(),
        std::stacktrace trace = std::stacktrace::current());
};
// 上层包装：catch (...) { std::throw_with_nested(AppError{ "加载失败" }); }
```
- **回归主线**：有了诊断利器后，在编写多分支 `catch` 处理器和应对极端内存耗尽时，还有两条必须牢记的捕获与自救规则。

### Q65｜多态异常捕获顺序与 `std::bad_alloc` 内存耗尽自救

`主线 · 阶梯 4/5 捕获顺序与内存耗尽`

> **Question**
> 在多态异常层次中，如果把 `catch (const std::exception&)` 写在 `catch (const std::out_of_range&)` 前面会发生什么？当系统彻底耗尽内存触发 `std::bad_alloc` 时，除了直接崩溃还有什么机制可以介入自救？

**Answer**
- **核心结论**：`catch` 块严格按自上而下的书写顺序执行首个匹配，因此**最具体的派生异常必须写在前面**，最通用的基类异常（以及兜底 `catch (...)`）必须写在最后；面对内存分配失败，可通过 `std::set_new_handler` 注册全局回调尝试释放预留缓存或优雅记录崩溃前日志。
- **底层机制**：因为 `out_of_range` 是 `exception` 的派生类，若把基类 `catch` 放在前面，所有派生异常都会被提前截胡，后面的具体处理分支永远沦为死代码（现代编译器通常会告警）。当默认 `operator new` 无法满足分配请求时，在抛出 `std::bad_alloc` 之前会先循环调用已注册的 `new_handler`；该回调可以释放一块预先保留的紧急内存池让分配重试成功，或者记录告警后把 handler 置空/主动抛 `std::bad_alloc` 退出循环。
- **设计取舍与边界**：谨慎使用 `catch (...)` 吞掉一切未知异常，通常只用在线程入口边界、C API 跨语言边界或需要兜底释放非 RAII 资源后立即 `throw;` 重抛的场景。
- **代码 / 场景对照**：
```cpp
// [反例] 基类异常排在派生类前面，SpecificError 分支永远无法到达
try { run(); }
catch (const std::exception& e) { /* 截胡一切 */ }
catch (const std::out_of_range& e) { /* 死代码！ */ }

// [正例] 严格按“最特化 -> 基类 -> 兜底”顺序排列 catch 块
try { run(); }
catch (const std::out_of_range& e) { /* 精准处理越界 */ }
catch (const std::exception& e)    { /* 处理其他标准异常 */ }
```
- **回归主线**：综合运用栈展开、RAII 与异常边界规则后，工程上用一套明确的四级标尺来衡量任何函数或类的抗异常能力。

### Q66｜异常安全四级保证（Exception Safety Guarantees）

`主线 · 阶梯 5/5 异常安全保证`

> **Question**
> 评审一个核心类库的代码质量时，如何界定它达到了“无异常保证”“强保证”还是“基本保证”？为什么连基本保证都达不到的代码在生产中是不可接受的？

**Answer**
- **核心结论**：C++ 异常安全分为四档——**无异常保证（Nothrow）**绝不抛异常；**强保证（Strong）**失败时状态完全回滚到调用前（原子性）；**基本保证（Basic）**失败时不泄漏资源且所有类不变式依然有效（对象处于合法但未指定的状态）；**无保证（None）**可能泄漏或破坏数据结构。所有生产代码至少必须达到**基本保证**。
- **底层机制**：析构、`swap` 与移动操作应满足无异常保证（`noexcept`），因为它们是构建上层强保证的砖石——例如第 9 章的 Copy-and-Swap 惯用法正是借助“先构造临时副本（可能抛异常但不改原状态）+ `noexcept` 交换”把普通赋值提升到了强异常安全保证。而任何依赖裸指针半途修改多个字段的函数，一旦中途抛异常，连基本保证都会失守。
- **设计取舍与边界**：不必强求所有操作都达到强保证（有时为了原子回滚做整份拷贝代价过高，例如 `std::vector` 中间插入多元素通常只提供基本保证）；但**基本保证是不可妥协的底线**，关键事务或赋值操作则力争强保证。
- **代码 / 场景对照**：
```cpp
// [反例] 先改内部状态再执行可能抛异常的操作，失败后对象不变式被破坏（无保证）
void update(const Data& d) {
    m_count = d.size();       // 已篡改计数
    m_buf = allocateCopy(d);  // 若抛 bad_alloc，m_count 与 m_buf 彻底脱节
}

// [正例] 先完成所有可能抛异常的分配，最后 noexcept 提交（强保证）
void update(const Data& d) {
    auto nextBuf = allocateCopy(d); // 失败则原对象毫发无损
    m_buf = std::move(nextBuf);
    m_count = d.size();
}
```
- **回归主线**：异常机制守住了程序在错误路径上的健壮性；接下来第 15 章将回到类的表达力巅峰——深入剖析 C++ 运算符重载的规则、红线与 C++23 新能力。

## 本轮技术复盘（第 14 章）

### 主线推演回顾
从按值抛、按常引用捕与裸 `throw;` 重抛的铁律出发，阐明了栈展开与 RAII 的协同机制、`noexcept` 违约终止语义，拆解了构造函数中途异常与析构禁抛的生命周期陷阱，引入嵌套异常与 C++20/23 诊断库，最终以四级异常安全保证收束工程质量标尺。

### 高频误区速查
- **误区 1**：在 `catch (const std::exception& e)` 中写 `throw e;` 重抛 -> 触发对象切片，丢失原始派生异常类型。
- **误区 2**：以为构造函数中途抛异常后会调用自身的析构函数 -> 自身析构不会执行，只有已构造完成的成员子对象会被逆序析构。
- **误区 3**：允许异常逃逸出析构函数 -> 析构默认 `noexcept`，在栈展开期二次抛异常会直接触发 `std::terminate()`。

### 工程落地清单
- 所有自定义异常继承自 `std::exception` 家族，捕获一律用 `const T&`，重抛一律用裸 `throw;`。
- 构造函数内绝不直接裸管多项资源，改用独立 RAII 成员确保半途失败零泄漏；析构函数内彻底消化一切潜在异常。
- 关键状态修改遵循“先执行可抛异常步骤，再 `noexcept` 提交”，确保核心模块至少满足基本保证、关键路径满足强保证。
