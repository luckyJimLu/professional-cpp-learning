### Q115｜彻底淘汰 C 风格 `rand()` 与 `% N` 取模偏差

`主线 · 阶梯 1/5 告别 C 风格 rand()`

> **Question**
> 为什么即便只是写个抽奖或洗牌程序，现代 C++ 也强烈禁止使用 `std::srand(time(0))` 配合 `std::rand() % N`？取模运算 `% N` 到底在底层制造了什么统计偏差？

**Answer**
- **核心结论**：`rand()` 存在五大硬伤——分布非均匀（`% N` 导致低位区间概率偏高）、低位比特周期极短且随机性差、`RAND_MAX` 上限过小（部分平台仅 32767）、全局共享静态状态导致**非线程安全**，以及用秒级 `time(nullptr)` 做种子使同一秒内启动的进程生成完全相同的序列。
- **底层机制**：假设 `RAND_MAX` 为 32767（共 32768 个等概率整数），你想生成 `[0, 9999]` 的随机数并写成 `rand() % 10000`：其中 `0` 到 `2767` 各对应 4 个原始输出（如 0、10000、20000、30000），而 `2768` 到 `9999` 只对应 3 个原始输出，导致前段数字出现概率高出整整 33%！此外，传统线性同余实现让最低比特位经常呈现 `0, 1, 0, 1` 交替规律，直接取模偶奇性极差。
- **设计取舍与边界**：所有 C++11 及以上代码一律禁用 `std::rand()` 和 `std::srand()`，全面迁移至 `<random>` 提供的引擎与分布组合。
- **代码 / 场景对照**：
```cpp
// [反例] 全局状态非线程安全，且 % N 制造明显的低位区间概率偏差
std::srand(static_cast<unsigned>(std::time(nullptr)));
int pick = std::rand() % 100;

// [正例] 使用 <random> 梅森旋转引擎配合无偏差均匀分布
std::mt19937 eng{ std::random_device{}() };
std::uniform_int_distribution<int> dist{ 0, 99 };
int pick = dist(eng);
```
- **回归主线**：`<random>` 之所以不像 `rand()` 那样把生成与范围映射混为一谈，核心在于将“引擎”与“分布”彻底解耦。

### Q116｜引擎（Engine）与分布（Distribution）的正交解耦

`主线 · 阶梯 2/5 引擎与分布架构`

> **Question**
> 为什么 `<random>` 要把生成随机数拆成“引擎（如 `std::mt19937`）”和“分布（如 `uniform_int_distribution`、`normal_distribution`）”两个独立对象，而不是提供一个直接返回指定范围随机数的单函数？

**Answer**
- **核心结论**：**引擎**只负责按确定性算法高效吐出高质量的原始均匀随机比特流；**分布**则负责把原始比特流精确映射为特定数学概率分布（均匀、正态、伯努利、泊松等）并消除取模偏差。二者正交组合，既能复用同一引擎服务多种分布，又能通过固定种子 $100\%$ 复现整条随机流以利调试与单元测试。
- **底层机制**：标准库提供三类基础引擎（线性同余 `linear_congruential_engine`、梅森旋转 `mersenne_twister_engine` 与带进位减法 `subtract_with_carry_engine`）及适配器（如 `discard_block_engine` 构成的 `ranlux`）。其中预定义的 `std::mt19937`（周期高达 $2^{19937}-1$，内部状态约 2.5 KB）在速度与统计质量间取得了极佳平衡。分布对象则内部采用拒绝采样（Rejection Sampling）等严谨数学变换消除 `% N` 偏差，且同一分布函数可随时切换接入不同引擎。
- **设计取舍与边界**：通用模拟、抽样与游戏逻辑首选 `std::mt19937`（64 位选 `std::mt19937_64`）；若对内存极度敏感（如嵌入式受限环境不能承受 2.5 KB 状态），可选用轻量级的 `std::minstd_rand` 或优质第三方 PCG 引擎。
- **代码 / 场景对照**：
```cpp
// [反例] 自己手写浮点归一化 rand() / (double)RAND_MAX，精度与端点闭区间常出错
double r = static_cast<double>(std::rand()) / RAND_MAX;

// [正例] 同一引擎对象驱动多种专业分布，数学特性严谨且可随时固定种子复现
std::mt19937_64 eng{ 12345ULL };
std::uniform_real_distribution<double> uDist{ 0.0, 1.0 };
std::normal_distribution<double> nDist{ 50.0, 10.0 };
```
- **回归主线**：引擎虽然强大，但如果种子喂得不对——或者放错了实例化位置——再好的引擎也会立刻退化成“假随机”甚至性能黑洞。

### Q117｜`std::random_device` 正确用法与循环重播种陷阱

`主线 · 阶梯 3/5 种子与生命周期`

> **Question**
> 既然 `std::random_device` 能从硬件读取真随机熵，为什么不能每次要随机数时都直接调用 `rd()`，而应该只用它为 `std::mt19937` 提供种子？更常见的是，为什么把引擎和种子初始化写进 `for` 循环内部会导致每次生成的“随机数”一模一样？

**Answer**
- **核心结论**：`std::random_device` 直接调用操作系统或硬件熵源，速度慢且部分系统熵池耗尽时可能阻塞或抛异常（甚至在极少数老旧工具链上退化为固定种子伪随机），因此**只应用来为伪随机引擎播种一次**；同时，绝对禁止在函数热路径或循环内部每次重新创建并播种引擎（尤其是用时间做种子，同一毫秒/秒内循环一万次会得到一万个完全相同的数字）。
- **底层机制**：`mt19937` 拥有长达 624 个 32 位整数（19937 比特）的内部状态，单一 32 位种子其实只能覆盖其极小一部分初始状态；对随机质量要求严苛时，可用 `std::seed_seq` 收集多个 `random_device` 输出填充完整状态。引擎创建后必须作为长期存活的状态对象（如类的成员变量或 `thread_local` 变量）反复调用 `eng()` 推进内部状态序列。
- **设计取舍与边界**：测试与需要确定性重放的场景直接传入常量种子（如 `42u`）；生产随机场景用 `random_device`（或 `seed_seq`）在初始化阶段播种一次，随后全程复用同一个引擎实例。
- **代码 / 场景对照**：
```cpp
// [反例] 每次调用函数都重新构造并按当前秒数播种，1 秒内全返回相同值！
int rollDice() {
    std::mt19937 eng{ static_cast<unsigned>(std::time(nullptr)) };
    return std::uniform_int_distribution<int>{ 1, 6 }(eng);
}

// [正例] 引擎作为持久状态（如 thread_local）仅在首次构造时用 random_device 播种
int rollDice() {
    thread_local std::mt19937 eng{ std::random_device{}() };
    thread_local std::uniform_int_distribution<int> dist{ 1, 6 };
    return dist(eng);
}
```
- **回归主线**：把引擎放对了位置之后，在使用各类分布对象本身时，还有两个极易忽略的区间边界与内部状态细节。

### Q118｜分布的开闭区间差异与有状态分布的并发陷阱

`主线 · 阶梯 4/5 分布边界与状态`

> **Question**
> `std::uniform_int_distribution<int>(1, 6)` 和 `std::uniform_real_distribution<double>(0.0, 1.0)` 的右边界开闭语义一样吗？为什么连分布对象本身（例如 `std::normal_distribution`）也不能在多线程间无锁共享？

**Answer**
- **核心结论**：整数均匀分布 `uniform_int_distribution(a, b)` 是**双闭区间 `[a, b]`**（可能取到 `b`），而实数均匀分布 `uniform_real_distribution(a, b)` 是**左闭右开区间 `[a, b)`**（理论上不包含 `b`）；此外，部分分布（如 `normal_distribution` 采用 Box-Muller / Marsaglia 极坐标法每次成对算出两个正态值并缓存第二个）内部**持有可变状态**，同样不是线程安全的。
- **底层机制**：生成数组随机下标时，写 `uniform_int_distribution<size_t>{ 0, vec.size() - 1 }` 是完全正确的闭区间用法（注意先判 `vec` 非空）；若需要取样或打乱容器元素，直接用标准算法 `std::ranges::shuffle(vec, eng)` 或 `std::ranges::sample`（C++17）更为安全。因为 `dist(eng)` 重载的是**非 `const`** 的 `operator()`（允许更新分布内部缓存状态），多条线程共用同一个分布对象也会发生数据竞态。
- **设计取舍与边界**：需要频繁变更范围时可用 `dist.param(...)` 或临时构造轻量级分布对象，但跨线程场景必须确保每个线程独占自己的引擎与分布实例（`thread_local`）。
- **代码 / 场景对照**：
```cpp
// [反例] 误把 uniform_int_distribution 当作左闭右开，传入 vec.size() 导致越界 UB
std::uniform_int_distribution<size_t> dist{ 0, vec.size() }; // 可能生成 vec.size()！

// [正例] 整数均匀分布严格为闭区间 [0, size - 1]，打乱容器直接用 ranges::shuffle
std::uniform_int_distribution<size_t> dist{ 0, vec.size() - 1 };
std::ranges::shuffle(vec, eng);
```
- **回归主线**：`<random>` 已经足够应付绝大多数科学与工程模拟，但一旦涉及安全领域（密钥、Token、验证码生成），哪怕是最高质量的 `mt19937` 也会带来灾难性漏洞。

### Q119｜非密码学 PRNG 的安全边界：为何 `mt19937` 不能用于生成密钥

`主线 · 阶梯 5/5 密码学安全边界`

> **Question**
> `std::mt19937` 的周期高达 $2^{19937}-1$，统计随机性极其优秀，为什么绝对禁止用它来生成加密密钥、会话 Token 或安全验证码？

**Answer**
- **核心结论**：`std::mt19937`（以及 `<random>` 中的所有伪随机引擎）都是**确定性非密码学伪随机数生成器（PRNG）**，不具备密码学不可预测性——攻击者只需连续观测区区 624 个 32 位输出值，就能线性反推出其全部内部状态，从而精准预测过去与未来的所有输出！
- **底层机制**：梅森旋转算法的状态转移与输出变换（Tempering）本质上是有限域 $GF(2)$ 上的线性变换，没有任何单向密码学哈希或分组加密保护；在安全语境下，可被观测反推等同于“零安全性”。C++ 标准库 `<random>` 的设计目标是仿真、统计与蒙特卡洛计算的高吞吐与可复现性，并非密码学安全（CSPRNG）。
- **设计取舍与边界**：凡涉及密码学密钥、Nonce、CSRF/Session Token、密码盐值等安全敏感随机值，**严禁使用 `std::mt19937` 等标准伪随机引擎**，必须调用操作系统或专业密码学库提供的 CSPRNG 接口（如 Linux `getrandom()` / `/dev/urandom`、Windows `BCryptGenRandom` 或 OpenSSL `RAND_bytes`）。
- **代码 / 场景对照**：
```cpp
// [反例] 用 mt19937 生成 API Token 或会话密钥，观测 624 个样本即可完全破解
std::mt19937_64 tokenEng{ std::random_device{}() };
uint64_t apiToken = tokenEng(); // 不具备密码学不可预测性！

// [正例] mt19937 仅用于模拟/游戏/抽样；安全密钥必须接入系统 CSPRNG
// 仿真抽样：std::mt19937_64 simEng{ ... };
// 安全令牌：调用 OS CSPRNG（如 getrandom / BCryptGenRandom / OpenSSL）
```
- **回归主线**：最后从代码工程的实用细节出发，探讨一下在复杂项目中如何把 `<random>` 优雅地封装成可测试、可注入的随机服务，同时避免跨线程隐蔽共享。

### Q120｜并发隔离（`thread_local`）与可测试随机源封装

`支线 L20 · 随机源工程封装`

> **Question**
> 在多线程服务中既想避免给全局引擎加互斥锁拖垮性能，又想让核心业务逻辑在单元测试里能够传入固定种子实现 $100\%$ 确定性回放，该如何设计随机数接口？

**Answer**
- **核心结论**：结合第 6 章的依赖倒置思想，业务算法不应在内部写死全局或 `thread_local` 随机源，而应通过模板参数（满足 C++20 `std::uniform_random_bit_generator` 概念）将引擎引用传入算法；生产环境各工作线程向其注入各自的 `thread_local` 引擎，单元测试则注入固定种子的独立引擎。
- **底层机制**：直接在函数里写死 `thread_local mt19937` 虽解决了无锁并发安全，却让测试代码无法控制种子以复现边界用例（这与第 6 章强调的“Mock 与可测试性”一脉相承）。通过接受 `std::uniform_random_bit_generator auto& eng` 形参（就像标准库 `std::ranges::shuffle(r, eng)` 所做的那样），既保留了零虚函数开销，又把引擎生命周期与播种策略彻底交还调用方。
- **设计取舍与边界**：上层线程调度器负责为每个工作线程持有独立 `thread_local` 引擎；底层核心算法只借用引擎引用，不拥有引擎也不自行播种。
- **代码 / 场景对照**：
```cpp
// [反例] 核心算法内部硬编码 random_device 播种，单元测试无法确定性复现偶发 Bug
int sampleScore() {
    std::mt19937 eng{ std::random_device{}() };
    return std::uniform_int_distribution<int>{ 1, 100 }(eng);
}

// [正例] 遵循 C++20 Concept 注入随机比特生成器引用，兼顾无锁并发与确定性单测
int sampleScore(std::uniform_random_bit_generator auto& eng) {
    return std::uniform_int_distribution<int>{ 1, 100 }(eng);
}
```

## 本轮技术复盘（第 23 章）

### 主线推演回顾
从淘汰存在取模偏差、小上限与并发隐患的 `rand()` 起步，剖析 `<random>` 引擎与分布的正交解耦设计，明确 `random_device` 仅作初始化播种与禁止循环内重播种的生命周期铁律，厘清整/实数分布开闭区间与内部状态线程安全边界，最终划定非密码学 PRNG 的安全红线并给出可测试并发封装范式。

### 高频误区速查
- **误区 1**：在函数或 `for` 循环内部每次临时构造并按当前时间播种 `std::mt19937` -> 短时间内产出完全相同的伪随机序列且开销巨大。
- **误区 2**：以为 `std::uniform_int_distribution<int>(0, vec.size())` 是右开区间 -> 整数分布为双闭区间 `[a, b]`，传 `vec.size()` 会越界。
- **误区 3**：用 `std::mt19937` 生成加密密钥或安全 Token -> 观测 624 个输出即可反推全部状态，安全场景必须使用 OS 或密码学库的 CSPRNG。

### 工程落地清单
- 全库禁用 `std::rand()` / `std::srand()`，统一采用 `<random>` 引擎 + 分布组合。
- 多线程环境通过 `thread_local` 为每个线程分配独立引擎与分布实例，核心算法通过 C++20 `std::uniform_random_bit_generator` 形参接收注入以支持确定性单测。
- 涉及密码学安全的随机令牌与密钥，严格路由至操作系统或专业密码学 CSPRNG 接口。
