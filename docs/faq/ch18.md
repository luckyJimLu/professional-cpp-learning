### Q85｜`std::vector` 扩容、元素要求与迭代器失效法则

`主线 · 阶梯 1/5 vector 底层机制`

> **Question**
> 为什么往 `std::vector` 中不断 `push_back` 时，先前保存的指针、引用和迭代器会突然全部失效引发崩溃？`reserve()` 与 `resize()`、`emplace_back()` 与 `push_back()` 在底层究竟有什么区别？

**Answer**
- **核心结论**：`std::vector` 底层维护单块连续内存，当 `size == capacity` 时触发扩容（按几何倍增分配新大块内存、移动或拷贝旧元素并释放旧块），导致**所有**指向旧块的迭代器、指针与引用瞬间失效；`reserve(n)` 只预分配容量不改变 `size`，`resize(n)` 则真正构造出 `n` 个元素；`emplace_back` 直接在容器末尾原地构造，省去临时对象构造与移动。
- **底层机制**：为了把尾部追加的均摊复杂度控制在 $O(1)$，每次扩容容量按固定倍数（如 1.5x 或 2x）增长。由于内存整体搬迁，在扩容瞬间旧元素地址全部作废（若元素移动构造未标 `noexcept`，搬迁还会被迫退化为昂贵的深拷贝）。此外，在 `vector` 中间 `insert` 或 `erase` 会导致操作点及之后的所有迭代器失效；而在遍历删除满足条件的元素时，C++20 应直接使用统一的 `std::erase(vec, val)` / `std::erase_if(vec, pred)`，告别冗长的 Erase-Remove 惯用法。
- **设计取舍与边界**：已知大致元素数量时务必提前调用 `reserve(n)` 消除多次扩容搬迁；切勿保存长期指向 `vector` 内部元素的裸指针或迭代器（或改用索引/稳定节点容器）。
- **代码 / 场景对照**：
```cpp
// [反例] 预知大小却不 reserve 导致反复扩容，且遍历中保存元素指针失效
std::vector<Item> items;
items.push_back(Item{ 1, "a" });
Item* first = &items[0];
items.push_back(Item{ 2, "b" }); // 若触发扩容，first 立即变成悬空指针！

// [正例] 提前 reserve 消除扩容 + emplace_back 原地构造 + C++20 erase_if
std::vector<Item> items;
items.reserve(100);
items.emplace_back(1, "a");
std::erase_if(items, [](const Item& it) { return it.expired(); });
```
- **回归主线**：`std::vector<T>` 几乎是所有顺序存储的首选默认容器，但唯独当模板参数 `T` 换成 `bool` 时，它竟会违背几乎所有容器契约。

### Q86｜`std::vector<bool>` 特化陷阱与替代方案

`支线 L15 · vector<bool> 特化坑`

> **Question**
> 为什么 `std::vector<int>` 可以通过 `int& r = v[0];` 拿到元素的真实引用，而看似一模一样的 `std::vector<bool>` 却连 `bool& r = vb[0];` 都编译不过，甚至在泛型代码与多线程下频频出事？

**Answer**
- **核心结论**：`std::vector<bool>` 是标准库历史遗留的**按位压缩特化版本**（每个 `bool` 只占 1 bit 而非 1 字节），由于 C++ 无法对单个比特取地址，其 `operator[]` 返回的不是 `bool&`，而是一个临时的代理对象（Proxy Reference），导致它根本不满足标准容器与连续范围的要求。
- **底层机制**：因为底层的 8 个或 64 个布尔标志打包挤在同一个整型字中，不仅 `auto& x = vb[0];` 无法绑定到真实 `bool&`（用 `auto x = vb[0];` 甚至拿到的是绑定到内部字位的代理对象，修改 `x` 竟会反向篡改容器！），而且多核线程并发写入 `vb[0]` 与 `vb[1]` 会落在同一内存字上引发严重的数据竞态。
- **设计取舍与边界**：工程中应**彻底避开 `std::vector<bool>`**——若尺寸在编译期固定且需位压缩，改用 `std::bitset<N>`；若需运行期动态大小的布尔数组，改用 `std::vector<uint8_t>`（或 `std::vector<char>`）以换取真实引用语义与线程安全。
- **代码 / 场景对照**：
```cpp
// [反例] vector<bool> 返回代理对象而非真实 bool&，在泛型模板与引用绑定中失败
std::vector<bool> flags{ true, false };
bool& first = flags[0]; // 编译错误！无法将临时代理对象绑定到 bool&

// [正例] 动态布尔数组使用 std::vector<uint8_t>，固定位集使用 std::bitset
std::vector<uint8_t> flags{ 1, 0 };
uint8_t& first = flags[0]; // 真实字节引用，线程安全且兼容全部标准算法
```
- **回归主线**：看清了 `vector` 的统治地位与 `vector<bool>` 特例后，什么时候才该把主容器切换为 `deque`、`list` 或 `array`？

### Q87｜`deque`、`list`/`forward_list` 与 `std::array` 的选型边界

`主线 · 阶梯 2/5 顺序容器选型`

> **Question**
> 链表 `std::list` 号称在任意位置插入删除只要 $O(1)$，为什么现代高性能 C++ 实战中却几乎总被连续内存的 `std::vector` 吊打？`deque` 与 `std::array` 又各自守着哪块不可替代的生态位？

**Answer**
- **核心结论**：`std::list` 虽有 $O(1)$ 已知位置插删与迭代器稳定性，但每个节点独立堆分配且内存分散，指针跳转极易触发 CPU 缓存未命中；小中规模数据下 `vector` 连续内存遍历与搬移往往比链表更快。`deque` 兼顾首尾双端 $O(1)$ 增删且扩容不移动已有元素；`std::array` 则是零开销、不退化为指针的固定大小栈数组。
- **底层机制**：`std::deque` 底层采用分段连续内存块配合中控指针数组，因此两端追加永不搬移已有元素（指向元素的指针/引用在首尾插删时保持有效，仅迭代器可能失效），但不保证整体内存完全连续；`std::forward_list`（单向链表）省去反向指针与 `size()` 维护以追求极致内存紧凑；`std::array<T, N>` 把尺寸固定在类型里，零堆分配，且比 C 风格数组保留长度信息、支持直接赋值与比较。
- **设计取舍与边界**：默认首选 `std::vector`；编译期已知固定大小选 `std::array`；需要高效双端队列选 `std::deque`（也是 `std::queue` 和 `std::stack` 的默认底层容器）；仅当必须频繁在序列中部大批量插删且绝对要求已有元素指针/迭代器永不失效（或利用 `list::splice` 零拷贝转移节点）时，才选用 `std::list`。
- **代码 / 场景对照**：
```cpp
// [反例] 为了偶发的中间删除选用 std::list，承受每次节点堆分配与缓存未命中
std::list<Order> orders; // 遍历查找耗时远超 vector 线性扫描

// [正例] 编译期定长用 std::array，动态序列默认首选 std::vector
std::array<int, 4> fixedCoords{ 1, 2, 3, 4 };
std::vector<Order> orders; // 连续存储，缓存命中率最大化
```
- **回归主线**：既然 `vector` 与 `array` 拥有最友好的连续内存布局，当函数只想“只读或原地修改”一段连续内存而不关心它原本来自栈数组还是堆 `vector` 时，该用什么视图类型？

### Q88｜C++20 `std::span` 与 C++23 `std::mdspan` 非拥有视图

`主线 · 阶梯 3/5 连续与多维视图`

> **Question**
> 函数参数既想接收 `std::vector<int>`，又想接收 `std::array<int, 10>` 和 C 风格数组，传统做法写 `const std::vector<int>&` 会把非 `vector` 调用方逼出多余拷贝；C++20 `std::span` 与 C++23 `std::mdspan` 如何以零开销统一它们？

**Answer**
- **核心结论**：`std::span<T>`（C++20）是“指针 + 长度”的轻量级非拥有一维连续视图，按值传递（通常仅 2 个机器字），可无缝绑定 `vector`、`array` 与原生数组；C++23 `std::mdspan` 则在此基础上提供了可定制步长与布局策略的多维非拥有视图。
- **底层机制**：传统 `void process(const std::vector<int>&)` 强迫栈数组调用方先构造临时堆 `vector`；而 `void process(std::span<const int> data)` 编译后直接传入首地址与长度，零拷贝、零堆分配，且支持子切片 `subspan()` 与固定编译期长度 `std::span<int, 4>`。C++23 `std::mdspan` 更进一步，把一维连续缓冲区包装成二维/三维矩阵视图，支持行主序（`layout_right`）、列主序（`layout_left`）及带填充步长（`layout_stride`），直接用 `m[r, c]` 访问而无需复制底层数据。
- **设计取舍与边界**：函数接口只需访问连续序列而不涉及增删扩容时，形参一律优先使用 `std::span<const T>`（只读）或 `std::span<T>`（可改元素值）；同样需注意 `span` 不拥有内存，绝不能绑定即将销毁的临时对象后向外返回。
- **代码 / 场景对照**：
```cpp
// [反例] 形参写死 const std::vector<double>&，限制了 std::array 与原生数组零拷贝传入
void normalize(const std::vector<double>& samples);

// [正例] C++20 std::span 按值传参统一接入一切连续序列；C++23 mdspan 零拷贝看多维
void normalize(std::span<const double> samples);
std::mdspan<double, std::dextents<size_t, 2>> matView{ buf.data(), rows, cols };
```
- **回归主线**：解决了顺序存储与零拷贝视图后，当业务的核心诉求变成“按 Key 快速检索”时，就需要深入有序与无序关联容器的操作细节。

### Q89｜`std::map` 高效插入（`try_emplace`）与哈希容器设计

`主线 · 阶梯 4/5 关联容器与哈希`

> **Question**
> 用 `myMap[key] = value;` 插入或查找元素有什么隐蔽副作用？C++17 的 `try_emplace` / `insert_or_assign` 与 C++20 的 `contains()` 如何同时修复性能浪费与语义歧义？使用 `std::unordered_map` 又必须满足哪些哈希契约？

**Answer**
- **核心结论**：`map::operator[]` 在键不存在时会**静默默认构造并插入新元素**，既无法用于 `const` 容器，也会在“先默认构造再覆盖赋值”中浪费一次构造开销；纯判存应使用 `contains()`（C++20）或 `find()`，插入不覆盖用 `try_emplace()`（C++17），覆盖更新用 `insert_or_assign()`（C++17）。
- **底层机制**：即便 `key` 已经存在，`myMap.emplace(key, BigObj{...})` 仍会先把临时 `BigObj` 构造出来再发现键冲突丢弃；而 `myMap.try_emplace(key, args...)` 承诺**仅在键不存在时**才原地构造值对象，零浪费。对于 `std::unordered_map`（哈希表平均 $O(1)$、最坏 $O(n)$），自定义键类型必须同时提供 `std::hash<Key>` 特化（或自定义哈希仿函数）与 `operator==`，并保证“相等的键必须产出相同的哈希值”；此外，通过透明哈希与 `is_transparent` 标记（C++20），可用 `std::string_view` 直接在 `unordered_map<std::string, V>` 中零分配查找。
- **设计取舍与边界**：需要按 Key 有序遍历、范围查询（`lower_bound`）或最坏情况稳定 $O(\log n)$ 选 `std::map`（或 C++23 `flat_map`）；纯精确点查且不关心顺序选 `std::unordered_map`；只读查找严禁调用 `operator[]`。
- **代码 / 场景对照**：
```cpp
// [反例] 用 operator[] 判存会意外插入垃圾键，用 emplace 冲突时仍先构造临时对象
if (cache[key].empty()) { /* 即使只想查询，不存在的 key 已被悄悄插进 map！ */ }

// [正例] C++20 contains 判存，C++17 try_emplace 键不存在时才原地构造
if (!cache.contains(key)) {
    cache.try_emplace(key, expensiveArg1, expensiveArg2);
}
```
- **回归主线**：除了存储通用对象，工程中还有一类高频需求——紧凑管理几十上百个开关标志位，这就要靠与普通容器截然不同的位集工具。

### Q90｜`std::bitset` 与标准库容器选型决策清单

`主线 · 阶梯 5/5 位集与容器决策`

> **Question**
> 相比于用普通整型手动做位掩码（`flags |= (1 << 5)`）或者使用 `std::vector<bool>`，`std::bitset<N>` 在安全性、可读性与位运算表达力上有何压倒性优势？

**Answer**
- **核心结论**：`std::bitset<N>` 把编译期固定数量的比特打包进紧凑整型字中，彻底免除手动移位溢出（如 `1 << 33` 触发 UB）的隐患，原生支持 `&`、`|`、`^`、`~`、`<<`、`>>` 全套位运算以及 `test()`（带越界检查）、`count()`、`all()`、`any()`、`none()` 等语义化接口。
- **底层机制**：手工位掩码受限于单个 `uint64_t` 最多 64 位，超过即溢出 UB 且位宽调整极易出错；`std::bitset<128>` 则透明跨越多个机器字，自动处理跨字移位与边界截断，且可通过二进制字符串（`"10110"`）直接构造或序列化输出。虽然它不是标准意义上的 STL 迭代容器（不提供 `begin`/`end` 迭代器），但在固定位宽状态机、权限掩码、布隆过滤器底层分块等场景中无可替代。
- **设计取舍与边界**：位数量在编译期固定时一律首选 `std::bitset<N>`；位数量必须在运行期动态指定时，优先使用 `std::vector<uint8_t>`（或在引入第三方库时使用 `boost::dynamic_bitset`），避免踩进 `std::vector<bool>` 坑。
- **代码 / 场景对照**：
```cpp
// [反例] 手工移位超出 32/64 位宽度直接触发未定义行为，且只能靠注释猜含义
uint32_t mask = 0;
mask |= (1u << channelId); // 若 channelId >= 32 即 UB

// [正例] std::bitset 自动跨字安全管理任意编译期固定位数
std::bitset<128> channels;
channels.set(channelId); // 超出 127 自动抛出 std::out_of_range
```

## 本轮技术复盘（第 18 章）

### 主线推演回顾
从 `std::vector` 连续内存扩容与失效规则出发，揭示 `vector<bool>` 代理特化的历史陷阱，对比 `deque`/`list`/`array` 与 C++20/23 `span`/`mdspan` 的非拥有视图优势，规范 `map` 现代查找/插入接口与哈希契约，最终以 `std::bitset` 收束容器选型版图。

### 高频误区速查
- **误区 1**：保存 `std::vector` 内部元素指针后继续 `push_back` -> 扩容搬迁后原指针瞬间变为悬空指针。
- **误区 2**：使用 `std::vector<bool>` 充当动态布尔数组 -> 无法取 `bool&`，且并发写相邻位存在数据竞态。
- **误区 3**：对 `std::map` 使用 `m[key]` 做只读查询 -> 键不存在时会静默插入默认构造值并污染容器。

### 工程落地清单
- 默认顺序容器选 `std::vector` 并预先 `reserve`；动态布尔序列改用 `std::vector<uint8_t>`；固定位宽标志用 `std::bitset<N>`。
- 函数接收只读或就地修改的连续序列一律使用 `std::span<const T>` / `std::span<T>`（C++20）。
- 关联容器判存用 `contains()`（C++20），惰性插入用 `try_emplace()`（C++17），覆盖写用 `insert_or_assign()`（C++17）。
