### Q157｜开发者自测职责与单元测试粒度把握

`主线 · 阶梯 1/5 单元测试哲学`

> **Question**
> 很多团队习惯认为“写完代码扔给 QA 测试团队测就行了”，为什么现代工程要求 C++ 开发者自己编写单元测试？测试粒度太粗（一次测整个子系统）或太细（测一个无逻辑的 getter）各有什么弊端？

**Answer**
- **核心结论**：测试绝不是 QA 的专属事后补救——开发者最清楚自己代码的边界假设与内部分支，自写单元测试能在编码当场暴露设计耦合问题（难测的代码往往就是耦合过重的代码）；粒度上应围绕**独立可观测的逻辑单元（类/核心函数行为）**设计，既不跳过依赖隔离直接测巨无霸流程，也不为纯转发空壳浪费精力。
- **底层机制**：第 6 章与第 18 章设计子系统接口时强调“依赖倒置与可 Mock 性”，正是为了在单元测试中能把昂贵或不可控的数据库、网络、系统时钟替换成轻量测试替身（Stub/Mock），让成百上千条单测在毫秒级内稳定运行完毕。如果直到 QA 手工介入才发现缺陷，定位与修复成本已呈十倍飙升。
- **设计取舍与边界**：每个单元测试应当满足 **FIRST** 原则——快速（Fast）、独立（Independent，测试间绝不共享可变全局状态）、可重复（Repeatable，不依赖当前时间或真随机数）、自验证（Self-validating，自动断言而非人工看控制台输出）与及时（Timely）。
- **代码 / 场景对照**：
```cpp
// [反例] 测试里依赖真实系统时钟或全局共享文件，时而通过时而随机失败
TEST(SchedulerTest, RunsAtMidnight) { sleepUntilMidnight(); /* 脆弱且极慢 */ }

// [正例] 通过注入 Mock 时钟接口，毫秒级确定性验证所有时间边界逻辑
TEST(SchedulerTest, TriggersExactlyAtMidnight) {
    FakeClock clock{ MidnightTime };
    Scheduler s{ clock };
    EXPECT_TRUE(s.shouldTrigger());
}
```
- **回归主线**：写单元测试最容易犯的懒，是只测“正常输入顺风顺水走通”的开心路径——真正把线上服务打崩的，恰恰是没人测过的非法输入与边界条件。

### Q158｜边界条件、负向测试（Negative Tests）与数据设计

`主线 · 阶梯 2/5 边界与负向测试`

> **Question**
> 为什么只测合法输入的“正向测试”永远不够？在设计测试用例样本数据时，为什么“负向测试（专门验证代码在错误输入下正确失败或抛异常）”与边界值（0、1、最大值、空串）往往比常规数据更能抓出致命 Bug？

**Answer**
- **核心结论**：代码在正常路径下很容易“看起来是对的”，而数组越界（off-by-one）、除零、空指针解引用、整数溢出与异常路径资源泄漏几乎全部藏在**边界条件与非法输入**中；负向测试明确断言函数在违约输入下必须抛出预期异常或返回指定错误码（如 `std::expected` 错误态），防止异常吞没或静默出错。
- **底层机制**：构造测试样本数据时，应系统性地脑暴覆盖：空输入/零长度、单元素、极值（`INT_MAX`/`INT_MIN`）、包含特殊字符/多字节 UTF-8、重复元素、已排序与逆序样本，以及故意构造格式损坏或越界索引的负向用例（例如用测试框架的 `EXPECT_THROW` 验证 `at(999)` 确实抛出 `std::out_of_range`）。
- **设计取舍与边界**：每写一个新类或修复一个逻辑分支，至少配套 1 组正常路径用例 + 2 组以上边界与负向用例；测试代码本身也应保持简洁直观，避免在测试里再写复杂的嵌套循环逻辑。
- **代码 / 场景对照**：
```cpp
// [反例] 只测正常插入读取，索引越界或空输入分支从未被测试触达
TEST(GridTest, BasicSetGet) { Grid<int> g{ 3, 3 }; g.at(1, 1) = 5; EXPECT_EQ(g.at(1, 1), 5); }

// [正例] 补充 0 尺寸边界与负向异常断言，锁定契约底线
TEST(GridTest, OutOfBoundsThrows) {
    Grid<int> g{ 3, 3 };
    EXPECT_THROW(g.at(3, 0), std::out_of_range);
}
```
- **回归主线**：即便人类工程师再怎么细心脑暴边界用例，人脑依然很难穷举出成千上万种畸形二进制报文或恶意嵌套字符序列——这正是自动化模糊测试大显身手的地方。

### Q159｜模糊测试（Fuzz Testing）挖掘人类想不到的崩溃与 UB

`支线 L27 · 模糊测试实战`

> **Question**
> 面对解析网络协议、图片格式或复杂配置文件的 C++ 代码，我们已经写了上百条人工单元测试，为什么接入覆盖率引导的模糊测试（Fuzzing，如 libFuzzer / AFL++）后，几分钟内依然能炸出堆缓冲区溢出和崩溃？

**Answer**
- **核心结论**：人工测试用例受限于人的思维定势，往往只测“我以为会出错的地方”；模糊测试器通过代码覆盖率反馈自动变异生成海量的随机与半畸形字节流（如截断包头、超大长度字段、非法 UTF-8 编码），结合 AddressSanitizer/UBSan，专门精准打击内存越界、空指针解引用、死循环与未定义行为。
- **底层机制**：现代覆盖率引导 Fuzzer（如 Clang 内置的 `-fsanitize=fuzzer,address,undefined`）接收一个标准入口 `LLVMFuzzerTestOneInput(const uint8_t* data, size_t size)`，在执行过程中监控哪些代码分支被新输入点亮，并保留能触发新分支的“语料种子”持续变异。相比传统盲目随机乱输，它能迅速穿透复杂的格式校验头，深入解析器核心状态机深处。
- **设计取舍与边界**：所有直接处理外部不可信输入（文件解析、网络解包、正则/字符串解析、反序列化）的 C++ 模块，强烈建议编写轻量 Fuzz Target 纳入持续测试；被测接口应避免在内部调用 `exit()` 或持有跨次调用的可变全局状态。
- **代码 / 场景对照**：
```cpp
// [反例] 仅靠手写 5 条合法和 2 条手造坏 JSON 样本就宣布解析器绝对安全
// [正例] 暴露无状态模糊测试入口，配合 ASan/UBSan 持续自动化轰炸边界
extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
    std::string_view input{ reinterpret_cast<const char*>(data), size };
    auto res = parsePacket(input); // 验证绝不崩溃、不越界、不触发 UB
    return 0;
}
```
- **回归主线**：单元测试把单个零件测得再牢，把十几个模块拼装在一起时，依然可能因为接口假设不一致或并发竞争而翻车。

### Q160｜集成测试与系统测试：验证模块边界与真实环境

`主线 · 阶梯 3/5 集成与系统测试`

> **Question**
> 所有单元测试都绿了，为什么一上线还是会在模块对接处报错？集成测试（Integration Test）和系统测试（System Test）分别在验证哪一层的问题，为什么它们不能用 Mock 完全替代？

**Answer**
- **核心结论**：单元测试为了隔离往往使用了 Mock 替身，而 Mock 只能验证“你以为下游接口怎么表现”，却无法验证**真实的下游模块、真实数据库、真实网络协议或多线程调度时序**是否真的符合你的假设；集成测试专门验证多个真实组件协同的接口契约，系统测试则站在最终用户视角在类生产环境中做全链路端到端验收。
- **底层机制**：典型的跨模块隐患包括：A 模块以为 B 模块返回 UTF-8 而 B 实际返回本地编码、数据库事务隔离级别与连接池超时在真实并发下发生死锁、或者两个子系统对同一枚举值或单位（秒 vs 毫秒）理解错位。测试金字塔模型主张：底层海量快速单元测试做基座，中层适度集成测试打通真实边界，顶层少量关键路径端到端系统测试把关。
- **设计取舍与边界**：切勿把所有测试都写成启动整个数据库与浏览器的缓慢端到端测试（倒金字塔会导致反馈极慢且频繁误报）；也绝不能因为单测全过就完全省略真实组件的集成测试。
- **代码 / 场景对照**：
```cpp
// [反例] 只测了 MockDb，上线才发现真实 SQLite/MySQL 驱动对空字符串的绑定行为不同
// [正例] 测试金字塔分层：单测用 Mock 保速度，集成测试连真实测试库验证边界契约
```
- **回归主线**：上线后难免还会遇到漏网之鱼，修完一个线上 Bug 后，如何保证半年后别人重构代码时不会把这个一模一样的 Bug 再改回来？

### Q161｜回归测试（Regression Testing）锁定每一个修复的缺陷

`主线 · 阶梯 4/5 回归测试防线`

> **Question**
> 团队里经常出现“修好了 B 功能，却把三个月前已经修过的老 Bug A 又搞复发了”的尴尬局面；建立回归测试防线最核心的一条铁律是什么？

**Answer**
- **核心结论**：回归测试铁律——**在动手修复任何已确认的 Bug 之前，先为这个 Bug 编写一个能稳定复现失败的自动化测试用例；修完代码让该测试变绿后，将其永久合入 CI 测试套件**，从此任何后续改动只要让该缺陷复发就会在提交前被立即拦截。
- **底层机制**：很多时候修复 Bug 只需要改一行 `<=` 为 `<`，但如果没有留下对应的自动化回归测试，几个月后另一位工程师重构同一段逻辑时根本不知道当初为什么这里写 `<` 而不是 `<=`，极易“顺手改回去”。先写失败测试再修复（Test-First Fix）还能百分之百证实你的测试确实精准命中了问题根因，而不是碰巧通过。
- **设计取舍与边界**：缺陷驱动的回归测试用例通常体积小、指向明确，应直接附带 Bug 编号或清晰注释说明复现条件，永远保留在 CI 快速测试集内。
- **代码 / 场景对照**：
```cpp
// [反例] 收到用户报障后直接改代码修好，手工验证一遍了事，不留任何自动化用例
// [正例] 先补一条复现故障的回归测试（当前必红），修复后变绿并永久纳入 CI
TEST(ParserRegressionTest, Issue412_TrailingBackslashDoesNotCrash) {
    EXPECT_FALSE(parseLine("abc\\").has_value());
}
```
- **回归主线**：写好了单元测试、负向测试、模糊测试和回归测试，如果测试跑得太慢或者测试之间互相干扰，工程师很快就会逃避运行它们。

### Q162｜成功测试体系的可持续准则与测试代码维护

`主线 · 阶梯 5/5 测试工程可持续性`

> **Question**
> 为什么有些项目初期写了一堆测试，半年后却因为“一改需求就要改 50 个脆弱测试”或“跑一遍测试要半小时”而被团队彻底弃用？如何避免测试本身变成维护负担？

**Answer**
- **核心结论**：测试应当验证模块的**可观察行为契约（Behavior）而非内部私有实现细节（Implementation）**；一旦测试过度耦合内部私有数据结构或脆弱的 Mock 调用次数校验，任何正常重构都会让测试大面积误报红灯。
- **底层机制**：保持测试长期健康的三大支柱是：第一，面向公有接口与业务结果断言，不为了测试去把 `private` 全改成 `public`；第二，严格维持测试独立性，每个测试自行准备并清理隔离环境，禁止依赖执行顺序；第三，保持单元测试套件在秒级完成，耗时长的慢速集成/压力测试拆分为独立 CI 流水线（如夜间构建），让本地开发即时反馈零阻力。
- **设计取舍与边界**：测试代码与生产代码享有同等的工程质量标准——提取公共测试夹具（Test Fixture）消除重复初始化样板，但注意夹具不要过度复杂导致单个测试用例难以独立看懂。
- **代码 / 场景对照**：
```cpp
// [反例] 断言内部调用顺序和私有缓存大小，导致内部重构优化直接破坏测试
EXPECT_EQ(cache.internalBucketCount(), 16); // 耦合实现细节！

// [正例] 仅针对公有契约与可观察输出断言，允许内部自由演进优化
EXPECT_EQ(cache.lookup("key1"), "val1");
```
- **回归主线**：当测试或线上告警终于成功捕获到一个神出鬼没的故障时，第 31 章将系统展开 C++ 调试的底层基本法与实战工具链。

## 本轮技术复盘（第 30 章）

### 主线推演回顾
从明确开发者自测职责与 FIRST 单元粒度切入，补充边界条件与负向异常断言，引入覆盖率引导的模糊测试（Fuzzing）对抗恶意与极端输入，厘清集成/系统测试在测试金字塔中弥补 Mock 盲区的作用，强化“先写复现用例再修 Bug”的回归测试铁律，最终以“测行为不测实现”保障测试体系长期可持续。

### 高频误区速查
- **误区 1**：只测合法输入正向路径 -> 越界、空值、异常路径资源泄漏几乎全部藏在边界与负向输入里。
- **误区 2**：修完线上 Bug 不补自动化回归测试 -> 极易在后续重构中静默复发。
- **误区 3**：测试直接断言私有内部状态或过度 Mock 内部调用细节 -> 正常内部重构一改就红，最终迫使团队放弃测试。

### 工程落地清单
- 新增逻辑必须配套正常路径 + 边界/负向测试用例，确保测试满足独立、无全局状态与确定性。
- 解析外部不可信输入（网络/文件/文本）的模块接入 Fuzzing 与 ASan/UBSan。
- 严格执行“先写失败回归测试 -> 再修 Bug -> 永久入库 CI”闭环。
