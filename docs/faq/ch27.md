### Q139｜数据竞态、撕裂读、死锁与“伪共享（False Sharing）”

`主线 · 阶梯 1/5 并发四大隐患`

> **Question**
> 数据竞态和死锁大家都很熟悉，但在多核高性能并发中，为什么两个线程明明各自读写完全独立的变量 `counters[0]` 和 `counters[1]`（没有任何锁也没有逻辑冲突），整体吞吐量却暴跌数倍？

**Answer**
- **核心结论**：这是由 CPU 缓存行引发的**伪共享（False Sharing）**——CPU 缓存以固定大小的缓存行（通常 64 字节）为单位同步，相邻的独立变量若恰好落在同一条缓存行上，两核交替写入会迫使该缓存行在核心间反复失效并跨总线来回传输（Cache-line Ping-pong），彻底抵消多核并行收益。
- **底层机制**：并发编程需防四大隐患：数据竞态（多线程无同步访问同一内存且至少一方写入，属未定义行为 UB）、撕裂（Tearing，非原子多字节读写读到一半被另一线程改写）、死锁（互等对方持有的锁，可通过固定加锁序或 C++17 `std::scoped_lock` 同时锁多把锁根治）以及伪共享。消除伪共享的标准做法，是使用 C++17 `<new>` 提供的 `alignas(std::hardware_destructive_interference_size)` 将并发写入的热点变量对齐隔离到各自独立的缓存行上。
- **设计取舍与边界**：仅对多线程高频写入的独立热点计数器或线程槽位做缓存行对齐（避免盲目给普通小结构体加 `alignas(64)` 导致内存膨胀）；多线程加两把以上锁时一律用 `std::scoped_lock`。
- **代码 / 场景对照**：
```cpp
// [反例] 两个线程高频写相邻元素，落入同一 64B 缓存行引发严重伪共享
struct Counters { std::atomic<long> t1{0}; std::atomic<long> t2{0}; };

// [正例] C++17 hardware_destructive_interference_size 强制对齐隔离缓存行
struct Counters {
    alignas(std::hardware_destructive_interference_size) std::atomic<long> t1{0};
    alignas(std::hardware_destructive_interference_size) std::atomic<long> t2{0};
};
```
- **回归主线**：看清了硬件与并发的底层危险后，第一步是用现代线程句柄把线程生命周期与异常传播彻底管住。

### Q140｜C++20 `std::jthread`、协作取消与跨线程异常传递

`主线 · 阶梯 2/5 线程生命周期与取消`

> **Question**
> 为什么说 `std::thread` 是并发编程中的 RAII 异类——一旦某条分支抛出异常提前退出作用域没来得及调用 `join()` 或 `detach()`，程序就会直接 `std::terminate()` 崩溃？C++20 `std::jthread` 如何根治这一缺陷并实现优雅停止？

**Answer**
- **核心结论**：`std::thread` 析构时如果仍处于 `joinable()` 状态会直接调用 `std::terminate()` 强杀进程；C++20 `std::jthread`（`<thread>`）不仅在析构时自动发出停止请求并执行 RAII `join()`，还内置了基于 `std::stop_token` 的协作式取消机制，安全取代危险的硬杀线程操作。
- **底层机制**：绝不能强行外部杀死线程（会导致该线程持有的锁永不释放、内存泄漏、状态损坏），唯一安全的方式是协作取消：`std::jthread` 若接收 `std::stop_token` 作为首个形参，调用 `jt.request_stop()` 或其析构时会自动置位停止信号，工作循环定期检查 `token.stop_requested()` 后清理现场并自然退出。另外，子线程内抛出的未捕获异常**不会自动传回主线程**（直接导致进程终止），必须在子线程内用 `try/catch` 捕获 `std::current_exception()` 存入 `std::exception_ptr`，再由主线程通过 `std::rethrow_exception()` 重新抛出处理（或使用 `std::future` 自动跨线程传递）。
- **设计取舍与边界**：C++20 及以上新代码一律全面使用 `std::jthread` 替代 `std::thread`；慎用 `detach()`（后台分离线程极难在程序退出前保证安全收尾，极易访问已销毁的全局或静态对象）。
- **代码 / 场景对照**：
```cpp
// [反例] std::thread 在异常分支漏掉 join()，析构瞬间调用 std::terminate()
std::thread t{ worker };
mayThrow(); // 若此处抛异常，t 未 join 直接强杀整个进程！
t.join();

// [正例] C++20 std::jthread 自动协作取消并 RAII join，杜绝意外崩溃
std::jthread t{ [](std::stop_token st) {
    while (!st.stop_requested()) { doChunk(); }
} }; // 离开作用域自动 request_stop() + join()
```
- **回归主线**：多条线程协作访问共享数据时，在“重量级互斥锁”与“轻量级无锁原子操作”之间，现代 C++ 提供了怎样的细粒度选择？

### Q141｜`std::atomic`、内存序与 C++20 `atomic_ref`/`atomic<shared_ptr>`

`主线 · 阶梯 3/5 原子操作与无锁`

> **Question**
> 在多线程里把 `std::shared_ptr` 作为全局配置指针直接读写为什么依然存在数据竞态？C++20 为此新增的 `std::atomic<std::shared_ptr<T>>` 与 `std::atomic_ref` 各自填补了什么并发空白？

**Answer**
- **核心结论**：`std::shared_ptr` 仅仅保证了其内部引用计数的原子增减，**指针对象本身的读写替换不是线程安全的**（一个线程正在赋值替换新配置，另一线程同时读取拷贝会触发撕裂竞态）；C++20 的 `std::atomic<std::shared_ptr<T>>` 彻底原子化智能指针本身（取代已弃用的自由函数重载），而 `std::atomic_ref<T>` 则允许在不改变现有普通数据结构内存布局的前提下，临时对其执行原子操作。
- **底层机制**：`std::atomic<T>` 默认采用最严格的顺序一致性内存序（`std::memory_order_seq_cst`），禁止危险的指令重排；还可用 `is_lock_free()` 检查底层是否真由 CPU 硬件原子指令实现而非内部暗藏自旋锁。C++20 还为 `std::atomic` 增加了高效的 `wait()`、`notify_one()` 与 `notify_all()` 等待通知方法，无需额外搭配 `mutex` 和 `condition_variable` 即可实现轻量级事件等待。
- **设计取舍与边界**：除非经过严谨的无锁内存序验证与性能实测，否则一律保留默认顺序一致性（`seq_cst`），切勿盲目滥用 `memory_order_relaxed`；若需保护多个相关联变量的一致性更新，使用互斥锁远比强行拆成多个独立原子变量更安全。
- **代码 / 场景对照**：
```cpp
// [反例] 误以为 shared_ptr 本身线程安全，多线程并发读写同一指针实例触发 UB
std::shared_ptr<Config> g_cfg; // 线程 A reset，线程 B 拷贝 -> 竞态崩溃！

// [正例] C++20 std::atomic<std::shared_ptr<T>> 原子安全发布与读取配置
std::atomic<std::shared_ptr<Config>> g_cfg;
auto snap = g_cfg.load(); // 线程安全获取当前配置快照
```
- **回归主线**：当需要保护跨多个变量的复杂临界区或长操作时，互斥锁与锁守卫依然是主力——但经典的“双检锁单例”反模式曾坑害过无数开发者。

### Q142｜`scoped_lock`、`shared_mutex` 与双检锁陷阱（`call_once`）

`主线 · 阶梯 4/5 锁原语与双检锁`

> **Question**
> 为什么教科书里曾流行一时的“双检锁（Double-Checked Locking）”懒汉单例在 C++ 多核环境下是彻底错误的？在并发读写比例悬殊以及需要同时锁定多把锁时，现代 C++ 分别提供了哪些标准武器？

**Answer**
- **核心结论**：非原子化的双检锁会因编译器和 CPU 指令重排，导致线程 B 看到已非空的指针却读到尚未构造完毕的半残废对象；现代 C++ 一律用 **`std::call_once` 配合 `std::once_flag`**（或 C++11 起线程安全的函数内局部 `static` 变量）安全实现一次性初始化。同时锁定多把锁必须用 C++17 `std::scoped_lock(m1, m2)` 防死锁；读多写少场景则采用 C++17 `std::shared_mutex` 配合 `std::shared_lock`（共享读）与 `std::unique_lock`（独占写）。
- **底层机制**：绝不要手动直接调用 `mtx.lock()` / `mtx.unlock()`（异常路径必致永久死锁），一律交给 RAII 锁管理类：`lock_guard` 最轻量（仅作用域锁）、`unique_lock` 支持延迟加锁（`defer_lock`）、手动提前解锁、移动所有权以及配合条件变量等待、`scoped_lock` 底层采用死锁避免算法一次性安全锁定任意数量的互斥量。
- **设计取舍与边界**：极简作用域单锁用 `lock_guard`（或 `scoped_lock`）；需要搭配条件变量、转移锁所有权或提前释放锁用 `unique_lock`；一次性懒初始化首选函数内局部 `static` 或 `std::call_once`。
- **代码 / 场景对照**：
```cpp
// [反例] 经典双检锁无内存屏障且裸指针可被重排先赋值后构造；手锁多把易死锁
if (!g_inst) { std::lock_guard lk{ m }; if (!g_inst) g_inst = new Mgr{}; } // 竞态 UB！

// [正例] std::call_once 保证一次性线程安全初始化；scoped_lock 防死锁多锁
std::once_flag g_flag;
std::call_once(g_flag, [] { g_inst = std::make_unique<Mgr>(); });
std::scoped_lock locks{ accountA.mtx, accountB.mtx }; // C++17 自动防死锁
```
- **回归主线**：互斥锁解决了“互相排斥”，而线程之间如何高效地“等待通知、协同汇合与限流”，则需要条件变量以及 C++20 补齐的三大同步原语。

### Q143｜条件变量虚假唤醒与 C++20 `latch` / `barrier` / `semaphore`

`主线 · 阶梯 5/5 线程同步原语`

> **Question**
> 使用 `std::condition_variable` 等待任务队列非空时，为什么只写 `if (q.empty()) cv.wait(lk);` 会因为“虚假唤醒（Spurious Wakeup）”而读取空队列崩溃？C++20 新增的 `latch`、`barrier` 与 `semaphore` 又分别适用于哪类同步拓扑？

**Answer**
- **核心结论**：操作系统底层允许条件变量在没有任何线程调用 `notify` 的情况下发生虚假唤醒（或被抢先消费），因此等待条件变量**必须永远搭配带谓词的循环形式 `cv.wait(lk, [&]{ return !q.empty(); })`**；对于纯一次性倒计时汇合、多阶段循环汇合以及并发资源配额限流，C++20 新增了更轻量专注的 `std::latch`、`std::barrier` 与 `std::counting_semaphore`。
- **底层机制**：带谓词的 `cv.wait(lk, pred)` 在底层等价于 `while (!pred()) { wait(lk); }`，每次醒来都会重新持锁校验业务条件，完美免疫虚假唤醒与惊群竞争。C++20 的 `std::latch` 是一次性倒数门闩（归零后不可重用，适合主线程等待 N 个启动初始化任务全部就绪）；`std::barrier` 支持可重用的多轮迭代阶段同步并在每轮结束执行可选完成回调（适合并行仿真多步迭代）；`std::counting_semaphore`（及 `binary_semaphore`）维护内部计数器，用于限制同时访问某资源池的并发线程上限。
- **设计取舍与边界**：线程间基于复杂共享队列状态通信用 `mutex` + `condition_variable`；纯计数起跑/汇合用 `latch`/`barrier`；简单信号通知或限流用 `semaphore` 或 C++20 `atomic::wait()`。
- **代码 / 场景对照**：
```cpp
// [反例] 用 if 判断条件变量，遭遇虚假唤醒或被其他消费者抢走后队列仍为空！
std::unique_lock lk{ mtx };
if (queue.empty()) { cv.wait(lk); } // 虚假唤醒后直接向下 pop() 崩溃！

// [正例] 条件变量永远传入谓词；一次性倒计时汇合直接用 C++20 std::latch
std::unique_lock lk{ mtx };
cv.wait(lk, [&] { return !queue.empty() || stop; });
std::latch workersReady{ 4 }; // 4 个工作线程各 count_down()，主线程 wait()
```
- **回归主线**：最后从更高层的任务调度视角审视：`std::async` 的隐藏阻塞坑在哪里，以及 C++20 协程（Coroutines）和操作系统多线程到底是什么关系？

### Q144｜`std::async` 隐蔽阻塞陷阱与 C++20 协程定位

`支线 L24 · 异步任务与协程边界`

> **Question**
> 很多人以为调用 `std::async(func)` 就会自动在后台异步跑起来，为什么不指定 `std::launch::async` 时它可能根本不创建新线程？更诡异的是，为什么连返回值都没接收而直接写 `std::async(std::launch::async, work);` 竟会让代码退化成完全同步串行阻塞？

**Answer**
- **核心结论**：未显式指定策略时，`std::async` 默认使用 `launch::async | launch::deferred`，允许运行时偷懒推迟到调用 `.get()` 时才在当前线程同步执行；此外，`std::async` 返回的**临时 `std::future` 析构函数会强制阻塞等待后台任务完成**，丢弃返回值等于退化为同步阻塞调用！而在高层并发模型上，C++20 协程（`co_await`/`co_yield`/`co_return`）是**无栈协作式状态机**而非操作系统线程，适合百万级 I/O 挂起与惰性生成器，通常需搭配线程池调度。
- **底层机制**：通过 `std::async(std::launch::async, task)` 显式强制创建异步执行，且必须将返回的 `std::future` 绑定到具名变量（注意即使把返回值赋给局部变量，离开当前作用域时其析构函数仍会阻塞直到任务结束，只有用 `std::packaged_task` 投递给自建线程池才完全异步脱离）。至于 C++20 协程，它把函数栈帧分配到可挂起恢复的协程帧上，切换成本仅相当于几条指令的函数调用（纳秒级），远低于 OS 内核线程上下文切换（微秒级），C++23 标准库还正式提供了基于协程的生成器 `std::generator<T>`（`<generator>`）。
- **设计取舍与边界**：需要确保真正并发执行并取回异常/结果时，显式传入 `std::launch::async` 并保存 `future`；高并发任务调度应构建受控线程池（Thread Pool）避免无节制创建销毁 OS 线程；大量 I/O 密集等待与惰性序列生成则优先考虑 C++20/23 协程生态。
- **代码 / 场景对照**：
```cpp
// [反例] 丢弃 std::async 返回的临时 future，析构阻塞导致两条任务串行执行！
std::async(std::launch::async, taskA); // 此行阻塞直到 taskA 结束才走下一行！
std::async(std::launch::async, taskB);

// [正例] 显式保存具名 future，让 taskA 与 taskB 真正并发后再汇总取结果
auto fA = std::async(std::launch::async, taskA);
auto fB = std::async(std::launch::async, taskB);
auto res = fA.get() + fB.get();
```

## 本轮技术复盘（第 27 章）

### 主线推演回顾
从数据竞态、撕裂、死锁与伪共享四大硬件并发陷阱切入，引入 C++20 `std::jthread` 协作取消与 `exception_ptr` 跨线程异常传递，剖析 `std::atomic` 与 C++20 `atomic<shared_ptr>`/`atomic_ref`，对比 `scoped_lock`/`shared_mutex` 并彻底否定双检锁反模式，进而理清条件变量防虚假唤醒与 `latch`/`barrier`/`semaphore` 同步原语，最终点破 `std::async` 临时 `future` 阻塞陷阱与 C++20 协程定位。

### 高频误区速查
- **误区 1**：使用 `std::thread` 却未用 RAII 包装，或直接丢弃 `std::async` 返回的临时 `future` -> 前者异常路径直接 `std::terminate()`，后者析构阻塞退化成串行执行。
- **误区 2**：条件变量等待写 `if (empty) cv.wait(lk);` 或手写双检锁单例 -> 分别遭受虚假唤醒崩溃与指令重排半残废对象竞态。
- **误区 3**：以为 `std::shared_ptr` 全局变量自身读写线程安全 -> 仅引用计数原子，指针替换必须用 C++20 `std::atomic<std::shared_ptr<T>>` 或互斥锁保护。

### 工程落地清单
- C++20 及以上线程生命周期管理全面采用 `std::jthread` + `std::stop_token` 协作退出。
- 多锁同时加锁统一使用 `std::scoped_lock`；一次性初始化使用 `std::call_once` 或局部 `static`；条件变量等待永远传入谓词 `cv.wait(lk, pred)`。
- 多核高频写入独立热点计数器时用 `alignas(std::hardware_destructive_interference_size)` 隔离伪共享，大并发任务分发使用受控线程池而非无限起新线程。
