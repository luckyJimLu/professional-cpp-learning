### Q103｜`wchar_t` 跨平台尺寸分裂与 C++20 `char8_t` Unicode 体系

`主线 · 阶梯 1/5 字符编码与宽字符`

> **Question**
> 很多人以为用 `wchar_t` 和 `std::wstring` 就能一劳永逸解决国际化多语言文本问题，为什么同一份 `wchar_t` 代码在 Windows 和 Linux 上编译运行却会出现字节宽度与编码彻底分裂？C++11/20 的 `char8_t`/`char16_t`/`char32_t` 如何规范这一混乱？

**Answer**
- **核心结论**：C++ 标准刻意未固定 `wchar_t` 的位宽与编码——Windows 上 `wchar_t` 为 16 位（UTF-16），而 Linux/macOS 上通常为 32 位（UTF-32）；现代跨平台代码应明确使用定宽 Unicode 字符类型：`char8_t`（C++20，UTF-8）、`char16_t`（UTF-16）与 `char32_t`（UTF-32），并配合 `u8""`、`u""`、`U""` 字面量前缀。
- **底层机制**：由于 `wchar_t` 尺寸随平台变化，将 `std::wstring` 直接按二进制写入文件或通过网络传输在不同系统间必然乱码。C++20 专门引入独立强类型 `char8_t`（及 `std::u8string`），与普通执行字符集 `char` 彻底区分，保证源代码中 `u8"你好"` 永远是严格合法的 UTF-8 字节序列。注意在代码中直接写非 ASCII 字符时，应确保源文件统一以 UTF-8 编码保存并开启编译器 UTF-8 选项（如 MSVC `/utf-8`、GCC `-finput-charset=UTF-8`）。
- **设计取舍与边界**：跨平台存储、网络协议与内部文本流优先统一采用 UTF-8（`std::string` 或 `std::u8string`）；仅在直接调用操作系统原生 API（如 Win32 `W` 后缀宽字符 API）的薄适配层中局部转换使用 `wchar_t`。
- **代码 / 场景对照**：
```cpp
// [反例] 依赖 wchar_t 做二进制序列化，Windows(2B) 与 Linux(4B) 字节布局不兼容
std::wstring title = L"数据"; // 跨平台字节长度与编码均不固定

// [正例] 使用明确位宽与编码的 C++20 char8_t / char16_t / char32_t
std::u8string utf8Title = u8"数据"; // 全平台严格 1 字节 UTF-8 编码单元
std::u32string utf32Title = U"数据"; // 全平台严格 4 字节 UTF-32 码点
```
- **回归主线**：有了统一的字符编码承载，不同国家地区在数字小数点、千分位、货币符号以及字母大小写分类上的差异，则需要通过 C++ 的本地化（Locale）与刻面（Facet）体系来适配。

### Q104｜`std::locale` 机制与 C 风格 `<cctype>` 的符号越界 UB

`主线 · 阶梯 2/5 Locale 与字符分类`

> **Question**
> 为什么调用 C 语言的 `std::isalpha(ch)` 或 `std::toupper(ch)` 判断一个普通 `char` 变量时，遇到中文或带重音符号的 UTF-8 字节竟然会直接触发未定义行为（UB）？`std::locale` 重载与 Facet 刻面如何解决区域适配？

**Answer**
- **核心结论**：C 风格 `<cctype>` 函数（如 `std::isalpha(int)`）要求传入值必须是 **`EOF` 或 `unsigned char` 范围内的非负整数**；在 `char` 默认有符号的平台上，任何高于 127 的字节都是负数，直接传入立刻触发 UB。使用 `<locale>` 提供的 `std::isalpha(ch, loc)` 模板重载或先强转为 `unsigned char` 可消除该漏洞，并通过 `std::locale` 精确控制区域规则。
- **底层机制**：`std::locale` 内部由一组刻面（Facets，如 `numpunct` 控制小数点/千分位、`moneypunct` 控制货币、`ctype` 控制字符分类）组成。默认全局区域是程序启动时的经典 `"C"` locale（纯 ASCII、点号小数点，不随系统改变），调用 `std::locale{ "" }` 则获取用户操作系统的当前首选区域。流对象可通过 `stream.imbue(loc)` 单独绑定特定 locale，避免污染全局状态。
- **设计取舍与边界**：解析机器可读协议（如 JSON、配置文件、CSV 数值）时务必保持经典 `"C"` locale（防止某些欧洲区域把小数点格式化成逗号 `3,14` 导致解析崩溃）；仅在面向终端用户展示时局部使用用户 locale；切勿再依赖已在 C++17 弃用的 `<codecvt>` 做编码转换。
- **代码 / 场景对照**：
```cpp
// [反例] 有符号 char 传入 C 版 isalpha 遇到非 ASCII 字节直接触发 UB
char c = '\xE4';
if (std::isalpha(c)) { /* c 为负值，UB！ */ }

// [正例] 传入明确 std::locale 的 C++ 重载，或先转为 unsigned char
std::locale loc{ "" };
if (std::isalpha(c, loc)) { /* 安全按区域规则分类 */ }
```
- **回归主线**：处理完字符集与区域格式后，面对半结构化文本的复杂模式匹配、提取与替换，就需要祭出 `<regex>` 正则表达式库——但它的语法转义与贪婪匹配极易让人栽跟头。

### Q105｜原始字符串字面量与 ECMAScript 正则核心语法

`主线 · 阶梯 3/5 正则语法与转义`

> **Question**
> 在 C++ 字符串里写一个匹配 Windows 路径或日期的正则表达式时，为什么反斜杠常常要连写四个 `\\\\` 才生效？贪婪量词 `.*` 和惰性量词 `.*?`、捕获组 `(...)` 与非捕获组 `(?:...)` 在匹配行为上有何关键差异？

**Answer**
- **核心结论**：普通 C++ 字符串字面量先经过编译器转义一次，再交给正则引擎解析第二次，导致匹配单个字面反斜杠需要写 `\\\\`；一律改用**原始字符串字面量（Raw String Literal）** `R"(...)"` 可彻底消除双重转义。量词默认“贪婪”（尽可能吞掉最多字符），后加 `?` 变为“惰性”（满足条件即停）；不需要提取的子组应写为 `(?:...)` 节省捕获存储开销。
- **底层机制**：`<regex>` 默认采用 ECMAScript 正则语法，支持锚点（`^`/`$`）、通配符（`.`）、字符集（`\d`、`\w`、`\s`）、单词边界（`\b`）、反向引用（`\1`）以及正/负向前瞻（`(?=...)` / `(?!...)`）。若原始文本本身包含 `)"` 序列，可在 `R"delim(...)delim"` 中添加自定义分隔符 `delim` 防提前闭合。
- **设计取舍与边界**：所有 C++ 正则表达式字面量一律采用 `R"(...)"` 书写；仅当确实需要通过 `smatch[i]` 读取子串或在替换中使用反向引用时才使用普通捕获括号 `(...)`，其余纯分组逻辑统一用 `(?:...)`。
- **代码 / 场景对照**：
```cpp
// [反例] 普通字符串双重转义可读性极差，且贪婪 .* 吞掉多个标签
std::regex re{ "<tag>(.*)</tag>\\\\s*(\\d+)" };

// [正例] 原始字符串字面量零额外转义 + 惰性量词 .*? 精准止步于首个闭合标签
std::regex re{ R"(<tag>(.*?)</tag>\s*(?:\d+))" };
```
- **回归主线**：写好了正则模式串之后，调用 `<regex>` 接口时最常见的逻辑错配，是把“全串匹配”和“子串搜索”混为一谈。

### Q106｜`regex_match` 与 `regex_search` 的语义边界及悬空陷阱

`主线 · 阶梯 4/5 匹配与搜索接口`

> **Question**
> 明明用测试工具验证过正则表达式完全正确，为什么在代码里调用 `std::regex_match(line, re)` 提取日志里的数字却总是返回 `false`？为什么对临时 `std::string` 调用 `regex_search` 后读取 `smatch` 结果会直接崩溃？

**Answer**
- **核心结论**：`std::regex_match` 要求正则表达式必须匹配**整个输入字符串从头到尾的每一个字符**（相当于隐式自带 `^...$`），只要前后多出一个空格就会返回 `false`；要在文本中查找**局部子串**必须使用 `std::regex_search`。此外，`std::smatch` 内部只保存指向原字符串内部区间的迭代器，传入临时字符串右值会在分号后立即悬空（C++11 起已在标准库中删除了接收临时 `string` 右值的重载以在编译期拦截）。
- **底层机制**：`std::smatch`（即 `std::match_results<std::string::const_iterator>`）的 `[0]` 元素代表整个匹配串，后续 `[1]`、`[2]` 代表各个捕获组。对于输入字符串字面量或 `std::string_view`，需匹配对应的迭代器类型 `std::cmatch` 或 `std::match_results<std::string_view::const_iterator>`。
- **设计取舍与边界**：校验整串合法性（如邮箱、日期格式整串校验）用 `regex_match`；从长文本提取片段用 `regex_search`；切勿将 `smatch` 传给已销毁的局部变量或临时字符串。
- **代码 / 场景对照**：
```cpp
// [反例] 误用 regex_match 在整行日志中搜索局部数字，必返回 false
std::regex numRe{ R"(\d+)" };
std::smatch m;
if (std::regex_match(logLine, m, numRe)) { /* 若 logLine 含非数字字符则永不进入 */ }

// [正例] 查找局部子串用 regex_search，整串校验才用 regex_match
if (std::regex_search(logLine, m, numRe)) {
    std::println("Found: {}", m[0].str());
}
```
- **回归主线**：单次 `regex_search` 只能找到第一个匹配项，要想遍历全部匹配、按分隔符切分文本，并在生产环境中避免正则成为 CPU 杀手，还需要掌握迭代器封装与编译期预热。

### Q107｜`regex_iterator` / `regex_token_iterator` 与正则编译性能陷阱

`主线 · 阶梯 5/5 遍历、分词与性能`

> **Question**
> 从长文本中提取全部匹配项或按正则分隔符切分字符串时，为什么用 `std::sregex_token_iterator`（传入 `-1`）比循环修改子串调用 `regex_search` 更优雅？更关键的是，为什么在热循环内部构造 `std::regex` 会让程序慢上数百倍？

**Answer**
- **核心结论**：`std::sregex_iterator` 自动遍历文本中所有不重叠匹配；`std::sregex_token_iterator` 不仅能直接抽取指定编号的捕获组，传入 `-1` 索引时还能自动吐出**匹配项之间的分隔片段**（完美实现正则 `split`）。同时，构造 `std::regex` 对象需要将其编译为有限状态机（NFA/DFA），代价极其高昂，**绝不能在循环内部反复构造**，而应作为 `static const` 或成员对象预编译复用。
- **底层机制**：每次执行 `std::regex re{ pattern };` 都要经历词法解析、语法树构建与状态转移表生成，耗时往往比单次匹配高出几个数量级。配合 `std::regex_replace` 与格式串（如 `"$1-$2"`）则可高效完成结构化文本重构。此外，面对已知极其简单的固定前缀或单字符分割，优先使用 `std::string_view::find` 或 `std::views::split`（C++20），避免杀鸡用牛刀。
- **设计取舍与边界**：高频调用函数内的固定正则模式一律声明为 `static const std::regex`（C++11 起局部静态变量初始化线程安全且仅编译一次）；注意标准 `<regex>` 在部分实现上遇到极端病态回溯表达式时性能较差，超高吞吐场景可评估第三方编译期正则库（如 CTRE）。
- **代码 / 场景对照**：
```cpp
// [反例] 每次处理一行日志都在循环内重新编译一次 std::regex
for (const auto& line : logs) {
    std::regex re{ R"((\w+)=(\d+))" }; // 灾难级重复状态机编译开销！
    /* ... */
}

// [正例] 预编译 static const 正则 + sregex_token_iterator 传 -1 优雅分词
static const std::regex sepRe{ R"(\s*[,;]\s*)" };
std::sregex_token_iterator it{ text.begin(), text.end(), sepRe, -1 }, end;
```
- **回归主线**：解决了多语言文本与正则解析后，工程中另一块以“细节繁琐、时区/闰秒/时钟跳变坑深”著称的标准库领域——日期与时间处理，将在第 22 章由 `<chrono>` 全面揭晓。

### Q108｜`std::regex` 的病态回溯与替代方案边界

`支线 L18 · 正则性能与回溯`

> **Question**
> 为什么某些看似正常的正则表达式（如 `(a+)+b`）一旦遇到长串不匹配的 `"aaaa...c"` 输入，CPU 会瞬间飙满卡死（ReDoS）？什么时候应当果断放弃 `<regex>` 改用字符串视图或手动解析？

**Answer**
- **核心结论**：多数标准库 `<regex>` 实现基于带回溯的 NFA 引擎，遇到嵌套量词（如 `(a+)+` 或 `(.*)*`）且末端失配时，引擎会尝试指数级 $O(2^n)$ 的回溯路径，造成灾难性回溯（Catastrophic Backtracking）；简单前缀、固定分隔符或高频结构化解析（如 URL、CSV、JSON）应优先用 `std::string_view`、C++20 `std::views::split` 或手写状态机替代。
- **底层机制**：NFA 引擎按字符顺序贪婪推进，一旦后续匹配失败就退回上一选择点尝试另一种拆分组合；嵌套量词导致同一段连续字符存在指数种拆分方式，短短几十个字符就能让匹配耗时达到数分钟。消除嵌套模糊量词、把可选分支写为互斥字符集（如 `[^,]+` 替代 `.*?`），能从根源缓解回溯爆炸。
- **设计取舍与边界**：绝不将未经审核的外部用户输入直接作为正则模式编译执行；处理固定格式（如 `starts_with`、`ends_with`、按单字符切分）一律用 C++20 `std::string_view` 与 Ranges 视图，零回溯风险且性能高出数个数量级。
- **代码 / 场景对照**：
```cpp
// [反例] 简单按逗号分割或前后缀检测也动用 std::regex，且含模糊嵌套量词
static const std::regex badRe{ R"(^([a-zA-Z]+)+$)" }; // 失配时指数级回溯卡死

// [正例] 简单分隔用 C++20 views::split / string_view；正则中避免嵌套重复量词
for (auto part : line | std::views::split(',')) { /* 零分配线性切分 */ }
```
- **回归主线**：接下来进入第 22 章，看看 `<chrono>` 如何用编译期有理数、单调时钟与 C++20 日历/时区库彻底终结传统 C 时间函数的混乱。

## 本轮技术复盘（第 21 章）

### 主线推演回顾
从 `wchar_t` 跨平台尺寸分裂与 `char8_t` 标准化切入，排除了 `<cctype>` 有符号 `char` 负值 UB 陷阱并理顺 `std::locale` 边界，继而以原始字面量、贪婪/惰性语义、`regex_match`/`regex_search` 差异、预编译优化与防回溯策略构建安全的正则实践。

### 高频误区速查
- **误区 1**：直接将 `char` 变量传给 `std::isalpha(c)` -> 有符号 `char` 处理非 ASCII 字节为负数，触发 UB。
- **误区 2**：用 `std::regex_match` 在长字符串中提取局部子串 -> `regex_match` 要求全串匹配，局部提取必须用 `regex_search`。
- **误区 3**：在循环体内部构造 `std::regex` -> 状态机重复编译造成极高的 CPU 浪费。

### 工程落地清单
- 跨平台内部文本统一使用 UTF-8（`std::string` / C++20 `std::u8string`），解析机器格式数据时保持经典 `"C"` locale。
- 所有正则模式统一使用 `R"(...)"` 原始字符串字面量书写，并提取为 `static const std::regex` 复用。
- 简单前后缀判断与固定分隔符切分优先使用 `std::string_view`（`starts_with`/`ends_with`）与 C++20 `std::views::split`。
