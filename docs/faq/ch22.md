### Q109｜`std::ratio` 编译期单位与 `duration_cast` 精度守卫

`主线 · 阶梯 1/5 时长与编译期单位`

> **Question**
> 为什么用 `int timeoutMs` 传参时经常因为调用方误传秒数而引发线上故障，而 `std::chrono::duration` 能直接在编译期拦截单位错配？为什么毫秒可以隐式转微秒，反过来微秒转毫秒却必须显式写 `duration_cast`？

**Answer**
- **核心结论**：`std::chrono::duration<Rep, Period>` 将**数值类型**与**编译期有理数周期 `std::ratio`** 绑定进 C++ 类型本身，彻底消除裸数字单位歧义；高粒度（低精度，如秒）转低粒度（高精度，如毫秒）是无损转换允许隐式进行，而高精度转低精度（如毫秒转秒）会截断余数，必须显式调用 `duration_cast`（或 `floor`/`ceil`/`round`）。
- **底层机制**：`std::ratio<Num, Den>`（`<ratio>`）在编译期完成分数约分与四则运算（如 `std::milli` 为 `ratio<1, 1000>`），零运行期存储开销。`std::chrono::seconds` 本质是 `duration<long long, ratio<1, 1>>`；把 `5s` 传给接收 `milliseconds` 的函数时，编译器在编译期自动乘以 1000 转换；反之从 `1500ms` 转为 `seconds` 会丢失 `500ms`，因此编译器强制要求程序员显式写出 `duration_cast<seconds>(1500ms)` 确认接受向零截断（若需四舍五入或向下取整可用 C++17 `round`、`floor`、`ceil`）。
- **设计取舍与边界**：所有涉及超时、间隔与频率的 API 形参一律使用 `std::chrono::milliseconds` 等强类型时长（配合 `using namespace std::chrono_literals;` 直接写 `500ms`、`2s`），彻底淘汰 `int timeout`；需要与浮点数秒交互时（如 `duration<double>`），因浮点转换通常无截断限制而允许隐式转换。
- **代码 / 场景对照**：
```cpp
// [反例] 裸整数形参无法约束单位，调用方传入秒数却被当成毫秒
void sleepFor(int ms);
sleepFor(5); // 原意想睡 5 秒，实际仅睡 5 毫秒

// [正例] 强类型 duration 自动无损转换，有损截断必须显式 duration_cast
void sleepFor(std::chrono::milliseconds d);
sleepFor(5s); // 隐式无损转为 5000ms；若从 1500ms 转秒则显式 duration_cast<seconds>
```
- **回归主线**：有了精准的时间间隔（Duration）后，要想测量一段代码的真实耗时或获取当前时刻，就必须选对背后的时钟（Clock）——选错时钟在系统调时瞬间会直接算出“负耗时”。

### Q110｜`steady_clock` 与 `system_clock`：为何测耗时绝不能用系统时钟

`主线 · 阶梯 2/5 时钟选择与单调性`

> **Question**
> 为什么用 `std::chrono::system_clock::now()` 前后相减来统计接口耗时或做超时判断，在生产环境中偶尔会出现负值或突然超时？`steady_clock` 与 `high_resolution_clock` 各自该怎么选？

**Answer**
- **核心结论**：`system_clock` 对应操作系统挂钟（Wall Clock），会受用户手动改表、NTP 网络校时或夏令时调整影响而**向前或向后跳变**；一切测量耗时、计算 FPS 与超时控制，必须严格使用保证永不倒流、单调递增的 **`std::chrono::steady_clock`**。
- **底层机制**：`<chrono>` 定义了三大核心基础时钟：`system_clock`（可与日历时间/C 风格 `time_t` 互通，但不单调）、`steady_clock`（物理单调递增时钟，两刻之差永远非负）与 `high_resolution_clock`。注意在各大主流标准库实现中，`high_resolution_clock` 往往只是 `system_clock` 或 `steady_clock` 的类型别名——如果它不幸别名了 `system_clock`，拿它测耗时同样会遭遇时钟回拨风险！此外，C++20 还补充了 `utc_clock`（含闰秒）、`tai_clock`、`gps_clock` 与 `file_clock`。
- **设计取舍与边界**：需要打印人类可读的当前年月日时间戳、记录日志时间或转换 `time_t` 用 `system_clock`；所有性能计时（Benchmark）、超时重试、定时器调度一律锁定 `steady_clock`。
- **代码 / 场景对照**：
```cpp
// [反例] 用 system_clock 测量函数耗时，NTP 校时回拨时 diff 可能为负值
auto t0 = std::chrono::system_clock::now();
work();
auto diff = std::chrono::system_clock::now() - t0;

// [正例] 性能计时与超时控制一律使用单调不回拨的 steady_clock
auto t0 = std::chrono::steady_clock::now();
work();
auto elapsed = std::chrono::duration_cast<std::chrono::microseconds>(
    std::chrono::steady_clock::now() - t0);
```
- **回归主线**：`now()` 返回的并不是裸数字，而是一个与特定时钟强绑定的 `time_point`（时间点）——理解时间点与时长之间的代数关系，才能避免把两个时间点直接相加的逻辑错误。

### Q111｜`time_point` 代数语义与时间点截断转换

`主线 · 阶梯 3/5 时间点代数`

> **Question**
> 为什么两个 `duration` 可以直接相加（`1s + 500ms`），`time_point` 加减一个 `duration` 或两个同源 `time_point` 相减也合法，但编译器却坚决禁止把两个 `time_point` 直接相加？

**Answer**
- **核心结论**：时间点 `time_point<Clock, Duration>` 本质上是“某时钟纪元（Epoch）+ 偏移时长”，如同坐标系里的“点”，两点相减得到向量（`duration`）、点加向量得到新点，而“两个绝对日期相加（如 2026 年 + 2025 年）”在数学与物理上毫无意义，因此被类型系统直接禁止。
- **底层机制**：不同时钟拥有各自的纪元与底层刻度，`system_clock` 与 `steady_clock` 的 `time_point` 属于完全不同的类型，不能混算或直接互转（C++20 提供了 `clock_cast` 用于在 `system_clock`、`utc_clock`、`tai_clock`、`file_clock` 等日历关联时钟间安全转换，但仍禁止转 `steady_clock`）。当需要把 `time_point` 截断到整秒或整天时，使用 `std::chrono::floor<days>(tp)` 或 `time_point_cast`。
- **设计取舍与边界**：严禁把 `time_point.time_since_epoch().count()` 抽成裸整数在不同模块间传递运算，始终保持 `time_point` 类型直到最终格式化输出。
- **代码 / 场景对照**：
```cpp
// [反例] 抽出裸计数混算，丧失时钟源与刻度精度保护
auto rawTick = std::chrono::steady_clock::now().time_since_epoch().count();

// [正例] 在类型安全的 time_point 与 duration 域内完成所有时间运算
auto deadline = std::chrono::steady_clock::now() + 250ms;
auto remaining = deadline - std::chrono::steady_clock::now();
```
- **回归主线**：从底层的秒与纳秒向上迈进到“年、月、日”业务日历时，传统的做法是手写 `86400 * 30` 这种充满闰年与大小月漏洞的算术，直到 C++20 日历库彻底改写了写法。

### Q112｜C++20 日历类型与 `sys_days` 日期算术

`主线 · 阶梯 4/5 C++20 日历算术`

> **Question**
> 在 C++20 `<chrono>` 中，对 `2024y / January / 31d` 直接加上 `std::chrono::months{ 1 }` 会得到什么结果？为什么做“加减若干天”的精确日历计算时，必须先将 `year_month_day` 转换为 `sys_days`？

**Answer**
- **核心结论**：`year_month_day` 支持直观的 `/` 构造语法与 `.ok()` 合法性校验（如 `2023y/February/29d` 的 `ok()` 为 `false`）；按月加减（如 1 月 31 日加 1 个月）会忠实保留 `2024-02-31` 这一待修正状态（需手动判断 `.ok()` 或取 `last` 月末），而**精确的按天加减算术**（跨大小月与闰年）必须先转为以天为刻度的 `sys_days` 时间点再执行加减。
- **底层机制**：`year_month_day` 内部仅分别存储年、月、日三个字段（字段型表示），因此做 `+ months{1}` 时只是简单给月份字段加 1，既不会静默溢出错乱也不擅自截断天数——由开发者显式决定溢出策略（比如钳位到当月最后一天 `ymd.year() / ymd.month() / std::chrono::last`）。相反，`sys_days` 是基于 `system_clock` 且精度为 `days`（86400 秒）的连续线性时间点，执行 `sys_days{ ymd } + days{ 45 }` 后再转回 `year_month_day`，就能自动精确跨越闰年 2 月与大小月。
- **设计取舍与边界**：所有日期输入解析后务必立即调用 `.ok()` 校验有效性；涉及工作日、到期日等“加 N 天”逻辑一律转 `sys_days` 计算；涉及“每月固定日（如每月 31 号账单）”逻辑则在 `year_month_day` 上加 `months` 后显式处理月末钳位。
- **代码 / 场景对照**：
```cpp
// [反例] 手写 days * 86400 算日期，遇到闰秒或手工大小月数组极易出错
// [正例] C++20 日历：field 算术处理月末，sys_days 处理精确天数偏移
using namespace std::chrono;
year_month_day ymd{ 2024y / January / 31d };
auto nextMonth = ymd.year() / (ymd.month() + months{ 1 }) / last; // 2024-02-29
year_month_day plus45{ sys_days{ ymd } + days{ 45 } };            // 自动跨月闰年
```
- **回归主线**：即便把年月日算得滴水不漏，只要应用跨越不同地区或遭遇夏令时（DST）切换，“本地墙上时间”和“全球绝对时间”之间就会出现最棘手的歧义。

### Q113｜C++20 时区库（`zoned_time`）与夏令时歧义处理

`主线 · 阶梯 5/5 时区与夏令时`

> **Question**
> 为什么说同一个本地墙上时间（如夏令时回拨当晚的 `01:30`）在一年里可能出现两次，而春季向前拨快一小时的 `02:30` 甚至根本不存在？C++20 的 `std::chrono::zoned_time` 如何基于 IANA 时区库精准化解这种转换歧义？

**Answer**
- **核心结论**：`std::chrono::zoned_time` 将一个绝对 UTC 时间点（`sys_time`）与 IANA 时区对象（`std::chrono::locate_zone("Asia/Shanghai")` 或 `current_zone()`）绑定，不仅能自动查表完成历史与未来的夏令时偏移转换，还通过 `std::chrono::choose::earliest` / `latest` 或抛出 `ambiguous_local_time` / `nonexistent_local_time` 异常强制处理夏令时边界歧义。
- **底层机制**：夏令时开始时本地时钟向前跳 1 小时，中间的 `local_time` 在现实中从未发生（`nonexistent_local_time`）；夏令时结束回拨 1 小时时，同一段 `local_time` 会经历两次（`ambiguous_local_time`）。直接用 `zoned_time{ zone, localTime }` 构造时若遇到歧义会抛出异常提醒，传入 `choose::earliest` 或 `choose::latest` 则可显式消歧；而从全局统一的 `system_clock::now()` 构造 `zoned_time` 则永远唯一确定。
- **设计取舍与边界**：系统内部存储、数据库持久化与跨服务通信一律统一使用 UTC（`sys_time`），只在最外层 UI 展示或解析用户本地输入时通过 `zoned_time` 映射到具体 IANA 时区（切忌硬编码 `+8` 小时偏移量，因为不同地区夏令时与历史时区政策会变化）。
- **代码 / 场景对照**：
```cpp
// [反例] 硬编码 + 8h 偏移计算本地时间，遇到跨夏令时地区立即错乱
auto local = std::chrono::system_clock::now() + 8h;

// [正例] C++20 zoned_time 基于 IANA 时区数据库安全映射与消歧
auto zt = std::chrono::zoned_time{
    std::chrono::locate_zone("America/New_York"),
    std::chrono::system_clock::now()
};
```
- **回归主线**：在时间工具之外，`<chrono>` 还自带了 C++20 `hh_mm_ss` 与 C++20/23 格式化支持，让打印时间告别老旧的 `localtime` 线程不安全函数。

### Q114｜告别线程不安全的 `std::localtime` 与 C++20/23 时间格式化

`支线 L19 · 线程安全时间格式化`

> **Question**
> 传统 C 语言 `<ctime>` 的 `std::localtime()` 为什么在多线程服务中是个隐蔽的并发炸弹？C++20 `hh_mm_ss` 与 `<format>` / `std::println` 如何做到完全线程安全且零静态缓冲区污染？

**Answer**
- **核心结论**：`std::localtime()` 在多数实现上返回指向**全局静态 `struct tm` 缓冲区**的指针，多线程并发调用会互相踩踏覆写结果导致时间串台；C++20 的 `std::chrono::hh_mm_ss` 与原生支持 `<chrono>` 类型格式化（`std::format("{:%Y-%m-%d %H:%M:%S}", tp)`）完全无全局状态、类型安全且天然线程安全。
- **底层机制**：`hh_mm_ss` 可直接把一天内的 `duration`（如 `sinceMidnight`）无状态拆解为时、分、秒与亚秒字段；而 `<format>` 与 C++23 `<print>` 为 `duration`、`time_point`、`year_month_day` 和 `zoned_time` 特化了 `std::formatter`，支持 `%Y-%m-%d`、`%T`、`%Z` 等完整格式化说明符，无需手动分配 `char buf[64]` 给 `strftime()`。
- **设计取舍与边界**：现代 C++20/23 代码应彻底清除 `std::localtime`、`std::gmtime` 与 `std::ctime` 调用；若在不支持 C++20 `<chrono>` 格式化的旧平台上必须使用 `<ctime>`，也应使用线程安全的平台替代（POSIX `localtime_r` / Windows `localtime_s`）。
- **代码 / 场景对照**：
```cpp
// [反例] 多线程调用 std::localtime 共享全局静态缓冲区，导致时间戳互相覆盖
std::tm* tmPtr = std::localtime(&rawTime); // 非线程安全！

// [正例] C++20/23 直接用 std::println / std::format 线程安全格式化时间点
auto now = std::chrono::floor<std::chrono::seconds>(std::chrono::system_clock::now());
std::println("UTC: {:%Y-%m-%d %H:%M:%S}", now);
```
- **回归主线**：时间与日历解决了确定性时序问题，而第 23 章将转向相反的维度——如何用现代 `<random>` 设施生成高质量、无偏差、并发安全的伪随机数。

## 本轮技术复盘（第 22 章）

### 主线推演回顾
从 `std::ratio` 编译期单位与 `duration_cast` 截断守卫出发，厘清了 `steady_clock` 单调性对耗时测量的不可替代性，掌握了 `time_point` 代数约束、C++20 `year_month_day` / `sys_days` 日历算术、`zoned_time` 夏令时消歧，以及线程安全的时间格式化方案。

### 高频误区速查
- **误区 1**：使用 `system_clock` 或 `high_resolution_clock` 测量执行耗时 -> 系统时钟可能因 NTP 校时回拨算出负耗时，必须用 `steady_clock`。
- **误区 2**：直接对 `year_month_day` 手写跨月天数算术或用 `86400s` 粗算日期 -> 必须先转为 `sys_days` 完成天数加减再转回。
- **误区 3**：多线程中继续调用 `std::localtime()` -> 共享全局静态缓冲引发数据竞态，应改用 C++20/23 `<chrono>` 格式化。

### 工程落地清单
- 所有接口时长参数统一使用 `std::chrono::milliseconds` 等强类型 `duration`，拒绝裸整数时间参数。
- 耗时统计与超时判定一律锁定 `std::chrono::steady_clock`。
- 内部存储与传输统一用 UTC `sys_time`，仅在展示层通过 C++20 `zoned_time` 映射至 IANA 时区。
