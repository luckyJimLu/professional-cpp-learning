### Q49｜模板定义可见性与选择性实例化（Selective Instantiation）

`主线 · 阶梯 1/5 实例化机制`

> **Question**
> 普通类的成员函数可以放进 `.cpp` 文件独立编译，为什么类模板（如 `Grid<T>`）的成员函数定义通常必须写在头文件或模块接口中？选择性实例化又为何会让某些成员函数里的类型错误长期潜伏？

**Answer**
- **核心结论**：模板本身不是可编译的机器码而是代码蓝图，编译器必须在调用点看到完整定义才能为具体类型 `T` 生成代码；同时，编译器只实例化程序实际调用到的成员函数（选择性实例化），未被调用的成员函数不会检查对 `T` 的语义约束。
- **底层机制**：若将 `Grid<T>::at()` 的实现藏在单独的 `.cpp` 中，调用端实例化 `Grid<int>` 时看不到函数体，链接期就会报未定义符号错误（除非在 `.cpp` 里用 `template class Grid<int>;` 显式实例化已知的全部类型）。由于隐式实例化具有“按需惰性”，即使 `T` 不支持 `operator<`，只要未调用依赖 `<` 的成员函数，代码依然能编译通过；这既允许类型只满足所用操作的最小子集，也可能让缺陷隐藏到未来调用时才爆发。
- **设计取舍与边界**：通用库模板应把声明与实现统一放在模块接口文件（`.cppm`）或头文件中；仅当模板允许的参数类型集合完全封闭且有限（如仅限 `float`/`double`）时，才采用显式实例化来缩减编译时间与目标文件体积。
- **代码 / 场景对照**：
```cpp
// [反例] 将模板成员函数实现分离到普通 .cpp 且未显式实例化
// Grid.h:   template <typename T> class Grid { public: T& at(size_t x, size_t y); };
// Grid.cpp: template <typename T> T& Grid<T>::at(...) { ... } // 链接报错

// [正例] 在模块接口或头文件中保留完整模板定义（或仅对封闭类型显式实例化）
export template <typename T>
class Grid {
public:
    T& at(size_t x, size_t y) { return m_cells[x * m_height + y]; }
};
```
- **回归主线**：弄清模板何时以及如何被编译器实例化之后，下一步要审视模板参数本身的多样性——除了类型参数，常量值参数与自动推导如何塑造类型系统？

### Q50｜非类型模板参数（NTTP）与类模板实参推导（CTAD）

`主线 · 阶梯 2/5 模板参数与推导`

> **Question**
> 把网格宽高做成非类型模板参数 `Grid<int, 10, 10>` 后，为什么不能把它赋值给 `Grid<int, 10, 20>`？C++17 的类模板实参推导（CTAD）又在什么场景下会失效而需要自定义推导指引？

**Answer**
- **核心结论**：非类型模板参数（NTTP）属于**类型签名本身的一部分**，不同常量值实例化出的是两个毫无关系的独立类型；CTAD 允许从构造函数实参自动推导模板类型，但面对复杂转换（如 `const char*` 需推导为 `std::string`）时必须提供显式推导指引（Deduction Guides）。
- **底层机制**：`Grid<T, Width, Height>` 把尺寸编码进编译期类型，可在栈上直接分配固定大小 `std::array` 并消除堆开销，但也导致不同尺寸间无法直接拷贝赋值——必须编写成员函数模板 `template <typename E, size_t W2, size_t H2> Grid(const Grid<E, W2, H2>&)` 才能实现跨尺寸转换。此外，C++20 已放宽 NTTP 限制，支持浮点类型与满足结构化条件的字面量类类型。
- **设计取舍与边界**：尺寸在编译期固定且追求零堆分配时选用 NTTP；若尺寸在运行期动态变化或需要跨尺寸统一存进同一容器，应将宽高作为构造函数运行期参数。
- **代码 / 场景对照**：
```cpp
// [反例] 误以为同为 Grid<int> 的不同尺寸模板实例可以直接赋值
Grid<int, 10, 10> g1;
Grid<int, 10, 20> g2;
g1 = g2; // 编译错误：完全不同的两种类型

// [正例] 通过成员函数模板支持跨尺寸拷贝，并用推导指引规范 CTAD
template <typename T>
class Box { public: Box(const T& v); };
Box(const char*) -> Box<std::string>; // 自定义推导指引
```
- **回归主线**：当某个特定类型（例如 C 风格字符串 `const char*`）需要与通用模板截然不同的底层处理逻辑时，该如何定制而不破坏通用版本？

### Q51｜类模板特化（Specialization）与继承的本质分野

`主线 · 阶梯 3/5 特化与继承取舍`

> **Question**
> 如果 `Grid<T>` 存入 `const char*` 时只拷贝了浅指针地址，于是写了一个全特化 `template <> class Grid<const char*>`；为什么在特化版本里不能自动复用主模板的成员函数，以及什么时候该用“继承模板”而非“特化模板”？

**Answer**
- **核心结论**：类模板全特化**不是继承**，它是针对特定类型从零开始重写一个全新的独立类，不会自动继承主模板的任何数据成员或方法；若只想在保留通用逻辑的基础上**扩展新行为**，应选择继承类模板而非特化。
- **底层机制**：全特化 `template <> class Grid<const char*>` 允许把底层存储替换为 `std::string` 来安全管理字符生命周期，但也意味着主模板里已写好的 `at()`、`getWidth()` 等方法必须在特化版中完整重新提供。相比之下，编写 `template <typename T> class GameBoard : public Grid<T>` 则属于标准的 is-a 复用，直接继承全部网格存储能力并新增 `move()` 等棋盘专属操作。
- **设计取舍与边界**：改变特定类型的**既有底层实现**（如修复 `const char*` 浅拷贝或做位压缩优化）用特化；为通用容器**增加领域专属功能**用继承（或组合）；给长模板名起简洁别名则用别名模板 `template <typename T> using Matrix = Grid<T, 4, 4>;`。
- **代码 / 场景对照**：
```cpp
// [反例] 误以为特化版会自动继承主模板的 getWidth()，导致漏实现编译失败
template <> class Grid<const char*> { /* 仅重写了 setAt，缺少其他全部接口 */ };

// [正例] 扩展新功能用继承复用主模板；仅需彻底替换底层存储时才写完整特化
template <typename T>
class GameBoard : public Grid<T> {
public:
    using Grid<T>::Grid; // 复用基类模板构造函数
    void move(size_t xSrc, size_t ySrc, size_t xDst, size_t yDst);
};
```
- **回归主线**：掌握了类模板的实例化、参数与特化后，函数模板在重载决议、返回类型推导与 C++20 简写语法上还有另一套精细规则。

### Q52｜函数模板重载决议、`decltype(auto)` 与 C++20 简写语法

`支线 L9 · 简写语法与推导`

> **Question**
> 当非模板普通函数与函数模板同时能匹配一次调用时，编译器会选谁？在推导函数模板返回类型时，为什么 `auto` 可能悄悄丢掉引用和 `const`，而必须改用 `decltype(auto)`？

**Answer**
- **核心结论**：重载决议中，若非模板函数与模板实例匹配度相同，编译器**优先选择非模板普通函数**；返回类型推导中，`auto` 按值推导会剥离顶层 `const` 与引用，必须使用 `decltype(auto)`（C++14）才能精确原样保留表达式的引用与限定符。
- **底层机制**：编写通用转发或包装函数（如 `template <typename T> decltype(auto) getRef(T& container)`）时，若返回类型写成 `auto`，返回容器元素的引用会被静默退化为按值拷贝，不仅产生多余副本，还使调用方无法通过返回值修改原元素。此外，C++20 引入简写函数模板语法（Abbreviated Function Template Syntax），允许直接写 `auto add(const auto& a, const auto& b)`，等价于多类型参数函数模板，大幅精简日常泛型代码。
- **设计取舍与边界**：需要为特定类型（如 `const char*` 比较）定制函数行为时，优先写普通函数重载而非函数模板特化（因为函数模板特化不参与重载决议且易产生意外顺序依赖）；简写语法中两个 `auto` 形参代表两个独立类型参数，若要求两参类型严格相同仍需显式写 `template <typename T>`。
- **代码 / 场景对照**：
```cpp
// [反例] 返回类型写 auto，悄悄把元素引用退化为按值拷贝
template <typename C> auto firstElem(C& c) { return c.front(); }

// [正例] 使用 decltype(auto) 精确保留引用；C++20 简写语法精简泛型形参
decltype(auto) firstElem(auto& c) { return c.front(); }
```
- **回归主线**：无论是类模板还是函数模板，传统 C++ 泛型最大的痛点在于“类型要求全靠文档口头约定，一旦传错类型就爆出几百行晦涩天书”——这正是 C++20 Concepts 彻底改写游戏规则的地方。

### Q53｜C++20 Concepts 与 `requires` 表达式的契约前置

`主线 · 阶梯 4/5 C++20 概念约束`

> **Question**
> 过去调用模板传入不兼容类型时，编译器会深入多层模板展开内部吐出数百行天书报错；C++20 的 Concepts 和 `requires` 表达式在底层如何把类型检查前置到接口边界？

**Answer**
- **核心结论**：Concept 是具名的编译期布尔谓词，通过 `requires` 子句绑定到模板参数上；一旦实参不满足约束，编译器在进入函数体或类体**之前**就立即终止实例化，精准指出违背了哪条约束。
- **底层机制**：`requires` 表达式支持四类编译期探测：简单要求（表达式合法，如 `x + y;`）、类型要求（嵌套类型存在，如 `typename T::value_type;`）、复合要求（校验表达式不抛异常且返回类型满足某概念，如 `{ x.size() } noexcept -> std::convertible_to<size_t>;`）与嵌套要求。标准库 `<concepts>` 已预定义 `std::integral`、`std::derived_from`、`std::invocable` 等基础概念，还支持用 `std::integral auto x = f();` 约束局部变量推导。
- **设计取舍与边界**：优先复用 `<concepts>` 中的标准概念组合，避免重复造轮子；不要为了写 Concept 而只检查单个孤立运算符，真正高质量的 Concept 应表达完整的语义抽象（如 `Sortable`、`Incrementable`）。
- **代码 / 场景对照**：
```cpp
// [反例] 无约束模板，传入不支持 + 运算的类型时在模板深处爆出冗长报错
template <typename T> T add(const T& a, const T& b) { return a + b; }

// [正例] C++20 Concept 显式声明编译期契约，不满足则在调用点精准报错
template <typename T>
concept Addable = requires(const T& a, const T& b) {
    { a + b } -> std::convertible_to<T>;
};
template <Addable T> T add(const T& a, const T& b) { return a + b; }
```
- **回归主线**：当同一个函数模板存在多个受不同 Concept 约束的重载版本时，编译器如何避免陷入“两个都满足约束”的二义性僵局？

### Q54｜约束包含（Constraint Subsumption）与基于概念的重载

`主线 · 阶梯 5/5 约束包含与重载`

> **Question**
> 如果同时提供了受 `Incrementable` 约束和受 `Incrementable && Decrementable` 约束的两个函数模板重载，传入 `int` 时两者都满足，为什么编译器不会报二义性错误，而是精准选中后者？

**Answer**
- **核心结论**：C++20 编译器会将约束拆解为合取（`&&`）与析取（`||`）范式并执行**约束包含（Constraint Subsumption）**分析：若约束 B 逻辑上严格包含约束 A（即 B 更具针对性），编译器会自动优先选择 B，彻底取代繁琐晦涩的 `std::enable_if` SFINAE 技巧。
- **底层机制**：只有用具名 `concept`（或相同原子约束）通过 `&&`/`||` 组合时，编译器才能识别包含关系。如果把相同条件直接写成两个独立匿名的 `requires` 表达式，哪怕文本一模一样，编译器也会把它们视为互不相干的原子约束而导致重载二义性。该机制同样适用于类模板偏特化选择。
- **设计取舍与边界**：凡是需要按类型能力分派多套算法实现（例如随机访问迭代器走 $O(1)$ 跳跃，普通输入迭代器走 $O(n)$ 步进），务必基于具名 Concept 组合层次来编写重载，以便触发约束包含。
- **代码 / 场景对照**：
```cpp
// [反例] 重复写匿名 requires 表达式，编译器无法识别包含关系导致二义性
template <typename T> requires requires(T x) { ++x; } void step(T& x);
template <typename T> requires requires(T x) { ++x; --x; } void step(T& x);

// [正例] 复用具名 Concept 组合，自动触发约束包含选中更特化版本
template <typename T> concept Inc = requires(T x) { ++x; };
template <typename T> concept BiDir = Inc<T> && requires(T x) { --x; };
template <Inc T>   void step(T& x);
template <BiDir T> void step(T& x); // 对 int 精确胜出，无二义性
```

从模板定义可见性与选择性实例化切入，辨析了 NTTP 类型边界、CTAD 推导指引、特化与继承的本质差异，以及 `decltype(auto)` 和 C++20 简写语法，最终落脚到 Concepts 与约束包含对现代泛型编程的范式升级。

### 高频误区速查
- **误区 1**：把类模板特化当成继承，以为特化版能自动复用主模板的成员函数 -> 全特化是彻底重写的独立类，复用功能应选继承或组合。
- **误区 2**：在通用包装函数中使用 `auto` 返回类型 -> 会剥离引用与 `const`，需要原样保留时必须用 `decltype(auto)`。
- **误区 3**：用重复的匿名 `requires` 表达式做重载约束 -> 无法触发约束包含，必须复用具名 `concept` 组合。

### 工程落地清单
- C++20 及以上代码全面使用 Concepts 与 `requires` 替代传统 SFINAE / `std::enable_if`。
- 编写成员函数模板实现跨尺寸或跨类型转换（如 `Grid<T, W, H>`）时，注意显式处理不同模板实例互为独立类型的访问权限。
- 优先使用 `<concepts>` 标准概念与具名语义概念构建层次，确保重载决议清晰无二义性。
