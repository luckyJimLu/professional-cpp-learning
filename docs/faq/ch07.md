### Q19｜栈与自由存储区：`new`/`delete` 与 `malloc`/`free` 的本质区别

`主线 · 阶梯 1/5 内存模型`

> **Question**
> 现代 C++ 反复告诫不要手写 `new`/`delete`，更严禁使用 C 语言的 `malloc`/`free`；从对象生命周期和底层内存模型来看，两者到底差在哪里？为什么连 `new (std::nothrow)` 也不被推荐？

**Answer**
- **核心结论**：`new`/`delete` 不仅分配与释放内存，还负责调用对象的构造函数与析构函数；`malloc`/`free` 只搬运原始字节，绝不能用于 C++ 对象。默认 `new` 失败抛出 `std::bad_alloc`，而 `nothrow` 返回空指针极易因漏判引发空指针解引用。
- **底层机制**：栈（Stack）内存随作用域自动分配与确定性销毁，速度极快；自由存储区（Free Store）由程序员显式管理生命周期，且对内置类型使用默认 `new` 不会自动清零。任何指针变量都应立即初始化（如 `nullptr`，遵循 C++ Core Guidelines ES.20），`delete` 后应置空以防悬空指针（`delete nullptr` 是安全的空操作）。
- **设计取舍与边界**：在现代 C++ 业务代码中，应优先使用栈对象、标准容器（`std::vector`、`std::array`、`std::string`）与智能指针；裸指针仅允许作为“非拥有观察者（Non-owning observer）”存在，绝不承担释放职责。
- **代码 / 场景对照**：
```cpp
// [反例] malloc 不调用构造函数，直接操作 std::string 成员立即触发 UB
auto* p = static_cast<std::string*>(std::malloc(sizeof(std::string)));

// [正例] 优先栈分配与标准容器，作用域结束自动确定性析构
std::string name{ "Modern C++" };
std::vector<int> values(100, 0);
```
- **回归主线**：理解了单个对象的构造、析构与内存区差异后，当扩展到连续数组与多维数组时，裸指针的陷阱会成倍放大。

### Q20｜数组退化、`delete[]` 错配与多维 `char**` 性能黑洞

`主线 · 阶梯 2/5 数组与指针`

> **Question**
> 为什么用 `delete` 释放 `new[]` 分配的数组会引发未定义行为？C 风格数组传参为什么会丢失长度，以及为什么自由存储区上的 `char**` 二维数组远不如展平的一维内存块？

**Answer**
- **核心结论**：`new[]` 必须严格配对 `delete[]` 才能对每个元素调用析构函数；C 风格数组传参会退化为首元素指针并丢失长度（且指针算术按 `sizeof(T)` 缩放）；动态二维 `char**` 内存分散、缓存命中率极低，应改为连续一维展平存储。
- **底层机制**：`new Simple[4]` 会在数组前记录元素个数并逐一调用默认构造函数；若误用标量 `delete`，可能导致仅析构首元素或直接破坏堆元数据。数组作为函数参数时，`int[]`、`int[2]` 与 `int*` 完全等价，长度信息彻底丢失；此外，切勿对 C++ 对象使用 `realloc()`，其按位拷贝会破坏非平凡对象内部状态。对于多维数组，栈上 `board[3][3]` 是连续内存，而动态 `char**` 是“指针数组指向多个分散堆块”，不仅释放需逐行循环，还严重破坏 CPU 空间局部性。
- **设计取舍与边界**：需要传递连续序列视图时，现代 C++ 应使用 `std::span<T>`（C++20）同时携带指针与长度（若必须接收固定大小栈数组可用引用模板 `int (&arr)[N]`）；多维动态矩阵应封装为持有单块一维 `std::vector<T>` 的 `Matrix<T>` 类，通过 `x * yDim + y` 寻址。
- **代码 / 场景对照**：
```cpp
// [反例] char** 造成多块分散堆分配，缓存不友好且释放繁琐易漏
char** grid = new char*[rows];
for (size_t i = 0; i < rows; ++i) { grid[i] = new char[cols]; }

// [正例] 单块连续一维 vector 展平存储，零泄漏且缓存局部性最优
std::vector<char> grid(rows * cols);
auto at = [&](size_t r, size_t c) -> char& { return grid[r * cols + c]; };
```
- **回归主线**：既然手动管理堆内存如此容易触发越界、泄漏与双重释放，为什么 C++ 不像 Java 或 Go 那样直接内置垃圾回收器？

### Q21｜C++ 拒绝内置垃圾回收与确定性 RAII 取舍

`主线 · 阶梯 3/5 垃圾回收取舍`

> **Question**
> 既然缓冲区溢出、内存泄漏与双重释放如此普遍，C++ 为什么不直接内置标记-清除式垃圾回收（GC）一劳永逸，而是坚持 RAII，并在极端场景下提供自定义分配器与对象池？

**Answer**
- **核心结论**：标记-清除式 GC 会带来不可预测的停顿（Stop-the-world），更致命的是它使析构时机变为非确定性，直接摧毁了 C++ 赖以管理文件句柄、互斥锁与网络连接的 RAII 根基。
- **底层机制**：C++ 的析构函数在对象离开作用域的精确时刻同步执行，这意味着不仅内存，连锁释放、文件刷新、事务回滚都能绑定到对象生命周期上。若改由 GC 延迟回收，资源会被无限期占用。而在高频分配海量极小对象的性能敏感场景中，通用分配器为每次分配附加的堆元数据头开销过大，此时可通过重载 `operator new`/`operator delete` 或引入对象池（Object Pool）预先批分配并循环复用对象，同时在开发期借助 Valgrind（Linux）或 Visual C++ CRT 调试钩子（`_CrtSetDbgFlag`）捕获泄漏。
- **设计取舍与边界**：绝大多数业务无需自定义内存管理器；只有经性能剖析证实堆分配器本身成为瓶颈时，才引入对象池或自定义分配器，常规场景一律交给 RAII 容器与智能指针。
- **代码 / 场景对照**：
```cpp
// [反例] 手动释放锁与内存，中间提前返回或抛异常即造成死锁与泄漏
mtx.lock();
auto* p = new Widget{};
if (!p->valid()) { return; } // 锁未解，p 未删
delete p; mtx.unlock();

// [正例] 依托确定性 RAII，任何路径退出作用域均精确释放资源
std::lock_guard lock{ mtx };
auto p = std::make_unique<Widget>();
if (!p->valid()) { return; } // 自动析构 p 并释放 mtx
```
- **回归主线**：RAII 之所以能在堆对象上无缝落地，核心载体正是 `<memory>` 中的智能指针家族；但不同智能指针的底层成本与误用陷阱截然不同。

### Q22｜`unique_ptr` 与 `shared_ptr` 的底层成本与 `make_*` 铁律

`主线 · 阶梯 4/5 独占与共享所有权`

> **Question**
> 同样是智能指针，为什么默认必须首选 `std::unique_ptr` 而非 `std::shared_ptr`？创建它们时为什么强调必须用 `std::make_unique` / `std::make_shared`，且绝不能用同一个裸指针构造两个 `shared_ptr`？

**Answer**
- **核心结论**：`std::unique_ptr` 是零额外开销的独占所有权（仅支持移动）；`std::shared_ptr` 需维护带原子引用计数的控制块，存在额外内存与同步开销。优先使用 `make_*` 工厂函数可保障异常安全并合并分配，而同一裸指针构造两个独立 `shared_ptr` 会直接引发双重释放。
- **底层机制**：`std::make_unique`（C++14）在 C++17 之前能防止多参数表达式求值交错导致的异常泄漏；`std::make_shared` 更是把被管对象与控制块合并为单次连续堆分配，提升缓存局部性。若需避免无意义的零初始化开销，C++20 提供了 `std::make_unique_for_overwrite` 与 `std::make_shared_for_overwrite`。注意智能指针禁用了类模板实参推导（CTAD）；同时，`unique_ptr` 的自定义删除器类型属于模板参数（无运行时开销），而 `shared_ptr` 的删除器采用类型擦除存于控制块中。若用同一裸指针分别构造两个 `shared_ptr`，会各自生成独立控制块，引用计数归零时同一对象被 `delete` 两次。
- **设计取舍与边界**：`std::auto_ptr` 已在 C++11 弃用、C++17 移除，严禁使用；能明确单一归属的资源一律用 `unique_ptr`，仅当资源确实存在多个不确定先后析构的共享者时才升级为 `shared_ptr`。
- **代码 / 场景对照**：
```cpp
// [反例] 同一裸指针构造两个独立 shared_ptr，离开作用域触发双重释放 UB
auto* raw = new Simple{};
std::shared_ptr<Simple> sp1{ raw };
std::shared_ptr<Simple> sp2{ raw }; // 独立控制块，析构时 double free

// [正例] 使用 make_shared 合并分配并通过拷贝共享同一控制块
auto sp1 = std::make_shared<Simple>();
auto sp2 = sp1; // 共享同一控制块，引用计数安全增至 2
```
- **回归主线**：一旦进入 `shared_ptr` 的共享所有权世界，循环引用、`this` 指针逃逸与子成员共享等隐蔽边界问题便会浮现。

### Q23｜`weak_ptr`、`enable_shared_from_this` 与别名构造

`支线 L4 · 控制块陷阱`

> **Question**
> 当两个对象通过 `std::shared_ptr` 互相引用，或者对象成员函数想把 `this` 包装成 `shared_ptr` 返回给外部时，底层控制块会发生什么故障？`weak_ptr`、`enable_shared_from_this` 与别名构造函数各自解决哪类边界问题？

**Answer**
- **核心结论**：循环引用会使强引用计数永不归零造成永久泄漏，需用 `std::weak_ptr` 打破；类内部直接 `std::shared_ptr<T>(this)` 会创建重复控制块导致双重释放，必须继承 `std::enable_shared_from_this<T>`；别名构造函数则用于共享整个父对象的生命周期同时对外只暴露其某个成员指针。
- **底层机制**：`std::weak_ptr` 仅观察控制块而不增加强引用计数，访问时调用 `lock()` 原子地尝试提升为 `shared_ptr`（若对象已销毁则返回空指针；直接用 `weak_ptr` 构造 `shared_ptr` 则抛出 `std::bad_weak_ptr`）。继承 `std::enable_shared_from_this<T>` 后，对象内部会保存指向自身控制块的弱引用，调用 `shared_from_this()` 或 `weak_from_this()`（C++17）即可安全复用既有控制块；但若对象尚未被任何 `shared_ptr` 托管就调用 `shared_from_this()`，会抛出 `std::bad_weak_ptr`。别名构造 `std::shared_ptr<int>{ fooPtr, &fooPtr->m_data }` 让新指针指向子成员地址，同时共享 `fooPtr` 的引用计数，防止父对象提前析构。
- **设计取舍与边界**：切勿为了省事把父子节点全设为 `shared_ptr`；明确主从关系时，父持子用 `unique_ptr`/`shared_ptr`，子回指父用非拥有裸指针或 `weak_ptr`。
- **代码 / 场景对照**：
```cpp
// [反例] 成员函数直接用 this 构造 shared_ptr，制造双控制块引发 double free
class Node { public: std::shared_ptr<Node> self() { return std::shared_ptr<Node>(this); } };

// [正例] 继承 enable_shared_from_this，安全复用已有控制块
class Node : public std::enable_shared_from_this<Node> {
public:
    std::shared_ptr<Node> self() { return shared_from_this(); }
};
```
- **回归主线**：掌握了智能指针的创建与控制块机制后，日常编码中最后一道高频错题，是如何把智能指针跨函数、跨 C API 边界正确传递出去。

### Q24｜智能指针的传参规范与 C++23 C-API 互操作

`主线 · 阶梯 5/5 跨边界传递`

> **Question**
> 很多人习惯在函数形参里随手写 `const std::unique_ptr<T>&` 或按值传递 `std::shared_ptr<T>`，这种写法有什么问题？当现代智能指针需要对接 C 语言 `T**` 输出参数 API 时又该如何安全衔接？

**Answer**
- **核心结论**：仅在函数确实需要转移或共享所有权时才按值传递 `unique_ptr` / `shared_ptr`；若只是读写对象，应直接传 `T&` / `const T&`（可为空时传裸指针 `T*`）。对接 C 风格 `T**` 输出参数时，C++23 引入了 `std::out_ptr` 与 `std::inout_ptr` 实现零泄漏桥接。
- **底层机制**：按值传递 `shared_ptr` 会触发不必要的原子引用计数增减开销；传递 `const std::unique_ptr<T>&` 既不转移所有权，又把调用方死死限制为“对象必须放在堆上且由 `unique_ptr` 托管”，丧失了接收栈对象的灵活性。返回智能指针时则直接按值返回，借助 C++17 强制拷贝消除（Copy Elision）与移动语义即可实现零开销。在调用 C 库输出句柄接口（如 `error_t create_handle(Handle** out)`）时，`std::out_ptr(smartPtr)`（C++23）会在临时适配器析构时自动将 C API 写回的裸指针安全交接给智能指针托管。
- **设计取舍与边界**：`unique_ptr::release()` 会彻底放弃所有权并返回裸指针，仅在手动向遗留 API 移交控制权时谨慎使用；日常仅需借用底层裸指针而不移交所有权时，调用 `get()` 即可。
- **代码 / 场景对照**：
```cpp
// [反例] 仅读取对象却强行要求传 const unique_ptr&，限制栈对象复用
void inspect(const std::unique_ptr<Widget>& w);

// [正例] 非拥有访问用引用/裸指针；对接 C 语言 T** 输出参数用 C++23 std::out_ptr
void inspect(const Widget& w);
std::unique_ptr<Handle, decltype(&destroyHandle)> h{ nullptr, &destroyHandle };
c_api_create_handle(std::out_ptr(h)); // C++23 安全接管输出句柄
```
- **回归主线**：至此，我们打通了从底层内存模型、数组布局、RAII 哲学到智能指针控制块与跨边界传递的现代 C++ 内存管理全链路。

## 本轮技术复盘（第 7 章）

### 主线推演回顾
从栈与自由存储区及 `new`/`malloc` 的本质差异切入，拆解数组退化、多维分散堆布局与 GC 非确定性析构的底层代价，进而系统建立以 `unique_ptr` 为默认、以 `make_*` 为创建入口、以 `weak_ptr`/`enable_shared_from_this` 防护控制块、以引用与 `std::out_ptr`（C++23）规范边界传递的现代内存安全防线。

### 高频误区速查
- **误区 1**：混用 `new[]` 与标量 `delete`，或对 C++ 对象调用 `malloc`/`realloc` -> 未调用构造/析构或破坏堆结构，直接 UB。
- **误区 2**：无脑到处使用 `std::shared_ptr` 或按 `const std::unique_ptr<T>&` 传参 -> 引入多余原子计数开销或限制调用方对象存储方式。
- **误区 3**：用同一裸指针构造多个 `shared_ptr`，或在类内直接返回 `shared_ptr<T>(this)` -> 生成独立控制块导致双重释放。

### 工程落地清单
- 代码审查中将手写 `new`/`delete` 与裸拥有指针列为高危项，优先替换为栈对象、标准容器、`std::make_unique` 或 `std::make_shared`。
- 函数不涉及所有权转移或延长生命周期时，形参一律使用 `T&`、`const T&` 或 `std::span<T>`（C++20）。
- 存在双向引用时明确主从方向，反向指针改用 `std::weak_ptr` 或非拥有裸指针；对接 C 输出参数接口时在 C++23 环境下优先采用 `std::out_ptr` / `std::inout_ptr`。
