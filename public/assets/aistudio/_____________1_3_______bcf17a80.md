### 第 1 回 · 弃旧头文件，括号锁灵气

> `炼气初期`

**【遇险】**
韩小码刚在洞府落座，习惯性地刻下几十行 `#include` 咒文，结果不仅编译慢如老牛，还在声明 `int firePower = 3.14;` 时被老式等号暗中削去小数，导致丹炉控温差之毫厘、险些炸炉。

**【问道】**
> **师兄**：你满篇 `#include` 让预处理器反复复制文本，老式等号 `=` 又对数据截断网开一面；C++23 时代，为何入门第一课便是 `import std;` 与 `{}` 统一初始化？

**【点拨】**
> **前辈**：此事需从根子上说起：`import std;` 直接引动标准库灵脉，编译器无需重复解析文本，且不会暴露内部杂乱定义；输出亦当弃用无类型安全的 `printf`，改用编译期校验类型的 `std::println()`。
>
> 至于 `{}` 统一初始化，既是语法大一统，更是防止“窄化转换”的铁壁防线。空括号 `{}` 可触发零初始化，彻底清除未初始化变量里的内存随机毒气；一旦试图把 `3.14` 塞进 `int x { 3.14 };`，小绿瓶（编译器）便会当场亮红灯报错。若确需舍弃精度，必须显式祭出 `static_cast<int>(3.14)` 立下军令状。

**【悟道】**
- 🧵 **主线**：以 `import std;`、`std::println` 与 `{}` 统一初始化建立现代 C++ 第一道防线。
- 🎖️ **破境**：踏入【炼气初期】，告别头文件泥潭与隐式窄化隐患。
- 🎵 **偈语**：百卷竹简一朝弃，花括锁灵窄化消。

### 第 2 回 · 弃剑修契约，左右辨真常

> `炼气初期 → 炼气小成`

**【遇险】**
韩小码在函数间传递动态分配的裸指针时漏写了 `delete[]`，灵力池瞬间泄漏；紧接着他想保护指针指向的数据不被修改，却误写成了 `int* const ip { new int[10] };`，结果数据依旧被随意篡改，指针反倒被焊死在原地。

**【问道】**
> **师兄**：在无需转移内存所有权时，为何引用（Reference）远胜裸指针？面对 `const int*` 与 `int* const` 的迷踪步，又该如何一眼辨清真常？

**【点拨】**
> **前辈**：引用即本尊的别名，天生不可为空且从一而终，是比裸指针安全百倍的“同命契约”。凡函数无需修改传入的大对象，一律奉上 `const T&` 常量引用，既免去拷贝损耗，又保本尊金身不坏；涉及动态数组与集合，直接交由 `std::vector` 托管。
>
> 辨析 `const` 修饰位置只需八字口诀——**“紧贴左侧，从右向左”**：`const` 默认修饰它左边紧挨着的成分，唯独位于最左边时才修饰右侧类型。因此 `int const*` 与 `const int*` 皆为“指向常量整数的指针”（数据不可改），而 `int* const` 则是“指向整数的常量指针”（指针不可改）。类中的只读查询方法亦须加冕 `const`（如 `getSalary() const`）。

**【悟道】**
- 🧵 **主线**：用引用与 `const` 正确性规范资源访问权限，摒弃无所有权的裸指针。
- 🎖️ **破境**：晋升【炼气小成】，初步掌握 `const` 契约与引用传功。
- 🎵 **偈语**：同命契约胜无鞘，紧贴左侧辨真常。

### 第 3 回 · 灵镜防剥离，传值返真元（章末大劫）

> `炼气小成`

**【遇险】**
韩小码调用返回庞大名册常量引用的函数 `const string& foo()`，随手写下 `auto f1 { foo() };`，竟在暗中触发了全量深拷贝；随后他在炼制员工档案系统时，又险些从函数里直接返回局部栈变量的引用 `Employee&`，眼看栈帧销毁在即，悬垂幽灵已扑面而来！

**【问道】**
> **师兄**：`auto` 为何会悄悄把零拷贝的常量引用变成深拷贝？而在现代 C++17/23 中，究竟该如何安全且零损耗地从函数返回大对象？

**【点拨】**
> **前辈**：`auto` 的推演法则天生会剥离表达式顶层的 `const` 与引用属性！`auto f1 { foo() }` 会把 `const string&` 还原为纯粹的 `string` 值类型从而引发拷贝，想要零拷贝必须显式写明 `const auto& f2 { foo() }`；推导指针时亦应加上星号写成 `const auto*`。
>
> 至于函数返回大对象，**严禁返回局部栈变量的引用或指针**（函数返回即栈帧销毁，必成悬垂指针），亦应摒弃丑陋的输出参数。现代 C++ 自 C++17 起已确立“强制复制/移动消除（Mandatory Elision）”铁律，配合命名返回值优化（NRVO），直接**按值返回（Return by Value）**即可在调用者目标内存上原地构造对象，全程零拷贝、零移动！

**【悟道】**
- 🧵 **主线**：驾驭 `const auto&` 推演与按值返回优化，构建出清晰的《员工记录系统》。
- 🎖️ **破境**：稳固【炼气小成】境界，圆满通过第一章考验。
- 🎵 **偈语**：灵镜欲保加引用，帐篷既拆莫留影。

### 第 1 回 · 结尾莫遗空，后缀定真身

> `炼气小成 → 炼气中期`

**【遇险】**
韩小码处理遗留 C 接口时写下 `new char[strlen(str)]`，因漏算结尾 `\0` 字节瞬间触发缓冲区溢出；转投 `std::vector` 后，他又写下 `vector names { "John", "Sam" };`，结果类模板参数推导（CTAD）推演出的竟是 `vector<const char*>` 而非 `vector<string>`。

**【问道】**
> **师兄**：为何 `strlen()` 总比实际所需内存少一字节？而双引号括起的字面量，又该如何让 `auto` 或 CTAD 认作真正的 `std::string`？

**【点拨】**
> **前辈**：`strlen()` 统计的只是有效字符数，不含作为生死界碑的空字符 `\0`（NUL），分配 C 字符串缓冲必须牢记 `strlen(str) + 1`；而 `sizeof` 作用于指针时测出的仅仅是指针本身大小（4 或 8 字节），绝不可用来测字符串长度。
>
> 源码中裸露的双引号字面量，真身乃是只读内存区里的 `const char[N]`（衰变为 `const char*`）。引入 `std::string_literals` 后，在字面量末尾缀上 `s`（如 `"John"s`），方能直接铸造纯正的 `std::string` 对象；若写多行含引号文本，则可用原始字符串字面量 `R"(...)"` 免去转义之苦。

**【悟道】**
- 🧵 **主线**：彻底摆脱易溢出的 `<cstring>` 陷阱，掌握 `std::string` 与字面量后缀 `s`。
- 🎖️ **破境**：晋升【炼气中期】，识破字符数组与只读字面量的底层真身。
- 🎵 **偈语**：莫忘结尾空字符，后缀加 s 化真身。

### 第 2 回 · 神瞳零拷贝，无配转乾坤

> `炼气中期`

**【遇险】**
韩小码把所有只读字符串形参都写成 `const string&`，结果每次传入字面量都在后台触发堆内存分配生成临时 `std::string`；随后他在高频报文解析中调用 `to_string()` 与 `stod()`，频繁的堆分配与本地化锁争用再次拖垮了灵力运转。

**【问道】**
> **师兄**：如何做到接收任意只读字符串（`string`、字面量、`const char*`）皆零拷贝？在高频协议序列化场景下，又该用何法器替代 `to_string` 与 `stoi`？

**【点拨】**
> **前辈**：只读字符串参数一律首选 `std::string_view`，且应**按值传递**！它仅含一枚指针与长度，不分配任何堆内存即可统一透视所有字符串形态；若需独立副本，再显式调用 `string { sv }`。
>
> 至于高频数值转换，当祭出 `<charconv>` 中的底层法器 `std::to_chars()` 与 `std::from_chars()`。它们直接在调用者预分配的缓冲区内刻画符文，**零堆分配、无视本地化设置（locale-independent）**，且保证浮点数序列化与反序列化的“完美往返（Perfect Round-tripping）”。调用时只需通过结构化绑定 `[ptr, ec]` 校验错误码 `ec == errc{}` 即可。

**【悟道】**
- 🧵 **主线**：以 `std::string_view` 与 `<charconv>` 构建零拷贝、零分配的高性能文本处理管线。
- 🎖️ **破境**：稳固【炼气中期】，炼成零拷贝传参与底层转换神通。
