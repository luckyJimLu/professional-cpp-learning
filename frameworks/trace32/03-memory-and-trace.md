# 03 · 栈、堆、踩内存与硬件追踪

[上一单元](02-fault-and-scheduler.md) · [专题首页](README.md) · [下一单元：自动采集与实验](04-automation-and-labs.md)

## 1. 先把“内存问题”拆开

| 现象 | 首先采集 | 下一步 |
|---|---|---|
| SP 越界 / 栈底哨兵变动 | 每任务栈起止、SP、填充、水位 | 栈分析与首次越界写观察点 |
| 可用堆缓慢下降 | 同业务阶段未释放量、最大空闲块 | 分配账本与回归阶段对比 |
| 堆总量足够但大块失败 | 最大连续块与空闲分布 | 分辨碎片与泄漏 |
| `free` / 调度器链表中死机 | 受损节点及相邻内存 | 向前追踪首次破坏者 |
| CPU 视图与 DMA 结果不同 | 地址、Cache 属性、传输长度 | 检查 DMA 所有权与维护顺序 |

## 2. 任务栈：边界正确后才谈水位

### 2.1 FreeRTOS 配置

在支持这些宏的内核 / port 中，根据项目需要开启：

```c
#define configRECORD_STACK_HIGH_ADDRESS 1
#define configCHECK_FOR_STACK_OVERFLOW 2
#define INCLUDE_uxTaskGetStackHighWaterMark 1
#define configQUEUE_REGISTRY_SIZE 16
```

实现匹配的 overflow hook，确认静态 / 动态任务创建路径、栈填充值和调度配置。`configCHECK_FOR_STACK_OVERFLOW` 是检测手段，不能阻止所有越界，更不能保证 handler 在坏栈下可靠运行。水位 API 的返回单位一般是 `StackType_t` 元素而非字节，按版本核对。

```text
TASK.CONFIG ~~/demo/arm/kernel/freertos/freertos.t32
TASK.TaskList
TASK.STacK.PATtern 0xA5
TASK.STacK
```

`0xA5` 仅适用于确认启动代码实际如此填充的栈；此命令声明分析模式，**不应为了得到漂亮水位重新填充正在使用的栈**。

### 2.2 栈大小未知怎么办

1. 检查 ELF 内核结构定义和实际 TCB 布局。
2. 新版本常通过 `pxEndOfStack` 等成员得知边界，不限于附件提到的 `usStackDepth`。
3. 不可自动识别时查当前版 `TASK.Option STacKSIZE` 和 `TASK.STacK` 帮助，按真实任务栈逐个配置。
4. 旧版本 `TASK.CONFIG ... 0 0x400` 的 stack_size 兜底通常给所有任务同一大小；**不能用它证明所有任务只有 1 KiB**。

填写表格再解释水位：

| 任务 | 栈低地址 | 栈高地址（闭区间） | 总字节 | 当前 SP | 最大使用估计 | 数据来源 |
|---|---|---|---|---|---|---|
| RxTask | 按实际填写 | 按实际填写 | 高 - 低 + 1 | 采集值 | 填充扫描 | TCB / map / 创建参数 |

### 2.3 水位为什么可能低估

局部数组预留但没有写满、填充值恰巧仍相同、曾经越界后又恢复、遗漏 ISR / MSP 或扫描边界错误，都会误导结果。当前 SP 是瞬时值；填充扫描是历史覆盖估计；最坏栈上界还需调用关系与中断嵌套分析。

对向低地址增长的栈，在确认空闲 guard 区间后设置写观察点，例如：

```text
; 仅示例：该 4 字节必须确实属于保护区，而非正常可用栈
Break.Set D:0x20002000--0x20002003 /Write /Onchip
Break.List
```

应在初始化填充结束后布防。命中后先保存现场，检查写入指令、访问宽度与调用链。比较器数量、对齐、覆盖范围和 halt 时刻由芯片实现决定；更大的区间可能分配失败，先验证硬件是否真正接受。

**验收：** 同时覆盖任务 PSP、handler / ISR 的 MSP 和已知最深调用路径；根据实测峰值与产品裕量制定预算，不能给所有任务机械加倍。

## 3. 堆：泄漏、缓存与碎片的区分

### 3.1 采集账本

在分配 / 释放边界记录：事件序号、指针、size、分配 site ID、任务 ID、操作类型、时间与失败原因。对齐分配、`new[]`、自定义 allocator、C 库与 RTOS 堆不能遗漏或混用释放接口。

插桩缓冲采用固定容量并记录丢失计数；记录函数禁止再次分配，避免递归。记录发生于 ISR 时须符合该 allocator 与日志缓冲的并发规则。

### 3.2 可重复实验

1. 系统初始化完成后等待缓存稳定，记录基线 B0。
2. 执行同一业务循环 N 次，完成所有异步取消与资源回收，再记录 B1。
3. 重复三轮，比较相同阶段的未释放块数 / 字节，而非任意两个时刻。
4. 按分配 site ID 聚合新增未释放对象，核对相应 owner 与释放路径。
5. 总空闲字节稳定但最大空闲块下降时，进一步检查碎片。

例：每轮创建并关闭 100 次 session；预热后每轮多 100 个未释放 RxBuffer，才是强泄漏线索。只看到最低可用堆刷新，不足以认定泄漏。

### 3.3 Data.AllocList 的前置条件

`Data.AllocList` 需要目标端提供它要求的分配记录 / 管理头布局；不会自动理解任意 FreeRTOS `heap_4` 或 C++ allocator。先按安装包示例适配并校验 guard、对齐、header 与 head symbol，再使用聚合视图。

```text
; 仅在目标端已接入与本版兼容的 T32 分配审计结构后使用
Data.AllocList
Data.AllocList /SumCaller
```

HEAD / TAIL 损坏只能证明对应保护字节改变，不能独立证明就是该块持有者写坏。邻接块、DMA、重复释放和任意野指针都可能造成相同结果。

不能插桩时，依据实际 allocator 源码检查空闲链表的范围、对齐、block size、next 指针与总量。不知道节点布局就不执行通用偏移遍历；环形链表中的环可能是合法哨兵结构。

## 4. 踩内存：从受害地址抓首次异常写入

1. 在 Dump 找到最小受损字段，记录正常值、变化范围、首次观察时机。
2. 列出全部合法写入者及合法生命周期，包括初始化、回收、ISR、DMA 与其他核。
3. 让初始化完成，再对稳定地址布防。动态对象地址会复用，记录 allocation generation。
4. 停机可接受时使用有限硬件写观察点；命中即保存现场并检查附近指令。
5. 合法写入太频繁或停机会掩盖问题时，再升级到芯片支持的数据追踪。

```text
; 替换为有类型信息的真实全局变量
Var.Break.Set g_system_health_magic /Write /Onchip
Break.List
```

核对正常写入是否也会命中。若变量已在 CPU 继续运行时改变而观察点未命中，不能排除 DMA、其他核、错误地址空间、Cache 视角或比较器覆盖不完整。

## 5. DMA 与 Cache 的专项检查

| 检查点 | 具体操作 | 典型错误 |
|---|---|---|
| buffer 与 descriptor 长度 | 对照实际分配容量、单位、硬件字段 | 字节数被当作元素数 |
| 所有权转交 | 确认 DMA 完成前 CPU 不释放 / 复用 | 析构后 DMA 仍写入 |
| 地址 | 核对总线地址、映射、可达 RAM | CPU 虚拟 / 别名地址直接交给 DMA |
| Cache line | 按 BSP 要求独立对齐并避免共享行 | 无关对象与 DMA buffer 共用缓存行 |
| Cache 维护 | 遵循厂商 TX / RX 顺序及 barrier | 过早 invalidate 或遗漏 clean |

CPU 的 DWT 数据观察点通常只观察该核访问；要追踪 DMA 总线写入需 SoC 支持的系统总线 trace / monitor 等能力。先做关闭 DMA、替换独立对齐 buffer 等对照实验，每次只改变一个变量。

## 6. 硬件 Trace：先确认能看到什么

### 6.1 能力核对

确认芯片实际实现 ETM / DWT / ITM、是否支持数据与 PC 关联、路由和时钟是否启用、板卡是否引出端口、片上缓冲是否可用、探头与许可是否匹配。SWD 接通不等于 ETM 可用；SWO 与并行 TPIU 不能套用相同端口配置。

采用安装包对应 SoC 的官方启动脚本。附件中的 pinmux 地址、电压阈值和端口频率不移植到其他芯片。

### 6.2 逐级布防

1. 录一段已知简单循环，确认指令流能正确解码。
2. 在可用的数据 Trace 通道中，仅选择一个受害字段。
3. 对支持该动作的硬件尝试以下配置，并核对实际 accepted 状态：

```text
; 能力相关示例：不是所有 Cortex-M 都支持该组合
Var.Break.Set g_system_health_magic /Write /TraceData
; 下面二选一，按硬件与官方示例配置
ITM.DataTrace DataPC
; ITM.DataTrace CorrelatedData
Trace.List
```

4. 用一次已知合法写入校验记录的地址、值、PC；字段缺失时降低结论范围。
5. 选择产品支持的循环覆盖模式保留异常前历史；异常触发与采集停止的联动按 BSP 验证。
6. 保存原始 Trace、对应代码镜像、时间基准与触发配置，再寻找第一个不符合业务约束的写入。

ETM 指令流不能自动补回未采集的数据值；ITM 数据模式不能自动看到 DMA。CPU 断点停住后 Trace sink 是否同步停止也需验证。

### 6.3 Trace 故障排查

| 现象 | 优先检查 | 通过标准 |
|---|---|---|
| HARDERROR | 端口、时钟、引脚复用、采样校准与信号质量 | 已知循环稳定解码 |
| FIFOFULL | 源带宽超过链路 / sink 能力 | 缩小过滤后关键时间段不再丢失 |
| FLOWERROR | 代码镜像不匹配、覆盖、缺包或同步失效 | 代码与记录匹配且目标区间连续 |
| unknown task | 尚无初始任务身份、缺切换事件、配置错误 | 与任务表及已知切换验证一致 |

FIFO 数据丢失期间不能宣称“期间没有非法写入”。缓冲覆盖历史与链路 FIFO 溢出是两件不同的事。

## 7. 检查题与设计题

1. 总空闲堆为 20 KiB，但 8 KiB 分配失败，一定是泄漏吗？
2. TAIL guard 坏了，能直接责怪分配调用者吗？
3. 设计题：UART DMA buffer 由 C++ 对象管理，销毁过程应先做什么？

参考答案：1. 也可能是碎片、对齐或分配域限制。2. 不能，需要首次写入证据。3. 停止新的提交，取消或等待 DMA 完成并确认硬件不再访问，再释放 buffer；析构函数的存在不等于这个协议已实现。
