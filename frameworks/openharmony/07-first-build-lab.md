# 07 · 首次构建与启动实验手册

状态：资料整理／操作手册；尚未完成完整源码构建、仿真或板端验证。研究来源基线为 `OpenHarmony-v5.0.0-Release`，不表示最新版本。本文不预设某块板的产品名、串口参数或烧录工具。

前置：[系统定位](01-system-overview.md)、[工程指南](04-engineering-guide.md)、[来源清单](05-sources.md)。目标是建立可重现的输入和证据，不是只生成一个固件文件。

## 1. 实验输入卡

开始下载前填齐：release、manifest revision、目标内核、芯片、开发板型号与硬件修订、所选产品、主机系统、工具链、Python／hb 版本、串口与烧录工具，以及对应固定版本官方指南的链接。

判断该 release 是否真的支持所选产品；同一块板上的不同系统形态不等价。若官方资料与源码配置不一致，先保存冲突并停止套用其他版本命令。

## 2. 获取和锁定源码

按照该 release 官方源码获取指南准备 repo 并同步要求的仓库组。这里不提供未经所选产品验证的通用 `repo init`／`hb set` 参数。

同步完成后，在多仓库工作区执行：

```bash
mkdir -p evidence/first-boot
repo manifest -r -o evidence/first-boot/manifest.xml
repo status > evidence/first-boot/repo-status.txt
```

记录同步失败和重试；不要仅保存浮动分支名。模块的 `sources.json` 是已采集文件清单，不能替代完整系统 manifest。

## 3. 构建与产物核对

1. 按所选指南准备工具链、选择产品，记录实际命令和工作目录。
2. 保存完整标准输出、错误输出和退出码；管道日志不得掩盖构建失败。
3. 归档配置差异、编译器版本、链接 map、ELF／符号和固件；保存 SHA-256。
4. 核对启动入口、向量表、内存分区、全局构造执行路径和所启用组件；不要根据公共头文件推断组件已启用。

若发生工具版本、头文件或链接符号错误，先比较锁定记录。随意替换工具链后成功，不代表原始环境已经可复现。

## 4. 烧录与观察启动

依据目标板文档完成电源、接线、启动模式和烧录，记录地址、镜像及工具版本。保存从复位开始的完整串口日志，而不只截取应用成功行。

对照 [启动调用链](06-mini-system-boot-flow.md)，定位复位入口、内核初始化、系统初始化和第一个应用／服务入口。某阶段没有输出不代表该函数没有执行：用符号、断点或受控日志补充证据。

## 5. 失败分支与最低验收

| 现象 | 首先核对 | 必须保留的证据 |
| --- | --- | --- |
| 源码同步失败 | release、网络、工具和剩余空间 | 失败仓库、revision、命令与日志 |
| 编译／链接失败 | 实际工具链、产品、组件和库配置 | 首个根因错误及 map／链接命令 |
| 无串口输出 | 供电、启动模式、镜像、串口配置 | 接线／配置、烧录日志，不能直接归因调度器 |
| 进入内核但应用未启动 | 配置、链接段、初始化等级、任务创建返回值 | 固定源码路径及相应输出／断点 |
| 重启或异常 | 堆栈、异常寄存器、镜像／符号一致性 | 故障现场与原始固件，不覆盖旧证据 |

完成标准：从记录重建一次干净构建；固件与符号匹配；日志／断点支持从复位到应用入口的解释；再次启动结果可重复；未验证组件单列。只有完成这些实际步骤后，才更新 [规划](ROADMAP.md) 为板端验证。

下一步逐项验证任务创建、队列满／空／超时、ISR 合法调用、内存失败及 C++ RAII；不要从首次启动成功直接推导这些能力可用。迁移主机案例时参考 [贯穿实验](../../docs/engineering-learning-path.md) 的契约映射。
