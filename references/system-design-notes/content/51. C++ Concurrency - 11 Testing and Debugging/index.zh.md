# 第 11 章：多线程应用的测试与调试

本章涵盖以下内容：

- 与并发相关的缺陷分类
- 通过测试与代码审查定位缺陷
- 面向可测试性设计并发代码
- 构建多线程测试框架
- 测试多线程代码的性能与可伸缩性

到目前为止，我们一直专注于编写并发代码所需的方方面面——可用工具、使用方法，以及代码的整体设计与架构。但在软件开发中还有一个至关重要的环节尚未涉及：**测试与调试**。如果你阅读本章是希望找到一种轻松测试并发代码的捷径，那你恐怕要失望了。测试和调试并发代码极其困难。本章将为你提供一些行之有效的技巧，帮助降低复杂性，并剖析那些在开发过程中必须审慎思考的关键问题。

测试与调试就像一枚硬币的两面——对代码施加测试是为了发现潜在缺陷，而调试则是为了移除这些缺陷。幸运的是，只要测试得当，你只需修复内部测试暴露出来的缺陷，而不必等到最终用户遭遇故障。在探讨具体的测试或调试技术之前，必须首先弄清楚可能会出现哪些并发问题。

## 11.1 并发相关缺陷的分类

在并发代码中可能会出现任何类型的普通程序缺陷，这并没有什么特别之处。但有些类型的缺陷与并发的使用直接相关，也是本书重点关注的内容。通常，这些与并发相关的缺陷可以划分为两大类：

- 非预期的阻塞（Unwanted blocking）
- 竞争条件（Race conditions）

这是两个非常宽泛的范畴，下面我们逐一展开详细分析。

### 11.1.1 非预期的阻塞

所谓“非预期的阻塞”是什么意思？当一个线程由于等待某些条件而无法继续执行时，它就处于阻塞状态。通常这包括等待互斥量（mutex）、条件变量（condition variable）、期物（future），或者是等待 I/O。这是多线程编程中自然的组成部分，但并不总是符合预期的——这就是非预期阻塞的问题所在。为什么这种阻塞是不希望发生的？通常是因为其他某个线程也在等待这个被阻塞的线程执行某些操作，从而导致连锁阻塞。这一现象有几种常见变体：

- **死锁（Deadlock）**：正如你在第 3 章中所见，发生死锁时，一个线程在等待另一个线程，而后者反过来又在等待第一个线程（或者形成环路等待）。如果线程发生死锁，它们本应执行的任务将永远无法完成。在最显眼的场景中，如果涉及的线程之一负责用户界面，UI 就会停止响应；在其他情况下，UI 可能依然响应，但某些后台任务却无法完成（例如搜索永远不返回结果，或者文档始终无法打印）。
- **活锁（Livelock）**：活锁类似于死锁，也是一个线程在等待另一个线程，而后者也在等待前者。关键区别在于：此时的等待不是休眠阻塞等待，而是处于活跃检查的忙循环中（例如自旋锁 spinlock）。在严重情况下，其外部症状与死锁相同（应用程序无法取得任何进展），但 CPU 占用率却居高不下，因为各个线程仍在全速运行却互相阻碍。在较轻微的情况下，由于随机调度的偶然性，活锁最终可能会自行解开，但在解除前任务会经历漫长的延迟，且伴随着极高的 CPU 消耗。
- **阻塞在 I/O 或其他外部输入上**：如果线程被阻塞在等待外部输入上，只要所等待的输入迟迟不来，该线程就无法继续推进。因此，绝不要让一个同时还承担着其他线程所依赖任务的线程去阻塞等待外部输入。

以上简要介绍了非预期的阻塞。接下来我们看竞争条件。

### 11.1.2 竞争条件

竞争条件是多线程代码中最为常见的故障根源——许多死锁和活锁之所以显现，追根溯源往往也是由于竞争条件触发的。并非所有的竞争条件都会带来危害；只要系统行为取决于不同线程操作的相对调度顺序，就存在竞争条件。大量竞争条件是完全良性的，例如由任务队列中的哪个工作线程来领取并处理下一个任务通常无关紧要。但许多严重的并发缺陷正是竞争条件所致。具体而言，竞争条件往往导致以下几类问题：

- **数据竞争（Data races）**：数据竞争是竞争条件的一种特定形式，指的是多个线程在没有同步机制的情况下并发访问同一个共享内存位置，且至少有一个访问是写入操作。这在 C++ 中属于未定义行为（Undefined Behavior）。第 5 章介绍 C++ 内存模型时详细讨论了数据竞争。数据竞争通常是由于错误使用原子操作进行线程同步，或者在访问共享数据时未锁定适当的互斥量所致。
- **破坏不变量（Broken invariants）**：这可能表现为悬挂指针（因为另一个线程删除了当前正在访问的数据）、随机内存损坏（因为一个线程读取了处于部分更新状态的不一致数据）以及重复释放（double-free，例如两个线程从队列中弹出了同一个元素，因而双方都试图释放相关联的资源）等。被破坏的不变量既可能是基于数值的，也可能是基于时间/顺序的。如果要求不同线程上的操作必须以特定顺序执行，不正确的同步可能导致竞争条件，进而偶尔破坏预期的执行顺序。
- **生命周期问题（Lifetime issues）**：虽然可以将其归入破坏不变量的范畴，但它值得作为单独的一类来对待。这类缺陷的根本问题在于：线程的生命周期超出了它所访问数据的生命周期。换言之，线程访问了已被析构、释放或其存储空间已被其他对象复用的内存。当线程引用了在线程函数完成前就已脱离作用域的局部变量时，最容易出现生命周期问题，但并不仅限于此。只要线程与其操作数据的生命周期没有进行严格绑定，就随时存在数据被提前销毁、导致线程脚下的“地毯被抽走”的危险。如果你通过手动调用 `join()` 来等待线程完成，必须确保即使抛出异常，`join()` 的调用也不会被跳过——这就是应用于线程的基础异常安全保证。

真正致命的是那些恶性的竞争条件。对于死锁和活锁，应用程序通常表现为挂起、完全失去响应或耗时过长，你往往可以通过将调试器挂载（attach）到运行进程上，直观地找出哪些线程陷入了死锁/活锁以及它们在争抢哪些同步对象。然而，对于数据竞争、破坏不变量和生命周期问题，故障的表象（如随机崩溃或计算错误）可能出现在代码的任何地方——有缺陷的代码可能会覆写系统另一部分所使用的内存，而那部分内存可能很久之后才被读取。故障因而会暴露在与缺陷代码风马牛不相及的位置，并且可能发生在程序运行很久之后。这就是共享内存系统的诅咒：无论你多么努力地限制线程能够访问的数据范围，并试图确保使用了正确的同步，任何一个线程的野蛮写入都有可能破坏应用程序中其他线程正在使用的数据。

在明确了要寻找的问题类型之后，我们来看看有哪些方法可以定位并修复代码中的这些缺陷。

## 11.2 定位并发相关缺陷的技术

前一节我们分析了常见的并发缺陷及其在代码中的外在表现。基于这些知识，接下来就可以审视代码，分析缺陷可能隐藏在何处，并尝试确定特定模块中是否存在潜在 Bug。

最显而易见的方法是**代码审查（Code Review）**。虽然听起来直接，但要彻底做好绝非易事。当阅读自己编写的代码时，极容易代入“自己原本打算写什么”的主观意图，而非代码“实际上写了什么”。同样，在审查他人代码时，人们往往容易草草浏览一遍、对照编码规范打个勾、挑出一些显眼的瑕疵便了事。真正需要的是用细齿梳梳理代码，深入剖析并发机制以及非并发逻辑中的每个细节（毕竟无论何种 Bug 都是 Bug）。稍后我们将讨论审查代码时需要思考的具体问题。

即便经过详尽的代码审查，仍有可能遗漏某些缺陷；无论如何，我们都需要通过测试来确认代码是否能正确工作。因此，我们将从代码审查延伸到多线程代码测试所应采用的实用技术。

### 11.2.1 通过代码审查定位潜在缺陷

如前所述，在审查多线程代码以排查并发缺陷时，必须做到极其彻底。如果可能，尽量请其他人来审查。因为他们没有参与编写，必须重新推演代码的工作逻辑，这有助于揭示隐藏的缺陷。审查者必须拥有充足的时间来进行认真的推敲，而不是两分钟的走马观花。绝大多数并发缺陷都不是一眼就能看出的，它们往往依赖于极其微妙的执行时序才会被触发。

如果让同事审查，他们能以全新的视角切入，可能会发现你所忽视的盲区。如果没有现成的同事可以请教，不妨向同行求助，甚至在不违反保密协议的前提下将脱敏代码发布到技术社区。如果实在找不到人审查，或者审查没有发现异常，也不必灰心。首先可以先把代码搁置一段时间——去处理项目的其他部分、读读书或散散步。当你暂时离开时，潜意识仍然会在后台处理这个问题；同时当你回过头来再次审视时，熟悉感会降低，你更容易以全新的客观视角进行审视。

除了请他人审查，还可以自己对自己进行“审查”。一个非常有效的技巧是：尝试向别人**极其详细地解释代码的工作原理**。听众甚至不需要真实存在——许多团队会使用“小黄鸭调试法”（用玩具小熊或橡皮鸭充当听众）；撰写详尽的技术笔记也具有异曲同工之妙。在解释的过程中，逐行推敲：这一行执行时会发生什么？它访问了哪些数据？向自己提出质疑并给出解答。这种自我盘问与严谨推演常常能让隐藏的漏洞无所遁形。

#### 审查多线程代码时应思考的问题清单
在审查代码时，围绕具体的问题展开推演能够帮助审查者聚焦于关键细节，精准定位潜在问题。以下是我在审查代码时经常问自己的问题（这绝非穷尽列表，你可以根据具体场景扩充）：

- **哪些数据需要受到并发访问的保护？**
- **你如何确保这些数据得到了充分的保护？**
- **在当前执行点，其他线程可能正处于代码的哪些位置？**
- **当前线程当前持有了哪些互斥量？**
- **其他线程此时可能持有着哪些互斥量？**
- **当前线程所执行的操作与另一线程的操作之间是否存在任何顺序要求？这些要求是如何得到强制保证的？**
- **当前线程读取加载的数据是否仍然有效？它是否可能已经被其他线程修改过了？**
- **如果你假设另一线程可能正在修改该数据，这意味着什么？你如何确保这种情况绝不会发生？**

上面最后一个问题是我最喜欢的思考切入点，因为它迫使我去深入分析线程间的交织关系。通过假设某一行代码存在 Bug，你就可以像侦探一样去追踪其触发原因。为了证明不存在 Bug，你必须穷尽每一种极端边界情况和可能的指令排列顺序。当数据在其生命周期内受多个互斥量保护时，这种思考尤为关键，例如第 6 章中的线程安全队列：队列的头部和尾部拥有独立的互斥量；为了确保在持有一个互斥量的同时能够安全访问节点，你必须绝对确信持有另一个互斥量的线程无法同时访问该节点。这同时也提醒我们：所有公有数据，或者其他代码能够轻松获取指针/引用的数据，都必须接受极为严苛的审视。

列表中倒数第二个问题同样至关重要，它针对的是一个极易犯的低级错误：**如果你释放了一个互斥量然后又重新获取它，你必须假定共享数据在此期间可能已被其他线程修改**。虽然道理很简单，但如果互斥锁的释放与获取被隐藏在某个对象的内部成员函数调用中，你可能会在不知不觉中犯下这个错误。在第 6 章中我们看到了由此引发的接口粒度过细问题：对于单线程栈，提供独立的 `top()` 和 `pop()` 操作十分合理；但对于并发栈而言，由于内部互斥锁在两次调用之间会被释放，另一个线程可能会趁虚而入修改栈顶，从而导致逻辑竞争。正如第 6 章所示，解决方案是将两项操作合并，使它们在同一个互斥锁保护下原子完成。

好了，代码已经审查完毕，你确信逻辑没有问题。然而“实践是检验真理的唯一标准”——你该如何测试代码，以证实或推翻你对代码正确性的判断呢？

### 11.2.2 通过测试定位并发相关缺陷

在开发单线程应用程序时，测试虽然耗时，但在原理上相对直观。原则上，你可以确定所有可能的输入数据集（或至少是所有具有代表性的边界场景），并在应用程序中运行它们。如果程序产生了正确的行为和输出，你就可以断定它在给定的输入下能够正常工作。虽然测试错误状态（如处理磁盘空间耗尽）更为复杂，但基本思想是一致的：搭建前置条件，然后运行程序并验证结果。

测试多线程代码的难度则呈指数级上升，因为**线程的具体调度时序是不确定的（indeterminate），并且每次运行都可能发生改变**。因此，即便使用完全相同的输入数据，如果代码中潜藏着竞争条件，它可能在某些时候运行完全正常，而在另一些时候偶发崩溃或得出错误结果。潜在竞争条件的存在并不意味着代码一定会失败，而只是意味着它“偶尔可能”会失败。

鉴于复现并发缺陷的固有难度，精心设计测试用例显得尤为重要。你应该力求让每个测试用例只运行**最小范围的代码**来重现潜在问题，以便在测试失败时能够精确隔离出出错的逻辑——直接对并发队列执行并发 push 和 pop 操作来验证其正确性，远比通过使用该队列的一整套庞大业务代码来进行测试有效得多。如果在设计代码之初就提前考虑如何测试它，将带来巨大益处——参见下文关于“面向可测试性设计”的讨论。

此外，**在测试中消除并发**对于验证问题是否确实与并发相关具有极高的价值。如果问题在所有任务都在单线程中运行时依然出现，那它就是一个普通的业务逻辑 Bug，而非并发缺陷。在排查生产环境（in the wild）中偶发的故障时，这一点尤为关键。仅仅因为 Bug 出现在多线程模块中，并不意味着它一定是并发引起的。如果你使用线程池来管理并发度，通常可以通过配置参数将工作线程数设为 1；如果是手动管理线程，可以修改代码在测试中仅使用单个线程。无论采用何种方式，只要将程序退化为单线程运行，就可以彻底排除并发这一诱因。反过来，如果一个问题在单核系统上完全消失（即使运行着多个线程），但在多核或多处理器系统上稳定复现，那么你面对的大概率是一个竞争条件，或者是底层同步及内存顺序（memory ordering）出现了漏洞。

测试并发代码不仅取决于被测代码本身的结构，测试本身的组织结构与测试环境同样举足轻重。继续以测试并发队列为例，你必须考虑各种可能的交织场景：

- 单个线程独立调用 `push()` 或 `pop()`，验证队列的基本功能
- 一个线程对空队列调用 `push()`，同时另一线程调用 `pop()`
- 多个线程同时对空队列调用 `push()`
- 多个线程同时对已满队列调用 `push()`
- 多个线程同时对空队列调用 `pop()`
- 多个线程同时对已满队列调用 `pop()`
- 多个线程同时对部分填充的队列调用 `pop()`，且队列中的元素不足以分配给所有线程
- 多个线程调用 `push()`，同时一个线程对空队列调用 `pop()`
- 多个线程调用 `push()`，同时一个线程对已满队列调用 `pop()`
- 多个线程调用 `push()`，同时多个线程对空队列调用 `pop()`
- 多个线程调用 `push()`，同时多个线程对已满队列调用 `pop()`

在设想了所有这些场景之后，还需要考虑测试环境的额外物理因素：

- 在上述每个场景中，“多个线程”具体指多少个线程？（3 个、4 个，还是 1024 个？）
- 物理系统中是否有足够的 CPU 核心，使得每个线程都能独占一个独立核心运行？
- 测试应当在哪些处理器架构上运行？
- 你如何确保测试中“同时进行”部分的各个线程能够达到精准同步的调度？

在这些考量中，第一点和第四点直接影响测试代码本身的结构设计（详见 11.2.5 节），而后两点则与运行测试的物理环境相关。测试所用的线程数量与被测代码的业务特征相关，但构建测试框架以获得理想调度的方式多种多样。在探讨这些具体测试技术之前，我们先来看看如何通过架构设计让代码更容易测试。

### 11.2.3 面向可测试性进行设计

测试多线程代码本身就极具挑战，因此必须在设计阶段扫清障碍。最重要的原则之一就是**面向可测试性进行设计（Designing for testability）**。软件工程中已有大量关于单线程代码可测试性设计的论述，其中的大部分准则在此依然适用：

- 每个函数和类的职责必须单一明确
- 函数应尽量短小精炼、直奔主题
- 测试用例应当能够完全掌控被测代码周围的环境依赖
- 执行特定操作的代码应该高度内聚，而不是分散在整个系统中
- **在编写代码之前就必须构思好如何测试它**

这些准则对于多线程代码不仅完全适用，而且由于多线程测试的天然困难性，其重要性被进一步放大。最后一点尤为关键：即使你没有严格采用测试驱动开发（TDD）在编码前先写测试，也必须在动手前认真思考：这段代码将如何被验证？输入什么样的数据最合适？哪些临界状态最容易引发异常？如何制造极限并发压力来激发潜在的同步漏洞？

设计并发代码以便于测试的最佳策略之一是**消除并发依赖（Eliminate concurrency）**。如果你能将代码清晰地划分为两部分：一部分专门负责线程间的通信通道与同步，另一部分则在单线程内部纯粹处理通信传递过来的数据，那么问题的复杂性就会呈数量级下降。对于仅由单一线程访问的数据处理逻辑，完全可以使用常规的单线程单元测试技术进行覆盖。那些难以测试的、负责线程间协调并确保独占访问的核心并发代码被压缩到了最小范围，从而使得严格的测试验证变得切实可行。

例如，如果你的应用程序设计为一个多线程状态机，你可以将其拆分为几个部分：每个线程的状态转换逻辑（确保针对每种可能的输入事件都能完成正确的状态迁移）可以完全通过单线程技术独立测试，测试框架只需模拟来自其他线程的输入事件即可；而核心的状态机事件路由机制（确保事件按正确顺序准确派发至目标线程）则可以使用轻量级、专为测试构建的桩逻辑，在多线程并发环境下进行针对性验证。

另一种拆分方式是将业务逻辑抽象为经典的流水线：“读取共享数据 -> 数据变换处理 -> 更新共享数据”。你可以对中间的数据变换逻辑应用所有单线程测试手段，因为这部分完全是纯粹的单线程代码。测试多线程复杂变换这一难题，就被简化为仅测试共享数据的读取和更新同步，后者的规模和验证难度要小得多。

需要警惕的一个陷阱是：**某些标准库或第三方库调用可能在内部使用了静态变量来存储状态**，当多线程并发调用同一组函数时，这些状态就会隐式变成共享资源。这极具欺骗性，因为从调用方代码表面看并没有显式访问共享数据。但随着经验的积累，识别这些非线程安全函数并不困难。你可以通过在外层加锁同步，或者替换为现代线程安全的替代函数（如使用可重入版本）来解决该问题。

### 11.2.4 多线程测试技术

当你梳理好了测试场景并编写了待测函数的最小测试逻辑后，如何才能确保触发那些潜在的致命调度序列，从而将隐藏的缺陷暴露出来呢？通常有几种核心途径，首先是暴力测试（压力测试）。

#### 暴力测试（压力测试，Brute-force testing）
暴力测试的核心思想是通过对代码施加极端压力来观察其是否会崩溃。这通常意味着在高并发多线程环境下循环运行代码成千上万次。如果某个 Bug 只有在特定的线程调度时序下才会暴露，那么运行测试的次数越多，触发该时序的概率就越高。如果运行一次测试通过，你可能略感欣慰；如果连续运行十次都通过，你的信心会增强；如果运行十亿次全部通过，你的信心自然更加坚定。

测试结果的可信度很大程度上取决于单次测试所覆盖的代码粒度。如果测试非常细粒度（例如前文针对并发队列设计的各项独立用例），暴力压力测试能够带来极高的置信度。相反，如果被测代码规模庞大、逻辑盘根错节，那么可能的线程调度排列组合数量将是天文数字，此时即便运行十亿次测试，所得出的置信度依然微乎其微。

暴力测试的致命缺陷在于它可能给人带来**虚假的安全感**。如果你编写测试的方式导致有问题的时序根本无法触发，那么无论运行多少亿次，测试都不会报错，而在现实场景中稍微改变一点运行条件就会立即崩溃。最极端的情况是：由于测试机器本身的物理特性，产生竞争的时序在当前测试环境中根本不可能出现。除非你的代码未来仅在与测试机完全相同的单一硬件和操作系统上运行，否则不同的软硬件环境可能会诱发你在测试机上永远看不到的问题。

经典例子是在单核单处理器系统上测试多线程程序。由于所有线程都必须在同一个物理核心上分时复用，所有指令访问在硬件层面上被自然串行化了，真实多处理器系统上才会暴露的数据竞争、缓存一致性颠簸（cache ping-pong）等问题在此完全隐形。不仅物理核心数是变量，不同的处理器架构所提供的同步与内存顺序保证也截然不同：例如在 x86 和 x86-64 架构下，原子加载操作无论被标记为 `memory_order_relaxed` 还是 `memory_order_seq_cst`，生成的汇编指令通常完全一致（参见 5.3.3 节）。这意味着一段使用了过于宽松的松弛内存顺序（relaxed ordering）的有缺陷代码，在 x86 机器上测试可能畅行无阻，但一旦移植到具有更弱内存模型的架构（如 ARM 或 SPARC）上就会频繁崩溃。

因此，为了确保可移植性，必须在具有代表性的目标硬件平台上进行测试。同时，为了避免虚假的安全感，必须精心设计测试用例与测试框架，确保尽可能覆盖各种代码执行路径与线程交互组合，并清楚地了解哪些路径已被覆盖、哪些仍处于盲区。

#### 组合仿真测试（Combination simulation testing）
尽管暴力测试能提供一定程度的信心，但它无法保证发现所有隐藏缺陷。如果条件允许并且拥有适当的工具软件，有一种技术可以保证找到所有潜在问题，我称之为**组合仿真测试**。

其原理是：在一个特殊的软件仿真环境中运行你的代码。类似于虚拟机监控器模拟物理硬件，这种仿真软件在运行过程中会精确记录每个线程执行的数据读写、锁操作以及原子操作序列。随后，它依据 C++ 内存模型规范的法定规则，穷举重放每一种合法允许的操作排列组合，从而在数学上严格识别出任何潜在的数据竞争和死锁。

这种穷尽式组合测试虽然在理论上能保证找出工具所支持的所有并发缺陷，但对于非凡微代码以外的程序而言，它需要耗费巨大的时间，因为操作排列组合的数量会随着线程数和指令数的增长呈**指数级爆炸**。因此，该技术最适合用于极细粒度、关键核心模块的严密验证，而不适用于整套大型应用程序。此外，它还受限于仿真分析工具对特定 C++ 现代语言特性的支持程度。

#### 使用专用检测库监控测试执行（Detecting problems exposed by tests with a special library）
第三种选择是在运行测试时，利用专用的检测库或插桩工具来动态捕获问题（如 Clang/GCC 的 ThreadSanitizer，TSan，或者定制的互斥量包装库）。

虽然这不如组合仿真那样能够穷尽所有排列，但它能在测试运行时通过对同步原语（互斥量、锁、条件变量等）进行追踪来捕获大量隐患。例如，通常要求对某块共享数据的访问必须在持有特定互斥锁的前提下进行；如果使用特殊的互斥量与指针检测包装，当访问该数据时检测当前线程是否真正持有该锁，若未加锁即可立即断言报错。

这类检测库还可以记录单个线程同时获取多个互斥量时的**加锁顺序（Lock-order acquisition graph）**。如果检测到另一个线程以相反或冲突的顺序获取相同的这组互斥量，工具就可以立即发出死锁风险警告，即使在本次具体的测试运行中由于时序巧合并未真正触发死锁挂起。

此外，专用的测试桩库还可以赋予测试人员对内部调度的控制权——例如精确控制当多个线程阻塞等待时由哪一个线程赢得锁，或者控制条件变量的 `notify_one()` 精确唤醒哪一个指定的线程。这使得测试编写者能够确定性地编排极端的执行场景，并验证系统在这些极端边界下的正确性。

### 11.2.5 构建多线程测试代码

在 11.2.2 节中我们提到，测试框架必须具备在特定时刻精确触发多线程交织执行的能力。本节我们将探讨如何具体实现这种测试调度。

核心目标是：**安排一组线程，让它们各自在预定的精确时间点同时并发执行指定的待测代码片段**。以最简单的双线程并发测试为例，首先需要理清测试的四个独立阶段：

1. **全局通用准备逻辑（General setup）**：在一切开始之前必须执行的代码（如实例化待测容器）。
2. **线程专属准备逻辑（Thread-specific setup）**：在各个线程内部独立执行的准备工作。
3. **并发核心执行逻辑（Concurrent execution）**：希望在各个线程上真正同时交织运行的待测操作。
4. **测试收尾与断言验证逻辑（Post-completion & assertions）**：在所有并发线程运行完毕后执行的验证代码，对最终状态施加断言。

我们以 11.2.2 节中列出的测试场景为例：一个线程对空队列调用 `push()`，同时另一个线程调用 `pop()`。

全局准备工作非常简单：实例化一个空队列。执行 `pop()` 的线程没有专属准备工作；而执行 `push()` 的线程的专属准备工作取决于队列中存储的数据类型：如果数据对象的构造开销极大或需要在堆上动态分配，应将其放入线程专属准备阶段完成，以防对象分配的耗时干扰真正的并发交织。核心待测操作则是一个线程调用 `push()`，另一个线程调用 `pop()`。

关于收尾断言验证：如果 `pop()` 是阻塞接口，那么显然最终应当验证弹出的数据值与推入的值一致，且操作后队列变为空；如果 `pop()` 是非阻塞接口，则有两种合法结果：要么 `pop()` 成功获取数据且队列变空，要么 `pop()` 提示无数据且队列中留存了该数据项。为了聚焦测试结构，这里我们假定 `pop()` 为阻塞式接口。

为了让两个线程在执行待测操作时能够尽可能“在同一起跑线上同时出发”，一种优雅可靠的方式是使用一组 `std::promise` 和 `std::future` 来构建就绪栅栏（Rendezvous barrier）。每个工作线程在完成自身的专属初始化后，通过设置对应的 promise 向主线程报告自己已就绪，随后在一个共享的 `std::shared_future` 上阻塞等待；主线程等待所有工作线程的就绪信号全部到位后，通过设置发令枪 promise 一次性唤醒所有工作线程。待测逻辑执行完毕后，主线程回收线程并执行断言。清单 11.1 展示了这一模式的具体实现。

清单 11.1 队列上并发 push() 与 pop() 调用的测试示例

```cpp
void test_concurrent_push_and_pop_on_empty_queue()
{
    threadsafe_queue<int> q; // 1. 全局初始化：创建空队列
    std::promise<void> go, push_ready, pop_ready; // 2. 准备信号设施
    std::shared_future<void> ready(go.get_future()); // 3. 广播触发信号
    std::future<void> push_done; // 4. 线程完成指示器
    std::future<int> pop_done;

    try
    {
        // 5. 启动 push 工作任务
        push_done = std::async(std::launch::async,
                             [&q, ready, &push_ready]()
                             {
                                 push_ready.set_value(); // 报告 push 线程就绪
                                 ready.wait();           // 等待发令枪响
                                 q.push(42);             // 执行并发待测操作
                             }
            );

        // 6. 启动 pop 工作任务
        pop_done = std::async(std::launch::async,
                            [&q, ready, &pop_ready]()
                            {
                                pop_ready.set_value();  // 报告 pop 线程就绪
                                ready.wait();           // 等待发令枪响
                                return q.pop();         // 7. 执行并发待测操作并通过 future 返回结果
                            }
            );

        // 8. 主线程等待所有工作线程就绪
        push_ready.get_future().wait();
        pop_ready.get_future().wait();

        // 9. 一齐开跑：解除两个线程的阻塞
        go.set_value();

        // 10. 等待任务完成并获取返回值
        push_done.get();

        // 11. 校验并发操作的最终状态不变量
        assert(pop_done.get() == 42);
        assert(q.empty());
    }
    catch(...)
    {
        // 12. 发生异常时强制放行，避免工作线程永久死锁悬挂
        go.set_value();
        throw;
    }
}
```

其结构清晰地体现了前述步骤：
1. 在通用准备阶段创建空队列；
2. 为各个线程的就绪状态创建单独的 `std::promise`，并获取对应发令信号的 `std::shared_future`；
3. 将表示任务完成的 `future` 声明在 `try` 块外部，确保在异常发生时能安全处理而不会导致死锁；
4. 使用 `std::async(std::launch::async, ...)` 启动任务，确保它们真正运行在独立的操作系统线程上；使用 `std::async` 相比原生 `std::thread` 极大地简化了异常安全性，因为 `future` 的析构函数会自动等待底层任务结束；
5. 各个任务设置自身的就绪状态后挂起等待发令枪；主线程检测到两个任务均已就绪后，通过 `go.set_value()` 同步释放两处阻塞；
6. 主线程通过 `get()` 回收结果并对数据完整性施加断言；
7. 若在测试准备期间发生任何异常，在 `catch` 中设置 `go` 信号，防止子线程因永久等待发令枪而产生资源泄露和死锁。

虽然为了测试两个简单的调用写了大量样板代码，但这对于最大概率捕捉并发缺陷是必不可少的。因为物理线程的创建与启动需要耗费一定的时间，如果不通过栅栏强制同步，执行 `push` 的线程可能在 `pop` 线程尚未初始化完成时就已经跑完了整个流程，使得并发测试沦为普通的先后串行调用，完全失去了测试意义。一旦熟悉了这种模式，就可以轻松将其推广到包含数十个甚至数百个线程的复杂测试用例中。

### 11.2.6 测试多线程代码的性能

在应用程序中引入并发的一个核心动机是充分利用现代多核处理器的计算能力来提升程序性能。因此，与常规优化工作一样，必须通过严格的基准测试来验证**性能是否确实获得了提升**。

并发性能测试的核心指标是**可伸缩性（Scalability）**：在理想情况下，如果其他条件保持不变，在 24 核机器上运行的代码应当比在单核机器上快大约 24 倍，或者能处理 24 倍的数据吞吐量。你绝不希望看到一段代码在双核机器上能带来 2 倍加速，但在 24 核机器上反而比单核运行还要慢。正如我们在 8.4.2 节所看到的阿姆达尔定律（Amdahl's law）：如果代码中有一小部分逻辑必须在单线程上串行执行，就会严重限制整个系统的最大加速比。因此在开始性能测试之前，必须对整体架构进行理论评估：理清你追求的是 24 倍的线性加速，还是由于串行部分的制约使得理论极限只能达到 3 倍。

正如前几章反复强调的，多个处理器核心在访问同一数据结构时的**资源争用（Contention）**会对性能造成毁灭性打击。某些设计在核心数量较少时伸缩性良好，但在核心数量大幅增加时，由于互斥锁竞争剧烈或缓存一致性流量激增，性能会发生断崖式下跌。

因此，在进行多线程性能基准测试时，最好在尽可能多的不同硬件配置（不同核心数、不同 NUMA 架构、不同缓存大小）上采集数据，绘制出完整的**性能伸缩性曲线（Scalability graph）**。作为底线要求，你至少应当在单处理器系统以及你所能获取到的最高核心数系统上分别完成基准测试，以此验证并发设计的有效性。
