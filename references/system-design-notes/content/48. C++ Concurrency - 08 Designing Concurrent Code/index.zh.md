# 第 8 章：并发代码设计与性能优化

> 本章包含英文原书核心技术内容与完整代码示例，提供专业、严谨的技术翻译。

**本章涵盖：**

- 在线程间划分数据的技术
- 影响并发代码性能的硬件与系统因素
- 性能因素如何影响并发数据结构的设计
- 多线程代码中的异常安全性
- 可扩展性（Scalability）与阿姆达尔定律
- 多个标准库并行算法的完整参考实现

在前面的章节中，我们主要关注了 C++ 并发工具箱中的各种基础工具。在第 6 章和第 7 章中，我们研究了如何利用这些工具来设计支持多线程安全并发访问的基础数据结构。然而，正如一个木匠要想制作出精美的橱柜或桌子，光懂得如何制作铰链或榫卯接头是远远不够的一样，设计并发代码绝不仅仅局限于基础数据结构的设计与运用。你现在需要站在更广阔的宏观视角，去构建能够执行实际有价值任务的大型结构。在本章中，我们将以 C++ 标准库中若干算法的多线程实现作为示例，但这些设计原则同样适用于任何规模的应用程序。

与任何软件开发项目一样，对并发代码的设计进行深思熟虑至关重要。但是对于多线程代码，需要考量的因素比编写顺序代码多得多。你不仅要思考传统的软件工程要素，如封装性、低耦合和高内聚（这些在大量软件设计书籍中已有详尽阐述），还必须考量：哪些数据需要共享、如何同步对这些数据的访问、哪些线程需要等待其他线程完成特定操作等等。

本章我们将重点探讨这些核心问题：从高层（但最根本）的考量——使用多少个线程、在哪个线程上执行哪段代码、这如何影响代码的清晰度与可维护性；到底层细节——如何精心组织共享数据的内存布局以获得极致的运行性能。

让我们首先从线程间划分工作的各种技术开始探讨。

---

## 8.1 线程间划分工作的技术

不妨设想一下：你被指派去建造一座房屋。为了完成这项工作，你需要挖地基、砌墙、铺设管道、布置电线等。从理论上讲，只要经过充分培训，你可以一个人完成所有这些工作，但这必然耗费漫长的时间，而且你必须在不同的任务之间频繁切换。另一种选择是雇佣其他人来协助你。此时你必须决定雇佣多少人，以及他们需要具备什么技能。例如，你可以雇佣几个具备通用技能的杂工，大家共同参与所有工作。你们仍然需要在各项任务之间灵活切换，但因为人手变多了，事情能更快做完。

或者，你也可以雇佣一个专业团队：比如泥瓦匠、木匠、电工和水管工。这些专才只做他们擅长的事；如果暂时不需要铺设管道，水管工就可以坐在旁边喝茶或喝咖啡。事情依然能更快完成，因为人数增多了，而且水管工在安装马桶的同时电工可以为厨房接线；但当某个专才没有对应工作可做时，就会产生等待与闲置时间。然而，即便存在闲置等待，由专才组成的团队往往依然比通用杂工团队完工得更快——专才们不需要频繁更换工具，而且他们在各自专业领域的施工速度通常远超通才。至于实际是否如此，取决于具体的工程环境与场景——你必须进行实际权衡与测试。

即便你雇佣了专才团队，你也可以为不同工种配置不同的人数。例如，配备比电工更多的泥瓦匠通常是合情合理的。此外，如果你需要同时建造多座房屋，团队的构成与整体效率可能会发生很大改变。即便水管工在一座房子里的活不算多，但在同时建造多座房子时，可能足以让他始终处于忙碌状态。同时，如果当专才没有活做时你不需要支付报酬，那么即使同一时刻工作的人数相同，整体上你也可以雇佣一个规模更大的团队。

好了，关于盖房子的比喻就谈到这里；这与线程有什么关系呢？在多线程并发编程中，面临的正是完全相同的权衡与考量。你需要决定使用多少个线程，以及它们应该执行什么任务。你需要决定是采用“通才型”线程（在任何时间点执行任何必要的工作），还是采用“专才型”线程（专精于做好一件特定工作），抑或是二者的某种结合。无论你采用并发的初衷是什么，都必须做出这些抉择，而你的选择将对代码的性能和清晰度产生决定性的影响。因此，深入理解这些选项至关重要，以便在架构设计应用程序时做出明智的决策。在本节中，我们将介绍几种划分任务的技术，首先从在执行任何工作之前先在线程间划分数据开始。

### 8.1.1 在处理开始前划分数据

最容易并行化的算法是那些简单的算法，例如 `std::for_each`，它们对数据集中的每一个元素执行相同的操作。为了使这种算法并行化，你可以将每个元素分配给某个工作线程来处理。为了获得最优性能，究竟该如何划分这些元素取决于底层数据结构的具体细节，我们稍后在探讨性能问题时会详细讨论这一点。

最简单的划分数据方式是：将前 $N$ 个元素分配给一个线程，接下来的 $N$ 个元素分配给另一个线程，依此类推，如图 8.1 所示。当然也可以采用其他分配模式。无论数据以何种模式划分，每个线程在处理自己分配到的元素时，直至处理完成之前都不需要与其他线程发生任何通信。

```
线程 1: [ 块 1 (N 个元素) ]
线程 2: [ 块 2 (N 个元素) ]
...
线程 m: [ 块 m (剩余元素)  ]

图 8.1 在线程间分配连续的数据块
```

对于使用过消息传递接口（MPI，Message Passing Interface）或 OpenMP 框架进行编程的开发者来说，这种架构再熟悉不过了：一个整体任务被拆分为一组并行子任务，工作线程各自独立运行这些任务，最后在最终的“规约（reduction）”步骤中合并结果。这正是第 2.4 节中 `accumulate` 示例所采用的方法；在该例中，并行任务与最终合并步骤都是累加操作。对于简单的 `for_each`，最终步骤是一个空操作（no-op），因为没有需要合并的结果。

将最后一步明确识别为“规约”是非常重要的。像清单 2.9 那样的朴素实现会将该规约操作作为最后的串行步骤执行。然而，这个规约步骤本身往往也可以并行化；由于 `accumulate` 本身就是一个规约操作，因此清单 2.9 可以修改为在线程数大于单个线程处理的最小项数时递归调用自身。或者，也可以让工作线程在各自完成分配的任务时顺便执行部分规约合并，而不是每次都生成新线程。

尽管这种预先划分数据的技术非常强大，但它并不能适用于所有场景。有时数据无法在预先被整齐地划分，因为具体的划分边界只有在实际处理数据的过程中才会逐步明朗。这在快速排序（Quicksort）等递归算法中体现得尤为明显；因此它们需要采用不同的划分策略。

### 8.1.2 递归划分数据

快速排序算法有两个基本步骤：根据选定的基准元素（pivot）将数据划分为排在该元素之前和之后两部分，然后递归地对这两“半”数据进行排序。你无法通过预先划分数据来使其并行化，因为只有在实际遍历和比较元素后，你才能确定它们属于哪一半。要使这种算法并行化，你必须充分利用其天然的递归性质。随着递归深度的增加，对 `quick_sort` 函数的调用会越来越多，因为你必须对基准之前和之后的子序列分别进行排序。这些递归调用之间是完全独立的，因为它们访问的是彼此独立的数据子集，因此它们是并发执行的绝佳候选对象。图 8.2 展示了这种递归划分过程。

```
原始数据: [ ......... P ......... ]
               /             \
划分阶段 1: [ < P ]          [ > P ]
           /      \         /      \
划分阶段 2: [<P1]  [>P1]    [<P2]  [>P2]

图 8.2 递归划分数据
```

在第 4 章中，你曾见过这种实现。在该实现中，我们没有针对较小和较大的两块数据直接进行两次串行递归调用，而是使用 `std::async()` 在每个阶段为较小的数据块派生一个异步任务。通过使用 `std::async()`，你可以请求 C++ 线程库自动决定何时在全新线程上运行任务，何时同步运行该任务。

这一点非常关键：如果要排序的数据集非常庞大，在每次递归时都盲目生成新线程将迅速导致线程数量爆炸。正如我们在分析性能时会看到的，系统中如果存在过多线程，反而会严重拖慢应用程序的速度。此外，如果数据集过于庞大，系统甚至可能会耗尽线程资源。因此，像这样以递归方式划分整体任务的想法非常好，但你必须对线程总数进行更加严格的控制。`std::async()` 可以在简单场景下处理这种调度，但它并不是唯一的选择。

另一种选择是使用 `std::thread::hardware_concurrency()` 函数来决定创建的线程数量，就像你在清单 2.9 的并行版 `accumulate()` 中所做的那样。随后，不再为每次递归调用启动新线程，而是将待排序的子数据块推入一个线程安全的栈中（例如第 6 章和第 7 章中介绍的并发栈）。如果某个线程当前没有其他工作可做（要么是因为它已经处理完了自己所有的块，要么是因为它正在等待某个依赖块完成排序），它可以从栈中弹出一个待处理块并进行排序。

下面的清单展示了使用该技术的一个示例实现。与大多数示例一样，此代码旨在演示设计思想，而非开箱即用的工业级代码。如果你使用的是支持 C++17 的编译器及标准库，通常直接使用第 10 章涵盖的标准库并行算法会是更好的选择。

#### 清单 8.1 使用待排序块栈的并行快速排序

```cpp
template<typename T>
struct sorter
{
    struct chunk_to_sort
    {
        std::list<T> data;
        std::promise<std::list<T> > promise;
    };

    thread_safe_stack<chunk_to_sort> chunks;
    std::vector<std::thread> threads;
    unsigned const max_thread_count;
    std::atomic<bool> end_of_data;

    sorter():
        max_thread_count(std::thread::hardware_concurrency()-1),
        end_of_data(false)
    {}

    ~sorter()
    {
        end_of_data=true;
        for(unsigned i=0;i<threads.size();++i)
        {
            threads[i].join();
        }
    }

    void try_sort_chunk()
    {
        boost::shared_ptr<chunk_to_sort > chunk=chunks.pop();
        if(chunk)
        {
            sort_chunk(chunk);
        }
    }

    std::list<T> do_sort(std::list<T>& chunk_data)
    {
        if(chunk_data.empty())
        {
            return chunk_data;
        }
        std::list<T> result;
        result.splice(result.begin(),chunk_data,chunk_data.begin());
        T const& partition_val=*result.begin();

        typename std::list<T>::iterator divide_point=
            std::partition(chunk_data.begin(),chunk_data.end(),
                           [&](T const& val){return val<partition_val;});

        chunk_to_sort new_lower_chunk;
        new_lower_chunk.data.splice(new_lower_chunk.data.end(),
                                    chunk_data,chunk_data.begin(),
                                    divide_point);
        std::future<std::list<T> > new_lower=
            new_lower_chunk.promise.get_future();
        chunks.push(std::move(new_lower_chunk));

        if(threads.size()<max_thread_count)
        {
            threads.push_back(std::thread(&sorter<T>::sort_thread,this));
        }

        std::list<T> new_higher(do_sort(chunk_data));
        result.splice(result.end(),new_higher);
        while(new_lower.wait_for(std::chrono::seconds(0)) !=
              std::future_status::ready)
        {
            try_sort_chunk();
        }
        result.splice(result.begin(),new_lower.get());
        return result;
    }

    void sort_chunk(boost::shared_ptr<chunk_to_sort > const& chunk)
    {
        chunk->promise.set_value(do_sort(chunk->data));
    }

    void sort_thread()
    {
        while(!end_of_data)
        {
            try_sort_chunk();
            std::this_thread::yield();
        }
    }
};

template<typename T>
std::list<T> parallel_quick_sort(std::list<T> input)
{
    if(input.empty())
    {
        return input;
    }
    sorter<T> s;
    return s.do_sort(input);
}
```

在此实现中，`parallel_quick_sort` 函数将大部分工作委托给了 `sorter` 类，该类封装了未排序数据块的并发栈 `chunks` 以及一组工作线程 `threads`。核心工作在 `do_sort` 成员函数中完成，它首先对数据进行常规的分区操作。与之前为某个分块直接启动新线程不同，这次它将较小的数据块推入栈中，并在系统处理器核心尚未占满（即当前线程数小于 `max_thread_count`）时按需派生新的工作线程。由于下半部分的数据块可能被其他工作线程取走处理，当前线程随后必须等待对应的 future 就绪。为了不让当前线程闲置（防止当前线程是唯一线程或者其他线程都在忙碌），在等待期间，当前线程会主动调用 `try_sort_chunk()` 从栈中弹出其他待处理块并尝试进行排序。`try_sort_chunk` 弹出分块并对其排序，将排序好的结果写入 promise，供最初提交该分块的线程拾取。

新派生的工作线程运行在一个循环中：只要 `end_of_data` 标志未被置位，就不断尝试从栈中取出分块并排序。在两次检查的间隙，它们调用 `std::this_thread::yield()` 让出 CPU 时间片，以便让其他线程有机会向栈中放入更多工作。该代码依靠 `sorter` 类的析构函数来妥善清理这些工作线程。当所有数据都完成排序后，`do_sort` 将返回（即便此时后台工作线程可能仍在运行），主线程将从 `parallel_quick_sort` 返回并销毁局部 `sorter` 对象。析构函数将 `end_of_data` 标志置为 `true`，并等待所有派生的工作线程执行 `join()`。置位该标志将终止工作线程中的循环。

采用这种设计方法，你不再会遇到无节制生成线程的资源耗尽风险，也不再依赖 C++ 线程库内部为你猜测合适的线程数量。相反，你将线程总数严格限制为 `std::thread::hardware_concurrency()` 的返回值，从而有效避免了过度频繁的上下文切换开销。然而，该方案引入了另一个潜在的挑战：这些线程的管理和相互之间的通信为代码带来了相当大的复杂度。此外，尽管各线程正在处理彼此独立的数据元素，但它们在向栈添加新分块以及从中取出分块时，都在频繁竞争访问同一个并发栈。这种高密度的争用（contention）可能会严重降低整体性能，即便你使用的是无锁（lock-free，即非阻塞）栈也是如此——其背后的底层原因我们稍后便会揭晓。

这种架构实质上是一种特定形态的**线程池（Thread Pool）**——即一组预先创建的工作线程，它们从待处理任务列表中获取任务、执行任务，然后返回列表中获取更多任务。关于线程池的潜在陷阱（包括工作列表上的争用）及其应对方案，将在第 9 章详细展开。多处理器架构下的扩展性难题也将在本章后文（第 8.2.1 节）深入剖析。

无论是在处理开始前划分数据，还是在执行过程中递归划分数据，它们都基于一个共同的前提假设：数据本身在处理前是静态给定的。但在现实场景中情况往往并非如此：如果数据是在运行时动态生成的，或者源源不断地来自外部输入（如网络或传感器），这些方法就无法直接奏效了。在这种情况下，按照**任务类型**来划分工作，往往比单纯依据数据来划分更为合理。

### 8.1.3 按任务类型划分工作

通过向每个线程分配不同的数据块来划分工作（无论是在预处理阶段还是在处理期间递归进行），其底层假设依然是：所有线程在各自的数据块上执行的是完全相同的操作。与之相反的替代方案是让各个线程成为“专才”，每个线程负责执行一项截然不同的特定任务，正如建造房屋时水管工和电工各司其职一样。线程可能会操作相同的数据，也可能操作不同的数据；但即便它们操作相同的数据，其目的与处理方式也各不相同。

这种工作划分方式正是利用并发来实现**关注点分离（separation of concerns）**的自然体现：每个线程拥有明确不同的职责，并独立于其他线程运行。偶尔，其他线程可能会向其传递数据或触发需要其处理的事件，但通常情况下，每个线程都全神贯注于做好属于自己的一件事。从软件工程角度来看，这本身就是优秀设计的基本准则：每段代码都应当具有单一的职责（Single Responsibility Principle）。

#### 按任务类型划分工作以实现关注点分离

单线程应用程序在面对单一职责原则时往往充满妥协：如果有多项任务需要在一段时间内持续运行，或者应用程序必须在处理繁重计算的同时及时响应传入事件（例如用户的按键点击或网络数据包的到达），单线程程序就不得不手动混杂各种控制流。在单线程的世界里，你最终不得不编写非常别扭的代码：先执行一小段任务 A，再执行一小段任务 B，然后检查是否有按键按下，再检查是否有网络数据包到达，然后循环回去继续执行一小段任务 A。这意味着任务 A 的核心逻辑被严重的样板代码所污染——它必须定期保存自身状态并将控制权交还给主事件循环。如果你向该循环中塞入了过多的任务，整体运行速度就会大幅下降，用户可能会明显感觉到界面对按键响应迟钝。相信每个人都见过这种极端情况：当某个程序开始执行某项耗时任务时，整个用户界面瞬间卡死（未响应），直到任务彻底完成才恢复。

这正是线程大显身手之处。如果你将每个任务放在单独的线程中运行，操作系统内核会为你妥善调度这一切。在任务 A 的代码中，你可以完全专注于执行任务本身的业务逻辑，根本无需担心保存执行状态、返回主循环或者两次返回之间耗时多久。操作系统会自动保存现场，并在适当时机将 CPU 调度给任务 B 或任务 C；如果运行目标机具有多个处理器或核心，任务 A 和任务 B 甚至能够真正并发并行运行。用于处理用户交互按键或网络数据包的代码也能够得到极其实时的调度响应。由此实现了双赢：用户获得了流畅敏捷的交互体验，而作为开发者的你也能拥有更加简洁清爽的代码，因为每个线程只需专注于执行与其核心职责直接相关的逻辑，而无需与复杂的控制流交织在一起。

这听起来十分美好。但在实际项目中真能如此顺利吗？与所有技术权衡一样，这取决于具体细节。如果各个任务之间完全独立，线程之间完全无需任何通信，那么事情确实如此简单。然而现实往往更为复杂：后台任务通常是响应用户请求而启动的，当其完成时，需要通过更新用户界面来告知用户结果；或者，用户可能希望在中途取消该任务，这要求用户界面能够向后台任务发送“停止”通知。这两种情况都需要仔细的设计考量与恰当的同步机制，但关注点分离的核心理念依然成立。UI 线程依然只负责处理用户界面，只是在收到其他线程请求时才去刷新控件；类似地，运行后台任务的线程依然专注于其算法步骤，只是其中增加了一项检查：“是否收到了其他线程发来的停止信号”。无论何种情况，线程都不需要关心请求的具体来源，只需确认该请求确实是针对自己的，并且直接属于自身职责范围即可。

通过多线程进行关注点分离存在两大严重的潜在危险：
1. **切分了错误的关注点**：其典型征兆是线程之间存在海量的共享数据，或者不同线程之间频繁发生相互等待；这两种情况归根结底都是由于**线程间通信过于频繁**造成的。如果出现这种情况，非常有必要仔细审视通信的根源。如果所有通信都围绕着同一件事，也许该事务本应属于单个线程的核心职责，应当从所有相关线程中剥离出来；或者，如果两个线程彼此之间通信极多，但与其他线程通信极少，也许它们本来就应当合并为同一个线程。
2. 当按任务类型在线程间划分工作时，并不局限于完全孤立的业务场景。如果多组输入数据需要按固定顺序依次应用一系列处理步骤，你可以通过构建流水线（pipeline）来切分工作，使每个线程分别执行整个处理流程中的某一个阶段。

#### 在线程间划分任务序列（流水线模型）

如果你的任务由一系列对大量独立数据项依次执行的处理步骤组成，你可以使用**流水线（pipeline）**架构来充分压榨系统的并发潜力。这在概念上与工业装配流水线完全一致：数据从一端流入，依次流经各个处理工位（管道阶段），最终从另一端流出。

为了以这种方式划分工作，你可以为流水线中的每个阶段分别创建一个独立的线程——每个线程对应处理序列中的一个操作。当某个阶段的操作完成后，该数据项会被放入一个线程安全队列中，由流水线中的下一个线程拾取。这使得负责第一个操作的线程在第二个线程处理第一个数据项的同时，可以立即开始对下一个数据项进行第一阶段的处理。

这是第 8.1.1 节介绍的数据划分模式的一种优秀替代方案，尤其适用于**输入数据无法预先全部获知**的场景。例如，数据可能通过网络连接流式传入，或者序列中的第一个操作是扫描文件系统以动态发现待处理的文件。

当序列中的每个操作都非常耗时时，流水线同样表现卓越；通过在线程间划分**任务阶段**而非划分数据块，你彻底改变了系统的性能剖析特征（performance profile）。假设你需要在 4 个核心上处理 20 个数据项，每个数据项需要经历 4 个连续步骤，每步耗时 3 秒。
- **数据划分模式**：如果将数据划分到 4 个线程，每个线程必须处理 5 个完整数据项。假定没有其他干扰，12 秒后系统将处理完 4 个数据项，24 秒后完成 8 个，以此类推，全部 20 个数据项将在 1 分钟后完成。
- **流水线模式**：4 个处理步骤分别分配给 4 个核心。第一个数据项必须依次通过这 4 个核心，因此它仍然需要整整 12 秒才能完成。事实上，在最初的 12 秒内系统仅输出了 1 个完成的数据项，初始产出慢于数据划分方式。但一旦流水线被充分填充（primed），后续的处理节拍将截然不同：第一个核心处理完第一个数据项后，立即开始处理第二个数据项；因此当最后一个核心完成第一个数据项的处理时，它可以立刻对第二个数据项执行最后一步。此时，系统**每隔 3 秒就能稳定产出 1 个处理完毕的数据项**，而不是像数据划分方式那样每隔 12 秒批量产出 4 个。

尽管处理完整个批次的总时间变长了（因为需要等待 9 秒流水线才完全排满），但在许多应用场景中，**平滑且稳定的输出速率**具有极高的价值。以高清数字视频播放系统为例：为了保证视频画面的流畅可读，通常至少需要每秒 25 帧（fps）的播放速率，甚至更高。此外，这些帧必须以均匀的时间间隔呈现在屏幕上，以营造连续运动的视觉效果；如果一个视频解码程序虽然宣称每秒能解码 100 帧，但其实际表现却是停顿卡顿 1 秒后瞬间刷出 100 帧，然后再卡顿 1 秒，那它根本毫无实用价值。相反，观众完全乐意在点击播放时容忍几秒钟的初始缓冲延迟。在这种情况下，采用流水线架构以匀速平滑地输出视频帧显然是绝佳的设计选择。

在讨论了线程间划分工作的各种核心技术之后，下面让我们深入探讨影响多线程系统性能的关键因素，以及它们如何影响我们对具体架构模式的选择。

---

## 8.2 影响并发代码性能的因素

如果你使用并发的目的是在多处理器硬件系统上显著提升代码的运行性能，那么你必须深刻理解究竟有哪些因素在主导着性能的表现。即使你引入多线程仅仅是为了分离关注点，也必须确保这样做不会对运行性能造成灾难性的反噬。试想一下，如果客户发现你的软件在他们刚买的全新 16 核高性能服务器上的运行速度，竟然比在淘汰的旧单核机器上还要慢，他们绝对无法接受。

正如我们即将看到的，影响多线程代码性能的因素错综复杂——甚至仅仅改变一下每个线程所处理的数据元素在内存中的排列（而其他代码逻辑完全保持一致），都可能对最终性能产生戏剧性的巨大影响。话不多说，让我们逐一剖析这些核心因素，首先从最显而易见的因素切入：你的目标硬件系统到底拥有多少个处理器？

---

### 8.2.1 处理器数量与硬件架构

处理器的数量及其拓扑结构是影响多线程应用程序性能的首要且最关键的因素。在某些特定领域（如嵌入式开发或专用计算集群），你对目标硬件的规格了如指掌，可以在确切的硬件环境下进行设计、基准测试与精细调优。如果属于这种情况，那你非常幸运；但对于绝大多数通用软件开发而言，开发者根本没有这种奢侈的条件。你可能在一台特定的机器上进行开发，但用户的硬件配置可能千差万别：你可能在双核或四核机器上开发，而用户的机器可能配备了单颗多核处理器（核心数量任意）、多颗单核处理器，甚至多颗多核处理器（NUMA 架构）。并发程序在这些不同的硬件拓扑下的运行行为和性能表现差异巨大，因此你必须深入思考潜在的影响，并在尽可能多的不同硬件配置上进行严密测试。

从最粗略的抽象角度来看，单颗 16 核处理器、4 颗四核处理器或 16 颗单核处理器在算力上是等价的：在任何时刻，系统都可以同时并发执行 16 个物理硬件线程。如果你希望充分利用这台机器的算力，你的应用程序必须具备至少 16 个能够独立运行的并发任务。如果少于 16 个线程，你就白白浪费了宝贵的处理器算力（除非系统同时还在运行其他重负载应用，但我们暂且忽略这种情况）。然而另一方面，如果系统中有超过 16 个处于**就绪态**（ready to run，即没有阻塞在等待 I/O 或锁等事件上）的线程，应用程序就会因为操作系统在不同线程之间频繁进行上下文切换而耗费大量的 CPU 周期，正如第 1 章所述。当这种现象发生时，该状态被称为**过度订阅（oversubscription）**。

为了使应用程序能够根据底层硬件能够并发执行的物理线程数量来自适应地伸缩线程规模，C++11 标准线程库提供了 `std::thread::hardware_concurrency()`。你之前已经看到如何利用它来使线程数量与物理硬件规模相匹配。

直接使用 `std::thread::hardware_concurrency()` 时必须格外谨慎：你的代码本身并不知晓系统上当前正在并发运行的其他线程情况，除非你显式进行跨进程协调。在最恶劣的情形下，如果多个线程在同一时刻同时调用了一个使用 `std::thread::hardware_concurrency()` 进行线程扩展的函数，系统将会瞬间陷入极其严重的过度订阅状态。`std::async()` 可以在一定程度上规避此问题，因为标准库运行时知晓所有 `async` 调用的状态，并能够统一进行合理的并发调度；此外，精心设计的全局线程池也是避免该问题的强力手段。

然而，即使你统计了自身应用程序内的所有线程，仍然会受到宿主操作系统上同时运行的其他应用程序的影响。尽管在单用户桌面系统上同时运行多个 CPU 密集型应用的情况较少，但在高性能计算或云原生服务环境中却非常普遍。专门针对这种场景设计的操作系统通常提供了一定机制，允许每个进程声明或协商适当的线程配额（尽管这些机制已超出了 C++ 标准的定义范畴）。一种解决方案是由类似 `std::async()` 的运行时设施在决定派生线程数时，将所有应用当前的异步任务总数纳入考量；另一种方案是由操作系统直接限制特定应用程序可以绑定的 CPU 核心数。在这种平台上，我们期望 `std::thread::hardware_concurrency()` 返回的数值能够真实反映该配额限制，尽管标准并未对此做出绝对保证。如果你的应用需要部署在类似环境中，建议查阅特定系统的官方技术文档。

该场景下还有一个额外的微妙之处：解决特定问题的“最佳算法”往往取决于**问题本身的规模相对于物理处理器数量的比例**。如果你面对的是一个拥有成千上万个处理单元的超大规模并行计算架构（Massively Parallel System），一个总计算操作数更多、但每个处理器分担的操作数极少的并行算法，其整体执行耗时反而可能远远低于一个在理论上总操作数更少、但并行度受限的算法。

随着系统中处理器核心数量的增加，另一个极其致命的性能瓶颈爆发的概率及其对性能的负面冲击也急剧攀升：那就是多个处理器试图同时访问相同的数据。

---

### 8.2.2 数据争用与缓存乒乓

如果两个线程在不同的物理处理器核心上并发执行，且它们都仅仅是**并发读取**相同的数据，这通常不会引起任何性能问题；该数据会被复制加载到各自核心的独立硬件高速缓存（L1/L2 Cache）中，两个核心都可以全速并行运行。然而，一旦其中一个线程**修改**了这块数据，该修改就必须通过底层的缓存一致性协议（Cache Coherence Protocol，如 MESI/MOESI）同步传播到另一个核心的缓存中，这需要耗费物理时钟周期。根据两个线程操作的具体性质以及所使用的内存顺序（Memory Ordering），这种修改可能会导致第二个处理器的执行流水线发生强制停顿（stall），不得不等待缓存行无效化并重新从内存子系统中拉取最新的数据。在 CPU 机器指令的尺度下，这种缓存同步可能慢得令人发指，其延迟相当于数百条独立的计算指令，具体的延迟代价主要取决于处理器的物理互连拓扑。

考虑下面这段极简的代码：

```cpp
std::atomic<unsigned long> counter(0);
void processing_loop()
{
    while(counter.fetch_add(1,std::memory_order_relaxed)<100000000)
    {
        do_something();
    }
}
```

这里的 `counter` 是一个全局原子变量，因此任何调用 `processing_loop()` 的线程都在修改同一个内存位置。对于每一次 `fetch_add` 自增操作，当前处理器必须确保其本地缓存中拥有该 `counter` 的最新有效副本，修改其值，并向其他处理器广播该失效/更新信息。尽管你在此处使用了最宽松的 `std::memory_order_relaxed` 使得编译器和硬件无需同步任何其他辅助数据，但 `fetch_add` 是一个典型的“读-改-写（Read-Modify-Write, RMW）”原子操作，必须取得该变量在全局修改顺序中的最新值。如果另一个核心上的线程也在并发运行相同的代码，`counter` 所在的缓存行就必须在这两个处理器的本地高速缓存之间频繁地来回穿梭传递，以确保每个处理器在执行自增时都能看到最新值。如果 `do_something()` 本身的执行时间极短，或者运行此循环的核心数量过多，处理器之间就会陷入无休止的相互等待：一个处理器正准备更新值，但另一个处理器恰好正在更新，导致前者必须停顿流水线，直到后者的修改完成并且缓存一致性同步彻底就绪。这种状态被称为**高争用（high contention）**；反之，如果各处理器很少需要彼此停顿等待，则被称为**低争用（low contention）**。

在这样一个紧凑的循环中，`counter` 对应的数据行在多个核心的私有缓存之间以极高的频率来回“弹跳”。这种灾难性的性能杀手被称为**缓存乒乓（cache ping-pong）**，它会对整个系统的吞吐量造成毁灭性的沉重打击。当处理器因为等待缓存传输而陷入流水线停顿时，它在此期间完全无法进行任何有意义的计算，哪怕系统中有其他就绪线程可以运行也是如此，这对整个软件系统的运行构成了巨大的性能浪费。

你可能会暗自庆幸：我的代码里从来没有写过类似的全局原子自增循环，这应该不会发生在我身上吧？千万不要盲目乐观！互斥锁（Mutex）又当如何？如果你在某个循环内部获取互斥锁，从底层数据访问的角度来看，你的代码与上述代码毫无二致！为了成功锁定互斥锁，调用线程所在的处理器必须将构成该互斥锁的内部状态数据加载到其私有缓存并进行原子修改；当它完成临界区操作后，又必须再次修改互斥锁状态以将其释放（解锁）；随后，互斥锁的数据又必须完整传输到下一个试图获取该锁的线程所在的处理器的缓存中。这种硬件级的缓存行传输开销，完全是**叠加**在第二个线程等待第一个线程释放锁的逻辑等待时间之上的：

```cpp
std::mutex m;
my_data data;
void processing_loop_with_mutex()
{
    while(true)
    {
        std::lock_guard<std::mutex> lk(m);
        if(done_processing(data)) break;
    }
}
```

最残酷的现实在于：如果数据和互斥锁被多个线程共享访问，那么**随着你向系统中添加越来越多的处理器核心，发生高争用以及处理器相互等待的概率将呈现爆炸式增长**！如果你试图利用更多线程来更快地处理相同的数据，这些线程势必会在底层为了争取相同的数据而激烈竞争同一个互斥锁。工作线程数量越多，它们在同一微秒内尝试抢夺互斥锁或并发访问原子变量的概率就越高。

互斥锁的争用效应通常与原子变量的争用效应略有不同，其原因在于：互斥锁的竞争通常会在**操作系统层面**将未争抢到锁的线程挂起（suspend/block）并进行序列化调度，而不是仅仅在处理器流水线级别忙等停顿。如果系统中存在足够多的就绪线程，当某个线程因等待互斥锁被挂起时，操作系统调度器可以调度另一个线程进入该 CPU 执行；而处理器硬件级的缓存停顿则会直接冻结整个物理流水线。但无论如何，互斥锁的争用依然会直接压垮那些竞争该锁的线程的性能——无论你有多少核，临界区终究在同一时刻只能串行运行一个线程。

回顾第 3 章，你曾学习过如何使用“单写多读”共享互斥锁（`std::shared_mutex`，见第 3.3.2 节）来保护极少发生修改的数据结构。然而，在不友好的工作负载下，缓存乒乓效应甚至会**彻底抹杀读写锁带来的所有并发红利**！因为所有并发访问该数据的线程（即便是纯粹的读线程）在加共享锁时，依然必须在底层原子地修改互斥锁自身的读者计数状态。随着并发读取的处理器数量大幅增加，对互斥锁内存位置本身的争用急剧恶化，包含互斥锁的缓存行必须在各个核心之间频繁转移同步，导致获取与释放锁的开销暴增至不可接受的地步。尽管存在通过将互斥锁状态分散在多个独立缓存行来缓解此问题的进阶技术，但除非你自己编写特定的读写锁，否则你只能受制于宿主操作系统和标准库提供的默认实现。

既然缓存乒乓危害如此巨大，我们究竟该如何避免它？正如本章后文将展示的，其解决方案与提升并发潜力的核心设计指南高度契合：**穷尽一切可能，消除或最小化两个不同线程竞争访问同一个内存位置的概率**。

然而，现实往往比理想更为残酷。即便你已经做到了极致，让某个内存位置自始至终只被单个特定线程独占访问，你依然可能会遭遇致命的缓存乒乓！导致这一离奇现象的元凶，就是臭名昭著的**伪共享（False Sharing）**。

---

### 8.2.3 伪共享（False Sharing）

现代处理器的硬件高速缓存并非以单个独立字节或单一内存变量为单位进行管理；相反，它们以**缓存行（Cache Line）**为基本块单位进行数据传输与一致性跟踪。在当今主流的 x86/ARM 架构处理器中，典型的缓存行大小为 32 或 64 字节（通常为 64 字节）。因为缓存硬件完全以固定大小的缓存行块为最小单位进行交互，所以位于相邻物理内存地址上的几个较小的数据项，必然会被打包存放在同一条缓存行中。

在某些情况下，这是一件好事：如果某个线程需要频繁访问的一组数据全都紧密排列在同一条缓存行内，其运行性能将极为出色，因为单次内存加载就同时将所需的数据全部预取到了私有高速缓存中。然而，如果位于同一缓存行内的若干数据项**在业务上彼此毫无关联**，但却需要被**不同的线程**分别高频并发访问和修改，这就会演变成灾难性的性能噩梦。

假设你分配了一个简单的 `int` 数组，并创建了一组工作线程，每个线程只负责循环读写并更新数组中属于自己的那一个元素。由于一个 `int` 通常只有 4 字节，远小于 64 字节的缓存行容量，因此数组中相邻的十几个元素将不可避免地物理挤在同一条缓存行内。结果就是：尽管每个线程在业务逻辑上只独立访问自己的专属元素，底层硬件的缓存一致性控制器却必须在各个核心之间疯狂地展开**缓存乒乓球赛**！每当负责元素 0 的线程需要更新数值时，该整条缓存行的独占所有权就必须强行迁移至运行该线程的 CPU 核心缓存；而紧接着，当负责元素 1 的线程需要更新其数据时，整条缓存行又被迫立即被抢夺迁移至第二个核心的私有缓存。**这条缓存行在物理上被强行共享了，尽管在软件语义上没有任何数据是真正共享的**——这正是**伪共享（False Sharing）**这一术语的由来。

解决伪共享的根本方案是：**精心重构数据结构的内存布局，使得由同一个线程访问的数据项在内存中紧密排列（更有可能落在同一缓存行内），而需要被不同线程分别并发访问的数据项在内存地址上被拉开足够遥远的物理距离，确保它们必定落在完全独立的缓存行中**。在 C++17 标准中，头文件 `<new>` 中正式定义了常量：
- `std::hardware_destructive_interference_size`：表示当前编译目标架构下可能受伪共享影响的最大连续字节数。只要你确保由不同线程并发修改的数据成员在内存中的物理间距至少达到该字节数（通常为 64 字节），就能从硬件层面上彻底杜绝伪共享的发生。

既然多线程同时访问同一缓存行内的数据如此有害，那么单个线程自身所访问的数据在内存中的布局方式又会对性能产生怎样的影响呢？

---

### 8.2.4 数据距离有多近？（数据邻近性）

伪共享是由于不同线程所访问的数据在物理内存中“靠得太近”引起的；而与数据内存布局相关的另一个严重陷阱，则会直接重创单个线程自身的纯计算性能。这个问题就是**数据邻近性（Data Proximity）**：如果单个线程需要密集处理的数据散乱地分布在内存各处，它们几乎必然会跨越大量不同的缓存行。相反，如果该线程所需的数据在内存中彼此紧挨着连续存放，它们就更有可能紧凑地挤在同一个缓存行中。显而易见，若数据过于分散，处理器就必须从缓慢的物理主存中向高速缓存加载数量庞大的不同缓存行，这不仅大幅拉长了内存访问的硬件延迟，更会导致有效计算性能的断崖式下滑。

此外，如果数据布局零散分布，包含当前线程所需数据的某个缓存行中，很可能充斥着大量对当前计算完全无用的无关垃圾数据。在极端情况下，私有缓存中充斥的绝大多数数据都是当前线程根本不需要的。这极大地浪费了珍贵的高速缓存空间，急剧增加了处理器发生**缓存缺失（Cache Miss）**的概率——处理器不得不频繁将有用的缓存行逐出（evict）以腾出空间加载新的行，甚至导致原本刚刚读取过的数据因为容量不足被反复换入换出。

你可能会问：这显然是传统单线程性能优化的老生常谈，为什么要在讨论并发设计的章节重点强调？其核心根源在于：**任务切换（Task Switching / 上下文切换）**。如果系统中的线程数量多于可用的物理核心数，每个物理核心就必须在多个线程之间来回时间片轮转。为了避免伪共享，你费尽心思确保不同线程访问不同的缓存行；然而，当操作系统在同一个核心上强制进行线程切换时，如果每个线程的工作集数据都零散地分布在大量缓存行上，该核心的硬件缓存就更容易被迅速冲刷污染，处理器不得不耗费漫长的时钟周期从头重新加载新线程的所有缓存行。

为此，C++17 标准在 `<new>` 头文件中还引入了另一个相伴的常量：
- `std::hardware_constructive_interference_size`：表示在满足适当对齐的前提下，保证落在同一缓存行内的最大连续字节数。如果你能将单线程紧密协同处理的数据项严格压缩在此字节限制之内，将能够在最大程度上削减缓存缺失率，显著提升局部性性能。

更严重的是，如果就绪线程数量庞大，操作系统调度器可能会在第 1 个时间片将线程 A 调度在核心 1 上运行，而在第 2 个时间片将其调度到核心 2 上运行。这就需要将维护该线程上下文的所有缓存行从核心 1 的私有缓存完整搬迁传输至核心 2 的私有缓存；需要搬迁的缓存行越多，线程迁移的代价就越昂贵。尽管现代操作系统的调度器（如 Linux CFS 的 CPU 亲和性机制）会竭尽全力避免这种跨核迁移，但这在多任务高负载环境下依然屡见不鲜，并会对系统性能产生切实可见的负面影响。

当大量线程处于“就绪可运行”状态而非“阻塞等待”状态时，任务切换带来的性能损耗将达到巅峰。这便引出了我们此前谈及的关键瓶颈：过度订阅。

---

### 8.2.5 过度订阅与频繁任务切换

在多线程系统中，线程总数多于物理处理器核心数是非常普遍且正常的现象，除非你运行在专用的大规模并行机上。因为在绝大多数实际业务中，线程有相当多的时间是处于被动等待中的：等待磁盘或网络 I/O 完成、阻塞在互斥锁上、等待条件变量被唤醒、处于休眠状态等等。在这些场景下，维持适量多余的线程对系统是有益的：它使得处理器可以在某个线程等待时无缝切换去执行其他具备计算就绪态的线程，从而避免硬件核心处于空转闲置状态。

然而，凡事过犹不及。如果系统中多余的线程数量泛滥成灾，使得处于**就绪态**的线程数远远超出了系统可用的物理核心承载能力，操作系统的内核调度器就不得不频繁介入，以极高的频率进行强制时间片上下文切换，以确保每个线程都能分得一杯羹。正如在第 1 章中所述，这不仅带来了保存和恢复寄存器、刷新硬件流水线的直接 CPU 上下文切换开销，更会彻底击穿 CPU 高速缓存的局部性（局部缓存被无情覆盖冲刷，加剧了数据距离拉长导致的性能损耗）。过度订阅的产生通常有两种典型根源：一种是任务在执行过程中无节制地盲目生成新线程（例如第 4 章中未经节制的递归快速排序）；另一种则是在按任务类型切分系统时，人为定义的并发线程数远大于物理核数，且这些任务在本质上全都是计算密集型（CPU-bound）而非 I/O 密集型。

如果过度订阅是因为**数据划分**不当导致的线程暴增，你可以通过设置工作线程数上限来轻松解决（正如我们在第 8.1.2 节中所做的那样）。但如果过度订阅源自于业务本身的**固有任务划分**，除了重新审视并推翻现有的任务拆分架构之外，往往没有太好的灵丹妙药。此时，选择更为合适的任务划分策略需要你对目标运行平台的硬件拓扑具备极深入的了解；而且只有在性能确实无法达到基准要求，且经过实际性能剖析（profiling）确凿证明调整任务划分确实能带来收益时，才值得进行这种重构。

当然，还有许多其他物理层面的因素会深刻影响多线程代码的性能。例如，两颗独立的单核物理 CPU 之间的缓存乒乓硬件开销，通常远远大于单颗集成双核 CPU 内部的缓存乒乓开销（因为后者往往共享高速 L2/L3 缓存与片上互连总线），即便它们的 CPU 型号和主频完全一致。但上述提及的诸项要素，绝对是决定系统吞吐量生死存亡的核心命门。

接下来，我们将探讨这些底层硬件因素如何直接指引并重塑我们的并发代码与数据结构设计。

---

## 8.3 为多线程性能设计数据结构

在第 8.1 节中我们剖析了在线程间划分工作的各种模式，在第 8.2 节中我们揭示了影响并发性能的关键底层硬件要素。那么，在面对具体工程问题时，我们该如何将这些理论知识转化为行之有效的**高性能并发数据结构设计**？

请注意，这与第 6 章和第 7 章所讨论的主题截然不同：那两章的核心聚焦点在于**并发正确性与安全性**（确保多线程在并发读写数据结构时不会引发数据竞争或破坏不变量）。而正如你在第 8.2 节中所看到的，即使某块内存数据自始至终只被单线程所访问、完全没有被其他线程共享，其物理内存布局依然会对整体性能产生决定性的影响。

在为多线程高性能设计数据结构时，必须时刻铭记在心的三大黄金法则就是：**减少争用（Contention）、杜绝伪共享（False Sharing）、优化数据邻近性（Data Proximity）**。这三者中的任何一项失控，都会对系统吞吐量造成灾难性打击。通常，你可以通过巧妙调整内存布局、对齐方式，或者改变具体数据项向线程的分配映射方式，来取得脱胎换骨的性能飞跃。首先，让我们从一个最具代表性的典型场景入手：在多线程间切分用于密集计算的连续数组元素。

---

### 8.3.1 为复杂操作划分数组元素

假设你正在编写高性能科学计算或图形渲染核心，需要将两个庞大的大型方阵进行矩阵乘法运算。回顾矩阵乘法的定义：将第一个矩阵第 $i$ 行的各个元素，与第二个矩阵第 $j$ 列的对应元素依次相乘并累加，其和即为结果矩阵第 $i$ 行第 $j$ 列的元素值。接着用第一行的各个元素与第二列的元素相乘累加得到第 1 行第 2 列的结果……以此类推。如图 8.3 所示，第一矩阵的第 2 行与第二矩阵的第 3 列配对，计算出结果矩阵第 2 行第 3 列的值。

```
[ a1,1  a1,2  a1,3  ...  a1,m ]   [ b1,1  b1,2  b1,3  ...  b1,k ]   [ c1,1  c1,2  c1,3  ...  c1,k ]
[ a2,1  a2,2  a2,3  ...  a2,m ] * [ b2,1  b2,2  b2,3  ...  b2,k ] = [ c2,1  c2,2  c2,3  ...  c2,k ]
[ ...   ...   ...   ...  ...  ]   [ ...   ...   ...   ...  ...  ]   [ ...   ...   ...   ...  ...  ]
[ an,1  an,2  an,3  ...  an,m ]   [ bm,1  bm,2  bm,3  ...  bm,k ]   [ cn,1  cn,2  cn,3  ...  cn,k ]

图 8.3 矩阵乘法示意图
```

现在假设这两个大矩阵规模庞大，各自拥有数千行和数千列，足以值得我们投入多线程并发来进行极致优化。在现代计算机体系中，非稀疏矩阵在内存中通常由一个巨大且连续的一维扁平数组来表示（行主序存储）：第一行的所有元素紧密相连，接着是第二行的所有元素，依此类推。为了完成乘法，你在内存中拥有三个这样的庞大数组。为了获取极限性能，你必须极度细致地审视内存访问模式（Access Patterns），尤其是对**第三个结果数组的高频写入操作**。

在工作线程之间切分该计算任务有许多种策略。假设可用核心数小于矩阵行/列数，常见的划分策略包括：
1. 让每个线程负责计算结果矩阵中的若干**列**；
2. 让每个线程负责计算结果矩阵中的若干**行**；
3. 让每个线程负责计算结果矩阵中的一个**矩形子块（Block）**。

回顾第 8.2.3 节和第 8.2.4 节的结论：**连续且紧凑地访问数组元素远优于在内存中跳跃式离散访问**，因为这能最大化缓存命中率，并将伪共享发生的几率降至冰点。

- **按列划分**：如果让每个线程计算结果矩阵的一组特定列，该线程必须完整遍历读取第一个输入矩阵的所有行，并读取第二个矩阵对应列的值，然后将结果写入结果矩阵的目标列。由于矩阵是按行连续存储的，这意味着该线程在结果数组中每隔一行才写入一个元素（写入第 1 行的第 $N$ 列、第 2 行的第 $N$ 列……）。而其他并发线程则在同时写入同一行的其他相邻列！由于同一行的多个相邻列元素在物理内存上挤在同一个缓存行中，**按列划分将导致各个核心在结果数组的同一缓存行上频繁发生灾难性的伪共享和缓存乒乓**！
- **按行划分**：如果让每个线程计算结果矩阵的一组特定行（比如分配连续的 $N$ 行），情况立刻发生质的逆转。由于矩阵在内存中是以行主序连续排布的，该线程在内存中写入的是一段长达 $N$ 行的绝对连续的物理内存空间。**在这个连续内存块内，除了首尾边缘可能与其他线程的行发生极小概率的跨缓存行重叠之外，该线程拥有对该整片缓存行集合的绝对独占写入权，根本不会受到任何其他线程的干扰**！这在写入端彻底消除了伪共享。
- **按矩形子块划分（Block Tiling）**：这种方法将大矩阵划分为 $M \times M$ 的小方块，每个线程独立计算一个小方块的结果。从写入端来看，只要仔细选取子块的宽度使其为缓存行大小的整数倍，同样可以完全避免伪共享。更重要的是，**矩形分块在“读取端”展现出了无与伦比的压倒性优势**！
  - 让我们通过一组真实的具体数字来直观感受这一差距：假设进行 $1000 \times 1000$ 规模的双精度矩阵相乘（每个矩阵包含 100 万个元素）。假设我们有 100 个计算核心。
  - **纯按行划分**：每个核心分配 10 行（共需计算 10,000 个结果元素）。为了计算这 10,000 个元素，每个核心必须完整读取第二个矩阵的全部 100 万个元素，外加第一个矩阵对应 10 行的 10,000 个元素——**单核心总计必须从内存中读取 1,010,000 个元素**！
  - **按矩形块划分**：每个核心分配一个 $100 \times 100$ 的矩形块（同样总计包含 10,000 个结果元素）。为了计算这 10,000 个元素，该核心只需读取第一个矩阵对应的 100 行（$100 \times 1000 = 100,000$ 个元素）以及第二个矩阵对应的 100 列（另 100,000 个元素）——**单核心总计仅需读取 200,000 个元素**！
  - 仅仅通过调整任务划分的几何形态，**内存读取总量直接被削减了整整 5 倍以上**！大幅缩减的内存读取量意味着 CPU 私有缓存能够完美容纳当前运算所需的全部数据，缓存缺失被彻底扼杀，进而激发出无可比拟的超高性能。

因此，将结果矩阵切分为小型的正方形或近似正方形的矩形计算块，其性能往往大幅优于单纯按行或按列硬切。你可以根据运行时矩阵的实际维度以及当前可用的处理器核心数，自适应地调整子块的大小。一如既往，若性能至关重要，必须在目标硬件架构上对各种方案进行严格的基准剖析（Benchmark Profiling）。

你可能会想：我的日常业务代码并非矩阵运算，这对我有什么参考价值？**完全相同的设计哲学适用于任何存在大块连续数据需要在多线程间切分的场景**：请极度严谨地审视数据的具体读取与写入流向，精准揪出潜在的伪共享与缓存击穿诱因。在你的业务领域中，往往只需调整一下任务划分在内存层面的映射逻辑，无需对业务算法本身伤筋动骨，就能换来成倍的性能飙升。

---

### 8.3.2 其他数据结构中的数据访问模式

在优化其他非数组形态的数据结构（如树、图、哈希表等）的数据访问模式时，底层的设计考量与数组优化完全一脉相承：
1. **尽可能调整线程间的数据分布，使物理内存上彼此相邻的数据由同一个线程集中处理。**
2. **尽可能削减并最小化任何单个线程在单次计算中所必须触及的数据总量。**
3. **确保由不同线程并发高频读写的数据在内存物理地址上被拉开足够遥远的间距，以 `std::hardware_destructive_interference_size` 为基准彻底隔绝伪共享。**

然而，在面对复杂指针型数据结构时，践行这些准则绝非易事。以二叉树为例：二叉树在逻辑上很难被平滑切割，除非以子树为单位进行划分；而子树划分的有效性完全取决于该树的平衡程度以及你需要切分的并发份数。更要命的是，由于二叉树节点通常是在堆（heap）上动态逐个分配的，它们在物理内存地址空间中往往极度零散离散。

当然，数据在堆上零散分布本身并非完全是一无是处的坏事：有时它能够天然形成物理屏障。例如，如果多个线程都需要遍历同一棵树，但树的节点本身仅仅存放指向实际业务数据的指针，那么处理器只有在确实需要访问该节点时才会从主存去抓取具体数据。如果业务数据正在被特定线程修改，这种指针间接引用反而能避免树拓扑结构指针与实际业务数据之间的伪共享。

在由互斥锁保护的数据结构中，同样存在着极其微妙的内存布局博弈。假设你设计了一个小巧的 C++ 类，内部包含几个业务数据成员和一个用于同步保护的 `std::mutex`。如果将互斥锁与被保护的数据在结构体内紧挨着放置，这对于**成功获取到锁的线程**来说体验极佳：因为在它执行锁指令将互斥锁加载到 CPU 缓存的同时，紧邻的业务数据往往也搭便车被一并加载到了同一缓存行中，随后的业务访问将百分之百缓存命中。

但这种设计存在着致命的负面暗礁：**如果其他并发线程在锁被持有的期间尝试去获取该锁，它们就必须强制并发读写该互斥锁所在的内存位置**！互斥锁的加锁操作通常被底层实现为一个原子“读-改-写”指令（以测试并设置锁标志），随后若失败则陷入内核。**该原子指令会导致持有锁的那个核心上的对应缓存行瞬间被硬件强制失效（Invalidate）**！对于互斥锁自身而言这无关紧要，因为持有者在临界区内不需要访问锁变量；但如果该互斥锁与正被持有者激烈读写的业务数据挤在同一个缓存行内，**持有锁的线程在执行业务计算时将遭遇莫名其妙的硬件缓存停顿——仅仅是因为外面的某个旁观线程尝试去抢锁**！

为了验证你的系统是否存在这种极其隐蔽的伪共享瓶颈，一种绝佳的诊断手段就是在可能被并发访问的数据元素之间强行插入巨大的**填充字节块（Padding）**。例如：

```cpp
struct protected_data
{
    std::mutex m;
    char padding[std::hardware_destructive_interference_size];
    my_data data_to_protect;
};
```

如果你的编译器尚未完全支持 `std::hardware_destructive_interference_size`，你可以临时硬编码一个足够夸张的填充大小（例如 65536 字节，这绝对比任何物理缓存行大上几个数量级）：

```cpp
struct my_data
{
    data_item1 d1;
    data_item2 d2;
    char padding[std::hardware_destructive_interference_size];
};
my_data some_array[256];
```

利用这种填充手段对数组或受保护数据进行 A/B 基准压测：**如果插入巨额填充后系统的并发吞吐量出现了显著暴涨，你便能百分之百断定此前存在严重的伪共享问题**！随后，你可以在生产代码中保留精细计算的对齐填充（如 `alignas`），或者通过重构算法流程彻底消除多线程争用。

除了数据访问模式与内存布局，设计并发软件时还有若干更为宏观的核心要素必须考量，让我们继续深入探讨。

## 8.4 设计并发代码时的其他考量

到目前为止，我们探讨了线程间工作划分的技术、影响性能的硬件机制，以及如何为多线程性能定制内存布局。然而，优秀的并发设计绝不仅限于吞吐量与耗时。你还必须将**异常安全性（Exception Safety）**与**可扩展性（Scalability）**作为不可逾越的设计红线。

代码被称为具有**良好的可扩展性（Scalable）**，是指随着宿主硬件系统中处理器核心数量的增加，系统的整体性能（表现为任务执行耗时的成比例缩短，或单位时间内吞吐量的成比例攀升）能够持续线性或近线性地上升。理想情况下，在 100 核机器上的性能应当是单核机器的 100 倍。

单线程代码尽管毫无可扩展性可言，但它至少能够保持逻辑正确；而**异常安全性则是关乎程序生死存亡的绝对正确性问题**。如果多线程并发代码缺乏异常安全设计，轻则导致共享数据的不变量被撕裂破坏、产生难以复现的数据竞争死锁，重则因为某个工作线程抛出未捕获异常而导致整个进程被操作系统直接闪退崩溃（Crash）。因此，让我们首先从异常安全这一基石切入。

---

### 8.4.1 并行算法中的异常安全

异常安全性是高质量现代 C++ 代码的核心标尺，而在并发编程的世界里，对异常的处理要求甚至比普通的顺序代码更为严苛。在普通的单线程顺序算法中，如果某个操作抛出了异常，算法通常只需确保自身利用 RAII 妥善清理了局部资源并恢复了数据不变量即可，它完全可以任由该异常自由向上传播到调用栈顶层由上层捕获处理。

但在并行算法中，核心计算是在**不同的物理线程**上异步展开的。在这种情况下，**绝不允许异常像在普通调用栈中那样自由向上传播——因为此时的调用栈已经完全脱离了主调方**！在 C++ 线程模型中，如果在一个派生线程顶层执行的函数因抛出未捕获异常而退出，C++ 运行时环境将毫不犹豫地直接调用 `std::terminate()`，强行杀死整个应用程序进程！

为了直观体会这一点，让我们重新审视清单 2.9 中那个朴素的 `parallel_accumulate` 实现（如下清单 8.2 所示）：

#### 清单 8.2 朴素的并行版 `std::accumulate`（源自清单 2.9）

```cpp
template<typename Iterator,typename T>
struct accumulate_block
{
    void operator()(Iterator first,Iterator last,T& result)
    {
        result=std::accumulate(first,last,result);
    }
};

template<typename Iterator,typename T>
T parallel_accumulate(Iterator first,Iterator last,T init)
{
    unsigned long const length=std::distance(first,last);
    if(!length)
        return init;
    unsigned long const min_per_thread=25;
    unsigned long const max_threads=
        (length+min_per_thread-1)/min_per_thread;
    unsigned long const hardware_threads=
        std::thread::hardware_concurrency();
    unsigned long const num_threads=
        std::min(hardware_threads!=0?hardware_threads:2,max_threads);
    unsigned long const block_size=length/num_threads;
    std::vector<T> results(num_threads);
    std::vector<std::thread>  threads(num_threads-1);
    Iterator block_start=first;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        Iterator block_end=block_start;
        std::advance(block_end,block_size);
        threads[i]=std::thread(
            accumulate_block<Iterator,T>(),
            block_start,block_end,std::ref(results[i]));
        block_start=block_end;
    }
    accumulate_block<Iterator,T>()(
        block_start,last,results[num_threads-1]);
    std::for_each(threads.begin(),threads.end(),
        std::mem_fn(&std::thread::join));
    return std::accumulate(results.begin(),results.end(),init);
}
```

现在让我们化身审查员，彻底排查其中所有可能抛出异常的致命断点：
1. `std::distance(first,last)`：在用户自定义迭代器上操作。由于此时尚未执行任何工作，且仍在主调线程上，即使抛出异常也完全安全。
2. `results` 和 `threads` 的动态内存分配：同样仍在主调线程上，此时尚未启动任何子线程；如果内存耗尽抛出 `std::bad_alloc`，局部变量会自动调用析构函数析构，完全安全。
3. **线程创建循环内部**：灾难从这里开始！一旦在循环中成功创建了第一个 `std::thread` 对象，如果后续迭代在创建后续线程时抛出了异常（例如操作系统线程资源耗尽），或者迭代器推进发生异常，由于没有任何异常捕获与 RAII 保护，栈展开（stack unwinding）将直接触发此前已创建的处于可结合状态（joinable）的 `std::thread` 对象的析构函数，而根据 C++ 标准，**析构一个尚未 `join()` 或 `detach()` 的 joinable 线程将直接触发 `std::terminate()` 杀死进程**！
4. `accumulate_block` 在主线程上的直接调用：如果它抛出异常，所有正在后台运行的子线程都将处于未 `join()` 状态，析构时同样瞬间触发 `std::terminate()`！
5. **工作子线程内部**：如果传递给 `accumulate_block` 的迭代器解引用或累加操作抛出了异常，由于子线程顶层没有任何 `try-catch` 块包裹，该异常将逃逸出线程入口函数，导致 C++ 运行时立即调用 `std::terminate()` 摧毁整个程序！

显而易见，这段代码完全处于极其危险的**异常不安全**状态。

#### 实现真正的异常安全性

既然找出了所有可能的抛异常断点与致命后果，我们该如何彻底治理？让我们首先解决子线程中抛出异常的问题。

我们在第 4 章中早已掌握了应对这一痛点的强大利器：`std::packaged_task` 与 `std::future`。细想一下我们的诉求：我们需要在子线程上计算出结果并回传给主线程，同时如果子线程在执行过程中发生异常，我们希望将该异常妥善捕获并无缝打包传递回主线程重新抛出。这正是 `std::packaged_task` 与 `std::future` 组合的拿手好戏！

重构后的代码如下清单 8.3 所示：

#### 清单 8.3 使用 `std::packaged_task` 实现的并行累加算法

```cpp
template<typename Iterator,typename T>
struct accumulate_block
{
    T operator()(Iterator first,Iterator last)
    {
        return std::accumulate(first,last,T());
    }
};

template<typename Iterator,typename T>
T parallel_accumulate(Iterator first,Iterator last,T init)
{
    unsigned long const length=std::distance(first,last);
    if(!length)
        return init;
    unsigned long const min_per_thread=25;
    unsigned long const max_threads=
        (length+min_per_thread-1)/min_per_thread;
    unsigned long const hardware_threads=
        std::thread::hardware_concurrency();
    unsigned long const num_threads=
        std::min(hardware_threads!=0?hardware_threads:2,max_threads);
    unsigned long const block_size=length/num_threads;
    std::vector<std::future<T> > futures(num_threads-1);
    std::vector<std::thread> threads(num_threads-1);
    Iterator block_start=first;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        Iterator block_end=block_start;
        std::advance(block_end,block_size);
        std::packaged_task<T(Iterator,Iterator)> task(
            accumulate_block<Iterator,T>());
        futures[i]=task.get_future();
        threads[i]=std::thread(std::move(task),block_start,block_end);
        block_start=block_end;
    }
    T last_result=accumulate_block<Iterator,T>()(block_start,last);
    std::for_each(threads.begin(),threads.end(),
        std::mem_fn(&std::thread::join));
    T result=init;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        result+=futures[i].get();
    }
    result += last_result;
    return result;
}
```

在此重构中：
- `accumulate_block::operator()` 不再通过引用参数写入结果，而是直接 `return` 累加值。
- 我们使用 `std::vector<std::future<T>>` 替代了原始的数值数组。每个子线程的计算逻辑被打包为一个 `std::packaged_task`，其捕获到的计算结果或异常被自动存入关联的 `std::future` 中。
- 当主线程在遍历调用 `futures[i].get()` 时，如果某个子线程中抛出了异常，该异常将在调用 `get()` 的瞬间在主线程中被**重新抛出（rethrow）**！这使得主线程能够像处理普通异常一样优雅地捕获并处理跨线程传递来的异常。如果有多个子线程抛出异常，通常首个被访问的 future 会将异常抛出，其他异常由 future 自身安全管理析构；如有需要，也可以使用 `std::nested_exception` 收集所有异常。

然而，还有一个至关重要的隐患尚未消除：如果在派生了前几个子线程之后、在执行最后的 `join()` 循环之前，主线程本身抛出了异常（如主线程的 `accumulate_block` 失败），已启动的子线程依然会发生泄露并触发 `std::terminate()`！

最笨拙的补救措施是在主线程周围包裹庞大的 `try-catch` 块并在其中显式逐个检查 `join()`，但这不仅丑陋，而且造成了大量重复的代码。在现代 C++ 中，**最地道、最优雅的解法永远是 RAII**！我们只需编写一个专用的线程汇合守卫类：

```cpp
class join_threads
{
    std::vector<std::thread>& threads;
public:
    explicit join_threads(std::vector<std::thread>& threads_):
        threads(threads_)
    {}
    ~join_threads()
    {
        for(unsigned long i=0;i<threads.size();++i)
        {
            if(threads[i].joinable())
                threads[i].join();
        }
    }
};
```

借助这个轻巧的 RAII 守卫类，我们可以将并行累加重构为坚不可摧的完全异常安全版本：

#### 清单 8.4 具备完全异常安全的并行版 `std::accumulate`

```cpp
template<typename Iterator,typename T>
T parallel_accumulate(Iterator first,Iterator last,T init)
{
    unsigned long const length=std::distance(first,last);
    if(!length)
        return init;
    unsigned long const min_per_thread=25;
    unsigned long const max_threads=
        (length+min_per_thread-1)/min_per_thread;
    unsigned long const hardware_threads=
        std::thread::hardware_concurrency();
    unsigned long const num_threads=
        std::min(hardware_threads!=0?hardware_threads:2,max_threads);
    unsigned long const block_size=length/num_threads;
    std::vector<std::future<T> > futures(num_threads-1);
    std::vector<std::thread> threads(num_threads-1);
    join_threads joiner(threads);
    Iterator block_start=first;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        Iterator block_end=block_start;
        std::advance(block_end,block_size);
        std::packaged_task<T(Iterator,Iterator)> task(
            accumulate_block<Iterator,T>());
        futures[i]=task.get_future();
        threads[i]=std::thread(std::move(task),block_start,block_end);
        block_start=block_end;
    }
    T last_result=accumulate_block<Iterator,T>()(block_start,last);
    T result=init;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        result+=futures[i].get();
    }
    result += last_result;
    return result;
}
```

在创建完 `threads` 容器之后，立即实例化 `joiner` 对象。无论后续代码以何种路径退出（无论是计算完毕正常返回，还是中途任何环节抛出任何异常），C++ 的局部对象逆序析构机制都能百分之百保证 `join_threads` 的析构函数被调用，从而将所有活跃子线程安全地 `join()` 完毕。此时，代码中甚至不再需要显式手写等待 `join()` 的循环！

#### 借助 `std::async()` 实现极致优雅的异常安全

既然显式管理线程需要如此大费周章地编写 RAII 守卫，那么使用 `std::async()` 又会呈现怎样的景象？由于 `std::async()` 会由标准库全权接管后台线程的生命周期，而且若未显式等待由 `std::async` 返回的 future，其析构函数会自动阻塞等待后台线程结束，这极其巧妙地杜绝了悬垂线程的出现。

结合第 8.1.2 节的递归划分策略，使用 `std::async` 实现的异常安全版 `parallel_accumulate` 呈现出令人惊叹的简洁之美：

#### 清单 8.5 使用 `std::async` 的递归异常安全并行累加算法

```cpp
template<typename Iterator,typename T>
T parallel_accumulate(Iterator first,Iterator last,T init)
{
    unsigned long const length=std::distance(first,last);
    unsigned long const max_chunk_size=25;
    if(length<=max_chunk_size)
    {
        return std::accumulate(first,last,init);
    }
    else
    {
        Iterator mid_point=first;
        std::advance(mid_point,length/2);
        std::future<T> first_half_result=
            std::async(parallel_accumulate<Iterator,T>,
                       first,mid_point,init);
        T second_half_result=parallel_accumulate(mid_point,last,T());
        return first_half_result.get()+second_half_result;
    }
}
```

该版本极其精炼：如果数据量小于阈值，直接调用串行 `std::accumulate`；否则寻找中点，使用 `std::async` 将前半部分派生为异步任务，在当前线程直接递归处理后半部分，最后合并两者结果。如果直接递归调用中途抛出异常，由 `std::async` 返回的 `first_half_result` 局部对象在栈展开销毁时，其析构函数会静静地等待异步线程执行完毕，绝对不会留下孤儿线程；而如果异步任务内部发生异常，该异常将在调用 `get()` 时被如实重新抛出。这在极致简洁的代码行数下实现了严丝合缝的全面异常安全。

接下来，我们将目光转向并发设计的另一核心维度：**可扩展性（Scalability）**。

### 8.4.2 可扩展性与阿姆达尔定律（Amdahl's Law）

可扩展性的本质在于：**确保你的软件能够充分吞吐并利用目标硬件系统中新增的物理处理器算力**。一个极端是纯单线程程序，其可扩展性为 0：即便向系统中添加 100 颗 CPU，其执行速度也纹丝不动；另一个极端则是诸如 SETI@Home 这类分布式网格计算项目，它能够几乎无上限地吸收成千上万台新加入网络的计算节点。

在任何实际的多线程程序中，能够真正并发执行有用计算的线程数量在运行期间必然是动态变化的。即便所有线程在生命周期内都在全力工作，程序在刚启动的瞬间通常也只有一个主线程，随后它才负责派生其他工作线程。更普遍的情况是：各个线程在运行过程中往往不可避免地需要彼此等待，或者等待外设 I/O 响应。

**只要有一个线程在等待某种资源，除非此时有另一个就绪线程能立刻顶替它占据 CPU，否则就必然存在一个物理核心处于纯粹的空闲浪费状态**。

一种简化的理论分析模型是将整个程序划分为两部分：
- **串行部分（Serial Sections）**：在此期间仅有单个线程能够执行有用工作；
- **并行部分（Parallel Sections）**：在此期间所有可用的处理器核心都能均摊工作。

假设串行部分在整个程序总工作量中所占的时间比例为 $f_s$（$0 \le f_s \le 1$），则根据经典的**阿姆达尔定律（Amdahl’s Law）**，在使用 $N$ 个并行处理器时，系统所能获得的最大理论加速比 $P$ 可以由下式给出：

$$P = \frac{1}{f_s + \frac{1 - f_s}{N}}$$

- 如果程序完全没有串行部分，即 $f_s = 0$，则理论加速比为完美的线性加速 $P = N$。
- 然而，如果程序中仅有区区 **三分之一（1/3）** 的工作无法被并行化（$f_s = 1/3$），那么**即使你向系统中投入无限多个处理器（$N \to \infty$），该程序的整体加速比永远不可能超过 3 倍**！

现实世界甚至比阿姆达尔定律所预测的更为残酷，因为实际任务几乎不可能做到无限均匀细分，而且正如我们此前所剖析的，多核之间的通信同步开销、缓存乒乓以及内存总线争用，都会使得实际加速比随着核数增加而迅速趋于饱和甚至倒退。

阿姆达尔定律向所有并发架构师敲响了警钟：**若要追求极致的并发性能，必须在宏观架构上极度敏锐地审视整个程序的设计，穷尽一切智慧来最大化并行比例，竭力压缩那些必须串行执行的代码段，并全力消除线程彼此阻塞等待的根源**。此外，如果你能为系统提供海量的数据集从而持续填满并行计算单元（即弱扩展性，Weak Scaling / Gustafson 定律），也能显著压低串行部分在整体中的比例，进而挖掘出更高的实际加速收益。

归根结底，可扩展性既体现为在面对固定规模问题时随着核数增加而带来的**执行耗时缩短**（强扩展性），也体现为在给定时间内能够从容处理**海量暴增的数据吞吐量**（弱扩展性）。在着手拆分系统工作之前，明确哪一种扩展能力是你的核心业务诉求至关重要。

### 8.4.3 用多线程隐藏延迟

在前面探讨性能时，我们通常默认线程在处理器上是“全速开动”持续进行纯粹计算的。然而在绝大多数企业级应用中，线程往往频繁遭遇**阻塞（Blocking）**：等待网络数据包、等待磁盘读写、等待互斥锁释放、等待条件变量或 future 就绪，甚至是显式的休眠等待。

**如果你的程序所维护的线程总数严格等于物理核心数，那么一旦有某个线程进入阻塞状态，就意味着有一个物理核心陷入绝对的空闲闲置，宝贵的算力被白白挥霍**。因此，如果你预知到某个线程在生命周期内必然有相当长的时间处于被迫等待状态，你完全可以多启动一个或多个工作线程，以榨干这部分被闲置的空闲 CPU 周期，从而实现**延迟隐藏（Latency Hiding）**。

以一款病毒查杀软件为例：该系统采用流水线模型切分工作。
- 线程 1 遍历扫描本地文件系统以检索待检查的文件路径，并将它们塞入任务队列中；
- 线程 2（以及其他工作线程）从队列中不断提取文件路径，将文件内容加载到内存中并进行深度病毒特征码扫描。

显而易见，负责遍历文件系统的第一个线程绝对是高密度的 **I/O 密集型（I/O-bound）** 任务，它的大部分时间都耗费在等待磁盘磁头寻道或文件元数据返回上。因此，为了榨干 CPU，完全应该为特征码扫描配置足额的计算线程（使得扫描线程数至少等于机器的物理核心数）。由于扫描线程在读取超大文件内容时偶尔也会发生 I/O 阻塞，甚至可以配置略多于物理核数的扫描线程。但这一数字绝不能无节制放大，否则过多的线程必然会再次诱发过度订阅与缓存颠簸（见第 8.2.5 节）。

延迟隐藏的另一种高阶形态是**异步非阻塞编程**：通过使用操作系统底层的高性能异步 I/O 设施（如 Linux 下的 epoll/io_uring），单个线程可以在后台进行数据传输的同时，立即转头去执行其他密集计算任务；或者像我们在第 7 章的无锁队列中看到的那样，当一个线程在等待其他线程推进某项操作时，主动协助推进未完成的步骤；抑或是像清单 8.1 中的快速排序那样，在等待特定数据块排序就绪的空当，主动帮助处理任务栈中积压的其他分块。

除了榨取 CPU 算力，多线程在许多时候还有着另一项不可替代的核心使命：**提升软件系统的交互响应敏捷度**。

### 8.4.4 用并发提高系统响应能力

几乎所有现代图形用户界面（GUI）框架都是纯粹由**事件驱动（Event-Driven）**的：用户通过敲击键盘、晃动鼠标与界面交互，这些物理操作被操作系统转化为一系列窗口消息或事件分发给应用程序处理。应用程序的主线程通常运行着一个死循环结构的事件泵（Event Loop）：

```cpp
while(true)
{
    event_data event=get_event();
    if(event.type==quit)
        break;
    process(event);
}
```

在单线程架构中，编写长耗时计算任务是一场灾难：为了保证用户界面不会陷入卡死假死，`get_event()` 和 `process()` 必须以极高的频率被反复轮询。这意味着耗时算法必须被极其恶心地切碎，在各个角落插入保存状态、交还控制权的逻辑，这会导致核心算法的可读性与健壮性遭受毁灭性打击。

通过并发来实现关注点分离，你可以将繁重的计算任务完整打包并抛到一个**独立的后台工作线程**上，而让**专用的 GUI 线程**心无旁骛地全速跑其事件循环。两者的交互可以通过简洁清晰的消息队列来实现。

下面的清单展示了这种经典界面的线程分离设计模式：

#### 清单 8.6 将 GUI 线程与后台长耗时任务线程解耦分离

```cpp
std::thread task_thread;
std::atomic<bool> task_cancelled(false);

void gui_thread()
{
    while(true)
    {
        event_data event=get_event();
        if(event.type==quit)
            break;
        process(event);
    }
}

void task()
{
    while(!task_complete() && !task_cancelled)
    {
        do_next_operation();
    }
    if(task_cancelled)
    {
        perform_cleanup();
    }
    else
    {
        post_gui_event(task_complete);
    }
}

void process(event_data const& event)
{
    switch(event.type)
    {
    case start_task:
        task_cancelled=false;
        task_thread=std::thread(task);
        break;
    case stop_task:
        task_cancelled=true;
        task_thread.join();
        break;
    case task_complete:
        task_thread.join();
        display_results();
        break;
    default:
        // 处理其他标准窗口事件，如重绘、最小化等
        break;
    }
}
```

在这种清晰的架构下，即使用台下的任务需要耗费数小时才能计算完毕，GUI 线程依然能以 60+ fps 的帧率极其流畅地响应窗口拖曳、重绘、尺寸缩放等用户交互；如果用户中途点击了“取消”按钮，GUI 线程只需简单将原子标志 `task_cancelled` 置位，后台任务就会在下一个细粒度步骤检测到并优雅清理退出。

## 8.5 实战并发代码设计

在为具体工程设计并发代码时，究竟应该在多大程度上权衡前文所述的各种考量要素，完全取决于实际的业务特征。为了深刻展示这些设计哲学的具体落地，我们将亲手打造 C++ 标准库中三个极具代表性的经典算法的并行化版本：
1. `std::for_each`：代表每一个数据项都完全相互独立的纯粹并行映射操作；
2. `std::find`：代表具备**提前终止（Early Exit）**特性的搜索匹配操作；
3. `std::partial_sum`（前缀和）：代表数据项之间存在严密**前后数据依赖**的高难度算法。

### 8.5.1 并行实现 `std::for_each`

`std::for_each` 在语义上极其清晰单纯：对指定迭代器区间内的每一个元素，依次调用用户传入的可调用对象。并行版本与串行版本之间最大的根本区别在于**执行顺序**：串行 `std::for_each` 严格保证按照迭代器从前到后的顺序逐个调用；而并行版本则**绝无任何先后顺序保证**，所有元素完全可能是无序且并发重叠处理的。

由于元素数量通常在调用前可以通过迭代器距离准确计算，我们可以在处理开始前预先将区间切分为若干大块（第 8.1.1 节）。我们假定该任务是系统中的主要并行工作，因此使用 `std::thread::hardware_concurrency()` 决定线程总数。由于每个元素是完全独立处理的，我们将每个线程分配给连续的物理数据块，以彻底杜绝伪共享（第 8.2.3 节）。

#### 清单 8.7 基于数据块预划分的并行 `std::for_each`

```cpp
template<typename Iterator,typename Func>
void parallel_for_each(Iterator first,Iterator last,Func f)
{
    unsigned long const length=std::distance(first,last);
    if(!length)
        return;
    unsigned long const min_per_thread=25;
    unsigned long const max_threads=
        (length+min_per_thread-1)/min_per_thread;
    unsigned long const hardware_threads=
        std::thread::hardware_concurrency();
    unsigned long const num_threads=
        std::min(hardware_threads!=0?hardware_threads:2,max_threads);
    unsigned long const block_size=length/num_threads;
    std::vector<std::future<void> > futures(num_threads-1);
    std::vector<std::thread> threads(num_threads-1);
    join_threads joiner(threads);
    Iterator block_start=first;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        Iterator block_end=block_start;
        std::advance(block_end,block_size);
        std::packaged_task<void(void)> task(
            [=]()
            {
                std::for_each(block_start,block_end,f);
            });
        futures[i]=task.get_future();
        threads[i]=std::thread(std::move(task));
        block_start=block_end;
    }
    std::for_each(block_start,last,f);
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        futures[i].get();
    }
}
```

其结构与清单 8.4 高度一致。核心差异在于：由于 `for_each` 不产生返回值，`futures` 容器存储的是 `std::future<void>`，任务体是一个简单的 lambda，在其中调用标准的串行 `std::for_each` 处理属于自己的区间。在末尾遍历调用 `futures[i].get()` 的唯一目的就是：**将任何在子线程内部抛出的异常正确且安全地重新抛出给主调方**。

同样地，借助 `std::async` 和递归分治，我们可以编写出结构更为紧凑的异步并行版本：

#### 清单 8.8 使用 `std::async` 实现的递归并行 `std::for_each`

```cpp
template<typename Iterator,typename Func>
void parallel_for_each(Iterator first,Iterator last,Func f)
{
    unsigned long const length=std::distance(first,last);
    if(!length)
        return;
    unsigned long const min_per_thread=25;
    if(length<(2*min_per_thread))
    {
        std::for_each(first,last,f);
    }
    else
    {
        Iterator const mid_point=first+length/2;
        std::future<void> first_half=
            std::async(&parallel_for_each<Iterator,Func>,
                       first,mid_point,f);
        parallel_for_each(mid_point,last,f);
        first_half.get();
    }
}
```

### 8.5.2 并行实现 `std::find`

`std::find` 是并发设计中一个极其迷人的案例，因为它是典型的**支持提前终止**的算法：如果第一个元素就击中了搜索目标，系统根本不需要、也不应当再去检查任何后续的成千上万个元素！

不妨设想你和家人在阁楼的多个杂物箱中寻找一张老照片：一旦你在第一个箱子里找到了照片，你绝不会默默揣着照片看着家人在其他箱子里白白折腾，而是会立刻大喊一声：“我找到啦！”让其他人立刻停下手头的工作。

在并行化类似 `std::find` 的算法时，**“提前终止”是关乎性能的核心特性，绝不容许被轻易挥霍**。如果你不设计提前中断机制，你的并行查找算法很可能会在实际场景下**惨败给单线程串行版本**！试想：在一个 4 核机器上，串行版本如果在前 5% 的数据中就找到了目标，它瞬间就会返回；而一个未经中断设计的拙劣并行版本，即使某个线程在第 1 微秒就匹配成功，它却必须强行等待其他 3 个线程老老实实把各自负责的后 75% 的数据全部傻傻遍历完毕才能收工！

因此，必须引入一个共享的原子标志（`done_flag`）作为广播信号：一旦任何一个线程找到了匹配项，或者发生了异常，它在写入结果的同时立刻将该标志置位；所有其他并发线程在每次遍历比较元素时，都顺带检查该标志，一旦发现已被置位，立即中止循环提前退出。

#### 清单 8.9 具备提前终止与异常捕获的完整并行 `std::find`

```cpp
template<typename Iterator,typename MatchType>
Iterator parallel_find(Iterator first,Iterator last,MatchType match)
{
    struct find_element
    {
        void operator()(Iterator begin,Iterator end,
                        MatchType match,
                        std::promise<Iterator>* result,
                        std::atomic<bool>* done_flag)
        {
            try
            {
                for(;(begin!=end) && !done_flag->load();++begin)
                {
                    if(*begin==match)
                    {
                        result->set_value(begin);
                        done_flag->store(true);
                        return;
                    }
                }
            }
            catch(...)
            {
                try
                {
                    result->set_exception(std::current_exception());
                    done_flag->store(true);
                }
                catch(...)
                {}
            }
        }
    };

    unsigned long const length=std::distance(first,last);
    if(!length)
        return last;
    unsigned long const min_per_thread=25;
    unsigned long const max_threads=
        (length+min_per_thread-1)/min_per_thread;
    unsigned long const hardware_threads=
        std::thread::hardware_concurrency();
    unsigned long const num_threads=
        std::min(hardware_threads!=0?hardware_threads:2,max_threads);
    unsigned long const block_size=length/num_threads;
    std::promise<Iterator> result;
    std::atomic<bool> done_flag(false);
    std::vector<std::thread> threads(num_threads-1);
    {
        join_threads joiner(threads);
        Iterator block_start=first;
        for(unsigned long i=0;i<(num_threads-1);++i)
        {
            Iterator block_end=block_start;
            std::advance(block_end,block_size);
            threads[i]=std::thread(find_element(),
                                   block_start,block_end,match,
                                   &result,&done_flag);
            block_start=block_end;
        }
        find_element()(block_start,last,match,&result,&done_flag);
    }
    if(!done_flag.load())
    {
        return last;
    }
    return result.get_future().get();
}
```

此实现细节耐人寻味：
- 工作任务 `find_element` 在每次循环前都检查 `!done_flag->load()`。一旦找到匹配项，直接调用 `result->set_value(begin)` 写入 promise 并设置 `done_flag` 为 `true`。
- 如果多个线程几乎在同一纳秒匹配成功，它们会产生向同一个 promise 写入结果的数据竞争；但这是一种**良性竞争（Benign Race）**：抢先一步成功的线程胜出，而后续失败的写入会抛出 `std::future_errc::promise_already_satisfied` 异常，该异常在内层 `catch(...)` 中被安静地吞噬忽略，确保了逻辑的严密自洽。
- 注意外层包裹的局部作用域 `{ join_threads joiner(threads); ... }`：由于可能根本不存在匹配的目标元素，主线程绝不能盲目在 future 上阻塞！它必须首先等待局部作用域析构、确保**所有线程都已全部安全汇合结束**后，再去检查 `done_flag`。如果标志仍为 `false`，说明搜索扑空，安全返回 `last`；如果为 `true`，通过 `get()` 返回有效迭代器或向外重新抛出内部捕获的异常。

同样地，下面给出基于 `std::async` 实现的递归版本：

#### 清单 8.10 使用 `std::async` 实现的并行 `std::find`

```cpp
template<typename Iterator,typename MatchType>
Iterator parallel_find_impl(Iterator first,Iterator last,MatchType match,
                            std::atomic<bool>& done)
{
    try
    {
        unsigned long const length=std::distance(first,last);
        unsigned long const min_per_thread=25;
        if(length<(2*min_per_thread))
        {
            for(;(first!=last) && !done.load();++first)
            {
                if(*first==match)
                {
                    done=true;
                    return first;
                }
            }
            return last;
        }
        else
        {
            Iterator const mid_point=first+(length/2);
            std::future<Iterator> async_result=
                std::async(&parallel_find_impl<Iterator,MatchType>,
                           mid_point,last,match,std::ref(done));
            Iterator const direct_result=
                parallel_find_impl(first,mid_point,match,done);
            return (direct_result==mid_point)?
                async_result.get():direct_result;
        }
    }
    catch(...)
    {
        done=true;
        throw;
    }
}

template<typename Iterator,typename MatchType>
Iterator parallel_find(Iterator first,Iterator last,MatchType match)
{
    std::atomic<bool> done(false);
    return parallel_find_impl(first,last,match,done);
}
```

请注意其至关重要的语义转变：**并行版本的 `find` 不再保证返回序列中“第一个”匹配的元素位置**！如果前半段和后半段都存在符合条件的元素，后半段的线程可能率先匹配并返回，这是为了获取极致并行性能而在语义上做出的必要妥协。

### 8.5.3 并行实现 `std::partial_sum`（前缀和）

`std::partial_sum` 用于计算区间的连续累加前缀和：原始序列中的每个位置都被替换为其自身以及此前所有元素的累加总和。例如：序列 `1, 2, 3, 4, 5` 经计算后变为 `1, 3, 6, 10, 15`。

该算法的并行化极具挑战性且发人深省：因为**序列中后面的每一个元素在数学上都死死依赖于它前面所有元素的计算结果**！你绝不可能把整个序列随意切成几段就直接扔给线程并行计算。

针对此问题，计算机科学家提出了两种截然不同的架构路线：

#### 方案一：分块计算与尾值向前传播（Forward Propagation）
1. 将序列均分为 $k$ 个大块，每个线程独立对自己的分块计算局部的串行前缀和。
   - 比如序列 `1, 2, 3, 4, 5, 6, 7, 8, 9` 切为三块，各块独立计算后分别得到：`{1, 3, 6}`, `{4, 9, 15}`, `{7, 15, 24}`。
2. 将第 1 块的末尾累加值（6）作为增量，加到第 2 块的所有元素上，第 2 块更新为 `{10, 15, 21}`。
3. 将第 2 块更新后的最新末尾累加值（21）作为增量，加到第 3 块的所有元素上，第 3 块更新为 `{28, 36, 55}`。

在此方案中，若将块末尾元素的更新排在前面，则各分块的向前传播增量累加同样可以部分重叠并行化。当**数据规模远大于物理核心数**时，该方案表现极佳，其总算力复杂度为非常优越的线性 $O(N)$。

#### 清单 8.11 通过分块与向前传播计算并行前缀和

```cpp
template<typename Iterator>
void parallel_partial_sum(Iterator first,Iterator last)
{
    typedef typename Iterator::value_type value_type;
    struct process_chunk
    {
        void operator()(Iterator begin,Iterator last,
                        std::future<value_type>* previous_end_value,
                        std::promise<value_type>* end_value)
        {
            try
            {
                Iterator end=last;
                ++end;
                std::partial_sum(begin,end,begin);
                if(previous_end_value)
                {
                    value_type& addend=previous_end_value->get();
                    *last+=addend;
                    if(end_value)
                    {
                        end_value->set_value(*last);
                    }
                    std::for_each(begin,last,[addend](value_type& item)
                                  {
                                      item+=addend;
                                  });
                }
                else if(end_value)
                {
                    end_value->set_value(*last);
                }
            }
            catch(...)
            {
                if(end_value)
                {
                    end_value->set_exception(std::current_exception());
                }
                else
                {
                    throw;
                }
            }
        }
    };

    unsigned long const length=std::distance(first,last);
    if(!length)
        return;
    unsigned long const min_per_thread=25;
    unsigned long const max_threads=
        (length+min_per_thread-1)/min_per_thread;
    unsigned long const hardware_threads=
        std::thread::hardware_concurrency();
    unsigned long const num_threads=
        std::min(hardware_threads!=0?hardware_threads:2,max_threads);
    unsigned long const block_size=length/num_threads;
    typedef typename Iterator::value_type value_type;
    std::vector<std::thread> threads(num_threads-1);
    std::vector<std::promise<value_type> > end_values(num_threads-1);
    std::vector<std::future<value_type> > previous_end_values;
    previous_end_values.reserve(num_threads-1);
    join_threads joiner(threads);
    Iterator block_start=first;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        Iterator block_last=block_start;
        std::advance(block_last,block_size-1);
        threads[i]=std::thread(process_chunk(),
                               block_start,block_last,
                               (i!=0)?&previous_end_values[i-1]:0,
                               &end_values[i]);
        block_start=block_last;
        ++block_start;
        previous_end_values.push_back(end_values[i].get_future());
    }
    Iterator final_element=block_start;
    std::advance(final_element,std::distance(block_start,last)-1);
    process_chunk()(block_start,final_element,
                    (num_threads>1)?&previous_end_values.back():0,
                    0);
}
```

#### 方案二：基于屏障（Barrier）的成对增量增跃算法（Pairwise Updates）
如果拥有极其海量的硬件计算单元（例如处理器核心数量与元素数量接近或相等），方案一的串行向前依赖就会沦为吞吐瓶颈。此时，我们可以转向**跨步成对增量算法**：
- 第 1 轮：步长为 1，每个元素加上其前 1 个元素的值；此时前 2 个元素已经得到最终正确结果；
- 第 2 轮：步长为 2，每个元素加上其前 2 个元素在上一轮产生的值；此时前 4 个元素已获得最终结果；
- 第 3 轮：步长为 4，加上前 4 个元素的值……以此类推。

该方案总共只需要 $\log_2(N)$ 轮迭代。虽然其总计算操作数膨胀到了 $O(N \log N)$，但由于所有计算单元在每一轮中都可以完全并行化，**每个处理核心实际只需要执行 $\log_2(N)$ 次运算**！

为了协调所有线程在每一轮迭代中整齐划一地向前推进、绝不发生“抢跑”，我们需要一个同步原语——**屏障（Barrier）**。它的物理机制就如同一辆游乐园的过山车：必须等所有指定数量的“座位”全部坐满后，过山车才会发车放行，并自动重置以等待下一批乘客。

#### 清单 8.12 一个简易的自旋式 `barrier` 类实现

```cpp
class barrier
{
    unsigned const count;
    std::atomic<unsigned> spaces;
    std::atomic<unsigned> generation;
public:
    explicit barrier(unsigned count_):
        count(count_),spaces(count),generation(0)
    {}
    void wait()
    {
        unsigned const my_generation=generation;
        if(!--spaces)
        {
            spaces=count;
            ++generation;
        }
        else
        {
            while(generation==my_generation)
                std::this_thread::yield();
        }
    }
};
```

为了让已经完成计算的边缘线程提前退出而不阻塞整个屏障，我们需要将 `count` 改为原子变量，并增加一个 `done_waiting()` 接口。结合双缓冲区（Buffer）交替读写以消除读写竞争，我们得到了终极的高并发成对前缀和实现：

#### 清单 8.13 通过成对跨步更新与屏障同步的并行 `std::partial_sum`

```cpp
struct barrier
{
    std::atomic<unsigned> count;
    std::atomic<unsigned> spaces;
    std::atomic<unsigned> generation;

    barrier(unsigned count_):
        count(count_),spaces(count_),generation(0)
    {}
    void wait()
    {
        unsigned const gen=generation.load();
        if(!--spaces)
        {
            spaces=count.load();
            ++generation;
        }
        else
        {
            while(generation.load()==gen)
            {
                std::this_thread::yield();
            }
        }
    }
    void done_waiting()
    {
        --count;
        if(!--spaces)
        {
            spaces=count.load();
            ++generation;
        }
    }
};

template<typename Iterator>
void parallel_partial_sum(Iterator first,Iterator last)
{
    typedef typename Iterator::value_type value_type;
    struct process_element
    {
        void operator()(Iterator first,Iterator last,
                        std::vector<value_type>& buffer,
                        unsigned i,barrier& b)
        {
            value_type& ith_element=*(first+i);
            bool update_source=false;
            for(unsigned step=0,stride=1;stride<=i;++step,stride*=2)
            {
                value_type const& source=(step%2)?
                    buffer[i]:ith_element;
                value_type& dest=(step%2)?
                    ith_element:buffer[i];
                value_type const& addend=(step%2)?
                    buffer[i-stride]:*(first+i-stride);
                dest=source+addend;
                update_source=!(step%2);
                b.wait();
            }
            if(update_source)
            {
                ith_element=buffer[i];
            }
            b.done_waiting();
        }
    };

    unsigned long const length=std::distance(first,last);
    if(length<=1)
        return;
    std::vector<value_type> buffer(length);
    barrier b(length);
    std::vector<std::thread> threads(length-1);
    join_threads joiner(threads);
    Iterator block_start=first;
    for(unsigned long i=0;i<(length-1);++i)
    {
        threads[i]=std::thread(process_element(),first,last,
                               std::ref(buffer),i,std::ref(b));
    }
    process_element()(first,last,buffer,length-1,b);
}
```
