# 第 1 章：C++ 并发世界初探

欢迎来到 C++ 并发世界！

本章主要内容包括：

- 什么是并发与多线程
- 为什么要在应用程序中使用并发与多线程
- C++ 语言对并发支持的演进历程
- 一个简单的 C++ 多线程程序是什么样的

对于 C++ 用户而言，当下正是一个令人振奋的时代。自 1998 年发布首个 C++ 标准整整 13 年之后，C++ 标准委员会对该语言及其支持库进行了一次重大重构。全新的 C++ 标准（通常称为 C++11 或 C++0x）于 2011 年正式发布，它带来了一系列翻天覆地的变化，使 C++ 的开发变得更加轻松且高效。委员会还确立了全新的“火车发布模型”（train model），承诺每三年发布一次新的 C++ 标准。到目前为止，我们已经见证了两次新标准的诞生：2014 年发布的 C++14 标准，以及 2017 年发布的 C++17 标准，同时还有多项描述 C++ 标准扩展的技术规范（Technical Specifications，简称 TS）。

C++11 标准中最重要的新特性之一便是对多线程程序的支持。C++ 标准首次在语言层面上承认了多线程应用程序的存在，并在标准库中提供了编写多线程应用程序所需的组件。这使得开发者无需依赖平台专属扩展即可编写多线程 C++ 程序，并能够编写出行为具有确定保证的可移植多线程代码。这一特性的推出，恰逢程序员普遍寻求利用并发（特别是多线程编程）来提升应用程序性能的时期。C++14 和 C++17 标准在此基线之上进一步完善了对 C++ 编写多线程程序的支持，各项技术规范亦是如此。例如，有专门针对并发扩展的技术规范，还有关于并行性的技术规范（后者已正式并入 C++17）。

本书的主题正是关于如何在 C++ 中使用多线程实现并发编程，以及使其成为可能的 C++ 语言特性和标准库设施。首先，我将阐述并发和多线程的具体含义，以及为什么要在应用程序中使用并发。在简要探讨为何可能不想在程序中使用并发之后，我们将梳理 C++ 中的并发支持体系，最后以一个简单的 C++ 并发实战示例结束本章。具有多线程应用程序开发经验的读者可以选择跳过前面的基础小节。在后续章节中，我们将探讨更复杂的示例并深入剖析库设施。本书最后将对 C++ 标准库中所有的多线程和并发设施进行详尽的参考介绍。

那么，究竟什么是并发与多线程呢？

## 1.1 什么是并发？

在最简单、最基础的层面上，并发是指两个或多个独立的活动在同一时间发生。在现实生活中，并发是一种极其自然的现象：我们可以一边走路一边说话，也可以两只手分别执行不同的动作；我们每个人都独立地过着各自的生活——你在看足球比赛的同时我可能在游泳，诸如此类。

### 1.1.1 计算机系统中的并发

当我们在计算机语境下讨论并发时，是指单个系统并行执行多个独立活动，而不是按部就班地依次顺序执行。这并不是一个新生事物。允许单台桌面计算机通过任务切换（task switching）同时运行多个应用程序的多任务操作系统已经普及多年；拥有多个处理器、能够实现真正并发的高端服务器机器同样历史悠久。真正的新变化在于，能够真正并行运行多个任务（而非制造并发假象）的计算机正变得越来越普及。

从历史上看，大多数桌面计算机只有一个处理器，且仅具备单个处理单元或核心（core），如今许多桌面机器依然如此。这类机器在某一时刻只能执行一个任务，但它可以每秒在任务之间切换很多次。通过先执行某个任务的一小部分，然后执行另一个任务的一小部分，如此循环往复，看起来任务就像是在并发发生一样。这被称为任务切换（task switching）。在这种系统中，我们依然称其为并发；因为任务切换的速度极其迅速，你根本察觉不到处理器在何时暂停了当前任务并切换到了另一个任务。任务切换为用户以及应用程序自身营造了一种并发的假象。正因为这只是一种并发假象，应用程序在单处理器任务切换环境下运行时的行为，可能与在具有真正并发的环境下运行时存在微妙差异。特别是对内存模型（第 5 章将详细介绍）做出的不正确假设，在单处理器任务切换环境下可能不会暴露出来。第 10 章将对此展开更深入的讨论。

包含多个处理器的计算机多年来一直用于服务器和高性能计算任务，而基于单芯片上集成多个核心（多核处理器）的计算机在桌面领域也已极为普遍。无论计算机是拥有多个物理处理器，还是单个处理器内部拥有多个核心（或者二者兼有），它们都具备真正并行运行多个任务的能力。我们称之为硬件并发（hardware concurrency）。

图 1.1 展示了一台拥有两个精确划分的任务（每个任务被分成 10 个等大小分块）的计算机的理想场景。在双核机器（拥有两个处理核心）上，每个任务都可以在自己的核心上独立执行。而在进行任务切换的单核机器上，每个任务的分块是交错执行的。但它们之间也存在一定的间距（在图 1.1 中，由分隔分块的灰色条体现，该条比双核机器上的分隔条更粗）；为了实现交错执行，系统每次从一个任务切换到另一个任务时都必须执行一次上下文切换（context switch），而这需要消耗时间。为了完成上下文切换，操作系统必须保存当前运行任务的 CPU 状态和指令指针，确定要切换到哪个任务，并重新加载目标任务的 CPU 状态。随后，CPU 可能还需要将新任务的指令和数据内存加载到缓存中，这会阻碍 CPU 执行任何实际指令，从而引入额外的延迟。

```
双核系统
核心 1: [任务1-1][任务1-2][任务1-3][任务1-4][任务1-5]...
核心 2: [任务2-1][任务2-2][任务2-3][任务2-4][任务2-5]...

单核系统
核心 1: [任务1-1]--切换--[任务2-1]--切换--[任务1-2]--切换--[任务2-2]...
```
*图 1.1 两种并发途径：双核机器上的并行执行 vs 单核机器上的任务切换*

尽管硬件并发在多处理器或多核系统中最显而易见，但某些处理器也可以在单个核心上执行多个线程（如超线程技术）。需要考量的重要因素是硬件线程数（hardware threads），它衡量了硬件能够真正并发运行的独立任务数量。即便系统具备真正的硬件并发能力，其任务数量也很容易超出硬件可并行运行的能力上限，因此在这些情况下仍然需要使用任务切换。例如，在典型的桌面计算机上，即使计算机名义上处于空闲状态，也可能有数百个后台任务在运行。正是任务切换机制，使得这些后台任务得以运行的同时，你还能同时开启文字处理器、编译器、代码编辑器和网页浏览器（或任意应用程序组合）。图 1.2 展示了双核机器上四个任务之间的任务切换，同样是在任务被均匀划分为相等分块的理想化场景下。而在实践中，许多现实问题会导致分块不均匀以及调度不规则。第 8 章在剖析影响并发代码性能的因素时将讨论其中的部分问题。

```
双核系统上的四个任务
核心 1: [任务1-1]--切换--[任务3-1]--切换--[任务1-2]--切换--[任务3-2]...
核心 2: [任务2-1]--切换--[任务4-1]--切换--[任务2-2]--切换--[任务4-2]...
```
*图 1.2 双核上四个任务的任务切换*

无论应用程序运行在单核单处理器机器上，还是运行在多核多处理器机器上，本书涵盖的所有技术、函数和类均可通用，不受并发是通过任务切换还是真正硬件并发所实现的影响。但正如你可以想象的那样，在应用程序中如何利用并发，在很大程度上取决于可用的硬件并发能力。这将在第 8 章中展开讨论，届时我将详细探讨在 C++ 中设计并发代码涉及的各种权衡。

### 1.1.2 实现并发的途径

不妨想象有两位程序员在一同开发一个软件项目。如果两位开发者身处各自独立的办公室，他们就可以安静地开展工作，互不干扰，并且各自拥有一套参考手册。但彼此之间的沟通并不直接；他们不能简单地转过身就交谈，而是必须使用电话、发送邮件，或者起身走到对方的办公室。此外，你还需要承担管理两间办公室的开销，并购买多套参考手册。

现在设想你把两位开发者安排在同一间办公室里。他们现在可以毫无阻碍地自由交谈、讨论应用程序设计，也可以轻松地在纸上或白板上画图来交流设计思路或讲解细节。你只需管理一间办公室，一套资源往往就足够了。但负面影响在于，他们可能会发现更难集中注意力，而且在资源共享上可能会产生摩擦（“参考手册现在被拿哪儿去了？”）。

组织开发者的这两种方式生动地说明了实现并发的两种基本途径。每位开发者代表一个线程，每间办公室代表一个进程。第一种途径是采用多个单线程进程（multiple single-threaded processes），这类似于让每个开发者呆在自己的办公室；第二种途径是在单个进程中运行多个线程（multiple threads in a single process），这好比把两位开发者安排在同一间办公室。你可以任意组合这两种方式，使系统包含多个进程，其中一部分是多线程的，另一部分是单线程的，但其核心原理是一致的。接下来让我们简要审视应用程序中的这两种并发途径。

#### 多进程并发
在应用程序中利用并发的第一种方式是将程序拆分为多个独立的单线程进程，这些进程同时运行，就如同你可以同时运行网页浏览器和文字处理器一样。这些独立的进程随后可以通过常规的进程间通信（IPC）机制（如信号、套接字、文件、管道等）互相传递消息，如图 1.3 所示。其缺点在于，进程间的此类通信通常设置复杂、运行缓慢（或者二者兼有），因为操作系统通常在进程之间提供了严密的保护屏障，以防止一个进程意外修改属于另一个进程的数据。另一个缺点是运行多个进程本身具有固有的开销：启动一个进程需要时间，操作系统必须分配内部资源来管理进程，等等。

```
[进程 1: 线程] <---(操作系统提供的进程间通信 IPC: 管道/套接字/共享内存)---> [进程 2: 线程]
```
*图 1.3 两个并发运行的进程之间的通信*

当然，这也并非全无益处：操作系统在进程之间提供的额外保护以及更高层次的通信机制，意味着采用进程而非线程往往更容易编写出安全的并发代码。事实上，像 Erlang（www.erlang.org/）这样的编程语言环境，正是将进程作为并发的基本构建块并取得了巨大的成功。

使用独立进程实现并发还具备另一个显著优势——你可以将各个独立的进程部署在通过网络连接的不同机器上运行。虽然这增加了通信成本，但在经过精心设计的系统上，这是一种提高可用并行度并改善性能的高性价比途径。

#### 多线程并发
实现并发的另一种替代途径是在单个进程内运行多个线程。线程非常类似于轻量级进程：每个线程彼此独立运行，各自可能执行不同的指令序列。但是，进程中的所有线程共享相同的地址空间，大部分数据都可以直接从所有线程访问——全局变量依然是全局的，指向对象或数据的指针与引用也可以在各个线程之间随意传递。虽然在进程之间共享内存也是可行的，但其配置较为繁琐且往往难以维护，因为相同数据在不同进程中的内存地址并不一定一致。图 1.4 展示了单个进程内通过共享内存进行通信的两个线程。

```
进程空间
┌─────────────────────────────────┐
│  [线程 1]           [线程 2]    │
│       \               /         │
│        \             /          │
│       ┌─────────────────┐       │
│       │    共享内存     │       │
│       └─────────────────┘       │
└─────────────────────────────────┘
```
*图 1.4 单个进程内并发运行的两个线程之间的通信*

共享地址空间以及线程间缺乏数据保护屏障，使得使用多线程相关的开销远小于使用多进程，因为操作系统需要维护的状态信息大幅减少。然而，共享内存的灵活性也是有代价的：如果数据被多个线程访问，应用程序程序员必须确保每个线程在访问数据时所看到的数据视图是一致的。围绕线程间共享数据的问题，以及避免问题所应遵循的准则和工具，贯穿于本书各章节，尤其是第 3、4、5 和 8 章。只要在编写代码时保持应有的审慎，这些问题绝非无法克服，但它们确实意味着必须对线程间的通信给予极其深思熟虑的设计。

与启动多个单线程进程并在其间进行通信相比，在进程内启动多个线程并进行线程间通信具有极低的开销，这使得多线程成为包括 C++ 在内的主流编程语言中备受青睐的并发途径。此外，C++ 标准并没有提供任何关于进程间通信的内置支持，因此使用多进程的应用程序必须依赖平台专属的 API 才能做到。因此，本书将完全专注于使用多线程实现并发，后续提及“并发”时均默认假定是通过使用多线程来实现的。

在多线程代码中，还有一个经常被提及的词：并行（parallelism）。让我们来阐明二者的区别。

### 1.1.3 并发 vs 并行

在多线程代码的语境下，并发（Concurrency）与并行（Parallelism）的含义在很大程度上是重叠的。事实上，对许多人来说它们表达的是同一个意思。它们之间的区别主要在于微妙的语境重心与设计意图。两个术语都关乎利用可用硬件同时运行多个任务，但并行的重心明显更加偏向性能。当人们关注的重点是充分利用可用硬件以提升海量数据处理的吞吐性能时，往往会使用“并行”；而当主要关注点在于关注点分离（separation of concerns）或响应能力（responsiveness）时，人们更多会使用“并发”。这种二分法并非界限分明，它们在含义上依然存在相当大的交集，但了解这种区别有助于澄清技术探讨。贯穿本书，我们将会看到这两种场景的具体示例。

明确了并发与并行的概念后，接下来我们探讨为什么要在应用程序中使用并发。

## 1.2 为什么使用并发？

在应用程序中使用并发主要有两个核心原因：关注点分离（separation of concerns）和性能提升（performance）。事实上，我认为这几乎是使用并发的仅有原因；深入探究下去，任何其他理由归根结底都可以归结为其中之一（甚至两者兼有）——当然，除了“纯粹因为我想用”这类非技术理由之外。

### 1.2.1 使用并发实现关注点分离

在编写软件时，关注点分离几乎总是一个绝佳的设计思路；通过将相关的代码片段组织在一起，并将无关的代码隔离开来，能够使程序更加易于理解和测试，同时也更不容易引入缺陷。你可以使用并发来拆分截然不同的功能领域，即便这些独立领域中的操作需要在同一时刻发生；如果不显式使用并发，你必须要么自行编写一套任务切换框架，要么在执行某一操作期间主动向无关的代码区域发起轮询或调用。

考虑一个计算密集型且带有用户界面的桌面应用程序，例如 DVD 播放器应用。从根本上讲，该程序承担着两套截然不同的职责。一方面，它必须从光盘读取数据，对图像和音频进行解码，并及时发送到图形和声卡硬件，确保 DVD 播放流畅不卡顿；另一方面，它还必须响应用户的输入操作，例如用户点击了“暂停”、“返回菜单”甚至是“退出”。在单线程设计中，应用程序必须在回放期间以固定的时间间隔检查用户输入，从而将 DVD 回放逻辑与用户界面逻辑紧密杂糅在一起。通过利用多线程将这些关注点分离开来，用户界面代码与 DVD 回放代码就不再需要如此纠缠不清：一个线程专门负责用户界面，另一个线程专门负责 DVD 回放。它们之间依然需要交互（例如用户点击了暂停按钮），但此时这些交互已经变成了与具体任务直接相关的清晰通信。

这种设计为用户带来了极佳的响应能力体验，因为用户界面线程通常可以立即响应用户请求，即便其响应方式只是显示一个等待沙漏光标或“请稍候”提示，同时将请求异步传递给正在处理实际工作的后台线程。类似地，独立的线程通常用于执行必须在后台持续运行的任务，例如桌面搜索应用程序中监视文件系统变更的线程。以这种方式使用线程通常能使各个线程内部的逻辑大幅简化，因为线程间的交互可以被限制在清晰可辨的点上，而不必在不同任务之间交错掺杂业务逻辑。

在这种情况下，线程的数量通常与可用的 CPU 核心数无关，因为划分线程的依据是概念架构设计，而不是为了提升计算吞吐量。

### 1.2.2 使用并发提升性能：任务并行与数据并行

多处理器系统已经存在了数十年，但在以往，它们主要仅见于超级计算机、大型机以及大型服务器系统中。然而，现代芯片制造商越来越倾向于在单个芯片上集成 2 个、4 个、16 个甚至更多处理器的多核设计，而不是执着于进一步挖掘单核的极致性能。因此，多核桌面计算机、甚至是多核嵌入式设备如今已经随处可见。这些机器计算能力的提升，不再源于单个任务运行速度的加快，而是源于多个任务能够并行运行。在过去，程序员可以高枕无忧地看着自己的程序随着每一代新处理器的推出而自然变快，无需付出任何额外的编码努力。但正如 Herb Sutter 所言：“免费的午餐结束了（The free lunch is over）”。软件若想充分利用这种不断增长的计算能力，就必须被设计为能够并发运行多个任务。因此，程序员必须对此引起高度重视，那些迄今为止一直忽视并发技术的人，现在必须将其纳入自己的核心工具箱。

使用并发提升性能主要有两种途径。第一种也是最显而易见的方式，是将单个任务拆分成若干部分并并行运行，从而缩短总运行时间。这就是任务并行（task parallelism）。尽管听起来很直观，但这可能是一个相当复杂的过程，因为各个部分之间可能存在大量的数据依赖。划分方式既可以基于处理逻辑——某个线程执行算法的第一阶段，另一个线程执行算法的第二阶段；也可以基于数据——每个线程在数据的不同分块上执行相同的操作。后一种途径被称为数据并行（data parallelism）。

易于适用于此类并行方式的算法通常被称为令人尴尬的并行算法（embarrassingly parallel，通常译为易并行或自然并行）。尽管字面上有“因代码太容易并行化而令人尴尬”的意味，但实际上这是一件极好的事情；对于这类算法，其他常见的描述还包括自然并行（naturally parallel）和便利并发（conveniently concurrent）。易并行算法具有优异的可伸缩性（scalability）——随着可用硬件线程数的增加，算法中的并行度可以相应提升以匹配硬件能力。这类算法完美印证了“人多力量大”这句谚语。对于算法中不属于易并行的部分，你可以尝试将算法划分为固定数量（因此不可伸缩）的并行任务。在线程间划分任务的技术将在第 8 章和第 10 章中深入讨论。

利用并发提升性能的第二种途径是利用可用的并行度去解决规模更大的问题；与其一次只处理一个文件，不如根据硬件情况并行处理 2 个、10 个或 20 个文件。虽然这也是数据并行的一种应用形式（通过对多组数据并发执行相同操作），但其侧重点有所不同。处理单个数据块所花费的时间依然相同，但在相同的时间内可以处理更多的数据。显然，这种方式存在物理边界，并非在所有场景下都能带来收益，但这种方法所带来的吞吐量提升可以使很多此前不可能的事情成为可能——例如在视频处理中提升分辨率，前提是画面的不同区域可以被并行处理。

### 1.2.3 何时不应使用并发

懂得何时**不使用**并发，与懂得何时使用并发同等重要。从根本上讲，不使用并发的唯一理由就是：其带来的收益抵不上付出的代价。在许多情况下，使用并发的代码更难理解，因此编写和维护多线程代码需要直接付出额外的智力成本，并且增加的复杂度极易引入隐蔽的缺陷。除非潜在的性能收益足够显著，或者关注点分离带来的模块清晰度足够高，足以证明编写正确代码所需的额外开发时间和维护多线程代码所需的额外开销是值得的，否则请不要轻易使用并发。

此外，性能收益可能并不像预期的那样美好；启动一个线程本身存在固有的开销，因为操作系统必须分配关联的内核资源和堆栈空间，然后将新线程添加到调度器中，这一切都需要消耗时间。如果要在线程上运行的任务转瞬即可完成，那么该任务的实际执行时间可能会被启动线程的开销彻底掩盖，甚至可能导致应用程序的整体性能比直接在主调用线程中同步执行还要差。

再者，线程是一种有限的系统资源。如果有过多的线程同时运行，这会消耗大量的操作系统资源，并可能导致整个系统的运行速度变慢。不仅如此，创建过多的线程还会耗尽进程可用的内存或虚拟地址空间，因为每个线程都需要独立的栈空间。这对于采用平坦架构的 32 位进程尤为致命（32 位进程通常只有 4 GB 的虚拟地址空间上限）：如果每个线程分配 1 MB 栈空间（在许多系统中是默认值），那么仅创建 4096 个线程就会彻底耗尽全部地址空间，根本没有空间留给代码段、静态数据或堆内存。虽然 64 位（或更大寻址空间）的系统没有这种直接的地址空间限制，但物理资源依然是有限的：运行过多的线程最终依然会引发系统问题。尽管线程池（详见第 9 章）可以缓解部分压力，但它们自身也有需要处理的问题。

在客户端/服务器架构的应用程序中，如果服务端为每个进来的网络连接都启动一个独立的线程，在连接数较少时这能工作良好；但如果在需要处理海量并发连接的高负载服务器上采用相同技术，则会因创建过多线程而迅速耗尽系统资源。在这种场景下，审慎地使用线程池能够提供最佳的性能（参见第 9 章）。

最后，运行的线程越多，操作系统必须执行的上下文切换就越频繁。每次上下文切换所花费的时间本可以用来做更有意义的实际工作，因此在某个临界点之后，额外增加线程反而会降低应用程序的整体性能而非提升它。出于这个原因，如果你试图榨取系统的极致性能，就必须根据可用的硬件并发能力（或缺乏并发能力的情况）来动态调整运行的线程数量。

为了性能而使用并发就像其他任何优化策略一样：它有可能大幅提升应用程序的性能，但同时也可能使代码变得复杂、更难理解且更容易滋生缺陷。因此，只应该在应用程序中那些对性能至关重要、且具备可衡量提升潜力的关键部分使用它。当然，如果追求性能只是次要目标，主要目标是设计的清晰性或关注点分离，那么采用多线程设计依然是非常值得的。

假定你已经决定要在应用程序中使用并发，不论是为了性能、为了关注点分离，还是仅仅因为“今天是写多线程的周一”，这对 C++ 程序员究竟意味着什么？

## 1.3 C++ 中的并发与多线程

通过多线程对并发提供标准化支持，对 C++ 而言是一个相对较新的特性。直到 C++11 标准出台，开发者才能够在不诉诸平台专属扩展的情况下编写可移植的多线程代码。为了理解标准 C++ 线程库中诸多设计决策背后的深层原因，了解其演进历史至关重要。

### 1.3.1 C++ 多线程演进史

1998 年发布的首个 C++ 标准（C++98）根本没有承认线程的存在，各种语言元素的运行效果都是基于顺序抽象机（sequential abstract machine）来定义的。不仅如此，内存模型也未作形式化定义，因此如果不借助特定编译器的专属扩展，根本无法在 C++98 标准下编写多线程应用程序。

编译器厂商可以自由为语言添加扩展，并且由于多线程 C 语言 API 的普遍存在（例如 POSIX C 标准中的 pthread 以及 Microsoft Windows API），许多 C++ 编译器厂商通过各种平台专属扩展提供了多线程支持。这种编译器支持通常仅限于允许使用对应平台的 C 语言 API，并确保 C++ 运行时库（例如异常处理机制背后的代码）在多线程并发存在时能够正常工作。尽管很少有编译器厂商提供形式化的多线程感知内存模型，但编译器和处理器的实际表现已经足够优秀，以至于业界基于这些扩展编写了海量的多线程 C++ 应用程序。

C++ 程序员并不满足于仅仅使用平台专属的 C 语言 API 来处理多线程，他们更渴望类库能够提供面向对象的多线程设施。诸如 MFC 等应用程序框架，以及 Boost 和 ACE 等通用 C++ 库，逐渐积累了一套套 C++ 类，用于封装底层平台专属的 API，并提供更高层次的多线程设施来简化任务。尽管这些类库的具体细节差异很大（尤其在启动新线程的方式上），但这些类的整体设计形态具有大量共通之处。许多 C++ 类库共有且为程序员带来巨大便利的一项极其重要的设计，就是使用 RAII（资源获取即初始化，Resource Acquisition Is Initialization）惯用法结合锁对象，以确保在退出相关作用域时互斥锁能够被自动释放。

在许多场景下，现有 C++ 编译器的多线程支持，结合平台专属 API 以及平台无关的类库（如 Boost 和 ACE），为编写多线程 C++ 代码提供了坚实的基础；因此，多线程应用程序中已经编写了数以百万计的 C++ 代码行。然而，缺乏标准支持意味着在某些场合下缺乏感知线程的内存模型会引发诡异的问题，尤其是对于那些试图通过利用处理器硬件知识来榨取极致性能的开发者，或者在编译器行为因平台而异的环境下编写跨平台代码的开发者而言更是如此。

### 1.3.2 C++11 标准中的并发支持

伴随着 C++11 标准的正式发布，这一切彻底改变了。新标准不仅引入了感知线程的内存模型，而且 C++ 标准库也得到了大幅扩展，包含了用于管理线程（参见第 2 章）、保护共享数据（参见第 3 章）、同步线程间操作（参见第 4 章）以及底层原子操作（参见第 5 章）的完备类族。

C++11 线程库在极大程度上借鉴了此前使用前述 C++ 类库所积累的成熟经验。尤其是 Boost 线程库（Boost Thread Library），被用作构建新标准库的主要蓝本，许多类的名称和结构与 Boost 中的对应组件完全一致。随着标准的演进，这种借鉴成为了双向的互动：Boost 线程库本身也进行了演进，在许多方面与 C++ 标准保持同步，因此从 Boost 迁移过来的用户会感到格外亲切自然。

并发支持只是 C++11 标准带来的诸多变革之一——正如本章开篇所述，语言本身也经历了大量的现代化增强，极大地改善了程序员的开发体验。虽然这些通用语言特性大体上超出了本书的主题范畴，但其中一些改动对线程库及其使用方式产生了直接而深远的影响。附录 A 对这些关键语言特性进行了简要介绍。

### 1.3.3 C++14 与 C++17 中更丰富的并发与并行支持

C++14 标准中专门针对并发与并行新增的特性相对较少，主要是引入了一种用于保护共享数据的新互斥锁类型（读写锁，参见第 3 章）。但 C++17 带来了更多实质性的飞跃：首先是引入了全套并行算法库（参见第 10 章）。这两个标准都进一步增强了核心语言特性和标准库的其他部分，这些增强有助于进一步简化多线程代码的编写。

如前所述，关于并发扩展的技术规范（Concurrency TS）描述了对 C++ 标准所提供的函数和类的进一步扩展，尤其是围绕线程间操作同步的设施（参见第 4 章）。

C++ 原生直接支持原子操作，使得程序员无需编写平台专属的汇编代码，即可编写出具备明确语义的高效代码。这对于致力于编写高效、跨平台代码的开发者来说是一大福音：不仅编译器负责处理平台底层细节，而且优化器在设计时也能充分理解这些操作的内存语义，从而对整个程序进行更加卓越的全局优化。

### 1.3.4 C++ 线程库的效率考量

从事高性能计算的开发者对于整个 C++ 以及封装了底层设施的 C++ 类（特别是新标准 C++ 线程库中的类）常常会提出一个核心关切：运行效率。如果你追求极致性能，那么理解使用任何高级设施相比于直接使用底层原始设施所带来的实现开销至关重要。这种开销通常被称为抽象惩罚（abstraction penalty）。

C++ 标准委员会在设计通用 C++ 标准库、尤其是标准 C++ 线程库时深刻意识到了这一点；其核心设计目标之一是：在提供相同功能的前提下，直接使用更低级别的底层 API 不应获得任何实质性的性能优势。因此，该标准库经过精心设计，确保在绝大多数主流平台上都能实现极高效率的底层映射（极低的抽象惩罚）。

C++ 标准委员会的另一个目标是确保 C++ 为那些希望紧贴底层硬件以榨取极限性能的开发者提供足够完备的底层设施。为此，伴随全新内存模型一同登场的是一个全面的原子操作库，用于对单个位和字节进行直接精细控制，以及实现线程间的同步和变更可见性控制。这些原子类型及其对应的操作现在可以广泛应用于开发者此前不得不求助于平台专属汇编语言的代码场景中。使用新标准类型和操作编写的代码不仅更加可移植，而且更易于维护。

C++ 标准库还提供了更高层次的抽象与设施，使多线程代码的编写更加轻松且更不易出错。有时，由于必须执行额外的管理代码，使用这些高级设施可能会带来一定的性能开销。但这种性能开销并不必然意味着更高的抽象惩罚；通常情况下，这种开销绝不会高于手工编写等效功能所付出的代价，并且编译器往往会将许多额外的辅助代码进行内联优化。

在某些情况下，高级设施所提供的功能可能超出了特定应用场景的实际需求。在绝大多数时候这都不是问题：你不需要为你没有使用的东西买单（零开销抽象原则）。在极少数情况下，这些未使用的功能可能会对其他代码的性能产生微弱影响。如果你追求极致性能而该成本过高，那么基于底层设施手工定制所需的功能或许更为合适。然而，在绝大多数实际工程中，手工定制所引入的额外复杂度和潜在出错几率，往往远超过微小性能提升所带来的微弱收益。即使性能剖析工具（profiler）确实表明性能瓶颈出现在 C++ 标准库设施中，这通常也是由于应用程序本身的设计不当所致，而非库实现低效。例如，如果过多线程激烈争用同一个互斥锁，势必会对性能造成严重冲击。与其试图在互斥锁操作上抠出微秒级的微小时间，不如重构应用程序架构以减少对互斥锁的争用，后者的收益将大得多。在第 8 章中我们将详细讨论如何设计应用程序以减少锁争用。

在极罕见的情况下，如果 C++ 标准库确实无法提供所需的性能或行为保证，可能才需要动用平台专属的底层设施。

### 1.3.5 平台专属设施

尽管 C++ 线程库提供了相当全面且强大的多线程与并发设施，但在任何给定的操作系统平台上，总会存在超出标准库范畴的平台专属设施。为了能够在不放弃使用标准 C++ 线程库优势的前提下轻松访问这些平台功能，C++ 线程库中的核心类型通常提供了 `native_handle()` 成员函数，允许直接获取其底层句柄，进而使用平台专属的 API 对底层实现进行操作。从本质上讲，任何使用 `native_handle()` 执行的操作都是完全依赖于具体平台的，超出了本书（以及 C++ 标准本身）的讨论范围。

在考虑使用平台专属设施之前，深入理解标准库所提供的功能至关重要，因此让我们先从一个示例正式起步。

## 1.4 初识多线程

好了，现在你已经拥有了一个现代化的 C++11/C++14/C++17 编译器。下一步该做什么？一个多线程 C++ 程序究竟长什么样？其实它看起来与任何其他 C++ 程序大同小异，同样包含变量、类和函数。唯一的本质区别在于，某些函数可能是并发运行的，因此你必须确保共享数据能够被安全地并发访问，正如第 3 章所详细阐述的那样。为了并发运行函数，必须使用特定的函数和对象来管理各个线程。

### 1.4.1 你好，并发世界

让我们从一个经典的示例开始：打印“Hello World”的程序。下面展示了一个在单线程中运行的简易 Hello World 程序，作为我们迈向多线程的对照基线：

```cpp
#include <iostream>
int main()
{
    std::cout<<"Hello World\n";
}
```

该程序所做的仅仅是向标准输出流写入“Hello World”。现在让我们将其与代码清单 1.1 中展示的简单的“Hello Concurrent World”并发程序进行对比，后者启动了一个独立的线程来输出这条问候语。

代码清单 1.1 一个简单的 Hello Concurrent World 程序

```cpp
#include <iostream>
#include <thread>
void hello()
{
    std::cout<<"Hello Concurrent World\n";
}
int main()
{
    std::thread t(hello);
    t.join();
}
```

第一个区别是额外包含了头文件 `#include <thread>`。C++ 标准库中对多线程支持的声明位于新的头文件中：用于管理线程的函数和类声明在 `<thread>` 中，而用于保护共享数据的设施则声明在其他头文件中（如 `<mutex>` 等）。

第二个区别是打印消息的代码被移到了一个独立的函数 `hello()` 中。这是因为每个线程都必须拥有一个初始函数（initial function），新线程的执行便从此处启程。对于应用程序的主初始线程而言，这个入口是 `main()`；而对于任何其他线程，入口函数则在 `std::thread` 对象的构造函数中指定——在本例中，名为 `t` 的 `std::thread` 对象将新函数 `hello()` 作为其执行起点。

接下来的区别在于：该程序不再是直接在 `main()` 中向标准输出写入内容或调用 `hello()`，而是启动了一个全新的线程来执行该操作，从而使线程总数增加到了两个——从 `main()` 开始运行的初始线程，以及从 `hello()` 开始运行的新线程。

在新线程启动之后，初始线程继续向下执行。如果初始线程不等待新线程执行完毕，它就会一路狂奔至 `main()` 的末尾并导致整个程序退出——此时新线程甚至可能还没来得及运行。这就是为什么代码中需要调用 `join()` 的原因——正如第 2 章所介绍的，这会导致调用线程（位于 `main()` 中）阻塞等待与 `std::thread` 对象（此处为 `t`）关联的线程执行结束。

如果为了在标准输出上打印一条消息而花费如此大的周折看起来像是小题大做，事实确实如此——正如 1.2.3 节所阐述的，对于如此简单的任务，使用多线程通常是不划算的，尤其是当初始线程在此期间无事可做的时候。在本书后续章节中，我们将通过大量实例展示在哪些业务场景下使用多线程能够带来显著且确切的收益。

### 本章小结

在本章中，我介绍了并发与多线程的基本概念，以及为什么要在应用程序中选择使用（或不使用）它。同时，我们回顾了 C++ 多线程的演进历史：从 1998 年标准的完全缺失，到各大平台的专有扩展，再到 C++11 标准中正式确立的完备多线程支持，以及 C++14、C++17 标准和并发技术规范（Concurrency TS）的进一步扩展。这一标准支持来得非常及时，使得程序员能够充分利用现代 CPU 提供的强大硬件并发能力；因为芯片制造商选择以多核形式增加处理能力，允许并发执行更多任务，而不是继续单纯提升单核的运行频率。

在 1.4 节的示例中，我还展示了使用 C++ 标准库中的类和函数是多么简单。在 C++ 中，使用多线程本身并不复杂；真正的难点在于如何设计代码，以确保其在并发环境下的行为完全符合预期。

经过 1.4 节的起步示例之后，我们该迈向更具实质性的内容了。在第 2 章中，我们将详细探讨用于管理线程的各种类与函数。
