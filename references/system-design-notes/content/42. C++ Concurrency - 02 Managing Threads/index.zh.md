# 第 2 章：线程管理

管理线程

本章主要内容包括：

- 启动线程，以及在全新线程上指定运行代码的多种方式
- 等待线程执行结束 vs 允许其在后台独立运行
- 唯一标识线程

好的，你已经决定在应用程序中使用并发技术，并且具体选定了使用多线程。那么接下来呢？该如何启动这些线程、检查它们是否已执行完毕，并对它们进行有效跟踪？正如你将看到的那样，C++ 标准库让绝大多数线程管理任务变得相当直观简单，几乎所有事情都可以通过与特定线程关联的 `std::thread` 对象来集中管理。而对于那些不那么直接的高级任务，标准库也提供了足够的灵活性，允许你使用基础构建块自由搭建所需功能。

在本章中，我将首先介绍最基础的操作：启动线程、等待线程结束，或者让线程在后台独立运行。随后我们将探讨在启动线程时向线程函数传递附加参数，以及如何在不同的 `std::thread` 对象之间转移线程的所有权。最后，我们将讨论如何在运行时合理选择要使用的线程数量，以及如何唯一标识特定线程。

## 2.1 线程管理基础

每个 C++ 程序都至少拥有一个由 C++ 运行时自动启动的线程：即执行 `main()` 函数的主线程。随后，你的程序可以启动额外的线程，并将另一个函数作为新线程的入口点。这些新线程将与初始主线程以及彼此之间并发运行。正如程序在从 `main()` 函数返回时会正常退出一样，当指定的入口点函数返回时，对应的线程也会终止退出。正如你将看到的，如果你持有一个与线程关联的 `std::thread` 对象，你就可以等待该线程执行完毕；但在此之前你必须先启动它，所以让我们首先来看如何启动线程。

### 2.1.1 启动线程

正如你在第 1 章中所见，启动线程是通过构造一个 `std::thread` 对象来实现的，构造时需要指定该线程要执行的任务。在最简单的场景下，该任务可以是一个普通的、无参数且返回值为 `void` 的函数。该函数在自己的独立线程上持续运行直至返回，随后该线程终止。而在另一个极端情况下，任务可以是一个接受额外参数的函数对象，并在运行期间通过某种消息传递系统执行一系列独立操作，且只有在通过消息系统接收到停止信号时才会终止退出。无论线程具体执行什么逻辑，或者从何处被启动，在 C++ 标准库中启动线程归根结底都是构造一个 `std::thread` 对象：

```cpp
void do_some_work();
std::thread my_thread(do_some_work);
```

这就是最直观的形式。当然，你必须确保包含了 `<thread>` 头文件，以便编译器能够识别 `std::thread` 类的定义。与 C++ 标准库的大多数组件一样，`std::thread` 可以与任何**可调用对象（callable type）**协同工作，因此你也可以向 `std::thread` 构造函数传递重载了调用运算符 `operator()` 的类实例：

```cpp
class background_task
{
public:
    void operator()() const
    {
        do_something();
        do_something_else();
    }
};

background_task f;
std::thread my_thread(f);
```

在此情况下，传入的函数对象会被**拷贝**到属于新创建执行线程的存储空间中，并从那里被调用。因此，拷贝出来的副本必须与原始对象具有完全等价的行为，否则执行结果可能与预期大相径庭。

向线程构造函数传递函数对象时，有一点必须格外注意：避免遭遇所谓的“C++ 最令人头痛的语法解析（C++'s most vexing parse）”。如果你传递的是一个临时对象而非具名变量，其语法可能会与函数声明完全一致，此时编译器会将其解析为函数声明，而非对象的定义。例如：

```cpp
std::thread my_thread(background_task());
```

这实际上声明了一个名为 `my_thread` 的函数，该函数接受一个单独参数（其类型为“指向无参数且返回 `background_task` 对象的函数指针”），并返回一个 `std::thread` 对象，而不是启动一个新线程！你可以通过前面所示的方式先定义具名变量，或者通过添加额外的一层括号，或者使用现代统一初始化列表（花括号）语法来规避此问题；例如：

```cpp
std::thread my_thread((background_task()));
std::thread my_thread{background_task()};
```

在第一种写法中，多加的括号阻止了编译器将其解释为函数声明，从而使 `my_thread` 被正确识别为 `std::thread` 类型的变量。第二种写法采用了花括号统一初始化语法，同样声明了一个变量。

能够避免该解析歧义的一种极其便利的可调用对象是 Lambda 表达式（Lambda expression）。这是 C++11 引入的核心特性，允许你编写就地匿名的局部函数，甚至可以按需捕获局部变量，省去传递多余参数的麻烦（参见 2.2 节）。前述示例可以使用 Lambda 表达式重写为：

```cpp
std::thread my_thread([]{
    do_something();
    do_something_else();
});
```

一旦启动了线程，你必须明确决定是等待它执行结束（通过汇合它——即调用 `join()`，参见 2.1.2 节），还是任由其自行在后台运行（通过分离它——即调用 `detach()`，参见 2.1.3 节）。如果你在 `std::thread` 对象被销毁之前未做出明确抉择，那么你的程序将会被强制终止（因为 `std::thread` 的析构函数会直接调用 `std::terminate()`）。因此，必须确保在任何执行路径下（即使发生异常）线程都能被正确地汇合（joined）或分离（detached）。关于如何妥善处理该场景的技术请参见 2.1.3 节。请注意，你只需要在 `std::thread` 对象被销毁前做出该决定即可——线程本身完全可能在你汇合或分离它之前很久就已经执行结束；而如果你分离了它，当线程仍在运行时它将继续在后台执行，并且完全可以在 `std::thread` 对象销毁很久之后依然存活；只有当它最终从线程函数返回时才会真正终止。

如果不等待线程结束，你必须确保该线程所访问的数据在线程运行期间始终保持有效。这并不是一个新问题——即便在单线程代码中，访问已经销毁的对象同样会导致**未定义行为（undefined behavior）**——但在引入多线程后，这种生命周期管理失误的几率显著增加了。

容易出现此类问题的一种典型场景是：线程函数持有指向局部变量的指针或引用，而当外部函数退出时，新线程尚未执行完毕。代码清单 2.1 展示了这样一个危险场景。

代码清单 2.1 函数返回后线程依然持有对局部变量的访问权

```cpp
struct func
{
    int& i;
    func(int& i_):i(i_){}
    void operator()()
    {
        for(unsigned j=0;j<1000000;++j)
        {
            do_something(i); // 存在访问悬空引用的巨大风险
        }
    }
};

void oops()
{
    int some_local_state=0;
    func my_func(some_local_state);
    std::thread my_thread(my_func);
    my_thread.detach(); // 不等待线程结束
} // 新线程可能仍在后台运行，但局部变量 some_local_state 已经在此处销毁
```

在本例中，当 `oops()` 函数退出时，与 `my_thread` 关联的新线程大概率仍在运行，因为你通过调用 `detach()` 显式决定了不等待它。如果新线程仍在运行，就会出现表 2.1 所示的致命情况：对 `do_something(i)` 的后续调用将访问一个已经被销毁的局部变量。这与普通单线程代码中的错误如出一辙——允许指针或引用在超出函数作用域后继续存活绝不是什么好事——但在多线程代码中更容易犯下此类错误，因为问题发生的时序隐蔽，往往无法立即显现。

表 2.1 分离线程在局部变量销毁后继续访问它的时序

| 主线程 (Main thread) | 新线程 (New thread) |
| :--- | :--- |
| 构造 `my_func`，持有对 `some_local_state` 的引用 | 尚未启动 |
| 启动新线程 `my_thread` | 启动中 |
| | 已启动，调用 `func::operator()` |
| 分离线程 `my_thread.detach()` | 运行 `func::operator()`；可能正在使用引用的 `some_local_state` 调用 `do_something` |
| 销毁 `some_local_state` | 仍在运行中 |
| 退出 `oops` 函数 | 仍在运行 `func::operator()`；调用 `do_something` 访问已销毁的 `some_local_state` => **未定义行为** |

应对这种场景的一种常见解决策略是：让线程函数保持自给自足（self-contained），将所需数据以值拷贝的方式复制到线程内部，而不是在线程间共享引用。如果你使用函数对象作为线程函数，该对象本身会被拷贝到线程内部，因此原始对象可以被安全销毁。但你仍然需要警惕对象内部包含的指针或引用，如代码清单 2.1 所示。特别是，除非你能确保新线程在函数退出前必然执行结束，否则在函数内部创建一个能够访问该函数局部变量的线程是非常糟糕的做法。

另一种确保安全的替代方案是：通过汇合（joining）该线程，确保其在函数退出之前彻底执行完毕。

### 2.1.2 等待线程完成

如果你需要等待某个线程执行完成，可以通过在对应的 `std::thread` 实例上调用 `join()` 来实现。针对代码清单 2.1，只需在函数体闭合花括号之前将 `my_thread.detach()` 替换为 `my_thread.join()`，便足以保证新线程在函数退出前彻底完成，从而在局部变量销毁之前安全终止。在本例中，这意味着在独立线程上运行该函数可能失去实际意义，因为主线程在此期间并没有执行任何有益的工作；但在实际生产代码中，原始线程要么有自己的计算任务要处理，要么会同时启动多个子线程并发执行任务，最后再等待所有子线程汇合。

`join()` 是一种简单且直接的粗粒度控制机制——要么你等待线程执行完，要么不等。如果你需要对等待线程实施更精细的控制，例如检测线程是否已执行结束、或者只允许等待特定超时时间，那么必须使用条件变量（condition variable）或期望值（future）等替代机制，这些内容将在第 4 章中深入探讨。调用 `join()` 的同时还会清理与该线程关联的所有底层存储资源，因此一旦调用完毕，`std::thread` 对象将不再与任何实际线程关联。这意味着对于给定的线程，你只能调用一次 `join()`；一旦对其调用了 `join()`，该 `std::thread` 对象就不再是可汇合的（joinable），此时调用 `joinable()` 将返回 `false`。

### 2.1.3 在异常情况下等待

如前所述，你必须确保在 `std::thread` 对象被析构之前，显式调用了 `join()` 或 `detach()`。如果是分离线程，通常可以在线程启动后立即调用 `detach()`，因此这往往不是难题。但如果你计划等待线程结束，就必须非常审慎地选择在代码的何处调用 `join()`。如果新线程启动之后、且在调用 `join()` 之前抛出了异常，那么对 `join()` 的调用将极易被跳过。

为了避免应用程序因未汇合的线程而在析构时被强制终止，你必须明确定义在出现异常时的处理行为。一般而言，如果你打算在正常路径下调用 `join()`，那么在发生异常的路径上也同样需要调用 `join()`，以避免意外的对象生命周期悬空问题。下面的代码清单展示了实现该逻辑的一种简单方式。

代码清单 2.2 在异常情况下等待线程完成

```cpp
struct func; // 定义参见代码清单 2.1

void f()
{
    int some_local_state=0;
    func my_func(some_local_state);
    std::thread t(my_func);
    try
    {
        do_something_in_current_thread();
    }
    catch(...)
    {
        t.join(); // 发生异常时等待线程汇合
        throw;    // 重新抛出捕获的异常
    }
    t.join();     // 正常退出路径等待线程汇合
}
```

代码清单 2.2 中的代码使用了 `try/catch` 块来确保持有局部状态引用的线程在函数退出前必定完成，无论函数是正常返回还是通过异常抛出。然而，使用 `try/catch` 显得十分冗长，而且很容易因作用域界定不慎而产生遗漏，因此这并非理想的设计方案。如果必须保证线程在函数退出前彻底完成（无论是因为它引用了局部变量还是出于其他架构要求），那么确保在所有可能的退出路径（包括正常路径与异常路径）上都执行汇合至关重要，因此提供一种简洁优雅、遵循 RAII 原则的自动化机制显得尤为必要。

实现此目的的一种规范方法是使用标准的“资源获取即初始化”（RAII）惯用法，提供一个在其析构函数中自动调用 `join()` 的守护类，如下面的代码清单所示。请注意它对 `f()` 函数的精简效果。

代码清单 2.3 使用 RAII 等待线程完成

```cpp
class thread_guard
{
    std::thread& t;
public:
    explicit thread_guard(std::thread& t_):
        t(t_)
    {}
    ~thread_guard()
    {
        if(t.joinable())
        {
            t.join();
        }
    }
    thread_guard(thread_guard const&)=delete;
    thread_guard& operator=(thread_guard const&)=delete;
};

struct func; // 定义参见代码清单 2.1

void f()
{
    int some_local_state=0;
    func my_func(some_local_state);
    std::thread t(my_func);
    thread_guard g(t);
    do_something_in_current_thread();
} // 无论正常结束还是抛出异常，g 的析构函数都会确保 t.join() 被调用
```

当当前线程的执行到达 `f` 的末尾时，栈上的局部对象会按照构造的相反顺序自动逆序析构。因此，`thread_guard` 对象 `g` 会最先被析构，并在其析构函数中自动对关联的线程执行 `join()`。即使函数因为 `do_something_in_current_thread()` 抛出异常而退出，栈展开过程也会同样保证 `g` 的析构函数被调用。

代码清单 2.3 中 `thread_guard` 的析构函数在调用 `t.join()` 之前，首先检查了 `std::thread` 对象是否依然处于 `joinable()` 状态。这是至关重要的防御性设计，因为对同一个执行线程只能调用一次 `join()`；如果之前已经由于其他原因汇合过了，再次调用 `join()` 将会引发程序崩溃。

拷贝构造函数和拷贝赋值运算符被显式声明为 `=delete`，以确保编译器不会自动生成它们。复制或赋值此类守护对象是非常危险的，因为新对象的生命周期可能会超出它所守护线程的作用域。通过将其声明为删除函数，任何试图拷贝 `thread_guard` 对象的尝试都会直接引发编译错误。

如果你完全不需要等待线程执行完毕，也可以通过分离它（detach）来彻底绕过这类异常安全问题。调用 `detach()` 会切断线程与 `std::thread` 对象之间的管理纽带，确保即使新线程仍在后台默默运行，`std::thread` 对象的析构也不会触发 `std::terminate()`。

### 2.1.4 在后台运行线程

在 `std::thread` 对象上调用 `detach()` 会让线程脱离控制并在后台独立运行，且外部不再拥有直接与该线程进行通信的手段。调用之后，将无法再等待该线程完成；一旦线程被分离，就没有任何 `std::thread` 对象能够再引用它，因此它也无法再被汇合。分离的线程真正运行在后台；其所有权和控制权完全交接给了 C++ 运行时库，运行时库负责在线程退出时自动且正确地回收该线程占用的系统资源。

分离线程通常被称为**守护线程（daemon threads）**，该术语源自 UNIX 系统中在后台默默运行且没有显式用户界面的守护进程（daemon process）。这类线程通常生命周期很长：它们几乎在应用程序的整个生命周期中持续运行，负责执行后台辅助任务，例如监控文件系统变动、清理对象缓存中的过期条目，或者定期优化内存数据结构。在另一个极端情况下，如果存在其他外部机制来检测线程是否完成，或者该线程纯粹用于执行“即发即弃”（fire-and-forget）的短小任务，使用分离线程也是非常自然的选择。

正如你在 2.1.2 节中所见，通过调用 `std::thread` 对象的 `detach()` 成员函数即可分离一个线程。调用完成后，`std::thread` 对象不再与实际的底层执行线程保持关联，因此也不再是可汇合的：

```cpp
std::thread t(do_background_work);
t.detach();
assert(!t.joinable());
```

为了从 `std::thread` 对象中分离线程，必须存在一个有效的关联线程可供分离：你不能对一个没有关联实际执行线程的空 `std::thread` 对象调用 `detach()`。这与调用 `join()` 的前置要求完全一致，且可以通过相同的方式进行前置校验——只有当 `t.joinable()` 返回 `true` 时，你才能合法地调用 `t.detach()`。

考虑一个诸如文字处理器之类的应用程序，它允许同时编辑多个文档。无论是从 UI 层面还是内部实现层面，都有多种架构设计来处理这一需求。当下一种越来越流行的架构是：为正在编辑的每个文档开启一个独立的顶级窗口。虽然这些窗口在视觉上看似完全独立（各自拥有菜单和工具栏），但它们都运行在同一个应用程序进程实例中。在内部实现上，一种优雅的方式是让每个文档编辑窗口在自己的独立线程中运行；每个线程运行相同的 UI 与事件循环代码，但操作与当前文档及对应窗口属性相关的独立数据。因此，打开新文档就需要启动一个新线程。当前处理打开请求的线程根本不需要等待另一个文档线程完成，因为它们处理的是完全不相干的独立文件，因此这正是使用分离线程的绝佳用例。

下面的代码清单展示了该方法的核心代码框架。

代码清单 2.4 分离线程以处理独立文档

```cpp
void edit_document(std::string const& filename)
{
    open_document_and_display_gui(filename);
    while(!done_editing())
    {
        user_command cmd=get_user_input();
        if(cmd.type==open_new_document)
        {
            std::string const new_name=get_filename_from_user();
            std::thread t(edit_document,new_name);
            t.detach();
        }
        else
        {
            process_user_input(cmd);
        }
    }
}
```

如果用户选择打开一个新文档，程序提示用户选择目标文件，启动一个新线程来加载该文档，然后立即分离它。由于新线程与当前线程执行相同的操作（只是操作不同的文件），我们可以复用同一个函数 `edit_document`，并将用户新选定的文件名作为参数传入。

这个例子还顺带展示了一个非常有用的技巧：在启动线程时向线程函数传递参数。我们不再是仅仅将函数名传递给 `std::thread` 构造函数，而是连同 `filename` 参数一起传入。虽然也可以使用其他机制来实现（例如使用带有成员数据的函数对象而非带参函数），但 C++ 标准库直接为你提供了一种极其便捷的参数传递方式。

## 2.2 向线程函数传递参数

正如代码清单 2.4 所示，向可调用对象或函数传递参数，本质上就如同向 `std::thread` 构造函数追加额外的实参一样简单。但必须时刻牢记：默认情况下，传入的参数会被**按值拷贝**到新线程的内部存储空间中，供新创建的执行线程访问，然后作为**右值（rvalue）**（如同临时变量一般）传递给可调用对象或函数。即使目标函数的对应形参明确声明为引用类型，这种默认的按值拷贝行为依然会发生。示例如下：

```cpp
void f(int i,std::string const& s);
std::thread t(f,3,"hello");
```

这将创建一个与 `t` 关联的新执行线程，并在其中调用 `f(3, "hello")`。请注意，尽管 `f` 的第二个参数接受一个 `std::string const&`，但字符串字面量在传递时仍是作为 `char const*` 存入内部存储的，只有在新线程的执行上下文中，它才会被隐式转换为 `std::string`。当传入的参数是指向自动变量（局部变量）的指针时，这种延迟转换行为可能会引发灾难性的未定义行为，如下所示：

```cpp
void f(int i,std::string const& s);
void oops(int some_param)
{
    char buffer[1024];
    sprintf(buffer, "%i",some_param);
    std::thread t(f,3,buffer); // 危险！buffer 是裸指针
    t.detach();
}
```

在这种情况下，传递给新线程内部存储的只是指向局部数组 `buffer` 的原始指针；而 `oops()` 函数极有可能在新线程于其上下文中将 `buffer` 转换为 `std::string` 之前就已经执行完毕并退出，从而导致新线程访问已销毁的栈内存，引发未定义行为。正确的解决方案是在将 `buffer` 传入 `std::thread` 构造函数之前，将其显式强制转换为 `std::string`：

```cpp
void f(int i,std::string const& s);
void not_oops(int some_param)
{
    char buffer[1024];
    sprintf(buffer,"%i",some_param);
    std::thread t(f,3,std::string(buffer)); // 显式转换为 std::string 规避悬空指针
    t.detach();
}
```

在这里，原始代码的问题在于它依赖了指针到函数形参所期望的 `std::string` 对象的隐式转换，但这一转换发生得太迟了，因为 `std::thread` 构造函数会原封不动地直接按值盲目拷贝传入的数据，并不会在主线程中先行转换为目标形参类型。

相反的情况也是无法直接通过编译的：即对象被拷贝了，而你的函数期望接收一个非常量引用（non-const reference）。如果你试图让线程更新一个按引用传入的数据结构时，可能会尝试这样写：

```cpp
void update_data_for_widget(widget_id w,widget_data& data);
void oops_again(widget_id w)
{
    widget_data data;
    std::thread t(update_data_for_widget,w,data);
    display_status();
    t.join();
    process_widget_data(data);
}
```

尽管 `update_data_for_widget` 的第二个参数期望按引用传递，但 `std::thread` 构造函数对此一无所知；它并不关心目标函数所期望的形参类型，而是直接拷贝传入的实参。然而，为了支持仅可移动（move-only）的类型，内部调用机制会将拷贝后的副本作为右值进行传递，因此它会尝试以右值调用期望非常量左值引用的 `update_data_for_widget`。由于 C++ 语法严禁将右值绑定到非常量左值引用，这段代码将无法通过编译。对于熟悉 `std::bind` 的开发者而言，解决方案显而易见：必须使用 `std::ref` 将需要作为引用的参数进行包装。在本例中，只需将线程的构造调用修改为：

```cpp
std::thread t(update_data_for_widget,w,std::ref(data));
```

此时 `update_data_for_widget` 将正确接收到对外部 `data` 的真正引用，而非一份临时副本，代码即可成功通过编译并按预期工作。

如果你熟悉 `std::bind`，那么这一套参数传递语义就不会令你感到意外，因为 `std::thread` 构造函数的底层工作原理与 `std::bind` 的调用转发机制是完全相同的。这也意味着，你可以传递一个成员函数指针作为线程函数，只要将合适的对象指针作为第一个参数提供即可：

```cpp
class X
{
public:
    void do_lengthy_work();
};
X my_x;
std::thread t(&X::do_lengthy_work,&my_x);
```

这段代码将在新线程上调用 `my_x.do_lengthy_work()`，因为 `my_x` 的地址被作为成员函数的 `this` 指针传入。你还可以为该成员函数调用提供额外的实参：传递给 `std::thread` 构造函数的第三个参数将成为成员函数的第一个参数，以此类推。

提供参数时的另一个常见且有趣的场景是：参数类型是不可拷贝、而只能被移动的（move-only）：即一个对象内部持有的数据所有权被转移给另一个对象，原始对象则被置空。这种类型的一个典型代表是 `std::unique_ptr`，它为动态分配的对象提供了自动化的内存管理。在同一时刻，只能有一个 `std::unique_ptr` 实例指向给定的堆对象，当该智能指针销毁时，其指向的对象会被自动释放。移动构造函数和移动赋值运算符允许在不同的 `std::unique_ptr` 实例之间安全转移对象的所有权。这种转移会使源对象变为 `nullptr`。这种移动语义允许该类型的对象作为函数参数传入或作为函数返回值返回。当源对象是临时变量时，移动是隐式且自动完成的；但如果源对象是一个具名变量，则必须通过显式调用 `std::move()` 来发起所有权转移。下面的示例展示了如何使用 `std::move` 将一个动态对象的所有权转移到线程中：

```cpp
void process_big_object(std::unique_ptr<big_object>);
std::unique_ptr<big_object> p(new big_object);
p->prepare_data(42);
std::thread t(process_big_object,std::move(p));
```

通过在 `std::thread` 构造函数中指定 `std::move(p)`，`big_object` 的所有权首先被转移到新创建线程的内部暂存区中，随后在线程启动执行时被进一步转移到 `process_big_object` 函数的形参中。

C++ 标准库中的若干类展现出与 `std::unique_ptr` 相同的独占所有权语义，而 `std::thread` 正是其中之一。尽管 `std::thread` 实例并不像 `std::unique_ptr` 那样拥有一个堆内存对象，但它们确实拥有具体的系统资源：每个实例负责管理一个底层的执行线程。这种所有权可以在不同实例之间自由转移，因为 `std::thread` 实例是**可移动但不可复制的**。这确保了在任何一个时刻，只能有一个对象与特定的底层执行线程相关联，同时赋予了程序员在不同对象之间灵活交接管理权的能力。

## 2.3 转移线程所有权

假定你想编写一个函数，该函数创建一个在后台运行的线程，但将新线程的所有权返回给调用方，而不是在函数内部等待其完成；或者你希望实现相反的需求：在外部创建一个线程，并将其所有权传递给某个负责等待其结束的管理器函数。在任何一种情况下，你都需要将线程的所有权从一个地方安全转移到另一个地方。

这正是 `std::thread` 的移动语义大显身手之处。正如前一节所述，C++ 标准库中许多负责管理稀缺资源的类型（如 `std::ifstream` 和 `std::unique_ptr`）都是可移动但不可复制的，`std::thread` 亦属此类。这意味着特定执行线程的所有权可以在不同的 `std::thread` 实例之间灵活移动，如下面的代码所示。该示例演示了两个执行线程的创建，以及在三个 `std::thread` 实例（`t1`、`t2` 和 `t3`）之间转移所有权的全过程：

```cpp
void some_function();
void some_other_function();
std::thread t1(some_function);
std::thread t2=std::move(t1);
t1=std::thread(some_other_function);
std::thread t3;
t3=std::move(t2);
t1=std::move(t3); // 致命错误！此赋值将导致程序直接调用 std::terminate() 终止！
```

首先，启动一个新线程并将其与 `t1` 关联。随后在构造 `t2` 时，通过调用 `std::move()` 显式将线程的所有权转移给了 `t2`。此时，`t1` 不再持有任何执行线程；运行 `some_function` 的线程现在与 `t2` 关联。

接着，启动另一个新线程并将其与一个临时的 `std::thread` 对象关联。随后的移动赋值转移给 `t1` 时不需要显式调用 `std::move()`，因为源对象是一个右值临时对象——从临时变量进行的移动是自动且隐式的。

`t3` 是采用默认构造的，这意味着它在创建时不持有任何执行线程。通过再次显式调用 `std::move()`，当前与 `t2` 关联的线程所有权被转移到了 `t3` 中。经过这一系列移动后，`t1` 与运行 `some_other_function` 的线程关联，`t2` 为空（不持有线程），而 `t3` 与运行 `some_function` 的线程关联。

最后一步试图将运行 `some_function` 的线程所有权从 `t3` 移回给 `t1`。然而，此时 `t1` 已经持有着一个有效的关联线程（正在运行 `some_other_function`），因此系统将直接调用 `std::terminate()` 强行终止整个程序！

这与 `std::thread` 的析构行为在设计上保持了高度一致。在 2.1.1 节中你已经看到，在对象销毁之前，你必须显式汇合或分离线程；这一铁律对于赋值操作同样适用：你绝不能通过直接给管理线程的 `std::thread` 对象赋予新值来随意“丢弃”它原本持有的活动线程。

`std::thread` 原生支持移动语义，意味着我们可以极为方便地将线程所有权从函数内部传递出来，如下面的代码清单所示。

代码清单 2.5 从函数返回 `std::thread`

```cpp
std::thread f()
{
    void some_function();
    return std::thread(some_function);
}
std::thread g()
{
    void some_other_function(int);
    std::thread t(some_other_function,42);
    return t;
}
```

同理，如果某个函数需要接管线程的所有权，它可以声明一个按值接收 `std::thread` 实例的形参，如下所示：

```cpp
void f(std::thread t);
void g()
{
    void some_function();
    f(std::thread(some_function));
    std::thread t(some_function);
    f(std::move(t));
}
```

利用 `std::thread` 的移动语义，一个显著的好处是我们可以对代码清单 2.3 中的 `thread_guard` 类进行升级，让其直接**接管**线程的所有权。这彻底避免了守护对象比它所引用的外部线程存活时间更长而导致的隐患，同时也意味着一旦所有权被转移进该对象，外部任何其他代码都无法再意外对其进行汇合或分离。由于该类主要用于确保在退出作用域前子线程必然执行完毕，我将其命名为 `scoped_thread`。其具体实现及使用示例如代码清单 2.6 所示。

代码清单 2.6 `scoped_thread` 及其使用示例

```cpp
class scoped_thread
{
    std::thread t;
public:
    explicit scoped_thread(std::thread t_):
        t(std::move(t_))
    {
        if(!t.joinable())
            throw std::logic_error("No thread");
    }
    ~scoped_thread()
    {
        t.join();
    }
    scoped_thread(scoped_thread const&)=delete;
    scoped_thread& operator=(scoped_thread const&)=delete;
};

struct func; // 定义参见代码清单 2.1

void f()
{
    int some_local_state;
    scoped_thread t{std::thread(func(some_local_state))};
    do_something_in_current_thread();
}
```

该示例与代码清单 2.3 类似，但新线程是直接以右值方式传入 `scoped_thread` 的，而无需先为其在外部声明一个独立的具名变量。当主调用线程到达 `f` 的末尾时，`scoped_thread` 对象被自动销毁，并在其析构函数中自动汇合传入构造函数的线程。与代码清单 2.3 中析构函数必须检查线程是否仍为 `joinable()` 不同，这里我们在构造函数中就严格完成了这一校验，如果传入的线程不可汇合则立即抛出异常。

针对 C++17，曾有一项关于引入 `joining_thread` 类的标准化提案，其行为与 `std::thread` 高度相似，区别在于它会在析构函数中像 `scoped_thread` 一样自动调用 `join()`。该提案当时未在委员会中达成充分共识，因此未被纳入 C++17（不过后来其思想在 C++20 中以 `std::jthread` 的形式被正式纳入标准），但自行编写这样一个包装类是非常容易的。代码清单 2.7 展示了一种可行的完整实现方案。

代码清单 2.7 自定义 `joining_thread` 类

```cpp
class joining_thread
{
    std::thread t;
public:
    joining_thread() noexcept=default;
    template<typename Callable,typename ... Args>
    explicit joining_thread(Callable&& func,Args&& ... args):
        t(std::forward<Callable>(func),std::forward<Args>(args)...)
    {}
    explicit joining_thread(std::thread t_) noexcept:
        t(std::move(t_))
    {}
    joining_thread(joining_thread&& other) noexcept:
        t(std::move(other.t))
    {}
    joining_thread& operator=(joining_thread&& other) noexcept
    {
        if(joinable())
            join();
        t=std::move(other.t);
        return *this;
    }
    joining_thread& operator=(std::thread other) noexcept
    {
        if(joinable())
            join();
        t=std::move(other);
        return *this;
    }
    ~joining_thread() noexcept
    {
        if(joinable())
            join();
    }
    void swap(joining_thread& other) noexcept
    {
        t.swap(other.t);
    }
    std::thread::id get_id() const noexcept{
        return t.get_id();
    }
    bool joinable() const noexcept
    {
        return t.joinable();
    }
    void join()
    {
        t.join();
    }
    void detach()
    {
        t.detach();
    }
    std::thread& as_thread() noexcept
    {
        return t;
    }
    const std::thread& as_thread() const noexcept
    {
        return t;
    }
};
```

`std::thread` 对移动语义的支持还使其能够被放置在标准容器中（只要这些容器支持移动语义，例如现代化的 `std::vector<>`）。这意味着你可以像代码清单 2.8 那样，批量启动一组线程，并统一等待它们全部执行完毕。

代码清单 2.8 批量生成线程并等待其全部完成

```cpp
void do_work(unsigned id);

void f()
{
    std::vector<std::thread> threads;
    for(unsigned i=0;i<20;++i)
    {
        threads.emplace_back(do_work,i); // 批量生成线程
    }
    for(auto& entry: threads)
        entry.join(); // 依次对每个线程调用 join()
}
```

如果将线程用于细分并行算法的工作负载，这通常正是标准做法：在返回调用方之前，所有子线程必须全部执行完毕。代码清单 2.8 的简洁结构假定了各个线程所做的工作是彼此独立的，操作结果纯粹通过共享数据的副作用来体现。如果 `f()` 需要根据这些线程的运算结果向调用方返回一个综合计算值，那么按照目前的代码写法，该返回值必须在所有线程终止之后，通过汇总检查共享数据来确定。在第 4 章中，我们将讨论在线程之间传递计算结果的其他替代方案（如使用期望值 future）。

将 `std::thread` 对象放入 `std::vector` 是迈向自动化管理线程的重要一步：我们不再需要为每个线程创建单独的命名变量并逐一手工汇合，而是可以将它们作为一个整体集合来批量调度。更进一步，我们可以在运行时动态计算并创建所需线程的数量，而不是硬编码像代码清单 2.8 中那样固定的线程数目。

## 2.4 在运行时选择线程数量

在动态决策线程数方面，C++ 标准库提供了一个极具价值的工具函数：`std::thread::hardware_concurrency()`。该函数返回当前程序在特定执行环境下能够真正并发运行的硬件线程数量的估算值。在多核系统上，这通常对应于 CPU 物理核心数或逻辑核心数（考虑超线程时）。需要说明的是，这仅仅是一个参考提示（hint）；如果系统无法提供此项底层硬件信息，该函数可能会返回 0，但这仍然是指导我们合理划分任务工作量的重要依据。

代码清单 2.9 展示了一个朴素的并行版 `std::accumulate` 实现。在实际生产代码中，你通常会直接采用第 10 章所介绍的标准库 C++17 并行版 `std::reduce`，而不是自行重复造轮子，但这里的代码生动展示了并行分治的核心思想。它将工作切分并分配给各个线程，同时为每个线程设置了最小处理元素数阈值，以避免创建过多线程带来的性能反噬。请注意，该示例代码假定所有操作均不会抛出异常（尽管在实际运行中抛出异常是完全可能的，例如 `std::thread` 构造函数在无法生成新系统线程时会抛出 `std::system_error` 异常）。在此类算法中妥善处理异常超出了本简易示例的范围，我们将在第 8 章中展开深入讨论。

代码清单 2.9 一个朴素的并行版 `std::accumulate` 实现

```cpp
template<typename Iterator,typename T>
struct accumulate_block
{
    void operator()(Iterator first,Iterator last,T& result)
    {
        result=std::accumulate(first,last,result);
    }
};

template<typename Iterator,typename T>
T parallel_accumulate(Iterator first,Iterator last,T init)
{
    unsigned long const length=std::distance(first,last);
    if(!length)
        return init;

    unsigned long const min_per_thread=25;
    unsigned long const max_threads=
        (length+min_per_thread-1)/min_per_thread;

    unsigned long const hardware_threads=
        std::thread::hardware_concurrency();

    unsigned long const num_threads=
        std::min(hardware_threads!=0?hardware_threads:2,max_threads);

    unsigned long const block_size=length/num_threads;

    std::vector<T> results(num_threads);
    std::vector<std::thread>  threads(num_threads-1);

    Iterator block_start=first;
    for(unsigned long i=0;i<(num_threads-1);++i)
    {
        Iterator block_end=block_start;
        std::advance(block_end,block_size);
        threads[i]=std::thread(
            accumulate_block<Iterator,T>(),
            block_start,block_end,std::ref(results[i]));
        block_start=block_end;
    }
    accumulate_block<Iterator,T>()(
        block_start,last,results[num_threads-1]);

    for(auto& entry: threads)
           entry.join();

    return std::accumulate(results.begin(),results.end(),init);
}
```

尽管这个函数看起来篇幅较长，但其内在逻辑十分直观清晰。如果输入的元素区间为空，则直接返回传入的初始值 `init`。否则，区间内至少存在一个元素，我们可以用待处理元素总数除以每个线程应承担的最小分块大小，计算出合理的**最大线程数**上限。这可以有效防止在拥有 32 个核心的高端机器上，为了累加区区 5 个整数而盲目创建 32 个线程的荒谬现象。

实际运行的线程数量取“计算出的最大上限”与“当前硬件支持的并发线程数”两者的较小值。我们坚决不希望创建超出硬件物理承载能力的过多线程（这种状态称为**超额订阅，oversubscription**），因为过度的线程上下文切换会使得增加线程不仅无法提速，反而导致整体性能严重劣化。如果 `std::thread::hardware_concurrency()` 返回了 0，我们可以回退指定一个保底数字；在这个示例中我选择了 2。我们既不想运行过多线程导致在单核机器上卡顿，也不想运行过少线程而平白浪费硬件本已具备的并行计算能力。

每个线程要处理的元素个数等于区间总长度除以计算出的线程数。如果你担心除不尽的问题，不必焦虑——稍后我们会妥善处理尾部的不均匀数据分块。

确定了具体的线程数之后，我们创建一个 `std::vector<T>` 用于保存各个线程的中间累加结果，同时创建一个 `std::vector<std::thread>` 用于持有工作线程。请注意，我们只需要启动 `num_threads - 1` 个子线程，因为当前主线程自身也将分担最后一个数据块的计算任务。

启动线程是一个简单的循环：将 `block_end` 迭代器推进到当前分块的末尾，然后启动一个新线程来累加该分块的元素并将结果写入对应的槽位。下一个数据块的起点即为当前数据块的终点。

在成功启动所有子线程后，主线程将亲自处理最后一个数据分块。正是在这里吸收了任何整除不尽的剩余元素：因为我们知道最后一个分块的终点必然就是输入区间的 `last`，无论该分块比其他分块多几个还是少几个元素都无关紧要。

当主线程计算完最后一个分块的结果后，我们通过遍历容器并调用 `entry.join()` 等待所有子线程执行结束，最后再次调用 `std::accumulate` 将各个分块的中间结果与初始值汇总累加并返回。

在结束本示例之前，有必要指出几个关键的技术细节：如果针对类型 `T` 的加法操作符不满足**结合律**（例如浮点数 `float` 或 `double`），由于将区间切分为多个分块并行累加改变了运算的结合顺序，本 `parallel_accumulate` 计算得到的结果可能会与标准单线程 `std::accumulate` 的结果存在微妙差异。此外，对迭代器的能力要求也更为严苛：输入迭代器必须至少满足前向迭代器（Forward Iterator）的要求，而单线程版的 `std::accumulate` 仅需单遍扫描的输入迭代器（Input Iterator）即可工作；同时类型 `T` 必须满足默认构造要求，以便预先开辟存储中间结果的 `results` 向量。这类要求的变化在并行算法中极其普遍；并行化的本质决定了数据访问模式的改变，这必然会对计算结果的精度和类型约束带来连锁影响。第 8 章将更加深入地剖析并行算法的实现模式，而第 10 章将系统介绍 C++17 标准库提供的现成并行算法（本示例中实现的 `parallel_accumulate` 在 C++17 中的标准对等实现即为并行版的 `std::reduce`）。另外值得注意的是，由于无法直接从原生线程中返回值，我们必须通过引用传入中间结果的槽位；而在第 4 章中，我们将介绍如何利用期望值（future）更加优雅地从子线程异步获取返回值。

在此例中，每个线程在启动时就获得了运行所需的全部信息，包括保存其计算结果的目标内存位置。但现实情况并非总是如此简单；在某些业务场景下，程序在处理流水线的深层环节需要能够以某种方式识别出当前代码运行在哪个特定线程中。当然，你可以显式向下传递一个编号参数（例如代码清单 2.8 中的循环索引 `i`），但如果需要使用线程标识的函数位于调用栈深处，且可能从任意线程被调用，那么层层透传参数会显得极其繁琐沉重。C++ 标准委员会在设计库时预见到了这一需求，因此为每个线程赋予了全局唯一的标识符。

## 2.5 标识线程

线程标识符的类型为 `std::thread::id`，可以通过两种途径获取。首先，可以通过与线程关联的 `std::thread` 对象调用其 `get_id()` 成员函数来获取该线程的标识符。如果该 `std::thread` 对象当前并未关联任何实际的执行线程，则 `get_id()` 会返回一个默认构造的 `std::thread::id` 对象，代表“不代表任何线程”（not any thread）。其次，可以通过在当前运行的线程内部调用 `std::this_thread::get_id()` 来获取当前线程自身的标识符，该函数同样声明在 `<thread>` 头文件中。

`std::thread::id` 类型的对象支持自由拷贝和比较；否则它们作为标识符的价值将大打折扣。如果两个 `std::thread::id` 对象相等，说明它们代表同一个执行线程，或者二者均持有“不代表任何线程”的空值。如果两个对象不相等，则它们代表不同的执行线程，或者其中一个代表有效线程而另一个持有空值。

C++ 标准库不仅允许你检查两个线程标识符是否相等，`std::thread::id` 还提供了一整套完整的比较操作符（`<`、`>`、`<=`、`>=`），为所有不同的线程 ID 提供了**严格全序关系（total ordering）**。这使得它们可以直接用作关联式容器（如 `std::set`、`std::map`）中的键（key），或者进行排序及任何程序员认为合适的比较操作。该全序关系表现完全符合直觉：若 `a < b` 且 `b < c`，则必有 `a < c`，等等。标准库还特化了 `std::hash<std::thread::id>`，使得 `std::thread::id` 也可以无缝作为无序关联容器（如 `std::unordered_set`、`std::unordered_map`）的键。

在工程实践中，`std::thread::id` 实例常用于判断当前线程是否需要执行某些特定的定制化逻辑。例如，如果使用线程来分担计算任务（如代码清单 2.9 所示），启动其他工作线程的主控线程可能需要在算法的中途执行某些截然不同的协调逻辑。在这种情况下，主控线程可以在启动其他线程之前先记录下 `std::this_thread::get_id()` 的值，随后所有线程共同执行的核心通用算法只需将自身的线程 ID 与保存的主控 ID 进行比对即可：

```cpp
std::thread::id master_thread;
void some_core_part_of_algorithm()
{
    if(std::this_thread::get_id()==master_thread)
    {
        do_master_thread_work(); // 主控线程专属任务
    }
    do_common_work(); // 通用公共任务
}
```

或者，当前线程的 `std::thread::id` 可以在某个操作阶段被存入特定的共享数据结构中。随后对该数据结构执行操作的其他代码可以通过检查记录的 ID 与当前执行操作的线程 ID 是否一致，来决定是否授予特定权限或执行某些关联动作。

类似地，当需要将特定私有数据与线程进行动态绑定、而线程局部存储（thread-local storage）因生命周期等原因不适用时，线程 ID 也可以作为关联容器的检索键。例如，主控协调线程可以使用以线程 ID 为键的容器来集中记录其下辖各个工作线程的状态信息，或者在线程间进行点对点的消息派发。

总体的设计思路是：在绝大多数普通场景下，`std::thread::id` 足以作为通用且可靠的线程唯一标识符；只有当标识符本身被赋予了明确的业务语义（例如表示数组中的直接索引下标）时，才需要考虑采用其他自定义替代方案。你甚至可以直接将 `std::thread::id` 实例输出到流中（例如 `std::cout`）：

```cpp
std::cout<<std::this_thread::get_id();
```

具体的输出格式完全取决于编译器的标准库实现；C++ 标准唯一作出的严格保证是：相等的线程 ID 必须产生完全一致的输出，而不相等的线程 ID 则必须输出互不相同的内容。因此，流输出功能主要用于调试定位和日志记录，输出的值本身没有任何可以依赖的跨平台语义。

在本章中，我们系统学习了使用 C++ 标准库进行线程管理的核心技术：如何启动线程、如何等待线程执行完毕（join），以及何时无需等待而让其在后台独立运行（detach）。我们还探讨了在启动线程时如何安全地向线程函数传递实参，如何在不同的对象间转移底层线程的所有权，以及如何利用线程组进行高效的分治任务调度。最后，我们讨论了如何利用线程 ID 对线程进行唯一标识，以便在不便采用替代机制的场景下将数据或特定行为与具体线程进行精准关联。

尽管使用各自操作独立数据的完全独立的线程已经能解决许多工程问题，但在很多时候，多个线程在运行过程中需要相互协作、共享数据。第 3 章将深入讨论在线程间直接共享数据的各种核心问题与挑战，而第 4 章将拓展探讨带有或不带有共享数据时的通用线程间操作同步。

## 3. 线程间数据共享（导引）

本部分涵盖：

- 线程间共享数据引发的核心问题
- 使用互斥量（mutex）保护数据
- 保护共享数据的替代设施

使用多线程实现并发的核心收益之一，在于能够极为轻松直接地在线程之间共享数据。现在我们已经掌握了线程的启动与管理，接下来让我们深入审视围绕共享数据所产生的关键问题。

不妨设想你与一位室友合租一套公寓。屋里只有一间厨房和一间浴室。除非你们关系非同寻常，否则你们不可能在同一时刻同时使用浴室；如果你的室友长时间霸占浴室，而你恰好急需使用，那肯定会令人非常抓狂。同理，虽然两个人有可能同时下厨做饭，但如果公寓里只有一个集成烤箱与烤架，要是其中一人在烤蛋糕的同时另一人试图烤香肠，结果必然是一场灾难。此外，合租过的人都深有体会：当你某项任务做到一半，却突然发现有人借走了你急需的工具，或者把你原本放置整齐的物品搞得面目全非，那种挫败感是不言而喻的。

在多线程世界中亦是完全相同的道理。如果你在多个线程之间共享数据，就必须建立严格的规则，明确哪个线程在何时可以访问哪一部分数据，以及如何将任何更新操作可靠地同步给其他关心该数据的线程。在单个进程内的多个线程之间共享数据虽然轻巧便捷，但这是一把双刃剑——它不仅是巨大的优势，也是致命隐患的温床。对共享数据的不当使用是引发并发缺陷的最主要元凶，其产生的严重后果甚至远甚于香肠味的夹心蛋糕。

后续内容将系统介绍如何在 C++ 中安全地在线程间共享数据，规避潜在的隐患陷阱，并最大化并发带来的性能红利。

## 3.1 线程间共享数据的问题

归根结底，多线程共享数据带来的所有隐患与问题，全都源于**修改数据**所引发的连锁反应。如果所有共享数据都是纯只读的，那么天下太平、没有任何隐患，因为某个线程读取数据丝毫不会受到其他线程是否也在读取同一数据的影响。但是，如果数据在线程间被共享，并且有一个或多个线程开始对数据进行修改，那么混乱与灾难的祸根就此埋下。在这种情况下，你必须付出极大的心力确保每一步操作都能正确无误。

为了帮助程序员理清逻辑并推导代码的正确性，计算机科学中广泛使用了一个核心概念——**不变式（invariants）**：即关于特定数据结构始终为真的事实断言，例如“该变量记录了链表中的节点总数”。在执行更新操作的过程中，这些不变式往往会被暂时打破，尤其是当数据结构本身较为复杂、或者一次更新需要连续修改多个独立内存字段时更是如此。

考虑一个双向链表，其中每个节点都同时持有指向后继节点和前驱节点的指针。其核心不变式之一是：如果你沿着节点 A 的 `next` 指针访问到节点 B，那么节点 B 的 `prev` 指针必然反向指向节点 A。为了从链表中删除一个节点，必须将该节点两侧的邻居节点更新为直接指向彼此。一旦其中一侧的指针被修改，不变式就被暂时打破了，直到另一侧的指针也被修改完成；只有当整套更新流程全部完成后，不变式才重新恢复成立。

从这样一个双向链表中删除一个节点包含以下典型步骤（如图 3.1 所示）：

- a. 确定待删除的目标节点 N。
- b. 更新 N 的前驱节点的 `next` 指针，使其指向 N 的后继节点。
- c. 更新 N 的后继节点的 `prev` 指针，使其指向 N 的前驱节点。
- d. 释放/删除节点 N。

正如在步骤 b 和步骤 c 之间所能看到的那样，一个方向的指针链接与反方向的指针链接出现了不一致，此时数据结构的不变式被严重破坏了。

当修改线程间共享的数据时，最直接的潜在隐患就是**不变式遭到破坏**。如果你未采取任何特殊的同步防护手段，一旦某个线程在遍历读取双向链表的同时，另一个线程正在执行删除节点操作，那么读取线程极有可能读到一个处于半删除半更新状态的混乱链表（因为此时只有一侧的指针完成了更新，如同图 3.1 中的步骤 b 那样），此时不变式处于破损状态。这种不变式遭到破坏所带来的后果千奇百怪：如果并发读取线程碰巧是从左往右遍历链表，它可能会跳过正在被删除的节点；而如果另一个并发线程试图删除图中最右侧的节点，则可能彻底破坏链表的指针结构，并最终导致程序崩溃。无论出现何种结局，这都是并发代码中最常见的缺陷源头之一：**竞争条件（race condition）**。

### 3.1.1 竞争条件 (Race Conditions)

设想你正在电影院排队购票。如果是一家大型影院，会有多个售票窗口同时办理售票，因此有多名顾客可以并发购买电影票。如果另一个窗口的顾客恰好也在购买同一场次电影的电影票，那么你能选择哪些座位，完全取决于对方先确认出票还是你先确认出票。如果该场次只剩下最后几张票，这种先后顺序就会变得性命攸关：这会演变成一场争夺最后入场券的真正赛跑。这就是竞争条件的一个典型生活映射：你最终获得哪些座位（甚至是否能买到票）完全取决于两笔交易发生的相对时间顺序。

在并发编程中，**竞争条件（race condition）**是指：程序的最终执行结果取决于两个或多个线程上操作执行的**相对时序**；线程之间竞相执行各自的操作。在多数时候，这种竞争是完全良性的，因为所有可能的交错结果在业务上都是完全可接受的，即便不同的相对顺序会产生不同的输出。例如，如果有两个工作线程向一个处理队列中追加待处理任务，只要系统的不变式得以完整维持，通常哪一个任务先入队并无大碍。只有当竞争条件导致数据结构的不变式遭到破坏时，才会酿成严重的缺陷，正如前面提到的双向链表示例那样。在讨论并发时，人们通常使用术语“竞争条件”来特指这种具有破坏性、导致缺陷的竞争条件；良性竞争并不值得大惊小怪，也不是缺陷的源头。此外，C++ 标准还专门定义了术语**数据竞争（data race）**，用于特指因多个线程对同一个内存位置进行并发访问、且至少有一个访问是写入操作、且没有进行任何同步保护时所引发的特定竞争条件（详见 5.1.2 节）；在 C++ 标准中，**数据竞争将直接引发令人闻风丧胆的未定义行为**。

破坏性的竞争条件通常发生在完成一项操作需要连续修改两个或多个不同数据片段的场景中，例如链表示例中的两个邻居指针。由于该操作必须访问两个独立的内存位置，它们必然是在独立的 CPU 指令中被修改的，因此另一个并发线程完全有可能在仅仅完成其中一个字段修改的夹缝时刻横插进来访问该数据结构。竞争条件往往极难排查、且极难稳定复现，因为出现异常的时间窗口往往极其狭窄。如果两次修改是紧密相邻的 CPU 指令，那么在单次常规运行中撞上竞态窗口的几率非常微小，即使当时有另一个线程在并发访问该数据结构。然而，随着系统工作负载的急剧增加、或者操作执行频次的成倍攀升，这种致命执行时序出现的概率也会急剧上升。墨菲定律在这里体现得淋漓尽致：此类偶发故障几乎不可避免地会在最不利、最不合时宜的生产时刻突然爆发。由于竞争条件通常对时间极度敏感，当程序在调试器（debugger）下单步运行时，问题往往会神奇地彻底消失不见，因为调试器的介入会从根本上改变程序的执行时间节奏（即经典的“海森堡缺陷”）。

如果你在编写多线程程序，竞争条件极易成为困扰你的噩梦；编写并发软件所面临的大部分复杂性，本质上都来自于如何规避具有破坏性的竞争条件。

### 3.1.2 规避破坏性竞争条件

处理破坏性竞争条件有若干经典途径。最直观的方案是为你的数据结构封装一层保护机制，以确保只有正在执行修改的线程才能看到不变式被暂时打破的中间状态。从访问该数据结构的其他外部线程的视角来看，此类修改要么尚未开始，要么已经完全结束。
